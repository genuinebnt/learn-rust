#[derive(Debug, PartialEq)]
struct HttpRequest {
    method: String,
    url: String,
    timeout_ms: u64,
}

#[derive(Debug, PartialEq)]
enum BuildError {
    MissingMethod,
    MissingUrl,
}

struct HttpRequestBuilder {
    method: Option<String>,
    url: Option<String>,
    timeout_ms: u64,
}

impl HttpRequestBuilder {
    fn new() -> Self {
        Self {
            method: None,
            url: None,
            timeout_ms: 30_000,
        }
    }

    fn method(mut self, method: impl Into<String>) -> Self {
        self.method = Some(method.into());
        self
    }

    fn url(mut self, url: impl Into<String>) -> Self {
        self.url = Some(url.into());
        self
    }

    fn timeout_ms(mut self, timeout_ms: u64) -> Self {
        self.timeout_ms = timeout_ms;
        self
    }

    fn build(self) -> Result<HttpRequest, BuildError> {
        Ok(HttpRequest {
            method: self.method.ok_or(BuildError::MissingMethod)?,
            url: self.url.ok_or(BuildError::MissingUrl)?,
            timeout_ms: self.timeout_ms,
        })
    }
}

fn main() {
    let req = HttpRequestBuilder::new()
        .method("GET")
        .url("https://example.com")
        .timeout_ms(5_000)
        .build()
        .unwrap();
    assert_eq!(req.method, "GET");
    assert_eq!(req.url, "https://example.com");
    assert_eq!(req.timeout_ms, 5_000);
    assert_eq!(
        HttpRequestBuilder::new().url("https://x").build(),
        Err(BuildError::MissingMethod)
    );
}
What to look for — unprompted signals
  • ★★★Stores required fields as Option<T> and validates in build() with Result rather than panicking, using dummy defaults, or forcing callers to pass everything in new() — the whole point of Builder is deferred, typed validation.
  • ★★Takes self by value (consuming builder) and returns Self for fluent setters — the idiomatic owned-builder style in Rust; &mut self builders exist but are a different ergonomics tradeoff.
  • ★Accepts impl Into<String> on string setters so both &str and String work without ceremony.
Follow-up probes
  • P1"Why Result instead of panicking in build()?" — Missing config is an expected, recoverable failure at construction time; Result forces callers to handle it and keeps libraries panic-free. Panic is for programmer bugs, not absent fields.
  • P2"How would typestate encode required fields at compile time?" — Phantom type parameters (or distinct builder types) that transition as fields are set, so build() only exists on the fully-configured state — no runtime Option check. Heavier, but zero-cost when the API surface is stable.
  • P3"When would you prefer a plain struct literal or Default over Builder?" — When there are few fields, all optional with good defaults, or when the type is internal and not a public construction API — Builder pays for itself on many optional/required combinations and validation rules.
🎯 Senior angle / Rust angle
In Rust, Builder shines for complex construction with validation — but prefer typestate or simply required arguments in new when the set of required fields is small and stable. The pattern is less about mimicking Java fluent APIs and more about making illegal states unrepresentable (Result, typestate) without forcing every caller through a mutable bag of options.

trait Shape {
    fn area(&self) -> f64;
    fn name(&self) -> &'static str;
}

struct Circle { radius: f64 }

impl Shape for Circle {
    fn area(&self) -> f64 {
        std::f64::consts::PI * self.radius * self.radius
    }
    fn name(&self) -> &'static str { "circle" }
}

struct Rectangle { width: f64, height: f64 }

impl Shape for Rectangle {
    fn area(&self) -> f64 { self.width * self.height }
    fn name(&self) -> &'static str { "rectangle" }
}

enum ShapeKind {
    Circle { radius: f64 },
    Rectangle { width: f64, height: f64 },
}

fn create_shape(kind: ShapeKind) -> Box<dyn Shape> {
    match kind {
        ShapeKind::Circle { radius } => Box::new(Circle { radius }),
        ShapeKind::Rectangle { width, height } => {
            Box::new(Rectangle { width, height })
        }
    }
}

fn main() {
    let c = create_shape(ShapeKind::Circle { radius: 2.0 });
    assert_eq!(c.name(), "circle");
    assert!((c.area() - (std::f64::consts::PI * 4.0)).abs() < 1e-9);

    let r = create_shape(ShapeKind::Rectangle { width: 3.0, height: 4.0 });
    assert_eq!(r.name(), "rectangle");
    assert!((r.area() - 12.0).abs() < 1e-9);
}
What to look for — unprompted signals
  • ★★★Centralizes construction in one match on ShapeKind returning Box<dyn Shape> — keeps variant knowledge in one place instead of scattering Box::new across the app.
  • ★★Volunteers that a single enum Shape { Circle(...), Rectangle(...) } is often better when the set of shapes is closed — no vtable, exhaustiveness checking, cheaper than trait objects.
  • ★Doesn't force Clone/Copy bounds on the trait just to make factory demos easier — keeps the trait minimal.
Follow-up probes
  • P1"When is dyn Shape the right call vs an enum?" — Prefer dyn when third parties must add new shapes (open set) or you need heterogeneous collections without naming every variant. Prefer enum when the set is closed and you want exhaustiveness + better codegen.
  • P2"What object-safety limits hit Shape if you add a generic method?" — Methods with type parameters (or returning Self) are not object-safe; you'd need a separate generic helper, associated type, or switch to enum/generics.
  • P3"How would you avoid heap allocation here?" — Return an enum, use stack-allocated enum dispatch, or generics (impl Shape / monomorphization) if the concrete type can stay generic at the call site.
🎯 Senior angle / Rust angle
Classic OOP Factory Method maps poorly onto Rust's preference for closed enums and static dispatch. A factory returning Box<dyn Trait> is valid for open hierarchies or plugin boundaries, but seniors usually say: "I'd make Shape an enum unless I truly need open extension." That tradeoff discussion is the real interview signal, not the Box::new boilerplate.

use std::rc::Rc;

#[derive(Clone, Debug, PartialEq)]
struct Paragraph {
    text: String,
}

#[derive(Clone, Debug, PartialEq)]
struct Section {
    title: String,
    paragraphs: Vec<Paragraph>,
}

#[derive(Clone, Debug, PartialEq)]
struct Document {
    title: String,
    sections: Vec<Section>,
}

/// Wrong shape for "prototype": Clone only bumps Rc counts — edits alias.
#[derive(Clone, Debug)]
struct SharedDoc {
    paragraphs: Vec<Rc<Paragraph>>,
}

fn main() {
    let original = Document {
        title: "Spec".into(),
        sections: vec![Section {
            title: "Intro".into(),
            paragraphs: vec![Paragraph {
                text: "hello".into(),
            }],
        }],
    };

    let mut copy = original.clone();
    copy.sections[0].paragraphs[0].text = "changed".into();
    assert_eq!(original.sections[0].paragraphs[0].text, "hello");
    assert_eq!(copy.sections[0].paragraphs[0].text, "changed");

    let shared = SharedDoc {
        paragraphs: vec![Rc::new(Paragraph {
            text: "shared".into(),
        })],
    };
    let twin = shared.clone();
    assert!(Rc::ptr_eq(&shared.paragraphs[0], &twin.paragraphs[0]));
    assert_eq!(Rc::strong_count(&shared.paragraphs[0]), 2);
}
What to look for — unprompted signals
  • ★★★Uses owned nested data + derived Clone so deep clone is structural — mutating the copy leaves the original intact without hand-written copy constructors.
  • ★★Explains that Rc::clone is not a prototype for editable trees — it shares the allocation; independent mutation needs Rc::make_mut / owned data / explicit deep copy.
  • ★Mentions #[derive(Clone)] recursively requiring Clone on every field — and that custom Clone is needed if some fields should be reset (ids, caches) rather than copied.
Follow-up probes
  • P1"When is Rc sharing the right design?" — Immutable shared subgraphs, interned strings, or DAG structures where identity/sharing is a feature. Wrong when each "copy" must diverge independently under mutation.
  • P2"How do you deep-clone through Rc<T> when you need to?" — Clone the inner T ((*rc).clone() if T: Clone), or Rc::make_mut for copy-on-write. Don't confuse bumping the strong count with duplicating content.
  • P3"What about cycles?" — Owned trees clone fine; graphs with cycles need care (or aren't Clone by derive). Rc cycles also need Weak to avoid leaks — a separate concern from prototype.
🎯 Senior angle / Rust angle
Rust's Prototype is basically Clone (or an explicit fn deep_clone) — there is no hidden copy constructor culture. The senior trap is treating Rc/Arc clones as deep copies: they share. Prefer owned trees for editable prototypes; use shared pointers only when immutability or intentional aliasing is part of the model.

use std::sync::OnceLock;

#[derive(Debug, Clone, PartialEq)]
struct Config {
    app_name: String,
    max_connections: usize,
}

fn global_config() -> &'static Config {
    static CONFIG: OnceLock<Config> = OnceLock::new();
    CONFIG.get_or_init(|| Config {
        app_name: "interview-app".into(),
        max_connections: 32,
    })
}

fn main() {
    let a = global_config();
    let b = global_config();
    assert_eq!(a.app_name, "interview-app");
    assert_eq!(a.max_connections, 32);
    assert_eq!(a, b);
    assert!(std::ptr::eq(a, b));
}
What to look for — unprompted signals
  • ★★★Uses OnceLock::get_or_init (or LazyLock) — thread-safe one-time init without unsafe, without lazy_static, and without a mutable static mut.
  • ★★Returns &'static Config that is immutable — callers cannot mutate global state through the API; config is read-only after init.
  • ★States they'd prefer dependency injection (pass &Config / Arc<Config>) for testability, using a global only at the binary edge.
Follow-up probes
  • P1"Why is a mutable global Singleton an antipattern in Rust?" — Mutable shared state needs Mutex/RwLock (or atomics), creates hidden coupling, races, and poison/lock ordering hazards, and makes unit tests order-dependent because every test shares one process-global. It also fights ownership: who "owns" the singleton? Prefer passing state explicitly; if you must share, share an Arc<T> from main.
  • P2"OnceLock vs LazyLock?" — LazyLock is for when the initializer is fixed at the static declaration; OnceLock is better when init might depend on runtime arguments (env, CLI) via get_or_init / set.
  • P3"How do you test code that calls global_config()?" — Hard — that's why seniors inject config. Mitigations: init once in test harness with known values, feature-gate the global, or refactor to take &Config.
🎯 Senior angle / Rust angle
Idiomatic Rust allows a read-only process global via OnceLock/LazyLock for true constants (config, metrics registry handles). Classic mutable Singleton is an antipattern here: it smuggles shared mutable state past the type system, wrecks test isolation, and reintroduces the locking/ordering bugs Rust was meant to push into explicit Arc<Mutex<T>> (or better, no global at all). Prefer constructing config in main and passing it down.

    }

    fn warn(&mut self, msg: &str) {
        self.inner.write_line_raw(2, msg);
    }

    fn contents(&self) -> &str {
        self.inner.dump()
    }
}

    log.warn("slow path");
}

    run_job(&mut adapter);

  • ★★★Wraps legacy type; does not modify it — maps clean trait methods onto awkward numeric levels, isolating the translation in one adapter type.
  • ★★App code takes &mut dyn AppLogger (or generic L: AppLogger) — dependency on the trait, not the third-party concrete type.

🎯 Senior angle / Rust angle
Adapter is one of the structural patterns that remains genuinely common in Rust — especially because the orphan rule pushes you toward newtypes when bridging foreign types to local traits. Prefer a thin wrapper that owns or holds the third-party value and exposes only your trait; keep magic constants and stringly APIs quarantined inside that boundary.

trait HttpHandler {
    fn handle(&self, path: &str) -> String;
}

struct BaseHandler;
impl HttpHandler for BaseHandler {
    fn handle(&self, path: &str) -> String {
        format!("OK {path}")
    }
}

struct LoggerMiddleware {
    inner: Box<dyn HttpHandler>,
    log: std::cell::RefCell<Vec<String>>,
}

impl LoggerMiddleware {
    fn new(inner: Box<dyn HttpHandler>) -> Self {
        Self { inner, log: std::cell::RefCell::new(Vec::new()) }
    }
    fn entries(&self) -> Vec<String> { self.log.borrow().clone() }
}

impl HttpHandler for LoggerMiddleware {
    fn handle(&self, path: &str) -> String {
        self.log.borrow_mut().push(format!("REQ {path}"));
        let resp = self.inner.handle(path);
        self.log.borrow_mut().push(format!("RESP {resp}"));
        resp
    }
}

struct MetricsMiddleware {
    inner: Box<dyn HttpHandler>,
    hits: std::cell::Cell<u64>,
}

impl MetricsMiddleware {
    fn new(inner: Box<dyn HttpHandler>) -> Self {
        Self { inner, hits: std::cell::Cell::new(0) }
    }
    fn hits(&self) -> u64 { self.hits.get() }
}

impl HttpHandler for MetricsMiddleware {
    fn handle(&self, path: &str) -> String {
        self.hits.set(self.hits.get() + 1);
        self.inner.handle(path)
    }
}

fn main() {
    let stacked = MetricsMiddleware::new(Box::new(
        LoggerMiddleware::new(Box::new(BaseHandler))
    ));
    assert_eq!(stacked.handle("/health"), "OK /health");
    assert_eq!(stacked.handle("/ready"), "OK /ready");
    assert_eq!(stacked.hits(), 2);

    let logged = LoggerMiddleware::new(Box::new(BaseHandler));
    let _ = logged.handle("/x");
    assert_eq!(logged.entries(), vec!["REQ /x".to_string(), "RESP OK /x".to_string()]);

    fn new(balance: i64) -> Self {

}

    amount: i64,
}

    fn execute(&mut self, account: &mut Account) {
        account.balance += self.amount;
    }

    fn undo(&mut self, account: &mut Account) {
        account.balance -= self.amount;
    }

struct Withdraw {
    amount: i64,
}

impl Command for Withdraw {
    fn execute(&mut self, account: &mut Account) {
        account.balance -= self.amount;
    }

    fn undo(&mut self, account: &mut Account) {
        account.balance += self.amount;
    }

struct CommandHistory {
    stack: Vec<Box<dyn Command>>,
}

impl CommandHistory {
    fn new() -> Self {
        Self { stack: Vec::new() }
    }

    fn run(&mut self, mut cmd: Box<dyn Command>, account: &mut Account) {
        cmd.execute(account);
        self.stack.push(cmd);
    }

    fn undo_last(&mut self, account: &mut Account) -> bool {
        if let Some(mut cmd) = self.stack.pop() {
            cmd.undo(account);
            true
        } else {
            false
        }
    }

    fn len(&self) -> usize {
        self.stack.len()
    }
}

    history.run(Box::new(Withdraw { amount: 30 }), &mut account);
    assert_eq!(account.balance, 120);
    assert_eq!(history.len(), 2);

    assert!(history.undo_last(&mut account));
    assert_eq!(account.balance, 150);

    assert!(history.undo_last(&mut account));
    assert_eq!(account.balance, 100);

    assert!(!history.undo_last(&mut account));
    assert_eq!(history.len(), 0);

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum OrderState {
    Pending,
    Paid,
    Shipped,
    Cancelled,
}

struct Order {
    id: u64,
    state: OrderState,
}

impl Order {
    fn new(id: u64) -> Self {
        Self {
            id,
            state: OrderState::Pending,
        }
    }

    fn state(&self) -> OrderState {
        self.state
    }

    fn pay(&mut self) -> Result<(), &'static str> {
        match self.state {
            OrderState::Pending => {
                self.state = OrderState::Paid;
                Ok(())
            }
            _ => Err("can only pay a pending order"),
        }
    }

    fn ship(&mut self) -> Result<(), &'static str> {
        match self.state {
            OrderState::Paid => {
                self.state = OrderState::Shipped;
                Ok(())
            }
            _ => Err("can only ship a paid order"),
        }
    }

    fn cancel(&mut self) -> Result<(), &'static str> {
        match self.state {
            OrderState::Pending | OrderState::Paid => {
                self.state = OrderState::Cancelled;
                Ok(())
            }
            OrderState::Shipped => Err("cannot cancel a shipped order"),
            OrderState::Cancelled => Err("order already cancelled"),
        }
    }
}

fn main() {
    let mut order = Order::new(1);
    assert_eq!(order.state(), OrderState::Pending);
    assert_eq!(order.id, 1);

    assert!(order.pay().is_ok());
    assert_eq!(order.state(), OrderState::Paid);
    assert!(order.pay().is_err());

    assert!(order.ship().is_ok());
    assert_eq!(order.state(), OrderState::Shipped);
    assert!(order.cancel().is_err());

    let mut cancelled = Order::new(2);
    assert!(cancelled.cancel().is_ok());
    assert_eq!(cancelled.state(), OrderState::Cancelled);
    assert!(cancelled.pay().is_err());
    assert!(cancelled.ship().is_err());
}
What to look for — unprompted signals
  • ★★★Chooses enum + match immediately instead of a Java-style trait State with Box<dyn State> — and can say why (exhaustiveness, no vtable, data can live on the variants later).
  • ★★Returns Result for illegal transitions rather than panicking or silently no-oping — makes invalid moves observable to the caller.
  • ★Derives Copy/PartialEq on the state enum so tests and comparisons stay ergonomic without cloning ceremony.
Follow-up probes
  • P1"Why is the GoF State pattern with a trait-object per state uncommon in Rust?" — Enums give compile-time exhaustiveness when you add a variant; trait objects push missing transitions to runtime. Per-state types also fight ownership when states need to move data between variants.
  • P2"How would you evolve this so Paid carries a payment_id and Shipped a tracking number?" — Put data on the enum variants themselves (Paid { payment_id }, Shipped { tracking }) and transition by moving the old variant out (often via mem::replace / take pattern).
  • P3"What's the difference between this and typestate (DP17)?" — Here illegal transitions fail at runtime with Result. Typestate encodes allowed operations in the type system so illegal calls do not compile.
🎯 Senior angle / Rust angle
In Java/C++, State is often a class hierarchy swapped at runtime. In Rust, an enum + match is the default: the compiler forces you to handle every variant, transitions stay in one place, and you can later attach per-state data without a zoo of heap-allocated state objects. Trait-object State is a yellow flag unless states are truly open-ended plugins.

trait DataExporter {
    fn export(&self, rows: &[&str]) -> String {
        let mut out = String::new();
        out.push_str(&self.header());
        for (i, row) in rows.iter().enumerate() {
            if i > 0 {
                out.push('\n');
            }
            out.push_str(&self.format_row(row));
        }
        out.push_str(&self.footer());
        out
    }

    fn header(&self) -> String {
        String::new()
    }

    fn format_row(&self, row: &str) -> String;

    fn footer(&self) -> String {
        String::new()
    }
}

struct CsvExporter;

impl DataExporter for CsvExporter {
    fn header(&self) -> String {
        "value\n".to_string()
    }

    fn format_row(&self, row: &str) -> String {
        format!("\"{row}\"")
    }
}

struct JsonExporter;

impl DataExporter for JsonExporter {
    fn header(&self) -> String {
        "[".to_string()
    }

    fn format_row(&self, row: &str) -> String {
        format!("\"{row}\"")
    }

    fn footer(&self) -> String {
        "]".to_string()
    }
}

struct Fibonacci {
    curr: u64,
    next: u64,
    remaining: usize,
}

impl Fibonacci {
    fn new(count: usize) -> Self {
        Self {
            curr: 0,
            next: 1,
            remaining: count,
        }
    }
}

impl Iterator for Fibonacci {
    type Item = u64;

    fn next(&mut self) -> Option<Self::Item> {
        if self.remaining == 0 {
            return None;
        }
        self.remaining -= 1;
        let value = self.curr;
        let sum = self.curr + self.next;
        self.curr = self.next;
        self.next = sum;
        Some(value)
    }
}

fn main() {
    let vals: Vec<u64> = Fibonacci::new(8).collect();
    assert_eq!(vals, vec![0, 1, 1, 2, 3, 5, 8, 13]);

    assert_eq!(Fibonacci::new(0).next(), None);
    assert_eq!(Fibonacci::new(1).next(), Some(0));

    let sum: u64 = Fibonacci::new(6).sum();
    assert_eq!(sum, 12);

    let mut iter = Fibonacci::new(3);
    assert_eq!(iter.next(), Some(0));
    assert_eq!(iter.next(), Some(1));
    assert_eq!(iter.next(), Some(1));
    assert_eq!(iter.next(), None);
}

use std::cell::Cell;
use std::panic::{catch_unwind, AssertUnwindSafe};

struct LockFlag {
    locked: Cell<bool>,
}

impl LockFlag {
    fn new() -> Self {
        Self {
            locked: Cell::new(false),
        }
    }

    fn is_locked(&self) -> bool {
        self.locked.get()
    }

    fn lock(&self) -> LockGuard<'_> {
        assert!(!self.locked.get(), "lock already held");
        self.locked.set(true);
        LockGuard { flag: self }
    }
}

struct LockGuard<'a> {
    flag: &'a LockFlag,
}

impl Drop for LockGuard<'_> {
    fn drop(&mut self) {
        self.flag.locked.set(false);
    }
}

fn main() {
    let flag = LockFlag::new();
    assert!(!flag.is_locked());

    {
        let _guard = flag.lock();
        assert!(flag.is_locked());
    }
    assert!(!flag.is_locked());

    let result = catch_unwind(AssertUnwindSafe(|| {
        let _guard = flag.lock();
        assert!(flag.is_locked());
        panic!("force unwind");
    }));
    assert!(result.is_err());
    assert!(!flag.is_locked());

    let _g = flag.lock();
    assert!(flag.is_locked());
}
What to look for — unprompted signals
  • ★★★Implements Drop for release and does not require an explicit unlock() call — understands RAII as the safety mechanism.
  • ★★Demonstrates unlock on panic unwind (via catch_unwind or clear verbal explanation that Drop still runs) — connects guards to exception-safety / unwind safety.
  • ★Uses Cell / interior mutability so lock(&self) works while the guard holds a shared reference — mirrors why real locks use unsafe/interior mutability under the hood.
Follow-up probes
  • P1"Why does std::sync::MutexGuard unlock in Drop instead of an unlock method?" — So every exit path (return, ?, panic) releases the lock. An explicit unlock is easy to forget and races with panic.
  • P2"What goes wrong if Drop does fallible work (e.g. flush that can fail)?" — Drop cannot return Result; failures must be logged, ignored, or surfaced earlier via an explicit close(self) -> Result that leaves a no-op Drop. Double-panic during unwind aborts.

🎯 Senior angle / Rust angle
RAII guards are how Rust encodes cleanup without finally or try-with-resources: ownership ends, Drop runs — including on unwind. This exercise is less "GoF pattern" and more "do you understand why MutexGuard / File / Span guards look the way they do."
