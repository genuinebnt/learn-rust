Ownership & Borrowing
Questions & model answers — click any row to expand
Q1Explain Rust's three ownership rules. What happens when a value goes out of scope?▼ answer
Model answer
(1) Each value has exactly one owner at any given time. (2) When the owner goes out of scope, the value is dropped — its Drop::drop is called (if implemented) and its memory is reclaimed deterministically, with no garbage collector involved. (3) Ownership can be transferred (moved) — assigning a non-Copy value to another binding, or passing it into a function by value, transfers ownership; the original binding becomes invalid and the compiler statically rejects any further use of it. This is checked entirely at compile time — there is zero runtime cost for ownership tracking. When a scope ends, Rust inserts calls to drop every owned value in reverse order of declaration, recursively — a struct's Drop runs before its fields' drops.
Q2What is the difference between Copy and Clone? Why can't String implement Copy?▼ answer
Model answer
Copy: a marker trait for types where assignment/passing performs an implicit, cheap bitwise duplication instead of a move — the original binding remains valid. Only types where a bit-for-bit copy is fully correct and cheap can implement it: integers, floats, bool, char, and tuples/arrays/structs composed entirely of Copy types. Clone: an explicit, possibly-expensive duplication via .clone() — must be called deliberately, can allocate, can run arbitrary logic. String owns a heap-allocated buffer; a bitwise copy would produce two Strings pointing at the same heap allocation, so when both go out of scope you'd get a double-free. Rust disallows Copy for any type containing a heap pointer or implementing Drop — the compiler enforces this at the trait-implementation level, it's not just convention.
Q3State the borrowing rules precisely. Why is "many immutable OR one mutable" the rule, rather than something more permissive?▼ answer
Model answer
At any point in a scope, for a given value you may have either any number of immutable references (&T) or exactly one mutable reference (&mut T) — never both simultaneously. This is the "aliasing XOR mutation" principle. The reason it's this strict: if two references could both read and one could write concurrently (even on a single thread), the reader could observe a partially-mutated, inconsistent value — e.g. a Vec being reallocated mid-iteration. By making mutation exclusive, the compiler guarantees that whenever you hold &mut T, no other code anywhere can be observing or changing that data — this is what allows aggressive compiler optimisations (no aliasing means no defensive reloads) and what eliminates data races when the same rule is extended across threads via Send/Sync.
Q4What is the borrow checker's "two-phase borrow" and how did NLL (non-lexical lifetimes) change what compiles?▼ answer
Model answer
Before NLL (stabilised in the 2018 edition), a borrow's lifetime extended to the end of the enclosing lexical scope (the innermost {}) regardless of whether it was actually used again — so code like taking a mutable borrow, using it, then trying to use the original variable in the same block would fail even though the borrow had logically ended. NLL makes the borrow checker analyse the actual control-flow graph and shrink a borrow's lifetime to its last real use — dramatically more code compiles without restructuring. Two-phase borrows solve a narrower problem: vec.push(vec.len()) looks like it needs &mut vec and &vec simultaneously. The compiler splits the mutable borrow into a "reserved" phase (can coexist with shared reads) and an "activated" phase (exclusive, begins only when the mutation actually happens) — letting this common pattern compile without unsafe workarounds.
Q5What is the difference between "moving out of a borrowed context" being disallowed, and how do Cell/RefCell let you bypass the compile-time borrow rules? What's the trade-off?▼ answer
Model answer
You cannot move a value out of a &T or &mut T because the reference's target must remain valid for its lifetime — moving out would leave a hole. (Exceptions: mem::take and mem::replace let you swap in a default/replacement value atomically, giving you ownership of the old value without leaving an invalid state.) Cell<T> and RefCell<T> provide interior mutability: they let you mutate a value through a shared &self reference by moving the aliasing-XOR-mutation check from compile time to runtime. Cell<T> only supports get/set/replace (T must be Copy or you move whole values in/out) — no runtime check needed because there's never a live reference into it. RefCell<T> hands out runtime-checked guards (borrow() / borrow_mut()) and panics if you violate the aliasing rule at runtime (e.g. two live mutable borrows). Trade-off: you lose compile-time guarantees and pay a small runtime check cost, and a violated invariant becomes a runtime panic instead of a compile error — this is why interior mutability is used surgically (e.g. one field of a struct) rather than everywhere.
Q6You need two &mut references into different, provably disjoint parts of the same Vec<T>/slice at once — e.g. to recurse into both halves of a slice for a divide-and-conquer algorithm. Why does the naive attempt not compile, and how does split_at_mut solve it soundly?▼ answer
Model answer
The naive attempt: 
let mid = slice.len() / 2;
let left = &mut slice[..mid];
let right = &mut slice[mid..];  // error: cannot borrow `slice` as mutable more than once at a time
fails because the borrow checker's analysis here is syntactic, not semantic — it sees two separate &mut borrows taken from the same place (slice) and rejects them as potentially aliasing, even though a human (and the runtime values of mid) can see [..mid] and [mid..] are provably non-overlapping byte ranges. The compiler does not do range-disjointness reasoning for you at the borrow-checker level. slice.split_at_mut(mid) -> (&mut [T], &mut [T]) is exactly the "trust me, these two are disjoint" escape hatch, implemented once, correctly, inside the standard library: internally it computes two raw pointers into the same allocation and constructs two independent &mut slices via a small, audited unsafe block — the unsafety is fully contained there, so callers never need unsafe themselves to get this pattern. This is exactly the mechanism in-place quicksort (partition, then recurse into both halves) and parallel divide-and-conquer algorithms (including how rayon's parallel sort recurses across threads) rely on to work on two halves of one slice simultaneously without cloning. A candidate whose first instinct on hitting this error is to reach for raw pointers/unsafe themselves, or to .clone() the whole slice to dodge the conflict, is missing that the standard library already ships the safe, idiomatic answer (split_at_mut, and its siblings split_first_mut/chunks_mut) for this exact, extremely common shape of problem.

// Topic 02
Structs, Enums & Pattern Matching
Questions & model answers
Q1What are the three kinds of structs in Rust? What is a "newtype" and why is it idiomatic?▼ answer
Model answer
Named-field structs (struct Point { x: f64, y: f64 }), tuple structs (struct Point(f64, f64) — fields accessed by .0/.1), and unit structs (struct Marker; — zero size, used as a type-level tag or trait implementation target with no data). A newtype is a tuple struct with exactly one field — struct UserId(u64); — that wraps an existing type to give it a distinct identity at the type level. It's idiomatic because: (1) it prevents mixing up semantically different values that share a representation (UserId vs ProductId, both u64, cannot be passed to the wrong parameter — the compiler rejects it), (2) it lets you implement traits you don't own for types you don't own (the "orphan rule" forbids impl ForeignTrait for ForeignType, but impl ForeignTrait for MyNewtype(ForeignType) is fine), and (3) it has zero runtime cost — the wrapper is erased at compile time.
Q2How do Rust enums differ from C-style enums? Explain how Option<T> is just a regular enum, and what its memory layout looks like.▼ answer
Model answer
C-style enums are just named integer constants. Rust enums are algebraic data types (sum types) — each variant can carry its own distinct payload: 
enum Shape {
    Circle { radius: f64 },
    Rectangle { w: f64, h: f64 },
    Point,
}
Option<T> is defined in std as enum Option<T> { None, Some(T) } — no special-casing by the compiler beyond a specific layout optimisation. For a type like Option<Box<T>> or Option<&T>, the compiler applies the null pointer optimisation: since a valid pointer is never zero, None is represented as the all-zero bit pattern and Some as the pointer value directly — so sizeof(Option<Box<T>>) == sizeof(Box<T>), no extra discriminant byte needed. For non-pointer types, the enum needs a discriminant tag plus space for the largest variant's payload (with padding for alignment) — this is why Option<bool> is often larger than 1 byte.
Q3What does exhaustiveness checking in match buy you? Explain the role of #[non_exhaustive] in library API design.▼ answer
Model answer
A match over an enum must cover every variant (or include a _ wildcard) or the code fails to compile. This means adding a new variant to an enum you own is a compile-time-detected breaking change everywhere it's matched — the compiler forces you to update every call site, eliminating a whole class of "forgot to handle the new case" bugs that plague switch-based languages at runtime. #[non_exhaustive] is the library-author escape hatch: applied to a public enum or struct, it forces downstream crates to always include a _ wildcard arm (or use .. for struct fields) — meaning the library can add new variants/fields in a minor version without that being a breaking change for consumers. The trade-off: consumers lose exhaustiveness checking for that type entirely, so it should only be applied where you genuinely expect to extend the type later.
Q4Explain match guards, bindings with @, and the difference between matching by value vs by reference (match &x vs match x).▼ answer
Model answer
match n {
    x if x < 0 => println!("negative"),
    x @ 0..=9 => println!("small: {x}"), // bind AND range-match
    _ => println!("large"),
}
Match guards (if after the pattern) add arbitrary boolean conditions but don't participate in exhaustiveness — the compiler can't prove a guard is unreachable, so you still need a fallback arm. @ bindings let you both destructure/range-match and capture the whole matched value under a name. Matching by reference vs value: match some_string { ... } on an owned, non-Copy value moves it into the match (fields bound by patterns take ownership) — the original variable becomes unusable afterward. match &some_string { ... } matches against a reference, so patterns bind &T by default (or you use ref in older code, now largely superseded by "match ergonomics" which auto-adjusts binding modes based on whether you're matching a reference). This distinction matters constantly when matching on a field accessed through &self — forgetting to match by reference causes "cannot move out of borrowed content" errors.
Q5How would you model a state machine using enums so that illegal states are unrepresentable? Give a concrete example of the "typestate" pattern.▼ answer
Model answer
The core idea — "make illegal states unrepresentable" — is to encode invariants into the type system so invalid combinations of data simply cannot be constructed, rather than being represented and then validated defensively at runtime. A state-machine enum where each variant only carries the data relevant to that state is one form: 
enum Connection {
    Disconnected,
    Connecting { attempt: u32 },
    Connected { socket: TcpStream, session_id: u64 },
}
// impossible to have a session_id without a live socket — the type enforces it
The typestate pattern goes further, encoding the state in the type itself so transitions are checked at compile time and old states can't be reused: 
struct Door<State> { _marker: PhantomData<State> }
struct Open;
struct Closed;

impl Door<Closed> {
    fn open(self) -> Door<Open> { Door { _marker: PhantomData } }
}
impl Door<Open> {
    fn close(self) -> Door<Closed> { Door { _marker: PhantomData } }
}
// door.close().close() — compile error: Door<Closed> has no close() method
self-by-value consumes the old state so it can't be reused; the returned type is the new state. This is used in real crates for builder APIs (can't call .build() until required fields are set) and protocol implementations (can't send data before a handshake completes). The trade-off is API surface bloat — one method set per state — so it's reserved for state machines with real safety value, not applied reflexively everywhere.
Q6Explain slice patterns ([first, .., last], [a, b, rest @ ..]) and or-patterns (1 | 2 | 3). How do they replace what would otherwise be manual indexing and if-chains?▼ answer
Model answer
fn describe(nums: &[i32]) -> String {
    match nums {
        [] => "empty".into(),
        [x] => format!("single: {x}"),
        [first, .., last] => format!("first={first}, last={last}"),   // matches ANY length >= 2
    }
}

fn split_head(nums: &[i32]) -> Option<(i32, &[i32])> {
    match nums {
        [head, rest @ ..] => Some((*head, rest)),  // `rest @ ..` binds the REMAINING slice, not just skips it
        [] => None,
    }
}

fn classify(n: i32) -> &'static str {
    match n {
        1 | 2 | 3 => "small",                        // or-pattern — one arm, three literals
        n if n < 0 || n > 100 => "out of range",  // or-patterns compose with guards
        _ => "other",
    }
}
Slice patterns destructure a slice/array by shape directly in the match, rather than indexing with bounds checks and .unwrap() scattered through the body — [first, .., last] matches any slice with length ≥ 2 (the compiler proves exhaustiveness across the [], [x], and length-≥2 arms for you) and binds both ends in one line with no possibility of an off-by-one panic. rest @ .. binds the remaining sub-slice as its own &[T] — this is exactly the pattern behind writing a recursive function over "head and tail" without ever calling .split_first() manually, and it composes naturally with recursion (peel one element per call). Or-patterns (1 | 2 | 3) collapse what would otherwise be several separate match arms — or a chain of || comparisons in an if — into a single arm, and they compose with @ bindings (n @ (1 | 2 | 3) binds n to whichever literal matched) and with match guards. The same .. "ignore/collect the rest" syntax also works for struct fields (Point { x, .. } ignores every field except x) and tuple structs — it's one consistent piece of pattern-matching vocabulary reused across slices, structs, and tuples.

A classic senior tell: given a struct with three optional fields that are only sometimes valid together (e.g. error: Option<String>, retry_count: Option<u32> that should only exist together), a senior candidate immediately proposes collapsing them into an enum variant instead of "just add a comment explaining the invariant." This single instinct — types over runtime discipline — is one of the highest-signal things you can demonstrate in a design discussion.
// Topic 03
Error Handling
Questions & model answers
Q1What is the difference between panic! and returning Result::Err? When is each appropriate?▼ answer
Model answer
panic! signals an unrecoverable programming error — an invariant the program logic assumed would always hold has been violated. By default it unwinds the stack (running destructors along the way, similar to a C++ exception) and aborts that thread; it can be configured to abort immediately instead (smaller binaries, no unwind tables, but no cleanup). A panic in the main thread terminates the process; a panic in a spawned thread only poisons that thread — JoinHandle::join() returns an Err to the joining thread, the rest of the program continues (unless it was holding a lock, which becomes poisoned — see mutex poisoning). Result<T, E> represents an expected, recoverable failure mode that's part of a function's normal contract — a file might not exist, a network call might time out, user input might be malformed. Use panics for "this should be logically impossible" (a bug if it happens — e.g. an internal invariant check) and Results for "this can plausibly fail and the caller should decide what to do about it." A library that panics on bad user input instead of returning an error is considered a design flaw in idiomatic Rust.
Q2Explain the ? operator. What does it do under the hood, and what trait makes it work across different error types?▼ answer
Model answer
expr? is sugar: if expr evaluates to Ok(v), it unwraps to v; if it evaluates to Err(e), it immediately returns Err(From::from(e)) from the enclosing function. The From trait conversion is the key mechanism: it lets you propagate a low-level error type (e.g. std::io::Error) up through a function whose return type is a higher-level custom error (e.g. MyAppError), as long as impl From<io::Error> for MyAppError exists — no manual .map_err() needed at every call site. ? also works on Option<T> inside functions returning Option (propagates None). Since Rust 2021 (via the Try trait, still partially unstable for custom types but fully working for Result/Option), it generalises the pattern. The main constraint: the function using ? must have a return type compatible with the propagated error — this is why main() can return Result<(), E> to use ? at the top level.
Q3Compare anyhow and thiserror. Why would a library crate use one and an application binary use the other?▼ answer
Model answer
thiserror is a derive macro that generates boilerplate for defining structured, typed error enums — you write the variants, it generates Display, Error, and From impls from attributes: 
#[derive(thiserror::Error, Debug)]
enum DbError {
    #[error("connection failed: {0}")]
    Connection(#[from] io::Error),
    #[error("row not found: id={id}")]
    NotFound { id: u64 },
}
anyhow provides anyhow::Error — a single type-erased error box (similar to Box<dyn Error> but nicer ergonomics: automatic ? conversion from anything implementing std::error::Error, easy .context("...") annotation for adding human-readable trace context as errors bubble up). Libraries use thiserror because their errors are part of the public API — callers need to match on specific variants to react differently (retry on timeout, don't retry on auth failure). Applications use anyhow at the top level because the binary usually just wants to log/display the error and exit — callers of a main() don't need to match variants, they need a good error message and maybe a chain of "caused by" context. A common pattern: internal library code returns thiserror enums; the top-level main() -> anyhow::Result<()> wraps and adds context as errors flow up through ?.
Q4What does mutex poisoning mean in the standard library, and what's the senior-level critique of that design? How does parking_lot differ?▼ answer
Model answer
If a thread panics while holding a std::sync::Mutex lock, the standard library marks the mutex as poisoned — every subsequent .lock() call from any thread returns Err(PoisonError) instead of blocking normally, because the data behind the lock might be in an inconsistent state (the panic could have happened mid-mutation). You can still recover the guard via .into_inner() on the error if you're confident the invariant wasn't actually broken. Senior-level critique: poisoning is a blunt instrument — it assumes any panic under a lock corrupts the data, which is often not true (a panic in unrelated code that happens to be called while the lock is held, or a panic that occurs strictly before any mutation) — yet it forces every caller everywhere to handle the PoisonError case, adding friction for a rare and often-irrelevant event. Most real-world code just calls .unwrap() on the lock result, which converts a recoverable design into "poisoning just panics again downstream" — arguably worse than not having poisoning at all. parking_lot::Mutex deliberately drops poisoning entirely — .lock() returns the guard directly, no Result — betting that most users want a faster, simpler mutex and will design their own recovery strategy if they actually need one. It's also measurably faster (smaller, no OS futex syscall in the uncontended fast path on some platforms) and adds features std lacks, like fair unlocking and reentrant mutexes.
Q5Design an error-handling strategy for a mid-sized service with a storage layer, an HTTP layer, and business logic in between. How do errors flow between layers?▼ answer
Model answer
Storage layer: a thiserror enum specific to that layer (StorageError::NotFound, ::ConnectionLost, ::Serialization) — this is the layer that knows about SQL error codes, connection pools, etc.; those details should never leak upward as-is. Business/domain layer: its own error enum (DomainError::InvalidState, ::PermissionDenied, ::Upstream(StorageError)) that wraps lower-layer errors via #[from] — this layer translates "connection lost" into a domain-meaningful concept and adds semantic variants the storage layer has no concept of (e.g. business-rule violations). HTTP layer: implements a trait (e.g. axum's IntoResponse) on the domain error to map each variant to an HTTP status + JSON body — NotFound → 404, PermissionDenied → 403, catch-all Upstream(_) → 500 with the internal detail logged but not exposed to the client (avoid leaking internals in error messages — a real security consideration). Cross-cutting: use tracing::error! with structured fields at the point an error is about to cross a trust boundary (e.g. right before converting to an HTTP response), so you get full context (request id, user id) in logs without needing every intermediate function to log redundantly. The key principle: each layer's error type should only expose concepts meaningful to its callers — propagating raw SQL errors to an HTTP client is a design smell showing layers aren't properly separated.

// Topic 04
Functions & Closures
Questions & model answers
Q1What are the three closure traits — Fn, FnMut, and FnOnce? How does the compiler pick which one a closure implements?▼ answer
Model answer
FnOnce: can be called at most once — it may move/consume captured variables. FnMut: can be called multiple times and may mutate captured variables (captures by &mut). Fn: can be called multiple times and only reads captured variables (captures by &). Every closure implements FnOnce at minimum; FnMut implies FnOnce; Fn implies both — it's a hierarchy, not three exclusive categories. The compiler infers which traits a closure implements by analysing its body: if it moves a captured value out (e.g. returns owned data it captured, or passes it to a function taking ownership), it's only FnOnce. If it mutates a capture, it's FnMut (and also FnOnce, since anything callable multiple times is trivially callable once). If it only reads captures, it's Fn (and thus also the other two). The move keyword forces captures to be taken by value instead of by reference — it doesn't by itself determine which trait is implemented, that's still based on what the body does with the moved data.
Q2What's the difference between impl Fn() -> i32 and Box<dyn Fn() -> i32> as a function's return type? When must you use the latter?▼ answer
Model answer
impl Fn() -> i32 (return-position impl trait, RPIT) returns a single concrete, compiler-known type — the actual closure type generated for that specific closure expression — but the caller doesn't get to name it, only knows it implements Fn() -> i32. This is static dispatch, zero overhead, and every call site returning from that function must return the same concrete closure type (you can't have an if branch return one closure and another branch return a different closure, even if both satisfy the trait — their concrete types differ). Box<dyn Fn() -> i32> heap-allocates the closure and stores it behind a trait-object fat pointer — dynamic dispatch, an allocation, and a vtable call per invocation, but now any closure matching the signature can be returned interchangeably, including from different branches. You must use the boxed trait-object form when the concrete closure type varies at runtime (a factory function selecting between several possible closures) or when you need to store heterogeneous closures in a collection (Vec<Box<dyn Fn()>>).
Q3Explain function pointers (fn type) vs closures. Can every closure be used where a function pointer is expected?▼ answer
Model answer
A fn pointer (e.g. fn(i32) -> i32) is a plain pointer to a function's machine code — it has a fixed, tiny size (one pointer word) and captures nothing from its environment. A closure is a compiler-generated anonymous struct holding its captured variables, plus a generated call implementation — its size depends on what it captures (zero-sized if it captures nothing). Non-capturing closures coerce to fn pointers automatically because they carry no state — let add_one: fn(i32) -> i32 = |x| x + 1; compiles fine. Capturing closures cannot — there's no way to represent captured state in a bare function pointer, so let x = 5; let add_x: fn(i32) -> i32 = |y| y + x; fails to compile. This distinction matters for FFI: C callback APIs expect a bare function pointer (plus often a void* userdata parameter as the idiomatic workaround for "capturing" state across the FFI boundary), so a capturing Rust closure can't be passed directly — you pass a non-capturing trampoline function plus a raw pointer to your state as the userdata.
Q4Write a function that takes a generic closure parameter using each of the three approaches (generic + trait bound, impl Trait param, dyn Trait param) and explain the performance and flexibility trade-offs of each.▼ answer
Model answer
// 1. Generic + trait bound — monomorphised, zero-cost, most flexible for the caller
fn apply_generic<F: Fn(i32) -> i32>(f: F, x: i32) -> i32 { f(x) }

// 2. impl Trait param — sugar for the same thing, reads cleaner for a single bound
fn apply_impl(f: impl Fn(i32) -> i32, x: i32) -> i32 { f(x) }

// 3. dyn Trait param — one compiled function body, dynamic dispatch per call
fn apply_dyn(f: &dyn Fn(i32) -> i32, x: i32) -> i32 { f(x) }
(1) and (2) are identical under the hood — both are monomorphised: the compiler generates a separate copy of apply_generic/apply_impl for every distinct closure type passed at any call site. Zero-cost, fully inlinable, but contributes to binary size and compile time if called with many distinct closure types across a large codebase. (3) compiles to exactly one function body, callable with any &dyn Fn(i32) -> i32 — smaller binary, faster compile, but each call goes through a vtable indirection (can't be inlined by the compiler across the call boundary) and the caller needs to already have the closure behind a reference or box. The senior-level judgement call: use generics/impl-Trait for hot-path, performance -critical code and for public library APIs (lets callers pass zero-cost closures); reach for dyn when you need to store heterogeneous callbacks in one collection, when compile-time/binary-size matters more than the last few nanoseconds, or when the function is not a hot path (e.g. one-time config callbacks).
Q5What is a higher-ranked trait bound (HRTB), and why does for<'a> Fn(&'a str) -> &'a str sometimes appear in error messages or trait definitions?▼ answer
Model answer
A normal generic lifetime parameter on a function is chosen once, by the caller, for that whole call. But a closure parameter that must work with any lifetime the caller hands it at the moment it's invoked — not fixed at the point the closure is passed in — needs a higher-ranked trait bound: for<'a> Fn(&'a str) -> &'a str means "for every possible lifetime 'a, this closure can be called with a &'a str and returns a &'a str with that same lifetime" — the closure must be generic over the lifetime, chosen fresh on each call, rather than the caller picking one lifetime up front. This comes up constantly with closures taking references as parameters — the compiler infers HRTBs automatically for most common cases (which is why you rarely write for<'a> yourself), but it surfaces in error messages when type inference can't figure out whether a closure needs to be higher-ranked or can use one concrete lifetime, or when writing generic functions/trait definitions that accept closures over references, like a callback that processes a borrowed item from an iterator without owning it. Deep understanding here separates "used closures" from "understands why some closure-taking generic code doesn't compile and how to fix the trait bound."
Q6As a parameter type specifically (not return type): what's the difference between f: &dyn Fn(i32) -> i32, f: &mut dyn FnMut(i32) -> i32, and f: Box<dyn FnOnce(i32) -> i32>? Why does each pick that particular reference/ownership form?▼ answer
Model answer
Each form's ownership/reference kind is dictated entirely by which closure trait it wraps, not by preference: 
// Fn: only reads captures, can be called any number of times through a shared reference
fn call_fn(f: &dyn Fn(i32) -> i32) -> i32 { f(1) + f(2) }

// FnMut: mutates captures, so calling it needs an EXCLUSIVE borrow each time
fn call_fn_mut(f: &mut dyn FnMut(i32) -> i32) -> i32 { f(1) + f(2) }

// FnOnce: may consume its captures, so the trait object itself must be consumed by value —
// a &dyn FnOnce can't work, since calling through a reference can't move out of it
fn call_fn_once(f: Box<dyn FnOnce(i32) -> i32>) -> i32 { f(1) }
&dyn Fn works because Fn::call only needs &self — you can call it through a shared reference as many times as you like, so no box/allocation is required if the caller already owns the closure elsewhere. &mut dyn FnMut needs &mut self because FnMut::call_mut requires exclusive access — still no heap allocation needed, just a mutable borrow. Box<dyn FnOnce> is the one that must own the closure: since FnOnce::call_once consumes self, you cannot call it through any kind of reference — the trait object has to be owned outright so it can be moved out of and dropped after the single call. This is exactly why APIs like thread::spawn take F: FnOnce() -> T + Send + 'static by value rather than by any reference — the closure is consumed exactly once, on the spawned thread, then the trait bound disappears (it's generic, not dyn, so it's monomorphised too).
✓ Strong
  • Explains the Fn/FnMut/FnOnce hierarchy via what the closure body does, not just definitions
  • Knows why capturing closures can't coerce to fn pointers (FFI relevance)
  • Can articulate monomorphisation vs dyn dispatch trade-off for closure parameters unprompted
  • Has at least a working mental model of HRTBs even if syntax is rusty
  • Picks &dyn Fn / &mut dyn FnMut / Box<dyn FnOnce> correctly based on the trait's self receiver
⚠ Probe
  • Uses move keyword but conflates it with FnOnce specifically
  • Always reaches for Box<dyn Fn> without considering impl Trait
  • Tries to write &dyn FnOnce and can't explain why it doesn't compile
✗ Concern
  • Cannot explain the difference between the three Fn traits
  • Thinks closures and function pointers are always interchangeable
🎯 Senior angle
A great probing question: "you have a callback-heavy API — should the callback parameter be generic (impl Fn) or a trait object (Box<dyn Fn>)?" There's no universally correct answer — the strong signal is walking through binary size, compile time, call-site ergonomics, and storage requirements out loud rather than picking one reflexively.
// Topic 05
Lifetimes Deep-Dive
Questions & model answers
Q1What does a lifetime annotation like 'a actually mean? Does it change how long a value lives?▼ answer
Model answer
A lifetime annotation never changes how long anything lives — it only describes an existing relationship to the compiler so it can verify it. Values live exactly as long as their scope dictates regardless of what you write; lifetime parameters are purely a way of telling the borrow checker "these references are related — this output reference cannot outlive that input reference." Given: 
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
this signature says: "the returned reference is valid for at most as long as the shorter-lived of the two input borrows" — because the function body might return either one. The caller's borrow checker then uses that contract to reject any use of the returned reference beyond that shared scope. If the function always returned x, you could annotate y with an unrelated lifetime; the annotation reflects the real data-flow, it isn't decorative.
Q2What are lifetime elision rules? Give an example of a function signature where you don't need to write lifetimes explicitly, and explain why the compiler can infer them.▼ answer
Model answer
The compiler applies three elision rules so common patterns don't require explicit annotation: (1) each elided reference parameter gets its own distinct lifetime; (2) if there's exactly one input lifetime, it's assigned to all elided output lifetimes; (3) if one parameter is &self or &mut self, its lifetime is assigned to all elided output lifetimes (methods almost always return something tied to self's borrow, not to other parameters). 
fn first_word(s: &str) -> &str { s.split(' ').next().unwrap() }
// desugars to: fn first_word<'a>(s: &'a str) -> &'a str  — rule 2 applies
Elision only fires for these specific, unambiguous shapes — as soon as a function has two or more input references and doesn't take self, the compiler can't guess which input the output borrows from, and you must annotate explicitly (this was exactly the longest() example from Q1).
Q3Explain variance for lifetimes: why does &'long T coerce to &'short T but not the other way? What about &mut T and variance?▼ answer
Model answer
&'a T is covariant in 'a: if 'long outlives 'short, then a &'long T can be used anywhere a &'short T is expected — this is sound because "valid for longer" is strictly more useful/restrictive than "valid for shorter"; you're never claiming a reference lives longer than it actually does, only using it for less time than it's capable of. This subtyping-like relationship ("'long is a subtype of 'short" in variance terms) is what lets you pass a longer-lived reference into a function expecting a shorter-lived one without any explicit cast. &'a mut T is covariant in 'a but invariant in T — you can shorten the lifetime of a mutable reference the same way, but you cannot substitute &mut Cat for &mut Animal even if Cat: Animal-like relationships existed, because through a mutable reference you could write a different concrete type back into the original slot, breaking the caller's assumption about what's stored there. This is why &T is covariant in T (read-only, no write-back risk) but &mut T is invariant in T — the asymmetry directly reflects the aliasing-XOR-mutation principle: shared/read access is safe to "widen," exclusive/write access is not.
Q4What is a self-referential struct, and why can't you naively write one in safe Rust? What are the real-world workarounds?▼ answer
Model answer
A self-referential struct has a field that borrows from another field of the same struct — e.g. a struct holding a String and a &str slice into that same String. The fundamental problem: Rust structs can be moved (memcpy'd to a new stack/heap address) freely by default — but a move relocates the owning field while the internal pointer in the borrowing field would still point at the old address, becoming immediately dangling. The borrow checker prevents you from expressing this at all in safe code because there's no lifetime you could correctly annotate — the borrow's target moves with the struct, but a lifetime parameter describes an external relationship, not an internal one. Workarounds used in real code, roughly in order of how often they're actually the right call: (1) Don't own the data in the same struct at all — push the owned value (e.g. the source String) out to the caller, and have your type hold only a borrowed &'a str/ &'a T into it, with an explicit lifetime parameter on the struct. This is the most common real-world fix by far — it sidesteps the problem entirely rather than working around it, at the cost of pushing responsibility for keeping the source alive onto the caller. (2) Store an index/offset instead of a reference — e.g. (String, Range<usize>) instead of (String, &str), recomputing the slice via &s[range] on demand; the right call specifically when the struct genuinely does need to own both pieces together (e.g. to be moved into a Vec, stored, or serialized as one unit). (3) Pin<Box<T>> — heap-allocates the struct and statically prevents it from being moved afterward (the mechanism async/await desugaring relies on internally, since a generated state-machine future is exactly this kind of self-referential structure holding borrows across .await points). (4) Crates like ouroboros or self_cell generate the unsafe plumbing for you via macros, for the cases where neither (1) nor (2) fit the API you need. Knowing that Pin exists specifically to solve this problem — and that it's the mechanism underpinning how async functions can hold references across await points — is a strong senior signal, but jumping straight to option (3)/(4) without first asking "could I just not own this data in the same place?" is a mild overengineering smell.
Q5Explain the difference between the lifetime 'static on a reference (&'static str) and the trait bound T: 'static in a generic function. This trips up almost everyone at first.▼ answer
Model answer
&'static str is a reference that is valid for the entire remaining duration of the program — typically a string literal baked into the binary's read-only data segment, or something explicitly leaked/boxed with a 'static lifetime. This is the narrow, literal meaning most people learn first. T: 'static as a trait bound on a generic type parameter means something broader and more subtle: "T contains no non-'static borrowed references" — i.e. T is either fully owned data (like String, Vec<u8>, or any type with no lifetime parameters at all) or it only contains 'static references itself. Crucially, an owned String satisfies T: 'static even though the String value itself might be dropped in five milliseconds — because "the type doesn't borrow from anything with a shorter lifetime" is a completely different claim from "this value lives forever." This is why tokio::spawn(future) requires future: Send + 'static: the spawned task might run on a different thread and outlive the current stack frame, so it cannot borrow anything from the caller's local variables — but it's perfectly fine for that future to itself be short-lived and own all its data. Confusing these two meanings of 'static is probably the single most common Rust misconception among people who've only used the language for a few months.
Q6When should a function with two reference parameters give them independent lifetimes ('a, 'b) versus forcing them to share one 'a? Most people default to sharing "just in case" — when is that actually wrong?▼ answer
Model answer
The deciding question is: does the return value's lifetime need to depend on both inputs, or only on one of them? The classic longest<'a>(x: &'a str, y: &'a str) -> &'a str genuinely needs one shared 'a because the function body might return either x or y depending on a runtime comparison — the signature can't know in advance which input the output borrows from, so it must be valid for the lifetime both inputs have in common. But consider: 
fn first_match<'a, 'b, T: PartialEq>(haystack: &'a [T], needle: &'b T) -> Option<&'a T> {
    haystack.iter().find(|item| *item == needle)
}
Here the returned reference provably only ever comes from haystack — needle is only ever compared against, never returned — so giving them independent lifetimes is not just allowed, it's more correct: forcing both under one shared 'a would incorrectly require needle to live at least as long as haystack, rejecting perfectly safe call patterns where needle's scope ends well before haystack's does, purely because the signature over-constrained a relationship that doesn't actually exist in the function body. Defaulting to one shared 'a "to be safe" is a real, if usually harmless, code smell — every lifetime parameter in a signature should be there because the return type or a where-clause bound actually needs it, not by default habit. The skill being tested is recognizing which of the two shapes a given function actually is, not memorizing either example in isolation.
✓ Strong
  • States clearly that lifetimes describe, never extend, a value's actual lifespan
  • Explains covariance of &T vs invariance of &mut T in terms of write-back risk
  • Knows Pin exists and why it's required for self-referential/async state machines
  • Correctly distinguishes &'static str from a T: 'static bound — the classic gotcha
  • Gives independent lifetime parameters their own names rather than defaulting to one shared 'a everywhere
⚠ Probe
  • Adds lifetime annotations by trial-and-error until it compiles, without a mental model
  • Knows elision exists but can't state the three rules
✗ Concern
  • Believes 'static means "the value lives forever" in all contexts, including generic bounds
  • Cannot explain why a function with two &str params sometimes needs explicit lifetimes and sometimes doesn't

The &'static str vs T: 'static distinction is a favourite "gotcha" question precisely because so many intermediate Rust developers have never had it explained clearly. Nailing this cleanly, especially connecting it to why tokio::spawn requires 'static, reliably reads as senior-level understanding rather than memorised syntax.
