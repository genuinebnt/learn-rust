B1 · The Borrow Checker Fight
ownership borrowing mutable aliasing Easy–Medium
This does not compile — ask the candidate to predict the compiler error, then explain the fix
fn find_and_remove_first_negative(nums: &mut Vec<i32>) -> Option<i32> {
    let first_negative = nums.iter().find(|&&n| n < 0);

    if let Some(&value) = first_negative {
        let pos = nums.iter().position(|&n| n == value).unwrap();
        nums.remove(pos);  // ← candidate should predict: E0502, cannot borrow as mutable
        Some(value)
    } else {
        None
    }
}

fn main() {
    let mut v = vec![1, 2, -3, 4, -5];
    find_and_remove_first_negative(&mut v);
}
Root cause · Fix · Follow-up probes
Root cause
first_negative borrows nums immutably (via .iter()), and that borrow's lifetime extends through the entire if let block because value is extracted from it (technically value is a copy, but the compiler's borrow-checker conservatively ties the borrow's scope to how the pattern binding is used — in practice with NLL, the immutable borrow from .iter() ends right after .find() returns since we destructure to an owned i32 via &value. The actual compile error here comes from the second call: nums.iter().position(...) creates another immutable borrow, and then nums.remove(pos) on the very next line requires a mutable borrow while conceptually you're still "inside" the reasoning chain that started with reading from nums. In this exact snippet as written, NLL is actually smart enough that each individual borrow ends as soon as its last use finishes — the position borrow ends right after .unwrap(), before remove() — so a candidate who tests this exact code might find it does compile with modern NLL. This is itself the valuable teaching moment: have the candidate explain why it compiles despite looking like a conflict, tracing through when each borrow's last use actually occurs — that reasoning is the real skill being tested, regardless of whether the final verdict is "compiles" or "doesn't."
A version that definitely fails, and the idiomatic fix
// This version DOES fail to compile — the borrow is held across the mutation:
fn broken(nums: &mut Vec<i32>) -> Option<i32> {
    if let Some(first) = nums.iter().find(|&&n| n < 0) {
        let pos = nums.iter().position(|n| n == first).unwrap();  // E0502: first still borrows nums
        nums.remove(pos);
        Some(*first)
    } else { None }
}

// Fix — find the index directly; only one borrow, ended before the mutation:
fn fixed(nums: &mut Vec<i32>) -> Option<i32> {
    let pos = nums.iter().position(|&n| n < 0)?;  // borrow ends here
    Some(nums.remove(pos))                       // mutation happens after
}
Follow-up probes
  • P1"Why does binding to first: &i32 vs destructuring to &value (copying out an owned i32) change whether the borrow persists?" — When you destructure with Some(&value) against an Option<&i32>, you're pattern-matching through the reference and copying the i32 out — value is an owned i32 with no lifetime tied to nums at all. When you bind Some(first) where first: &i32, you're holding onto the reference itself, and NLL must keep the borrow alive as long as first is used.
  • P2"What is 'two-phase borrows' and does it help here?" — Two-phase borrows relax the rule for method calls like vec.push(vec.len()) — the mutable borrow for push is reserved but not activated until after arguments are evaluated. It doesn't help across statement boundaries the way this bug spans two separate lines/lookups.
  • P3"Why is finding the position directly, rather than the value, the more idiomatic Rust fix?" — It collapses two separate borrows (one to find the value, one to find its position) into a single borrow that ends as soon as .position() returns — fewer borrows outstanding is generally both simpler to reason about and more likely to satisfy the borrow checker without fighting it.
  • P4"How would you solve this with the entry-style pattern if nums were a HashMap instead of a Vec?" — The equivalent bug (borrow from a lookup held across a subsequent mutation) shows up constantly with HashMaps too — the entry API (from the collections topic) exists specifically to collapse a lookup-then-mutate sequence into one borrow, avoiding this exact class of fight.
🎯 Senior angle
The strongest candidates predict the compiler's exact reasoning about when a borrow's last use occurs rather than just pattern-matching "looks like two borrows, must be an error." Being able to correctly say "actually, I think this compiles because the first borrow's last use is before the mutation" — and being right — is a stronger signal than reflexively assuming every multi-borrow snippet is broken.
// Bug Exercise 02 · 15 min
B2 · The Rc Cycle Leak
Rc RefCell memory leak Medium
This compiles and runs without panicking — but leaks memory. Find out why.
use std::cell::RefCell;
use std::rc::Rc;

struct Node {
    value: i32,
    parent: RefCell<Option<Rc<Node>>>,
    children: RefCell<Vec<Rc<Node>>>,
}

fn main() {
    let parent = Rc::new(Node {
        value: 1,
        parent: RefCell::new(None),
        children: RefCell::new(vec![]),
    });

    let child = Rc::new(Node {
        value: 2,
        parent: RefCell::new(None),
        children: RefCell::new(vec![]),
    });

    parent.children.borrow_mut().push(Rc::clone(&child));   // parent → child (strong)
    *child.parent.borrow_mut() = Some(Rc::clone(&parent)); // child → parent (strong) — CYCLE

    println!("parent strong_count = {}", Rc::strong_count(&parent)); // 2, not 1!
    // Neither Node is ever dropped, even after both `parent` and `child` go out of scope.
}
Root cause · Fix · Follow-up probes
Root cause
parent holds a strong reference to child (via children: Vec<Rc<Node>>), and child holds a strong reference back to parent (via parent: Option<Rc<Node>>) — a reference cycle. When main ends, the local variables parent and child drop, decrementing each's strong count by one — but each node's strong count was 2 (one from the local variable, one from the other node's field), so after both locals drop, each count is still 1, never reaching zero. Neither Node's destructor ever runs, and the memory for both nodes (plus their RefCells and any heap data inside) leaks for the remaining lifetime of the program. This does not crash, does not panic, and produces no error of any kind — it's a silent leak, exactly the "unsound but every test passes" category of correctness issue discussed in the unsafe/soundness topic, except achievable in entirely safe Rust code.
Correct fix — break the cycle with Weak
use std::rc::{Rc, Weak};

struct Node {
    value: i32,
    parent: RefCell<Option<Weak<Node>>>,   // ← back-edge is now non-owning
    children: RefCell<Vec<Rc<Node>>>,      // forward edge stays strong
}

fn main() {
    let parent = Rc::new(Node { value: 1, parent: RefCell::new(None), children: RefCell::new(vec![]) });
    let child  = Rc::new(Node { value: 2, parent: RefCell::new(None), children: RefCell::new(vec![]) });

    parent.children.borrow_mut().push(Rc::clone(&child));
    *child.parent.borrow_mut() = Some(Rc::downgrade(&parent));  // Weak — no strong count increment

    println!("parent strong_count = {}", Rc::strong_count(&parent)); // 1 — correct
    // To use the parent from the child: child.parent.borrow().as_ref().unwrap().upgrade()
    // returns Option> — None if the parent has already been dropped.
}
Follow-up probes
  • P1"How would you actually detect this leak, given that it doesn't crash or panic?" — Rc::strong_count() checked in tests/asserts after dropping all expected owners is the direct way; more generally, a leak-detection tool (Valgrind works on Rust binaries too, or a heap profiler like dhat-rs / heaptrack showing steadily growing retained memory with no corresponding drops) would surface it in a running process over time.
  • P2"Why doesn't the borrow checker catch this at compile time the way it catches other memory bugs?" — Rc/RefCell deliberately opt out of the borrow checker's compile-time reasoning — Rc provides runtime-managed shared ownership specifically because compile-time-checked single ownership isn't expressible for this use case (a genuine graph with shared parent/child ownership). The trade-off is that some correctness properties (like acyclicity) move from "enforced by the compiler" to "the programmer's responsibility," exactly as discussed in this packet's Rc/RefCell design-smell critique.
  • P3"What happens if you call .upgrade() on a Weak after the parent has actually been dropped?" — Returns None — this is exactly why Weak::upgrade() returns an Option rather than a bare Rc: the compiler forces you to handle the case where the referenced value no longer exists, unlike a dangling raw pointer which would just be undefined behaviour to dereference.
  • P4"Is there a way to design this data structure to avoid Rc/RefCell entirely?" — Yes — an arena-based design (e.g. all nodes stored in one Vec<Node>, with parent/child relationships represented as plain usize indices into that Vec rather than Rc pointers) sidesteps the whole Rc/Weak/RefCell machinery, trading a small amount of index-based ergonomics for a data structure with no possibility of reference cycles or runtime borrow panics at all — a common pattern in Rust game engines and compilers (e.g. AST representations).
🎯 Senior angle
A candidate who immediately reaches for an arena/index-based redesign as an alternative to Rc/Weak — rather than treating Weak as the only tool in the box — is showing awareness that Rc-based graphs are one valid design among several, not the default correct answer for every parent/child structure.

B3 · Mutex Deadlock
Mutex lock ordering self-deadlock Medium
This hangs forever on the second call. Why?
use std::sync::Mutex;

struct Account { balance: Mutex<i64> }

impl Account {
    fn balance(&self) -> i64 {
        *self.balance.lock().unwrap()
    }

    fn withdraw(&self, amount: i64) -> Result<(), String> {
        let mut bal = self.balance.lock().unwrap();  // lock acquired, held for the rest of the function
        if *bal < amount {
            return Err("insufficient funds".to_string());
        }
        println!("current balance: {}", self.balance());  // ← calls balance(), which tries to lock again
        *bal -= amount;
        Ok(())
    }
}

fn main() {
    let acct = Account { balance: Mutex::new(100) };
    acct.withdraw(30).unwrap();  // hangs forever, never returns
}
Root cause · Fix · Follow-up probes
Root cause
This is a self-deadlock — the same thread tries to acquire a lock it's already holding. withdraw() calls self.balance.lock() and binds the guard to bal, which stays alive (the lock stays held) for the rest of the function since it's used again later (*bal -= amount). While still holding that lock, it calls self.balance(), which itself tries to self.balance.lock() — but std::sync::Mutex is not reentrant: a thread trying to lock a mutex it already holds simply blocks forever waiting for itself to release it, which of course never happens. Unlike some other languages' mutex implementations (e.g. certain reentrant-by-default lock types), Rust's standard mutex — and most mutex implementations generally — assume a thread never tries to re-acquire a lock it holds, and provide no special-casing for it; there's no error, no panic, just a silent, permanent hang.
Fix — don't call a locking method while already holding the lock
fn withdraw(&self, amount: i64) -> Result<(), String> {
    let mut bal = self.balance.lock().unwrap();
    if *bal < amount {
        return Err("insufficient funds".to_string());
    }
    println!("current balance: {}", *bal);  // read the already-held guard directly, no re-lock
    *bal -= amount;
    Ok(())
}
// General rule: within a method that holds a lock guard for its whole body,
// never call another method on self that itself tries to acquire the same lock.
Follow-up probes
  • P1"Would this bug happen with parking_lot::Mutex too?" — Yes — parking_lot's Mutex is also non-reentrant by default (it does offer a separate ReentrantMutex type specifically for cases where re-entrant locking is genuinely needed, but that's opt-in, not the default Mutex).
  • P2"How would you detect this in a larger codebase where the re-entrant call isn't so obviously two lines apart?" — parking_lot has an optional deadlock-detection feature (parking_lot::deadlock::check_deadlock()) that can be run periodically or on a debug endpoint to detect stuck locks in a running process. More generally, if a request/task hangs indefinitely, a stack dump of all threads (or, in async code, tokio-console's task inspection) showing a thread blocked inside its own call stack on the same lock is the diagnostic signature.
  • P3"Is this the same class of bug as the four-Coffman-conditions deadlock discussed elsewhere in this packet?" — It's a degenerate, single-thread special case of circular wait — the "cycle" here is a single thread waiting on a lock that only it could release, forming a cycle of length one. All four Coffman conditions technically still apply, just with the same thread playing both roles in the cycle.
  • P4"What's a design pattern that would make this class of bug structurally harder to write?" — Keep public methods that lock internally very small and non-recursive — never have a locking method call another public method on self. Alternatively, split into a private, lock-free "core logic" method operating on the already-unlocked data, called by multiple small public wrapper methods that each lock once, call the core method, and unlock — this avoids ever needing to call a self-locking method while a lock is held.
🎯 Senior angle
Self-deadlock via an innocuous-looking helper-method call is a genuinely common real-world bug, especially as codebases grow and a "just call the getter" habit creeps into methods that already hold the lock. Candidates who've hit this in production usually recognize it instantly; candidates who haven't often take a while to see it even after being told it hangs.

B4 · Panic in Production
unwrap error handling untrusted input Easy
This axum handler works fine in every manual test but crashes the whole worker thread under real traffic. Find all three problems.
async fn get_user_age(Path(params): Path<String>) -> String {
    let parts: Vec<&str> = params.split(',').collect();
    let name = parts[0];                                // panics if params has no comma
    let birth_year: i32 = parts[1].parse().unwrap();  // panics on bad index AND bad parse
    let age = 2026 - birth_year;
    format!("{name} is {age} years old")
}
// GET /age/Alice,1990   → "Alice is 36 years old"   (works)
// GET /age/BadInput     → panics: index out of bounds
// GET /age/Bob,notayear → panics: ParseIntError
Root cause · Fix · Follow-up probes
Root cause — three separate panic sources from untrusted input
(1) parts[0] / parts[1] indexing panics if the split produces fewer than 2 elements (input has no comma, or is empty) — indexing a slice out of bounds is one of the most common panic sources in Rust, precisely because it looks like ordinary, safe-looking code. (2) .parse().unwrap() panics if the second part isn't valid integer text — any non-numeric string after the comma crashes the handler. Why "works in every manual test": manual testing naturally uses well-formed input; it's exactly the adversarial/malformed inputs a fuzzer or real internet traffic would send (empty strings, missing delimiters, non-numeric text, extremely large numbers overflowing i32::parse) that trigger these — precisely the class of bug the fuzzing topic discussed as fuzzing's specialty. Blast radius: by default, a panic inside a Tokio task does not crash the whole process — Tokio catches the panic at the task boundary and the specific request fails (the client gets a connection reset or 500, not a graceful error response) — but every other concurrent request being handled correctly on that worker continues unaffected. This is a real, if lesser, availability issue (a whole request fails ungracefully rather than the framework being able to catch it and return a clean error), but it's a common misconception that this pattern crashes the entire server process — worth having the candidate state this precisely.
Fix — replace every unwrap/index with explicit error handling
async fn get_user_age(Path(params): Path<String>) -> Result<String, (StatusCode, String)> {
    let (name, year_str) = params.split_once(',')
        .ok_or((StatusCode::BAD_REQUEST, "expected format: name,year".into()))?;

    let birth_year: i32 = year_str.parse()
        .map_err(|_| (StatusCode::BAD_REQUEST, format!("'{year_str}' is not a valid year")))?;

    let age = 2026 - birth_year;
    Ok(format!("{name} is {age} years old"))
}
// split_once returns Option<(&str, &str)> — no indexing, no panic on missing comma.
// map_err turns the parse failure into a client-facing 400 instead of a task panic.
Follow-up probes
  • P1"Does a panic in one Tokio task bring down the whole server?" — No — Tokio isolates panics per task by default (catch_unwind at the task boundary); that specific request/task fails, but the process and other in-flight tasks continue. It's still a real bug (an ungraceful failure, potentially with no client-visible error message and confusing logs), just not a full outage — precision on this distinction matters.
  • P2"How would clippy have helped catch this before it shipped?" — clippy's `unwrap_used` and `indexing_slicing` lints (part of the stricter "pedantic" or "restriction" lint groups, not enabled by default) specifically flag exactly this pattern — many teams enable these lints project-wide for handler/parsing code that touches untrusted input, exactly to prevent this class of bug from ever compiling cleanly.
  • P3"Would fuzzing have caught this, and how quickly?" — Yes, almost immediately — a fuzzer given this function (or exercised via cargo-fuzz against the parsing logic in isolation) would find the empty-string and non-numeric-input panics within the first few seconds/iterations, since they require no cleverness to hit — this is exactly the class of "adversarial input causes a panic" bug the fuzzing topic names as fuzzing's specialty.
  • P4"Is unwrap() ever acceptable in production code?" — Yes, when the invariant it's asserting is genuinely guaranteed by earlier code in the same function/module (e.g. unwrapping a value you just inserted into a HashMap two lines earlier) — the distinguishing question is always "can external, untrusted input reach this unwrap," not "is unwrap used at all." A good habit: use `.expect("reason this can't fail")` instead of bare `.unwrap()` for these justified cases, documenting the invariant at the call site.
🎯 Senior angle
The most senior-sounding answer distinguishes "panic isolated to one task, not a process crash" from "panic crashes the whole server" — precision about blast radius, not just "this is bad," is the differentiator, and it directly informs how urgently a team should treat this class of bug.

B5 · Integer Overflow — Debug vs Release
integer arithmetic overflow debug vs release Easy–Medium
Why does this behave differently in `cargo run` vs `cargo run --release`?
fn calculate_total_price(unit_price_cents: u32, quantity: u32) -> u32 {
    unit_price_cents * quantity  // ← what happens when this overflows u32?
}

fn main() {
    let price = calculate_total_price(4_000_000_000, 3);
    println!("total: {price} cents");
}
// cargo run             → panics: "attempt to multiply with overflow"
// cargo run --release   → prints a silently wrapped, wrong number — no panic
Root cause · Fix · Follow-up probes
Root cause
Unlike C++, integer overflow in Rust is not undefined behaviour — but its observable behaviour deliberately differs between build profiles for performance reasons. In debug builds (cargo run, or explicitly [profile.dev] overflow-checks = true, the default), every arithmetic operation on primitive integers is instrumented with an overflow check that panics if it would overflow — this exists to catch overflow bugs early during development. In release builds (cargo run --release, default overflow-checks = false), these checks are compiled out entirely for performance, and overflowing arithmetic instead wraps silently (two's-complement wraparound, well -defined and consistent, unlike C++'s UB) — 4_000_000_000 * 3 = 12_000_000_000, which exceeds u32::MAX (~4.29 billion), wraps to a much smaller, wrong value with zero indication anything went wrong. This is a genuinely dangerous default combination for real code: your dev/test environment panics loudly on overflow (so you might reasonably believe your test suite would catch this class of bug), but production — the release build — silently produces wrong numbers instead, with no error, no log, no crash, which for something like a price calculation is a real, quiet financial-correctness bug that could easily reach production undetected.
Fixes — choose explicit overflow semantics rather than relying on build-profile behaviour
// Option 1: checked_mul — returns None on overflow, force the caller to handle it
fn calculate_total_price(unit_price_cents: u32, quantity: u32) -> Option<u32> {
    unit_price_cents.checked_mul(quantity)
}

// Option 2: use a wider type if the domain genuinely allows larger totals
fn calculate_total_price_u64(unit_price_cents: u32, quantity: u32) -> u64 {
    unit_price_cents as u64 * quantity as u64
}

// Option 3: enable overflow-checks in release too, if correctness > raw speed here
// Cargo.toml:
// [profile.release]
// overflow-checks = true
Follow-up probes
  • P1"Is this the same class of bug as C++'s signed integer overflow UB?" — No, and this is an important distinction — C++ signed overflow is undefined behaviour (the compiler can assume it never happens and optimise on that assumption, sometimes removing overflow checks entirely). Rust's release-mode wrapping is well-defined, deterministic two's-complement wraparound — wrong, but not UB. The danger here is purely "silent + wrong," not "the compiler might do something totally unrelated to what you wrote."
  • P2"Why doesn't Rust just always panic on overflow, even in release?" — Performance — overflow checks add a branch to every single arithmetic operation project-wide, and for code with tight numeric loops (games, numerical computing, codecs) this can be a measurable throughput cost. The debug/release split is a deliberate trade-off: fast feedback during development, raw speed in production, with the expectation that developers who need release-mode safety explicitly opt in via checked/wrapping/saturating methods at the specific call sites that matter.
  • P3"What's the difference between wrapping_mul, saturating_mul, and overflowing_mul?" — wrapping_mul always wraps (same as release-mode default behaviour, but explicit and intentional). saturating_mul clamps to the type's MAX/MIN instead of wrapping — often more useful for user-facing quantities where "clamp to max" is a more sensible failure mode than wrapping to a small number. overflowing_mul returns a (value, bool) tuple — the wrapped value plus whether overflow occurred — giving you both pieces of information in one call.
  • P4"For a real payments/pricing system, which of these would you actually pick and why?" — checked_mul (or the wider-type approach if the valid range is well understood) — for money-related calculations specifically, silently wrong output is much worse than an explicit, handleable failure. Enabling overflow-checks in release everywhere is the blunt-instrument version of the same idea but pays the performance cost project-wide rather than just at the sensitive call sites — for most services, targeted checked arithmetic at the handful of money-touching call sites is the better trade-off.
🎯 Senior angle
Precisely distinguishing "well-defined wrapping" from "undefined behaviour" is a great litmus test for whether a candidate's C++ background has led them to over-generalize a UB-flavoured fear onto Rust, where the actual risk profile (silent wrong answer, not memory corruption or compiler-assumption chaos) is real but categorically different and worth describing accurately.

B6 · Blocking the Async Runtime
Tokio async worker starvation Hard
Under low traffic this works fine. Under moderate concurrent load, p99 latency explodes across totally unrelated endpoints. Why?
async fn generate_report(Query(params): Query<ReportParams>) -> Json<Report> {
    let data = fetch_raw_data(&params).await;

    // Heavy CPU-bound aggregation over potentially 100k+ rows — no .await inside
    let report = compute_expensive_aggregation(data);  // ← runs synchronously, ~200ms for large datasets

    Json(report)
}

// This handler is registered alongside dozens of other, unrelated, fast endpoints
// on the same axum Router, all served by the same default Tokio runtime.
Root cause · Fix · Follow-up probes
Root cause
compute_expensive_aggregation(data) is a purely synchronous, CPU-bound function with no .await points inside it — while it runs, it monopolises the Tokio worker thread it happens to be scheduled on for its entire ~200ms duration, during which that worker thread cannot make progress on any other task — not just other calls to this same endpoint, but literally any other in-flight request being handled by that specific worker thread, including completely unrelated, normally-fast endpoints. Under low traffic, there's a good chance each request lands on an otherwise -idle worker, so the effect is invisible; under moderate concurrent load, with multiple requests to this endpoint (or just enough general traffic) landing on the same worker at overlapping times, other requests queued behind it on that worker stall for however long the aggregation takes, producing exactly the symptom described — unrelated endpoints suddenly showing p99 latency spikes correlated with load on this one endpoint. This is precisely the "blocking calls inside async fn" failure mode described in the async/Tokio topic, except the blocking operation here isn't I/O (an obvious blocking call like a synchronous file read) — it's plain CPU-bound computation, which is easy to overlook as a "blocking" concern since nothing about it looks like blocking I/O.
Fix — move CPU-bound work off the async worker thread
async fn generate_report(Query(params): Query<ReportParams>) -> Result<Json<Report>, StatusCode> {
    let data = fetch_raw_data(&params).await;

    // spawn_blocking moves the sync work to Tokio's dedicated blocking-thread pool,
    // freeing the async worker thread to keep serving other tasks in the meantime.
    let report = tokio::task::spawn_blocking(move || compute_expensive_aggregation(data))
        .await
        .map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)?;  // JoinError if the blocking task panicked

    Ok(Json(report))
}
// Alternative if this is called frequently and is truly parallelisable across rows:
// use rayon inside spawn_blocking for the CPU-bound aggregation itself, exactly as
// discussed in the thread-pool-sizing system design exercise in this packet.
Follow-up probes
  • P1"Why doesn't the Tokio scheduler just preempt this task once it's run too long on the worker thread?" — Tokio's scheduler is cooperative, not preemptive — a task only yields control back to the scheduler at its own .await points (or when it returns). Without any .await inside the CPU-bound function, there's no opportunity for the scheduler to intervene at all; it has no mechanism to forcibly interrupt a running task mid-computation the way an OS preemptively schedules threads.
  • P2"How would you have detected this before it caused a production incident?" — tokio-console specifically surfaces long-running, non-yielding tasks (it can show poll durations per task) — a task that takes 200ms inside a single poll() call without yielding is exactly what it's built to flag. Load testing with concurrent requests specifically to this endpoint alongside a baseline load of other endpoints, watching for cross-endpoint latency correlation, would also have caught it before production.
  • P3"Would rayon alone (without spawn_blocking) fix this?" — No — calling rayon's parallel iterators directly from inside the async fn still runs synchronously on the calling Tokio worker thread while it waits for rayon's parallel computation to finish (rayon threads do the parallel work, but the calling thread blocks waiting for the result) — you'd still be blocking that Tokio worker for the duration. You need spawn_blocking (or a channel-based bridge) specifically to get off the Tokio worker thread while the computation (rayon-parallelised or not) runs.
  • P4"Is there a threshold below which this DOESN'T matter?" — Yes — very short CPU-bound work (microseconds, or low-single-digit milliseconds) genuinely isn't worth the overhead of spawn_blocking (which itself has a real cost — moving to a different thread, synchronizing the result back). The rule of thumb many teams use: if a synchronous operation inside an async fn could plausibly take more than ~100 microseconds to a few milliseconds, it's worth moving off the worker thread; for anything shorter, the cure can be worse than the disease.
🎯 Senior angle
Recognizing that "blocking the runtime" isn't limited to obviously-blocking I/O calls — plain CPU-bound computation with no .await inside is just as much a blocking hazard, and is far easier to accidentally introduce since it doesn't look like a synchronous syscall the way a blocking file read does.

B7 · The Lazy Iterator That Never Ran
iterators laziness side effects Easy
This is supposed to log every failed validation and return the count of failures. It compiles cleanly with a warning — but the log lines never print. Why?
fn validate_all(records: &[Record]) -> usize {
    records.iter()
        .filter(|r| !r.is_valid())
        .map(|r| {
            eprintln!("validation failed for record {}", r.id);
            r
        });  // ← the whole chain is just constructed and dropped, never consumed

    records.iter().filter(|r| !r.is_valid()).count()
}
// Compiler warning: unused `Map` that must be used — easy to miss in noisy build output
Root cause · Fix · Follow-up probes
Root cause
As covered in the iterators topic, adapters like .filter() and .map() are lazy — they build a chain of wrapper structs, and none of the closures inside actually run until something consumes the iterator (a for loop, .collect(), .count(), .for_each(), etc.). The first statement constructs a Filter<Map<...>> value, immediately drops it (the expression's result is discarded, since it's a statement, not a let binding used afterward), and the closure inside .map() — including the eprintln! — never executes even once. The final line then does a completely separate, correct count via a fresh iterator chain. The compiler does flag this — #[must_use] on iterator adapter types produces an "unused ... that must be used" warning — but warnings are trivially easy to miss in a busy build log or CI output, especially if the project has other pre-existing warnings creating noise.
Fix — consume the iterator (and avoid duplicating the traversal)
fn validate_all(records: &[Record]) -> usize {
    records
        .iter()
        .filter(|r| !r.is_valid())
        .inspect(|r| eprintln!("validation failed for record {}", r.id))  // side effect, still lazy
        .count()  // ← THIS consumes the whole chain, running every closure exactly once per item
}
// .inspect() exists specifically for side effects mid-chain without altering the item —
// cleaner intent here than repurposing .map() to run a side effect and pass the value through.
Follow-up probes
  • P1"Why is .map() with a side effect and no real transformation a code smell, separate from this specific bug?" — .map() signals "I am transforming each item into something new" — using it purely for its side effect while passing the value through unchanged (as the original buggy code does) is misleading to a reader and hides the actual intent. .inspect() exists precisely to make "I'm just observing/logging, not transforming" explicit — using the right-named combinator communicates intent even before considering the laziness bug.
  • P2"How would clippy have caught this specific bug?" — clippy's `unused_must_use` lint (which backs the compiler's own warning) would flag it; more specifically, clippy has lints like `suspicious_map` that flag exactly the pattern of calling .map() purely for side effects with no subsequent consumption. Running `cargo clippy -- -D warnings` in CI (as discussed in the testing/tooling topic) turns this from an easily-missed warning into a hard build failure.
  • P3"The fixed version iterates the records twice in the buggy original (once in the dead chain, once in the count) — does the fix actually reduce that to one pass?" — Yes — the fix's single chain does the filtering, the logging side effect, and the counting all within one traversal via .count(), whereas the original buggy code's final working line was a completely separate second traversal (the dead first chain didn't count as a traversal at all since nothing ever polled it) — so the fix is both correct and marginally more efficient.
  • P4"Is there an analogous 'silently does nothing' bug pattern in async code?" — Yes, directly analogous — constructing an async fn's Future value and never .awaiting or spawning it means the function body never runs at all, for exactly the same underlying reason (both iterators and futures are lazy state machines that require an external driver to make progress). The compiler emits a similar unused-must-use-style warning for unawaited futures too.
🎯 Senior angle
This bug and its async-future analogue share the exact same root cause (laziness requiring an external consumer) — a candidate who spots that connection unprompted is demonstrating they understand the underlying "lazy value requiring a driver" pattern generally, not just memorizing "iterators are lazy" as an isolated fact.

B8 · Unsafe UB via Aliasing
unsafe aliasing undefined behaviour Hard
This "helper" function passes every test the author wrote. It is nonetheless unsound. Find the missing invariant check.
/// Swaps the elements at indices `a` and `b` in-place. Caller must ensure a and b are in bounds.
fn swap_unchecked<T>(slice: &mut [T], a: usize, b: usize) {
    unsafe {
        let ptr = slice.as_mut_ptr();
        let ra: &mut T = &mut *ptr.add(a);
        let rb: &mut T = &mut *ptr.add(b);  // ← what if a == b?
        std::mem::swap(ra, rb);
    }
}

fn main() {
    let mut v = vec![1, 2, 3, 4, 5];
    swap_unchecked(&mut v, 1, 3);  // passes — [1, 4, 3, 2, 5]
    println!("{:?}", v);

    swap_unchecked(&mut v, 2, 2);  // ← same index twice — UB, even though nothing crashes
    println!("{:?}", v);  // may print a plausible-looking result anyway — UB doesn't require a visible symptom
}
Root cause · Fix · Follow-up probes
Root cause
When a == b, ra and rb are two simultaneously live &mut T references pointing at the exact same memory location — a direct violation of Rust's fundamental aliasing guarantee (at most one mutable reference to any given memory location may exist at a time), smuggled past the borrow checker entirely via the unsafe block's raw pointer arithmetic. This is undefined behaviour regardless of whether it happens to "work" on any given run — std::mem::swap internally may assume its two reference arguments never alias (this is a real, documented safety assumption many standard library functions taking multiple references rely on for correctness and for enabling certain compiler optimisations), and even if this particular swap implementation happens to produce a plausible-looking result today on a given compiler version, a future compiler version, a different optimisation level, or a tool like Miri would be entitled to detect or exploit this violation in ways that produce genuinely wrong or crashing behaviour. This is exactly the unsound-but-passes-every-test scenario discussed at length in the unsafe/macros topic — the bug is invisible until precisely the input (here, a == b) that the author's own test suite happened not to cover.
Fix — check the invariant explicitly, or use a safe abstraction that already enforces it
// Fix 1: explicit early-return guard for the aliasing case
fn swap_unchecked<T>(slice: &mut [T], a: usize, b: usize) {
    if a == b { return; }  // swapping an element with itself is a correct no-op — handle it before aliasing occurs
    unsafe {
        let ptr = slice.as_mut_ptr();
        let ra: &mut T = &mut *ptr.add(a);
        let rb: &mut T = &mut *ptr.add(b);
        std::mem::swap(ra, rb);
    }
}

// Fix 2: just use the standard library's own, already-audited swap — don't hand-roll this at all
fn swap_safe<T>(slice: &mut [T], a: usize, b: usize) {
    slice.swap(a, b);  // [T]::swap — handles a == b correctly, no unsafe needed at the call site
}
Follow-up probes
  • P1"Would this bug be caught by cargo test passing every existing test?" — No — that's precisely the point of this exercise. A test suite that never happens to call swap_unchecked(v, i, i) would pass every time, forever, while the unsoundness sits latent. This is exactly why "all tests pass" and "is sound" are different claims, as discussed in the unsafe topic.
  • P2"How would Miri (cargo miri test) behave differently here than a normal test run?" — Miri specifically instruments and checks Rust's aliasing rules at runtime, even inside unsafe blocks — it would very likely flag this as an aliasing violation (two live &mut references to the same location) the moment a test actually exercises the a == b case, turning "silent unsoundness" into an explicit, actionable error during CI, well before it ever reaches production.
  • P3"Why does the standard library's own [T]::swap not have this bug?" — The standard library's implementation is written and reviewed with exactly this edge case in mind (and internally uses techniques like `ptr::swap` designed to be correct even when the two pointers are equal, since a swap-with-self at the raw pointer level, done correctly, is a well-defined no-op operation). This is a good illustration of why "just use the audited standard library function" is almost always better advice than hand-rolling unsafe code for a problem the standard library already solves.
  • P4"If you inherited this function in a codebase and needed to write a doc comment justifying its safety, what would you write?" — Something like: "Safety: caller must ensure a < slice.len() and b < slice.len(). Additionally, this implementation requires a != b to avoid constructing two aliasing &mut references — see the early-return guard." Writing this explicit safety contract, and recognizing the a != b clause specifically needs stating, is exactly the kind of rigor the unsafe topic's PR-review discussion calls for.
🎯 Senior angle
This is one of the highest-value bugs in the whole packet for separating theoretical unsafe knowledge from practiced unsafe discipline — candidates who've actually reviewed or written unsafe code in anger tend to immediately ask "what if a == b?" the moment they see two raw-pointer-derived &mut references being created from the same base pointer, without needing to be prompted.
// Bug Exercise 09 · 18 min
B9 · Send/Sync Misuse
Send Sync FFI Hard
A teammate "fixed" a compile error by adding the two lines below. It compiles now — and immediately causes intermittent data corruption in production. What's wrong?
struct LegacyParserHandle {
    raw: *mut c_void,  // opaque handle into a third-party C parsing library
}

// The C library's documentation says nothing about thread-safety.
// It uses internal static/global lookup tables shared across all handles.

unsafe impl Send for LegacyParserHandle {}
unsafe impl Sync for LegacyParserHandle {}  // "fix" for: `*mut c_void` cannot be shared between threads safely

struct ParserPool {
    handles: Vec<Arc<LegacyParserHandle>>,
}
// ParserPool is now used from many Tokio tasks across many worker threads simultaneously,
// each calling parse() on its checked-out handle concurrently.
Root cause · Fix · Follow-up probes
Root cause
The compiler correctly refused to let LegacyParserHandle (containing a raw pointer, which is neither Send nor Sync by default) cross thread boundaries or be shared via Arc across threads — that default is a conservative "the compiler cannot verify this is safe," not an obstacle to be silenced. The teammate's fix manually asserts, via unsafe impl, a safety property the compiler has zero ability to check: that the underlying C library is safe to use concurrently from multiple threads. But the comment right above the fix says the opposite — the library's documentation is silent on thread-safety, and worse, it explicitly uses internal global/static lookup tables shared across all handles. This is exactly the scenario flagged in the FFI topic's discussion of thread-safety: even if each individual LegacyParserHandle looks independent from Rust's point of view, the C library's shared global state means two threads calling parse() on two different handles concurrently can still race on that shared internal state — unsafe impl Sync makes a claim about this type's safety that is almost certainly false, and the compiler has no way to catch it because unsafe impl is explicitly the escape hatch where the programmer overrides the compiler's own safety analysis. The "intermittent data corruption" symptom is the classic signature of a data race in the C library's internal tables — not something Rust's usual guarantees have any visibility into, precisely because this code told the compiler to stop checking.
Fix — serialise access to the actually-unsafe-to-share resource
// Fix: don't lie to the compiler about Sync. Instead, force serialised access
// with a single mutex around ALL handles, since the C library's global state
// means "one handle per thread" isn't even sufficient — the whole library isn't reentrant.

struct LegacyParserHandle {
    raw: *mut c_void,
}
#[allow(unsafe_code)]
unsafe impl Send for LegacyParserHandle {}  // Send alone (move to one thread at a time) may be justifiable —
// verify the specific C library actually permits ownership transfer between threads before even this.
// Sync is NOT added — this type is not claimed safe to access concurrently from multiple threads.

struct ParserPool {
    // A single mutex around the single shared handle — all parse() calls serialise through it,
    // which correctly reflects "this C library is not safe for concurrent use at all."
    handle: Mutex<LegacyParserHandle>,
}

impl ParserPool {
    fn parse(&self, input: &[u8]) -> ParseResult {
        let handle = self.handle.lock().unwrap();
        // call into the C library here — only one thread can be inside at a time
    }
}
Follow-up probes
  • P1"Why does the compiler accept `unsafe impl Sync` without any error, given it's wrong here?" — Because unsafe impl is, by design, the mechanism for asserting properties the compiler fundamentally cannot verify — a raw pointer's pointee could be anything, backed by any external system, and Rust's type system has no visibility into a foreign C library's internal implementation. The compiler trusts the programmer completely at this boundary; that trust is exactly what was misplaced here.
  • P2"How would you have caught this before it reached production?" — Code review specifically scrutinising any unsafe impl Send/Sync as a special, high-risk category (as discussed in the unsafe topic's PR-review framework) — demanding a written justification referencing the actual C library's documented thread-safety guarantees, not just 'it made the compile error go away.' A stress test running many concurrent parse() calls under ThreadSanitizer-equivalent tooling (or simply high concurrency + assertions on output correctness) would likely have surfaced the corruption pre-production too.
  • P3"Is 'one handle per thread, no Arc, no sharing' a safe fix instead of a mutex?" — Only if the C library's global state issue doesn't apply across separate handles used from separate threads simultaneously — but the scenario explicitly states shared global lookup tables across all handles, meaning even fully separate handles on separate threads still race on that shared internal state. A mutex serialising ALL access to the library (not just per-handle) is the fix that actually matches the stated constraint.
  • P4"What would you want documented directly next to any unsafe impl Send/Sync in this codebase going forward?" — A comment citing the specific evidence for the safety claim — a link to the C library's documentation explicitly stating thread-safety guarantees, or a description of testing/auditing performed, plus which specific operations were verified. 'Compiles now' or 'seems to work' should never be treated as sufficient justification for a claim the compiler is otherwise unable to check at all.
🎯 Senior angle
"I added unsafe impl Send/Sync to fix a compile error" should be treated by any reviewer as an immediate stop -and-justify moment, not a routine fix. A candidate who reacts to this scenario with instant suspicion — rather than accepting "it compiles now" as evidence of correctness — is showing exactly the calibrated skepticism this entire packet has been building toward.
