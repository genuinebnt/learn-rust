// Common Code Patterns · Primitives
Primitives & Conversions
Interview problems live and die on getting primitives right under pressure — an i32 vs usize mismatch or a silent overflow will eat five minutes you don't have. These are the reflexes to build so type juggling never slows you down mid-interview.
Integer types & indexing
let x: i32 = -5;              // i32 is the default integer type Rust infers
let v = vec![10, 20, 30];
let n: usize = v.len();     // .len() ALWAYS returns usize — a size can't be negative
for i in 0..n {              // range bound must match — this is why loop indices are usize
    let _ = v[i];
}
Why usize: array indices and lengths are architecture-width unsigned integers by design — you cannot have a negative-length collection. This is the single most common source of "expected usize, found i32" compiler errors for interview candidates.
Overflow-safe arithmetic
200u8.checked_add(100);      // None — overflow detected, no panic, no wraparound
10i32.checked_sub(20);      // Some(-10) — fits fine, so Some(result)
250u8.wrapping_add(10);     // 4 — silently wraps around modulo 2^8
250u8.saturating_add(10);   // 255 — clamps to the type's MAX instead of wrapping
let (res, overflowed) = 250u8.overflowing_add(10);
// res == 4, overflowed == true — wraps AND tells you it happened

i32::MAX;  // 2147483647      u8::MAX;  // 255
i32::MIN;  // -2147483648     u8::MIN;  // 0
Debug vs release: a plain + that overflows panics in debug builds but silently wraps in release builds (with optimizations). Never rely on either behavior — pick the explicit checked_/wrapping_/saturating_ variant that matches your intent.
Floating point
let f: f64 = -4.0;         // f64 is the default float type Rust infers
f.abs();                 // 4.0
16.0f64.sqrt();          // 4.0
2.0f64.powi(3);         // 8.0 — integer exponent, faster
2.0f64.powf(0.5);       // 1.414... — float exponent (nth roots, etc.)
3.7f64.floor();         // 3.0
3.2f64.ceil();          // 4.0
3.5f64.round();         // 4.0

let a = 0.1 + 0.2;
let b = 0.3;
let epsilon = 1e-9;
assert!((a - b).abs() < epsilon);  // never use `a == b` on floats
Gotcha: f64 doesn't implement Eq/Ord (because of NaN), so you can't put floats directly in a HashSet/BTreeMap key or use .sort() without .sort_by(|a,b| a.partial_cmp(b).unwrap()). Always compare via epsilon, never ==.
Boolean
let a = true;
let b = false;
a && b;   // logical AND, short-circuits
a || b;   // logical OR, short-circuits
!a;       // NOT

let visited = vec![false; n];  // classic DP / graph-traversal visited array
Use when: vec![false; n] is the idiomatic go-to for visited flags in BFS/DFS and boolean DP tables — far cleaner than a manual initialization loop.
Char
c.is_alphabetic();     c.is_numeric();      c.is_whitespace();
c.is_uppercase();      c.is_ascii_digit();

// mapping a lowercase letter to a 0-25 index — the classic 26-letter alphabet problem pattern
let idx = (c as u8 - b'a') as usize;
// 'a' -> 0, 'z' -> 25 — pairs perfectly with a `[i32; 26]` frequency array
Use when: anagram/frequency-count problems ("group anagrams", "valid anagram") almost always use this cast to index into a fixed 26-slot array instead of a HashMap<char, i32> — faster and simpler when the alphabet is known and small.
The Copy trait
fn takes_by_value(n: i32) -> i32 {
    n + 1
}

let original = 41;
let result = takes_by_value(original);
// `original` is still usable here — i32 is Copy, so passing it by value
// duplicates the bits instead of moving/invalidating the original
Why it matters: all the primitives (integers, floats, bool, char) implement Copy, so passing them by value into functions never triggers a move — no borrow-checker fights, no .clone() needed. This is exactly why primitives feel "normal" while String/Vec require more ownership discipline.
Useful numeric methods
(-5i32).abs();       // 5
(-5i32).signum();    // -1  (0 -> 0, positive -> 1)
2i32.pow(10);       // 1024 — integer exponentiation
0b1011u32.count_ones();  // 3 — Hamming weight, see Bit Manipulation section
1u32.leading_zeros();  // 31
42.to_string();       // "42" — any Display type -> String
"123".parse::<i32>(); // Ok(123) — Result, always handle the Err case
Fixing type mismatches fast
let i: i32 = 5;
let u: usize = i as usize;   // `as` is infallible-looking but SILENTLY truncates/wraps on bad input

let big: i64 = 300;
let checked: Result<u8, _> = u8::try_from(big); // Err(...) — 300 doesn't fit in a u8
When NOT to use as: `as` between integer types never panics — it just truncates bits, which silently produces wrong-but-valid-looking numbers (a negative i32 as usize becomes a huge positive number). Prefer TryFrom/TryInto whenever the input range isn't guaranteed safe; reserve `as` for indices/lengths you've already bounds-checked.
min / max between values
std::cmp::min(3, 7);   // 3 — free function, works on any Ord type
std::cmp::max(3, 7);   // 7

// chaining .max() for 3+ values — reads left to right
let biggest = a.max(b).max(c);

let arr = [5, 1, 9, 3];
arr.iter().max();   // Option<&i32> — Some(&9), None only if the iterator is empty
arr.iter().min();   // Option<&i32> — Some(&1)
Gotcha: the inherent .max()/.min() methods on primitives take self by value (no reference needed since they're Copy), but the iterator adapters .max()/.min() return Option<&T> — you'll often need a .copied() or a dereference to get an owned value back out.
✓ Reach for this when
  • Indexing into a collection — always use usize, never fight the compiler with casts everywhere
  • Arithmetic could plausibly overflow (large sums, products) — use checked_*/saturating_*
  • Comparing floating-point results — always via an epsilon, never ==
⚠ Watch out for
  • Debug-mode overflow panics that vanish in release mode — don't let passing tests hide a real bug
  • as casts between signed/unsigned or narrowing types truncate silently, no error
  • Iterator .max()/.min() return Option<&T>, not T — remember to dereference
✗ Common mistakes
  • Mixing i32 loop counters with usize lengths and fighting the type checker instead of just using usize from the start
  • Comparing floats with == and getting flaky results from rounding error
  • Using as for a fallible conversion instead of TryFrom, masking a real out-of-range bug
// Common Code Patterns · Strings
String & &str
String problems (anagrams, palindromes, parsing) are LeetCode's bread and butter, and Rust's split between owned String and borrowed &str — plus UTF-8 correctness — trips up more candidates than almost anything else in this packet. Get the mental model straight once and every string problem gets dramatically easier.
String vs &str
let owned: String = String::from("hello");  // heap-allocated, growable, you own it
let borrowed: &str = &owned;             // a borrowed VIEW into a String (or a literal)
let literal: &str = "hello";             // literals are &'static str — baked into the binary
When to use each: take &str in function parameters whenever you only need to read (it accepts both &String and literals via deref coercion); return/store String when you need ownership — e.g. building a new string or returning something that must outlive the function call.
Converting between them
let s = String::from("hi");
let view: &str = &s;              // zero-cost borrow, no allocation

let a = "hi".to_string();          // &str -> String, allocates
let b = String::from("hi");        // equivalent to .to_string(), allocates
let c = "hi".to_owned();          // also equivalent — generic version of to_string()
Splitting
"a,b,,c".split(',');              // ["a", "b", "", "c"] — keeps empty fields
"  hello   world  ".split_whitespace();  // ["hello", "world"] — collapses runs, trims ends
"a:b:c".splitn(2, ':');        // ["a", "b:c"] — at most 2 pieces, rest kept intact
"a:b:c".rsplit(':');           // ["c", "b", "a"] — splits from the right
Gotcha: .split() on "," keeps empty strings between consecutive delimiters ("a,,b" → ["a","","b"]) — use .split_whitespace() or .filter(|s| !s.is_empty()) if you need those collapsed away.
Reversing
let reversed: String = s.chars().rev().collect();  // correct for ANY UTF-8 string

// byte-indexing reversal is UNSAFE for non-ASCII — multi-byte chars would get shredded.
// only reverse raw bytes when you've confirmed the input is ASCII-only:
let mut bytes: Vec<u8> = s.as_bytes().to_vec();
bytes.reverse();
let ascii_reversed = String::from_utf8(bytes).unwrap();
Gotcha: you cannot reverse by naively swapping byte indices on a general Rust string — a multi-byte UTF-8 character (e.g. "é" = 2 bytes) would be split apart into invalid byte sequences and panic. The byte-array trick is only a valid perf shortcut when the input is guaranteed ASCII.
Bytes
let bytes: &[u8] = s.as_bytes();   // zero-cost view as raw UTF-8 bytes
for b in s.bytes() {              // iterator yielding u8, one per BYTE not per char
    // b: u8
}
Gotcha: for ASCII text, bytes and chars line up 1:1 — but any multi-byte UTF-8 character means .bytes().count() > .chars().count(). Use .bytes() only when you know the input is ASCII or you specifically want byte-level access.
Searching
"hello world".find("world");   // Some(6) — Option, a BYTE offset, not char offset
"hello world".contains("lo wo"); // true — bool
"hello world hello".rfind("hello"); // Some(12) — last occurrence, searching from the right
Concatenation
let mut buf = String::new();
buf.push('h');         // append a single char
buf.push_str("ello");  // append a &str

let left = String::from("foo");
let combined = left + "bar";  // `+` MOVES `left` — it's unusable afterward

// format! never takes ownership of its inputs — usually the safer, more readable choice
let safer = format!("{a}{b}");
Gotcha: String + &str compiles because + is sugar for Add::add(self, &str), which consumes the left-hand String by value — reuse it afterward and the compiler will flag a use-after-move. Chain more than two pieces with + and it gets unreadable fast; reach for format!() instead.
Prefix / suffix
"hello.rs".starts_with("hello");       // true
"hello.rs".ends_with(".rs");          // true
"hello.rs".strip_prefix("hello");   // Some(".rs") — None if it doesn't actually start with it
"hello.rs".strip_suffix(".rs");      // Some("hello")
Parsing to numbers
let n = "42".parse::<i32>().unwrap();  // turbofish tells parse() what type to target

// bulk-parsing a whitespace-separated line of numbers — extremely common warm-up pattern
let nums: Vec<i32> = "1 2 3 4"
    .split_whitespace()
    .map(|s| s.parse().unwrap())
    .collect();
Formatting
format!("{} and {:?}", "raw", "debug");
// "raw and \"debug\"" — {} uses Display, {:?} uses Debug (adds quotes for strings)

format!("{:5.2}", 3.14159);  // " 3.14" — width 5, precision 2 decimal places
Use when: {:?} is your fastest debugging tool — it works on almost everything via #[derive(Debug)], unlike {} which requires manually implementing Display.
from_utf8
let bytes = vec![104, 101, 108, 108, 111];
let s = String::from_utf8(bytes);  // Result — FALLIBLE
// bytes might not form valid UTF-8, so this can't just be an infallible conversion
Use when: reconstructing a String after byte-level manipulation (e.g. the ASCII-reversal trick above) or reading raw bytes from I/O — always handle the Err case rather than blindly .unwrap()-ing on untrusted input.
Trimming
"  padded  ".trim();         // "padded" — both ends
"  padded  ".trim_start();   // "padded  " — left only
"  padded  ".trim_end();     // "  padded" — right only
Case conversion
"HeLLo".to_lowercase();       // "hello" — allocates a new String, Unicode-correct
"HeLLo".to_uppercase();       // "HELLO"
"HeLLo".to_ascii_lowercase(); // "hello" — cheaper, correct ONLY for ASCII input
Use when: if you know the input is ASCII (most LeetCode string problems), prefer to_ascii_lowercase/to_ascii_uppercase — they skip full Unicode case-folding rules and are noticeably cheaper.
Iterating chars vs. bytes
let word = "héy";
word.chars().count();     // 3 — one Unicode scalar value per char ('h', 'é', 'y')
word.bytes().count();     // 4 — 'é' takes 2 bytes in UTF-8, others take 1

for (byte_offset, ch) in word.char_indices() {
    // pairs each char with its BYTE offset — needed to slice the original string correctly
}
Use when: .char_indices() is essential whenever you need both the character and a byte offset you can safely slice the original string with — plain .enumerate() on .chars() gives you a char-count index, which is WRONG for slicing non-ASCII strings.
Arbitrary character access (no s[i]!)
// Rust forbids `s[i]` entirely — a byte index into multi-byte UTF-8 could land mid-character.
// three alternatives, in order of how often you need repeated access:

s.chars().nth(i);              // Option — O(n) EVERY call, fine for a single one-off lookup

let as_vec: Vec<char> = s.chars().collect();
as_vec[i];                       // O(n) once to build, then O(1) per access — best for repeated indexing

s.as_bytes()[i] as char;         // O(1), but ONLY correct if the string is guaranteed ASCII
Use when: if a problem statement guarantees lowercase-English-letters-only input (extremely common on LeetCode), .as_bytes()[i] is the fastest option; otherwise collect to Vec<char> once up front if you'll index more than a couple times.
✓ Reach for this when
  • Reading string problem input character-by-character or comparing substrings
  • Building a new string incrementally — String + .push_str() or format!()
  • Repeatedly indexing by position — collect to Vec<char> once, up front
⚠ Watch out for
  • Byte offsets from .find()/.char_indices() are not char counts on non-ASCII text
  • + concatenation moves the left String — it's gone afterward
  • .to_lowercase()/.to_uppercase() allocate every call — cache the result if reused in a loop
✗ Common mistakes
  • Trying to write s[i] directly — Rust strings don't support integer indexing, full stop
  • Byte-reversing a string that might contain multi-byte UTF-8 characters, corrupting them
  • Calling .chars().nth(i) in a hot loop instead of collecting to Vec<char> once

Arrays & Slices
Most LeetCode problems that "take an array" actually take a &[T] slice under the hood — understanding the array/slice split, and how freely one converts to the other, means you stop worrying about it and focus on the actual algorithm.
Fixed arrays [T; N] vs. slices &[T]
let arr: [i32; 3] = [1, 2, 3];  // size is part of the TYPE, stack-allocated, fixed forever
let sl: &[i32] = &arr;         // a borrowed VIEW — any length, works over arrays, Vecs, or sub-ranges
Use when: function parameters should almost always take &[T], not &[T; N] or &Vec<T> — a slice accepts anything contiguous, giving you maximum flexibility for zero cost.
Initialization
let lit = [1, 2, 3];      // literal form, type + size both inferred
let repeat = [0; 5];      // [0, 0, 0, 0, 0] — repeat form, requires T: Copy
Access + slicing
let big = [10, 20, 30, 40, 50];
big[0];             // 10 — PANICS on out-of-bounds, runtime bounds-checked
&big[1..4];         // &[20, 30, 40] — range slicing, end-exclusive
Gotcha: indexing out of bounds panics immediately with no compile-time warning — if the bound isn't obviously safe, use .get(i) instead, which returns Option<&T>.
Iterating
for &item in &big {              // destructure the &i32 into an owned i32 directly in the pattern
    // item: i32
}
for (i, &v) in big.iter().enumerate() {  // index + value together
    // i: usize, v: i32
}
contains() / position()
big.contains(&30);                     // true — O(n) linear scan
big.iter().position(|&x| x == 30); // Some(2) — Option, first matching index
Sorting / reversing arrays
let mut a = [5, 3, 1, 4, 2];
a.sort();                       // [1, 2, 3, 4, 5] — same method as Vec, arrays deref to slices
a.sort_by(|x, y| y.cmp(x));  // [5, 4, 3, 2, 1] — descending via custom comparator
a.reverse();                    // in-place O(n) reversal
Why this works: arrays are just fixed-size contiguous memory, so they deref-coerce to &[T]/&mut [T] automatically — every slice method (sort, sort_by, sort_by_key, reverse, windows, chunks...) works on arrays for free, no separate API to learn.
Splitting
let data = [1, 2, 0, 3, 4, 0, 5];
let groups: Vec<&[i32]> = data.split(|&x| x == 0).collect();
// [[1, 2], [3, 4], [5]] — an iterator of subslices, delimiter itself dropped
Conversions
let arr = [1, 2, 3];
let as_slice: &[i32] = &arr;      // array -> slice, zero cost (deref coercion)
let as_vec: Vec<i32> = arr[..2].to_vec();  // slice -> Vec, ALLOCATES a new owned buffer
let v = vec![7, 8, 9];
let vec_as_slice: &[i32] = &v;    // Vec -> slice, zero cost
.len() usage patterns
if arr.len() < 2 { return; }   // early-return guard — extremely common at the top of two-pointer/DP solutions

for i in 0..arr.len() {          // bounds-checked looping by index when you need i for math (i+1, i-1, etc.)
    // ...
}
Mutability + split_at_mut
let mut a = [1, 2, 3, 4, 5, 6];
a[0] = 99;  // direct index assignment requires `mut`

let (left, right) = a.split_at_mut(3);  // (&mut [T], &mut [T]) — two DISJOINT mutable halves
// safe because the borrow checker can prove left/right never overlap
Why: the borrow checker won't let you hold two &mut slices into the same array normally — split_at_mut is the sanctioned escape hatch (covered in depth elsewhere in this packet).
✓ Reach for this when
  • Size is known at compile time and small/stack-friendly — use a fixed array
  • Writing a function that should accept arrays, Vecs, or sub-ranges alike — take &[T]
  • You need two independent mutable views into one buffer at once — split_at_mut
⚠ Watch out for
  • Indexing panics on out-of-bounds with no compile-time protection — guard with .len() checks or use .get()
  • .to_vec() allocates — don't call it in a hot loop when a borrowed slice would do
  • Arrays require T: Copy for the [v; n] repeat form — won't compile for non-Copy types
✗ Common mistakes
  • Forgetting mut on an array binding you intend to sort/reverse/mutate in place
  • Trying to take two separate &mut slices manually instead of using split_at_mut
  • Confusing &[T; N] (reference to array) with &[T] (slice) in function signatures — usually you want the latter
// Common Code Patterns · Bit Manipulation
Bit Manipulation
A small, fixed set of bit tricks covers the overwhelming majority of "bit manipulation" interview questions — power-of-two checks, popcount, subset enumeration, and the XOR-cancellation trick. Memorize these patterns rather than re-deriving them under pressure.
Basic bitwise operators
OpNameExampleResult
&AND0b1010 & 0b11000b1000
|OR0b1010 | 0b11000b1110
^XOR0b1010 ^ 0b11000b0110
!NOT!0u8255 (all bits flipped)
<<Left shift1u32 << 416
>>Right shift16u32 >> 24
Use when: << k is "multiply by 2^k" and >> k is "integer-divide by 2^k" — both far cheaper than the arithmetic ops, and the idiomatic way to build/test masks.
Checking power of two
fn is_power_of_two(n: i32) -> bool {
    n > 0 && (n & (n - 1)) == 0
}
Why it works: a power of two has exactly one set bit (e.g. 0b1000). Subtracting 1 flips that bit off and every bit below it on (0b0111) — ANDing the two clears the lowest set bit entirely, leaving zero only if there was exactly one set bit to begin with. The n > 0 guard rules out 0 (which would otherwise pass) and negatives.
Counting set bits (Hamming weight)
fn count_bits_manual(mut n: u32) -> u32 {
    let mut count = 0;
    while n > 0 {
        count += n & 1;   // check the lowest bit
        n >>= 1;         // shift everything right by one
    }
    count
}

// the built-in is faster (often a single CPU instruction) — prefer it whenever available:
0b1011u32.count_ones();  // 3
Use when: know the manual loop for whiteboard/explanation purposes, but always reach for .count_ones() in real code — it compiles to a hardware POPCNT instruction on most targets.
Other built-in bit methods
0b1011u8.count_zeros();     // 5 — u8 has 8 bits total, 3 are set, so 5 are zero
1u32.leading_zeros();     // 31 — zeros before the first set bit (from the MSB side)
8u32.trailing_zeros();    // 3  — zeros after the last set bit (from the LSB side)
0b0001u8.rotate_left(1);   // 0b0010 — bits that fall off the top wrap to the bottom
0b0001u8.rotate_right(1);  // 0b1000_0000 — wraps the other way
Use when: trailing_zeros() doubles as "index of the lowest set bit" — useful in bitmask DP when you want to peel off one element from a set at a time.
Isolating the lowest set bit
let x: i32 = 0b0110_1000;
let lowest = x & (-x);              // 0b0000_1000 — two's-complement negation trick
let lowest_alt = x & x.wrapping_neg(); // identical result, avoids overflow panic on i32::MIN in debug builds
Use when: this exact expression is the core primitive behind Fenwick trees / Binary Indexed Trees (BIT) for prefix-sum updates, and shows up in "sum of two integers without +" style bit-arithmetic problems.
Bitmask subset enumeration
let n = elements.len();
for mask in 0..(1 << n) {          // 2^n total masks, one per possible subset
    for i in 0..n {
        if (mask >> i) & 1 == 1 {   // bit i set -> element i is IN this subset
            // include elements[i]
        }
    }
}
Use when: the standard brute-force pattern for "enumerate all subsets" problems (subset sum, partition problems) when n is small enough (typically n ≤ ~20) that 2ⁿ is tractable.
Toggling a bit
let mut flags: u8 = 0b0000_0000;
flags ^= 1 << 2;   // 0b0000_0100 — XOR-ing with a set bit flips it: off->on
flags ^= 1 << 2;   // 0b0000_0000 — XOR again flips it back: on->off
XOR trick for "single number" problems
fn single_number(nums: &[i32]) -> i32 {
    nums.iter().fold(0, |acc, &x| acc ^ x)
}
// [4, 1, 2, 1, 2] -> 4 — every paired value XORs to 0, leaving only the unpaired one
Why it works: XOR is commutative, associative, and x ^ x == 0 — so XOR-ing every element together cancels every value that appears an even number of times, leaving exactly the value(s) that appear an odd number of times. Classic O(n) time, O(1) space alternative to a HashSet.
✓ Reach for this when
  • The problem explicitly mentions bits, powers of two, or XOR/AND/OR properties
  • You need O(1) extra space and the input size is bounded by an integer's bit width
  • Enumerating all subsets of a small set (n ≤ ~20) — bitmask loop over 0..(1<<n)
⚠ Watch out for
  • Negating i32::MIN with unary - panics in debug builds (no positive counterpart) — use wrapping_neg()
  • Shifting by an amount ≥ the type's bit width is undefined-behavior-adjacent and panics in debug mode
  • 1 << n overflows if n is large relative to the integer type — size it (e.g. u64, u128) to fit
✗ Common mistakes
  • Forgetting the n > 0 guard in the power-of-two check, letting 0 slip through as "true"
  • Reaching for a HashSet to find a lone unpaired element when XOR solves it in O(1) space
  • Off-by-one errors in (mask >> i) & 1 bit-position indexing when enumerating subsets
// Common Code Patterns · Core Collections
Vec<T> — The Workhorse
Vec<T> is the growable, heap-allocated array at the center of almost every non-trivial Rust program and interview problem — Python's list, Java's ArrayList, but with ownership and no hidden boxing. Master these methods cold; you'll reach for them constantly.
Creating
let empty: Vec<i32> = Vec::new();          // explicit type needed — empty vec can't infer T
let filled = vec![1, 2, 3];               // macro form — almost always preferred
let zeros = vec![0; 5];                   // [0, 0, 0, 0, 0] — repeat form, great for DP tables
let from_iter: Vec<i32> = (1..=5).collect();  // build from a Range or any Iterator
Use vec![v; n] for: visited arrays, zero-initialized DP tables, fixed-size buffers — it's the idiomatic replacement for a manual initialization loop.
Accessing elements
let v = vec![10, 20, 30];
let first = v[0];         // panics on out-of-bounds — only use when bounds are guaranteed
let maybe = v.get(5);      // Option<&T> — the safe choice in edge-case-prone code
let last = v.last();       // Option<&T>, None if empty
v[0] = 99;               // direct mutable index write (requires `mut v`)
Modifying
let mut m = vec![1, 2, 3];
m.push(4);              // append, O(1) amortized
let popped = m.pop();      // remove + return last as Option, O(1)
m.insert(1, 99);        // insert at index, O(n) — shifts everything after it
let removed = m.remove(0);  // remove + return at index, O(n) — shifts left
m.swap_remove(0);       // remove + swap-in last element, O(1) — use when order doesn't matter
m.clear();              // drop every element, keeps allocated capacity
Gotcha: insert/remove in the middle are O(n) — prefer swap_remove or push/pop (both ends of a Vec aren't equally cheap; only the back is O(1), use VecDeque if you need cheap front operations too.)
Iterating & enumerating
for val in &v { /* val: &T, immutable borrow */ }
for val in &mut v { *val += 1; }        // val: &mut T, mutate in place
for val in v { /* val: T, consumes v — v unusable after */ }
for (i, val) in v.iter().enumerate() { // (usize, &T) — index-aware loops
    println!("{i}: {val}");
}
Transforming & collecting
let squares: Vec<i32> = v.iter().map(|&x| x * x).collect();
// `|&x| ...` destructures the &i32 the iterator hands you into an owned i32
Searching & filtering
v.contains(&3);                          // bool, O(n) linear scan
v.iter().position(|&x| x == target);  // Option — first matching index
v.iter().any(|&x| x % 2 == 0);       // true if ANY element matches
v.iter().all(|&x| x > 0);           // true if EVERY element matches
v.iter().find(|&&x| x > 5);         // Option<&T> — first matching element itself
Sorting & reversing
v.sort();                          // ascending, stable, requires T: Ord
v.sort_unstable();                // faster, no stability guarantee — use when items compare unique or order-of-ties doesn't matter
v.sort_by(|a, b| b.cmp(a));    // descending, full comparator control
v.sort_by_key(|x| x.len());     // sort by a derived key — cleanest for single-field sorts
v.reverse();                       // in-place O(n) reversal
Deduplication & retention
v.dedup();                    // removes only ADJACENT duplicates — sort first if you want a fully global dedup
v.retain(|&x| x % 2 == 0); // keep only elements matching predicate, in place
Gotcha: dedup() only merges neighbors — [1,2,1] stays [1,2,1]. For true set-style dedup, sort first or collect into a HashSet.
Capacity & allocation
v.reserve(100);          // pre-allocate room for 100 more elements — avoids repeated reallocation
v.capacity();           // current allocated capacity (>= len)
v.shrink_to_fit();     // release unused capacity back — rarely needed, but useful post-bulk-removal
Binary search (sorted vectors only)
let sorted = vec![1, 3, 5, 7, 9];
sorted.binary_search(&5);   // Ok(2) — found at index 2
sorted.binary_search(&4);   // Err(2) — not found, but this is where it WOULD be inserted to stay sorted
The Err(insert_pos) branch is the whole reason to prefer this over a hand-rolled binary search — it gives you the sorted insertion point for free.
Cloning & slice-to-vec
let cloned = v.clone();          // deep clone — new allocation, new ownership
let slice_copy = v[..2].to_vec();  // clone a slice into an owned Vec
2D grids (Vec<Vec<T>>)
let mut grid: Vec<Vec<i32>> = vec![vec![0; cols]; rows]; // rows × cols, all zero
grid[i][j] = 1;  // mutate a cell — standard pattern for "Number of Islands", "Unique Paths", etc.
Gotcha: vec![vec![0; cols]; rows] works because i32 is Copy — never do this pattern with non-Copy inner types expecting independent allocations without checking; here each row IS an independently-allocated Vec, so this is actually safe (unlike the classic JS "array of same reference" trap).
Windows, chunks & split
v.windows(3);   // overlapping &[T] views of length 3 — [1,2,3],[2,3,4],[3,4,5]... — sliding window problems
v.chunks(2);    // non-overlapping &[T] groups of 2 — [1,2],[3,4],[5] (last chunk may be shorter)
v.split(|&x| x == 0); // split into slices wherever predicate is true, delimiter dropped
windows vs. chunks: windows overlap (size-k subarray problems), chunks partition (grouping/batching problems) — mixing these up is one of the most common Vec-related mistakes under time pressure.
✓ Reach for Vec when
  • You need a growable, owned, contiguous sequence
  • Random-access indexing matters and elements are mostly appended at the back
  • You're building a result to return from a function
⚠ Watch out for
  • insert(0, x) / remove(0) in a loop — silently O(n²), use VecDeque instead
  • Forgetting `mut` on the binding — every mutating method needs it
  • windows(n) on a vec shorter than n silently yields zero windows, not a panic
✗ Common mistakes
  • Cloning inside a hot loop instead of borrowing a slice
  • Calling binary_search on an unsorted Vec (undefined which result you get)
  • Expecting dedup() to remove all duplicates rather than just adjacent ones
// Common Code Patterns · Maps & Sets
HashMap, HashSet & BTree Variants
Key-value lookups and uniqueness checks are everywhere in interview problems — frequency counters, grouping, memoization, visited-sets, graph adjacency. HashMap/HashSet are your O(1)-average default; reach for the BTree variants only when you specifically need sorted iteration or range queries.
Import, creating & inserting
use std::collections::HashMap;

let mut map: HashMap<&str, i32> = HashMap::new();
map.insert("a", 1);
map.insert("b", 2);
map.insert("a", 99);   // insert on an existing key overwrites the old value
Requirement: keys must implement Eq + Hash — this is why raw floats (f64) can't be map keys (see pitfalls card below).
Accessing values
let v = map.get("a");          // Option<&V> — the safe, idiomatic way to read
let exists = map.contains_key("b");  // bool, no borrow of the value itself
let direct = map["a"];         // Index impl — panics if key is missing, use sparingly
Gotcha: unlike Vec indexing (out-of-bounds), missing-key indexing on a map is a much easier mistake to make silently — prefer .get() unless the key's presence is already guaranteed.
The entry() API — counting & grouping
// frequency counting — THE canonical entry() idiom
let mut counts: HashMap<&str, i32> = HashMap::new();
for w in &words {
    *counts.entry(*w).or_insert(0) += 1;
}

// grouping into a HashMap>
let mut groups: HashMap<i32, Vec<&str>> = HashMap::new();
for (k, v) in pairs {
    groups.entry(k).or_insert_with(Vec::new).push(v);
}
Why it matters: entry() does the "check-then-insert-or-update" dance in one lookup instead of two (avoiding a double hash + a borrow-checker fight with a naive if map.contains_key + map.get_mut approach).
Iterating a HashMap
for (k, v) in &map { /* k: &K, v: &V */ }
for (k, v) in &mut map { *v += 1; }   // v: &mut V, mutate values in place
for k in map.keys() { /* &K only */ }
for v in map.values() { /* &V only */ }
Critical gotcha: iteration order over a HashMap is not guaranteed and effectively randomized between runs — never write code (or test assertions) that depend on the order you get back. Use BTreeMap if order matters.
Removing entries
let removed = map.remove("c");   // Option — Some(old_value) or None if key wasn't present
HashSet
use std::collections::HashSet;

let mut seen: HashSet<i32> = HashSet::new();
seen.insert(5);
seen.insert(6);
seen.contains(&5);   // bool, O(1) average
seen.remove(&5);    // bool — true if it was present and got removed
Under the hood: HashSet<T> is literally a thin wrapper over HashMap<T, ()>. Reach for it for deduplication, "have I visited this node/cell?" tracking in DFS/BFS, and fast uniqueness/membership checks.
Vec → HashSet instant dedup
let nums = vec![1, 2, 2, 3, 3, 3, 4];
let unique: HashSet<i32> = nums.into_iter().collect();
// unique.len() == 4 — order is gone, but duplicates are too
The fastest one-line dedup you'll write in an interview — no sorting required, unlike Vec::dedup() which only merges adjacent duplicates.
Set algebra
let a: HashSet<i32> = [1, 2, 3, 4].into_iter().collect();
let b: HashSet<i32> = [3, 4, 5, 6].into_iter().collect();

let inter: Vec<i32> = a.intersection(&b).cloned().collect();  // [3, 4]
let uni: Vec<i32>   = a.union(&b).cloned().collect();         // [1,2,3,4,5,6]
let diff: Vec<i32>  = a.difference(&b).cloned().collect();     // [1, 2] — in a, not in b
All three return borrowing iterators over &T — you almost always immediately .cloned().collect() them into an owned Vec or another HashSet.
BTreeMap / BTreeSet — sorted, deterministic
use std::collections::BTreeMap;

let mut btm: BTreeMap<i32, &str> = BTreeMap::new();
btm.insert(3, "three");
btm.insert(1, "one");
btm.insert(2, "two");

for (k, v) in &btm { /* always visits keys 1, 2, 3 in that order */ }

btm.range(2..);              // iterator over keys >= 2, inclusive/exclusive ranges both work
btm.first_key_value();     // Option<(&K, &V)> — smallest key (stable since Rust 1.66)
btm.last_key_value();      // Option<(&K, &V)> — largest key
Trade-off: same API shape as HashMap/HashSet, but requires K: Ord instead of K: Hash, and operations are O(log n) instead of O(1) average. Use it when you need sorted iteration, range queries, or min/max-key access — not as a default.
Common pitfalls
// 1. type inference sometimes needs an explicit annotation on an empty map
let mut m: HashMap<i32, i32> = HashMap::new();  // HashMap::new() alone can't infer K, V

// 2. forgetting `mut` — every insert/remove/entry-mutate needs it

// 3. mutating while iterating — borrow checker rejects this outright
let keys_to_remove: Vec<i32> = m.keys().cloned().filter(|k| *k % 2 == 1).collect();
for k in keys_to_remove { m.remove(&k); }   // collect keys first, or use m.retain(|k, _| ...)

// 4. f64 does not implement Hash/Eq (NaN breaks equality) — can't be a HashMap key directly;
// wrap it (e.g. bit-cast to u64, or an ordered-float newtype) if you truly need float keys
✓ Reach for this when
  • Counting frequencies, grouping items by a derived key, or memoizing recursive results
  • You need O(1)-average membership/lookup checks (visited sets, seen values)
  • You need sorted keys, range queries, or a running min/max key — reach for BTreeMap/BTreeSet
⚠ Watch out for
  • HashMap iteration order is randomized — never rely on it, use BTreeMap if order matters
  • entry() takes the key by value — clone or copy small keys, don't fight the borrow checker
  • Indexing a map with [] panics on a missing key, unlike .get() which returns None
✗ Common mistakes
  • Trying to mutate a map while holding an active iterator over it
  • Forgetting HashSet::contains takes a reference: .contains(&x), not .contains(x)
  • Reaching for BTreeMap "just in case" when a plain HashMap would be faster and order never matters
// Common Code Patterns · Queues & Deques
VecDeque — Queues & Deques
VecDeque<T> is a ring-buffer-backed double-ended queue — the go-to structure whenever you need cheap operations at both ends, not just the back. It's the backbone of BFS (as a FIFO queue) and of the monotonic-deque family of sliding-window optimizations.
Import & why VecDeque
use std::collections::VecDeque;

let mut dq: VecDeque<i32> = VecDeque::new();
vs. Vec: Vec is only O(1) amortized at the back — insert(0, x)/remove(0) are O(n). VecDeque gives you O(1) push/pop at both the front and the back.
As a FIFO queue (BFS's best friend)
let mut queue: VecDeque<i32> = VecDeque::new();
queue.push_back(start);
while let Some(node) = queue.pop_front() {
    // visit node, push_back its unvisited neighbors
}
This push_back / pop_front shape is the standard skeleton for breadth-first search on graphs, grids, and trees.
As a deque (double-ended)
let mut dq: VecDeque<i32> = VecDeque::new();
dq.push_back(10);
dq.push_front(5);
dq.push_back(20);
dq.push_front(1);
// dq is now [1, 5, 10, 20]
dq.pop_back();    // removes 20, acts like a stack from the right
dq.pop_front();   // removes 1, acts like a stack from the left
front() / back() — peek without removing
dq.front();   // Option<&T> — None if empty
dq.back();    // Option<&T> — None if empty
Monotonic deque pattern — Sliding Window Maximum
fn sliding_window_maximum(nums: &[i32], k: usize) -> Vec<i32> {
    let mut deque: VecDeque<usize> = VecDeque::new(); // stores indices, values decreasing
    let mut result = Vec::new();

    for i in 0..nums.len() {
        // drop indices that fell out of the window from the front
        while let Some(&front) = deque.front() {
            if front + k <= i { deque.pop_front(); } else { break; }
        }
        // drop everything smaller than the new element — they can never be the max again
        while let Some(&back) = deque.back() {
            if nums[back] <= nums[i] { deque.pop_back(); } else { break; }
        }
        deque.push_back(i);

        if i + 1 >= k {
            result.push(nums[*deque.front().unwrap()]);
        }
    }
    result
}
// sliding_window_maximum(&[1,3,-1,-3,5,3,6,7], 3) == [3, 3, 5, 5, 6, 7]
The trick: the deque holds indices, always in strictly decreasing value order. The front is always the max of the current window — front-eviction handles "fell out of window", back-eviction handles "a bigger element makes everything before it useless." Amortized O(n) overall since each index is pushed and popped at most once.

Common pitfalls
// pop_front()/pop_back() return Option — they do NOT panic on an empty deque,
// but silently ignoring the None case can quietly break your algorithm's invariants
if let Some(x) = dq.pop_front() { /* handle x */ }

// forgetting `mut` on the binding — every mutating call needs it, same as Vec
Don't over-reach: if you only ever push/pop at the back, a plain Vec is simpler and marginally faster (no ring-buffer wraparound bookkeeping) — bring in VecDeque specifically when you need both ends.
✓ Reach for VecDeque when
  • Implementing BFS or any FIFO-processing queue
  • You need O(1) operations at both the front and back of a sequence
  • Maintaining a monotonic window (sliding window max/min, first-negative-in-window, etc.)
⚠ Watch out for
  • Indexing a VecDeque (dq[i]) works but is less idiomatic — prefer front()/back()/iter()
  • pop_front()/pop_back() return None on empty rather than panicking — always handle it
  • The monotonic deque stores indices, not values, so you can check window position
✗ Common mistakes
  • Using VecDeque when a plain Vec (back-only) would do — unnecessary complexity/overhead
  • Evicting from the back on "smaller-or-equal" vs. "smaller" — off-by-one changes tie-breaking
  • Forgetting the front-eviction window-bound check, letting stale indices leak into results
// Common Code Patterns · Priority Queues
BinaryHeap — Priority Queues
BinaryHeap<T> is a max-heap built on a binary tree stored in a Vec — reach for it any time you need "give me the current largest/smallest efficiently, repeatedly" rather than a full sort: Dijkstra's algorithm, top-K problems, merge-K-sorted-lists, task scheduling.
Imports
use std::collections::BinaryHeap;
use std::cmp::Reverse;   // needed for min-heap usage — see below
Creating
let mut heap: BinaryHeap<i32> = BinaryHeap::new();

// or heapify an existing collection in O(n) — faster than n individual pushes
let heap2: BinaryHeap<i32> = nums.into_iter().collect();
push()
heap.push(3);
heap.push(1);
heap.push(4);   // O(log n) — sifts the new element up to restore heap property
pop()
let top = heap.pop();   // Option — removes & returns the greatest element, O(log n)
Default BinaryHeap is max-heap only — pop() always gives you the current largest element, never the smallest.
peek()
let top = heap.peek();   // Option<&T> — O(1), look without removing
Min-heap via Reverse
let mut min_heap: BinaryHeap<Reverse<i32>> = BinaryHeap::new();
min_heap.push(Reverse(5));
min_heap.push(Reverse(1));
min_heap.push(Reverse(3));

if let Some(Reverse(val)) = min_heap.pop() {
    // val == 1 — Reverse flips the Ord comparison, turning max-heap into min-heap
}
This is the standard trick since std only ships a max-heap — wrap every element (or just the priority field) in Reverse on the way in, and unwrap it on the way out.
Other methods reference
MethodEffectCost
len()current element countO(1)
is_empty()true if length is 0O(1)
clear()remove every elementO(n)
into_sorted_vec()consumes heap, returns ascending Vec<T>O(n log n)
Gotcha: despite the heap being max-first, into_sorted_vec() returns ascending order (smallest first) — always double check this against the actual docs/behavior rather than assuming.
Custom types in a heap
#[derive(Eq, PartialEq)]
struct Task { priority: i32, name: &'static str }

// manual Ord: reverse the natural comparison so the heap is smallest-priority-first
// (handy for task schedulers — avoids wrapping every push in Reverse)
impl Ord for Task {
    fn cmp(&self, other: &Self) -> std::cmp::Ordering {
        other.priority.cmp(&self.priority)
    }
}
impl PartialOrd for Task {
    fn partial_cmp(&self, other: &Self) -> Option<std::cmp::Ordering> {
        Some(self.cmp(other))
    }
}

// simpler alternative: a (priority, item) tuple heap — tuples compare lexicographically,
// so #[derive(Ord, PartialOrd, Eq, PartialEq)] on the tuple's fields is all you need
let mut tuple_heap: BinaryHeap<(i32, &str)> = BinaryHeap::new();
tuple_heap.push((5, "a"));
tuple_heap.push((2, "b"));   // compares by .0 first, .1 only breaks ties
A type only needs to derive/impl Ord (plus PartialOrd, Eq, PartialEq) to go in a BinaryHeap — #[derive(...)] gives you natural field-order comparison, a manual impl lets you flip it without a Reverse wrapper everywhere.
Top-K pattern
// keep a size-K heap; whenever it overflows, evict the current extreme
let mut heap: BinaryHeap<Reverse<(i32, i32)>> = BinaryHeap::new();  // min-heap of (count, value)
for (val, count) in freq_map {
    heap.push(Reverse((count, val)));
    if heap.len() > k {
        heap.pop();   // evicts the smallest count — the least "top-K-worthy" so far
    }
}
// heap now holds exactly the K largest-count entries seen
This exact skeleton solves "Top K Frequent Elements," "K Closest Points to Origin," and "Kth Largest Element" — keep a min-heap capped at size K when hunting the K largest values (and vice versa for K smallest), so the heap always evicts the item furthest from qualifying.
✓ Reach for BinaryHeap when
  • You repeatedly need "the current min/max" without re-sorting (Dijkstra, task scheduling)
  • Solving a Top-K / K-closest / Kth-largest style problem
  • Merging K sorted sequences (push one head from each, pop the smallest, repeat)
⚠ Watch out for
  • Default BinaryHeap is max-heap — wrap in Reverse for min-heap behavior
  • into_sorted_vec() returns ascending order, not descending — easy to misremember
  • push/pop are O(log n), not O(1) — don't assume heap ops are free in tight loops
✗ Common mistakes
  • Using a min-heap-of-K-largest pattern backwards (evicting the max instead of the min)
  • Forgetting to implement Ord/PartialOrd/Eq/PartialEq on a custom struct before pushing it
  • Calling peek()/pop() on an empty heap and unwrapping without checking for None
// Common Code Patterns · Sorting & Searching
Sorting & Searching
Sorting shows up everywhere — not just "sort this array" problems, but as a prerequisite for two-pointer, binary-search, and greedy techniques. Knowing the exact method to reach for (and which comparator shape to write) without hesitation is a big speed win in an interview.
sort() vs sort_unstable()
let mut v = vec![5, 3, 1, 4, 2];
v.sort();              // stable, TimSort-derived — equal elements keep their relative order
v.sort_unstable();     // often faster (no stability bookkeeping), order of ties is unspecified
Use when: reach for sort_unstable whenever your compare key is unique (e.g. sorting plain i32s) or you genuinely don't care about tie order — it's a free performance win with zero downside in that case. Keep sort() whenever ties carry meaning (e.g. sorting records by one field but wanting insertion order preserved among ties).
Custom comparator with sort_by()
let mut nums = vec![5, 1, 4, 2, 8];
nums.sort_by(|a, b| b.cmp(a));  // descending — swap the argument order to flip direction
// nums == [8, 5, 4, 2, 1]
sort_by gives full control — the closure returns an Ordering, so you can compose multi-key comparisons with .then_with(...) when a single field isn't enough.
sort_by_key()
let mut words = vec!["banana", "fig", "apple", "kiwi"];
words.sort_by_key(|s| s.len());
// words == ["fig", "kiwi", "apple", "banana"]
Cleaner than sort_by when you're sorting on a single derived value — no need to write out a two-argument comparator by hand.
Sorting f64 / floats
let mut floats = vec![3.1, 1.5, 2.7, 0.2];
// floats.sort(); // ✗ WON'T COMPILE — f64 is only PartialOrd, not Ord (NaN breaks totality)
floats.sort_by(|a, b| a.partial_cmp(b).unwrap());  // works, but panics if a NaN sneaks in

let mut with_nan = vec![3.1, f64::NAN, 1.5];
with_nan.sort_by(|a, b| a.total_cmp(b));  // NaN-safe — defines a total order, NaN sorts to one end
Gotcha: f64/f32 don't implement Ord because NaN != NaN, which violates the reflexivity Ord requires — that's why plain .sort() is a compile error on floats, not a runtime surprise. Prefer .total_cmp() (stable since 1.62) over .partial_cmp().unwrap() whenever input might contain NaN, since it never panics.
binary_search()
let sorted = vec![1, 3, 5, 7, 9];
sorted.binary_search(&5);   // Ok(2)  — found, this is its index
sorted.binary_search(&4);   // Err(2) — not found; 2 is where it WOULD go to keep the vec sorted
Gotcha: only valid on already-sorted data — running it on an unsorted slice returns an unspecified (not necessarily useful) result rather than panicking, which makes the bug easy to miss.
partition_point()
let nums = vec![1, 2, 3, 6, 7, 9];
let idx = nums.partition_point(|&x| x < 6);
// idx == 3 — first index where the predicate flips from true to false
A generalized binary search over a boolean predicate instead of an exact value — think of it as "where does this condition stop holding?" It's the same algorithm as binary_search under the hood, just parameterized differently, and it's the cleanest way to express lower-bound/upper-bound style queries.
min / max
std::cmp::min(3, 7);            // 3 — free function, exactly two values
std::cmp::max(3, 7);            // 7

let v = vec![4, 1, 9, 2];
v.iter().min();   // Option<&T> -> Some(&1)
v.iter().max();   // Option<&T> -> Some(&9), None on an empty collection
Don't reach for std::cmp::min/max when you actually have a collection — .iter().min()/.max() is the idiomatic O(n) scan and correctly returns None for empty input instead of forcing you to pick a sentinel.
Custom Ord/PartialOrd for structs
#[derive(Debug, PartialEq, Eq, PartialOrd, Ord)]
struct Task {
    priority: i32,   // compared FIRST — field order determines comparison priority
    name_len: i32,   // tie-breaker — only consulted when priority is equal
}

let mut tasks = vec![
    Task { priority: 2, name_len: 1 },
    Task { priority: 1, name_len: 5 },
    Task { priority: 1, name_len: 2 },
];
tasks.sort();
// sorted by priority asc, then name_len asc within equal priority (lexicographic)
Deriving Ord gives you lexicographic comparison in declared field order — exactly like comparing tuples (a, b). This is also what you need to drop a type straight into a BinaryHeap<T> or use it as a sort()-able key without writing a custom comparator.
Practical tips
// ✗ sorting inside a loop — O(n² log n) and wholly unnecessary
for _ in 0..queries.len() { data.sort(); /* ... */ }

// ✓ sort once up front, reuse the sorted state for every subsequent query
data.sort();
for q in &queries { /* binary_search / partition_point / two-pointer over `data` */ }
Sorting is the on-ramp to a whole family of techniques — two-pointer, binary search, greedy interval scheduling — all of which assume sorted input as a precondition. If you catch yourself re-sorting inside a loop, that's almost always a sign the sort should have happened once, outside it.
✓ Reach for this when
  • You need sorted order as a precondition for binary search, two-pointer, or greedy logic
  • You're sorting structs/records by one or more fields — derive Ord or use sort_by_key
  • You need the "would-be" insertion point for sorted data — binary_search's Err arm or partition_point
⚠ Watch out for
  • f64/f32 not implementing Ord — always partial_cmp or total_cmp
  • binary_search/partition_point on unsorted data gives a meaningless result, not a panic
  • Re-sorting inside a loop instead of once up front
✗ Common mistakes
  • Calling .sort() on a Vec<f64> and being confused by the compile error
  • Forgetting sort_by's comparator returns Ordering, not a bool
  • Deriving Ord with fields in the wrong order and getting the wrong sort priority
// Common Code Patterns · Pattern Matching
Pattern Matching
Pattern matching is Rust's control-flow backbone — it's how you unwrap Option/Result, branch on enums, and destructure data, all while the compiler checks you've covered every case. Picking the right flavor of match (full match, if let, while let, let-else) for the situation is what separates idiomatic Rust from Rust that merely compiles.
Basic match
match n {
    0 => "zero",
    1..=4 => "small",   // inclusive range pattern
    _ => "large",      // wildcard — REQUIRED unless every value is covered
}
Gotcha: match must be exhaustive — the compiler rejects it if any possible value of the matched type isn't covered by some arm, which is exactly what makes it safer than a chain of if/else.
Matching Option<T>
let maybe_val: Option<i32> = Some(7);
match maybe_val {
    Some(v) => println!("got {v}"),
    None => println!("nothing"),
}
This is the whole reason Option exists — it forces you to handle the "nothing here" case at compile time instead of silently calling .unwrap() and hoping the value is there at runtime.
Matching Result<T, E>
let res: Result<i32, String> = Err("boom".to_string());
let handled = match res {
    Ok(v) => v,
    Err(_) => -1,   // fallback value on failure
};
if let
let opt = Some(10);
if let Some(v) = opt {
    println!("got {v}");
}
// vs. a full match that would need a throwaway `_ => {}` arm — if let is the cleaner shape here
Use when you only care about ONE variant and want to do nothing (or something trivial) for the rest — a full match with an empty _ => {} arm is just noise by comparison.
while let
let mut stack = vec![1, 2, 3];
while let Some(top) = stack.pop() {
    println!("{top}");   // prints 3, 2, 1 — drains the stack completely
}
The standard idiom for "process until empty" — DFS with an explicit stack, draining a queue, consuming a linked list node-by-node. Loop condition and value extraction happen in one line.
let-else (Rust 1.65+)
fn first_even(items: &[i32]) -> i32 {
    let Some(&x) = items.iter().find(|&&x| x % 2 == 0) else {
        return -1;   // the failure path must diverge: return / continue / break / panic
    };
    x   // here x is unwrapped and available for the rest of the function — no nested block
}
A flatter alternative to if let Some(x) = opt { ... } else { return; } — instead of the happy path living nested inside an if block, it lives at the top level of the function and the failure path is the one that's indented away.
Matching tuples
let point = (0, 5);
match point {
    (0, 0) => "origin",
    (0, _) => "on y-axis",
    (_, 0) => "on x-axis",
    (x, y) if x > 0 && y > 0 => "Q1",
    _ => "other",
}
Destructures both elements directly in the pattern — no point.0/point.1 access needed, and each field can independently be a wildcard, a literal, or a bound variable.
Destructuring in let bindings & for loops
let pair = (3, 4);
let (a, b) = pair;   // pull both fields out in one binding

for (i, val) in names.iter().enumerate() {
    println!("{i}: {val}");   // (usize, &T) unpacked directly in the loop head
}
Matching structs and enums
enum Direction { Up, Down, Left, Right }

fn move_dir(d: &Direction) -> (i32, i32) {
    match d {
        Direction::Up => (0, 1),
        Direction::Down => (0, -1),
        Direction::Left => (-1, 0),
        Direction::Right => (1, 0),
        // no `_` needed — all four variants are covered, compiler verifies this
    }
}
Matching every enum variant by name (instead of falling back to _) means the compiler forces you to update every match site if you ever add a new variant — a huge refactoring safety net.
Match guards
match n {
    n if n % 2 == 0 && n > 0 => "positive even",
    n if n % 2 == 0 => "even",
    _ => "odd",
}
A guard adds an extra if condition on top of a pattern match — useful when the pattern alone can't express the condition (ranges/literals can't express "is even"), but note guards are checked in order and don't count toward exhaustiveness the way plain patterns do.
@ bindings and or-patterns
match n {
    n @ 1..=5 => format!("small:{n}"),  // @ binds the whole value AND checks the range in one go
    n => format!("other:{n}"),
}

matches!(x, 1 | 2 | 3)   // or-pattern — one arm matches several discrete values
@ is essential when a range/literal pattern would otherwise discard the matched value — without it you'd need a separate guard plus a re-reference to n to get the same information.
✓ Reach for this when
  • Unwrapping Option/Result safely instead of calling .unwrap()
  • Draining a stack/queue — while let Some(x) = ...pop()
  • Branching on an enum where the compiler should enforce exhaustiveness
⚠ Watch out for
  • Match guards don't count toward exhaustiveness — you still need a catch-all arm
  • let-else's else-branch MUST diverge (return/break/continue/panic), or it won't compile
  • Order matters — the first matching arm wins, even if a later one is "more specific"
✗ Common mistakes
  • Reaching for .unwrap() instead of a match/if-let when a value can genuinely be absent
  • Writing an unreachable arm after a broader range/wildcard pattern already caught it (compiler warns, but easy to miss)
  • Using a full match with a single meaningful arm plus _ => {} instead of the simpler if let
// Common Code Patterns · Iterators
Iterators & Functional Tools
The iterator chain is the single most idiomatic tool in Rust — almost any loop that transforms, filters, or reduces a collection can be rewritten as a chain, and doing so is usually both more readable and just as fast (the compiler aggressively inlines and optimizes these chains, so there's rarely a performance excuse to hand-roll a loop instead). This section is deliberately the deepest one — fluency here is what "idiomatic Rust" actually looks like in practice.
map / filter / collect
let nums = vec![1, 2, 3, 4, 5, 6];
let evens_sq: Vec<i32> = nums.iter().filter(|&&x| x % 2 == 0).map(|&x| x * x).collect();
// evens_sq == [4, 16, 36]

let copied: Vec<i32> = nums.iter().copied().collect();  // .copied()/.cloned() instead of a |&x| map when you just want owned values
.iter() over a Vec<i32> yields &i32, so filter needs |&&x| (double deref through the filter's own &&T) while map only needs |&x| — this asymmetry trips people up constantly; .copied()/.cloned() sidesteps it entirely when there's no actual transformation to do.
sum / product
let total: i32 = nums.iter().sum();
let prod: i32 = nums.iter().take(4).product();
// total == 21, prod == 24
The turbofish (::<i32>) or an explicit type on the binding is required — sum/product are generic over the target numeric type and can't infer it from the iterator alone.
fold
let words = vec!["a", "b", "c"];
let sentence = words.iter().fold(String::new(), |acc, w| acc + w + " ");
// sentence == "a b c "
The general-purpose reduce — you supply the starting accumulator explicitly, so it works even on an empty iterator (unlike reduce). Almost every sum/product/string-building loop can be expressed as a fold.
reduce
let max_val = nums.iter().copied().reduce(|a, b| if a > b { a } else { b });
// Some(6) — first element seeds the accumulator, no separate initial value needed

let empty: Vec<i32> = vec![];
empty.iter().copied().reduce(|a, b| a + b);  // None — nothing to seed the accumulator with
Like fold but without an explicit seed — the first element IS the seed. Returns Option<T> for exactly that reason: an empty iterator has nothing to seed from, so you get None instead of a made-up default.
find / position
nums.iter().find(|&&x| x > 4);      // Option<&T> -> Some(&5) — the element itself
nums.iter().position(|&x| x > 4);  // Option<usize> -> Some(4) — its index
Both stop at the first match and short-circuit — pick find when you need the value, position when you need where it is (e.g. to slice around it afterward).
any / all
nums.iter().any(|&x| x == 3);   // true — stops as soon as ONE match is found
nums.iter().all(|&x| x > 0);   // true — stops as soon as ONE mismatch is found (short-circuits on failure)
Both are short-circuiting, so they're O(1)-ish in the best case rather than always scanning the whole collection — much cheaper than .filter(...).count() > 0 for the same check.
zip / chain
let letters = vec!['a', 'b', 'c'];
let zipped: Vec<(i32, char)> = nums.iter().copied().zip(letters.iter().copied()).collect();
// [(1,'a'), (2,'b'), (3,'c')] — stops at the SHORTER of the two iterators

let chained: Vec<i32> = vec![1, 2].into_iter().chain(vec![3, 4].into_iter()).collect();
// [1, 2, 3, 4] — concatenates two iterators end-to-end
zip pairs element-wise (great for parallel-array problems); chain concatenates (great for "process this collection, then that one" without an intermediate allocation).
flat_map / flatten
let nested = vec![vec![1, 2], vec![3], vec![4, 5]];
let flat: Vec<i32> = nested.into_iter().flatten().collect();
// [1, 2, 3, 4, 5] — collapses Vec<Vec<T>> into Vec<T>

let chars: Vec<char> = vec!["hi", "yo"].iter().flat_map(|s| s.chars()).collect();
// ['h','i','y','o'] — map to an iterator per element, then flatten in one step
flat_map(f) is exactly .map(f).flatten() fused into one call — reach for it whenever your mapping function itself produces an iterator/collection per element.
take / skip / step_by / take_while / skip_while
let v: Vec<i32> = (1..=10).collect();
v.iter().take(3);                    // [1, 2, 3] — first n, regardless of value
v.iter().skip(7);                    // [8, 9, 10] — drop first n
v.iter().step_by(3);                 // [1, 4, 7, 10] — every 3rd element
v.iter().take_while(|&&x| x < 4);   // [1, 2, 3] — stops permanently at the first failure
v.iter().skip_while(|&&x| x < 4);   // [4..10] — skips until the first failure, then takes everything else
All five are lazy slicing operations — none allocate on their own, so chaining several together before a final collect() is still just one pass over the data.
peekable()
let mut it = vec![1, 2, 3].into_iter().peekable();
it.peek();    // Some(&1) — look at the next item WITHOUT consuming it
it.next();    // Some(1) — now actually consumes it
it.peek();    // Some(&2)
The standard tool for lexers/parsers — "look at the next token, decide what to do, only advance if it matches" is exactly the peek-then-conditionally-next pattern.
scan
let running_sums: Vec<i32> = vec![1, 2, 3, 4].iter().scan(0, |acc, &x| {
    *acc += x;
    Some(*acc)
}).collect();
// [1, 3, 6, 10] — running total, one output per input element
Like fold, but instead of only returning the final accumulator, it yields every intermediate value as its own iterator — the classic use case is exactly this running-sum/running-total pattern. Returning None from the closure stops the iterator early.
rev()
let reversed: Vec<i32> = (1..=5).rev().collect();
// [5, 4, 3, 2, 1]
Requires DoubleEndedIterator — works on ranges, slices, Vec iterators, and most standard adapters, but NOT on things like filter's output from an arbitrary lazily-generated source without that bound; in practice this is rarely a problem for the collections you'll use in interviews.
Common pitfalls
let iter = nums.iter().map(|&x| x * 2);
// ✗ nothing has happened yet — iterators are LAZY, this line does zero work
let doubled: Vec<i32> = iter.collect();
// ✓ only NOW does the map closure actually run, once per element

// ✗ nums.iter().sort() — doesn't exist; sort() is a Vec/slice method, not an Iterator one
let mut v: Vec<i32> = nums.iter().copied().collect();
v.sort();   // ✓ collect into a Vec first, then sort the Vec
Three classics: forgetting the final .collect() (or other consumer) and wondering why nothing ran; trying to sort an iterator directly instead of collecting to a Vec first; and confusing chunks(n) (non-overlapping partitions, see the Arrays & Slices section) with windows(n) (overlapping subarrays) — they solve different problem shapes and mixing them up under time pressure is extremely common.
✓ Reach for this when
  • Transforming/filtering/reducing a collection — almost always cleaner than a hand-rolled loop
  • You need a running accumulation (scan) or a single final accumulation (fold/reduce)
  • Look-ahead parsing logic — peekable()
⚠ Watch out for
  • Iterators do nothing until consumed by collect/for/sum/etc. — a chain by itself is a no-op
  • zip silently truncates to the shorter iterator instead of erroring
  • reduce returns Option (empty -> None); fold doesn't need to, because you supply the seed
✗ Common mistakes
  • Trying to call .sort() directly on an iterator instead of collecting to a Vec first
  • Using chunks() when the problem actually needs overlapping windows(), or vice versa
  • Writing |&x| vs |&&x| incorrectly and fighting the borrow checker instead of just using .copied()

Closures & Functions
Closures are how Rust does "pass behavior as data" — comparators, callbacks, iterator adapters, and thread bodies are all closures under the hood. The tricky part isn't writing them, it's knowing which of Fn/FnMut/FnOnce you're dealing with and whether you need generics, a trait object, or a plain function pointer to hold one.
Fn / FnMut / FnOnce
let factor = 3;
let times_factor = |x: i32| x * factor;      // Fn — reads `factor` immutably, callable any number of times
assert_eq!(times_factor(4), 12);
assert_eq!(times_factor(5), 15);         // called again, no problem

let mut count = 0;
let mut increment = || { count += 1; count };  // FnMut — mutates `count`, still callable repeatedly

let owned = String::from("hello");
let consume = move || owned;               // FnOnce — moves `owned` out, can only be called once
The compiler infers the least restrictive trait automatically from what the closure body actually does — you never annotate this yourself. A closure that merely reads a capture is Fn; one that mutates is FnMut; one that consumes/moves a capture out is FnOnce. Every Fn is also FnMut and FnOnce (the traits nest), which is why generic bounds usually just ask for the loosest one that's actually needed.
Passing a closure as a generic parameter
fn apply<F: Fn(i32) -> i32>(f: F, x: i32) -> i32 {
    f(x)
}
let doubled = apply(|x| x * 2, 10);  // 20
Zero-cost — the compiler generates a separate monomorphized copy of apply for every distinct closure type it's called with, so the call can be fully inlined. This is the default choice unless you specifically need dynamic dispatch.
Passing a closure as a trait object
fn apply_dyn(f: &dyn Fn(i32) -> i32, x: i32) -> i32 {
    f(x)
}
let squared = apply_dyn(&|x| x * x, 6);  // 36
One non-generic function body, dynamic dispatch through a vtable — needed when you don't want a separate monomorphized copy per call site, or when you need a heterogeneous collection like Vec<Box<dyn Fn(i32) -> i32>> where each element can be a genuinely different closure type.
Returning closures
fn make_adder(n: i32) -> impl Fn(i32) -> i32 {
    move |x| x + n       // single concrete closure type — impl Fn is enough
}
let add5 = make_adder(5);
assert_eq!(add5(10), 15);

fn make_op(op: char) -> Box<dyn Fn(i32) -> i32> {
    match op {
        '+' => Box::new(|x| x + 1),   // each match arm is a DIFFERENT closure type
        '-' => Box::new(|x| x - 1),   // impl Fn wouldn't compile here — types must match across all branches
        _ => Box::new(|x| x),
    }
}
impl Fn(i32) -> i32 works when the function always returns the same underlying closure type (even with different captured values, like the adder factory) — the moment different branches return textually different closures, you need Box<dyn Fn...> to erase the type differences.
move closures
let data = vec![1, 2, 3];
let handle = thread::spawn(move || data.iter().sum::<i32>());
let sum = handle.join().unwrap();  // 6
move forces the closure to take ownership of its captures by value instead of borrowing them. Essential for anything that might outlive the current stack frame — thread::spawn is the textbook case, since the spawned thread can't hold a borrow into a frame that may have already returned.
Function pointers vs closures
fn triple(x: i32) -> i32 { x * 3 }
let fn_ptr: fn(i32) -> i32 = triple;      // plain function pointer — smallest, no captures
let non_capturing: fn(i32) -> i32 = |x| x + 1;  // a closure that captures nothing coerces to fn just fine
fn(i32) -> i32 is a bare pointer, not a trait — it's the smallest, simplest way to pass "some function" around, but only non-capturing closures (or actual named functions) can coerce into one. The moment a closure captures anything from its environment, it must be passed as a generic Fn/FnMut/FnOnce or a dyn trait object instead.
Comparator closures
nums.sort_by(|a, b| b.cmp(a));      // two-argument comparator — full control, returns Ordering
words.sort_by_key(|s| s.len());  // single-key extractor — simpler when one derived value is enough
See the Sorting & Searching section for the full comparator picture — the closure shape here is the same Fn-flavored pattern as everywhere else in this section, just applied to sort_by/sort_by_key specifically.
Common pattern: callback/event registration
struct Event { code: i32 }

let callbacks: Vec<Box<dyn Fn(&Event)>> = vec![
    Box::new(|e: &Event| println!("handler A saw code {}", e.code)),
    Box::new(|e: &Event| { /* handler B does something else entirely */ }),
];
let ev = Event { code: 7 };
for cb in &callbacks {
    cb(&ev);   // invoke every registered handler with the same event
}
This is exactly why trait objects exist for closures — a Vec can't hold multiple distinct closure types directly (they're all different concrete types even with identical signatures), but Box<dyn Fn(&Event)> erases that difference so heterogeneous handlers can live side by side in one list.
✓ Reach for this when
  • You need to pass custom behavior into a function — comparators, predicates, transformations
  • Storing a heterogeneous list of callbacks — Vec<Box<dyn Fn...>>
  • Spawning work onto another thread — always pair with move
⚠ Watch out for
  • A capturing closure can never coerce to a bare fn pointer, only a non-capturing one can
  • impl Fn return types require every code path to return the SAME underlying closure type
  • FnOnce closures can only be called once — trying to call twice is a compile error, not a panic
✗ Common mistakes
  • Forgetting move on a closure passed to thread::spawn and hitting a lifetime error
  • Reaching for Box<dyn Fn> everywhere out of habit when a generic <F: Fn...> parameter would be zero-cost and sufficient
  • Trying to return different closures with impl Fn from different if/match branches instead of boxing them

Ownership, Borrowing & Lifetimes — Quick Reference
The deep theory on ownership/borrowing/lifetimes already lives elsewhere in this packet — this is the fast-scan cheat sheet: the exact syntax and standard fixes you reach for mid-interview when the borrow checker pushes back. Each card is code-first and short on purpose.
Move semantics
let s1 = String::from("hi");
let s2 = s1;              // s1 is MOVED into s2 — String is not Copy
println!("{}", s1);   // ERROR: value borrowed after move

// fix 1: clone if you truly need two independent owners
let s2 = s1.clone();
// fix 2: pass by reference instead of moving, if a function only needs to read it
fn show(s: &String) { println!("{}", s); }
Gotcha: the compiler error is always "value used/borrowed after move" — the fix is almost always clone-it or borrow-it-instead, never fighting the compiler on the move itself.
Copy vs Clone at a glance
// Copy (implicit bitwise copy, old binding stays valid): all integer/float/bool/char types,
// tuples and fixed-size arrays and structs made ENTIRELY of Copy fields
let a = 5; let b = a;   // both a and b usable — i32 is Copy

// Clone-only (explicit, potentially expensive, old binding INVALIDATED unless you .clone()):
// String, Vec<T>, HashMap, Box<T>, Rc<T> — anything that owns a heap allocation
let v1 = vec![1, 2]; let v2 = v1.clone();  // v1 still usable
Rule of thumb: if the type has a heap allocation or an OS handle behind it, it's Clone-only; if it's "just bits" and small, it's Copy.
Borrowing rules at a glance
let mut v = vec![1, 2, 3];
let r1 = &v;
let r2 = &mut v;      // ERROR: cannot borrow `v` as mutable because it's also borrowed as immutable
println!("{:?}", r1);

// fix: end the immutable borrow's lifetime before taking the mutable one
let r1 = &v;
println!("{:?}", r1);   // r1's last use — NLL ends its borrow here
let r2 = &mut v;      // OK now
The rule: at any point, either many &T OR exactly one &mut T into the same data — never both at once. This is what prevents data races and iterator-invalidation bugs at compile time.
mem::take / mem::replace / mem::swap
use std::mem;

struct Buffer { data: String }
impl Buffer {
    // need to move `data` out to consume it, but only have &mut self — can't just do `self.data`
    fn take_data(&mut self) -> String {
        mem::take(&mut self.data)   // leaves String::default() ("") behind, returns the real value
    }
}

let mut a = String::from("old");
let old = mem::replace(&mut a, String::from("new")); // old = "old", a = "new"

let (mut x, mut y) = (String::from("left"), String::from("right"));
mem::swap(&mut x, &mut y);   // x = "right", y = "left" — no clone needed
Use when: you need to move a value out of a struct field through &mut self without leaving it in an invalid state — take substitutes Default::default(), replace substitutes a value you supply, swap exchanges two places in-place.
Lifetime annotation basics
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
// reads as: "for some lifetime 'a, both inputs live at least 'a, and the
// returned reference is only guaranteed valid for that same 'a"
Lifetimes don't change how long anything actually lives — they're a compile-time constraint telling the borrow checker how the output's validity relates to the inputs'.
Lifetime elision rules
// 1. Each elided input reference gets its OWN lifetime parameter
fn first_word(s: &str) -> &str      // desugars to fn first_word<'a>(s: &'a str) -> &'a str

// 2. If there's EXACTLY ONE input lifetime, it's assigned to all elided outputs (rule 1 already covers this case)

// 3. If one input is &self / &mut self, its lifetime is assigned to all elided outputs
impl Parser {
    fn peek(&self) -> &str { &self.buf }  // output tied to &self, no annotation needed
}
If your function has multiple reference inputs and none is &self, none of these rules apply and you MUST annotate explicitly — that's exactly the longest case above.
split_at_mut for disjoint mutable borrows
fn split_at_mut(&mut self, mid: usize) -> (&mut [T], &mut [T])
When you need two &mut references into provably-disjoint halves of the same slice (e.g. divide-and-conquer recursion), the naive attempt won't compile because the borrow checker can't see the split — split_at_mut does it soundly with one internal unsafe call. Full walkthrough lives in Topic 1 (Ownership & Borrowing) of this packet.
Interview triage: clone/own instead of fighting lifetimes
// fighting the borrow checker under time pressure:
fn first_or_default<'a>(v: &'a Vec<String>) -> &'a str { /* lifetime juggling */ }

// pragmatic interview fallback: return an OWNED value, sidestep the lifetime entirely
fn first_or_default(v: &Vec<String>) -> String {
    v.first().cloned().unwrap_or_default()
}
Not "best practice" for production (extra allocations), but perfectly valid interview triage: if a lifetime puzzle is costing you minutes, return an owned String/Vec via .clone(), get a working solution, and mention the trade-off out loud.
✓ Reach for this when
  • You get a "value moved" or "cannot borrow as mutable" compiler error and need the standard fix fast
  • You need to take a field's value out through &mut self (use mem::take)
  • A function returns a reference and you're unsure whether to annotate — check the 3 elision rules first
⚠ Watch out for
  • Forgetting that mem::take requires the field type to implement Default
  • Confusing "the value's actual lifetime" with "the lifetime annotation" — annotations are constraints, not durations
  • &self-shaped elision (rule 3) only fires when self is one of the reference params, not any struct field
✗ Common mistakes
  • Adding lifetime annotations everywhere out of habit instead of letting elision handle the common cases
  • Trying to return a reference to a local variable created inside the function (dangling reference — always a compile error, never a valid fix)
  • Reaching for Rc/RefCell to dodge a simple lifetime issue that a .clone() would solve in one line

Error Handling — Option & Result Patterns
Rust has no exceptions and no null — Option<T> and Result<T, E> carry absence/failure explicitly in the type system. Fluency with their combinator methods (not just match-ing everything by hand) is one of the fastest tells of Rust experience in an interview.
Option core methods
let x: Option<i32> = Some(5);
x.unwrap();                     // 5, or PANICS if x is None — use only when None is a bug
x.expect("x must exist");     // same panic, but with a custom, debuggable message
x.unwrap_or(0);               // 5, or 0 if None — default is computed eagerly even if unused
x.unwrap_or_else(|| expensive()); // like unwrap_or, but the closure only runs on the None path
x.unwrap_or_default();        // 5, or T::default() if None (0 for i32, "" for String, etc.)
Gotcha: prefer unwrap_or_else over unwrap_or whenever the fallback is expensive to compute (an allocation, a function call) — unwrap_or's argument is evaluated unconditionally.
Option transformation — map / and_then
let x = Some(5);
let y = x.map(|v| v * 2);            // Some(10) — transforms Some's inner value, None passes through untouched

fn half_if_even(v: i32) -> Option<i32> { if v % 2 == 0 { Some(v / 2) } else { None } }
let z = x.and_then(half_if_even);   // None — 5 is odd; and_then chains Option-returning ops (flatMap)
.map() when your function returns a plain value; .and_then() when it returns another Option — using .map() with an Option-returning closure gives you an Option<Option<T>>, almost never what you want.
Option ⇄ Result conversion
let x: Option<i32> = None;
let r: Result<i32, &str> = x.ok_or("missing value");        // Err("missing value")
let r2: Result<i32, String> = x.ok_or_else(|| build_msg()); // lazy — closure only runs on None

let good: Result<i32, String> = Ok(42);
let as_opt: Option<i32> = good.ok();   // Some(42) — Result -> Option, discards the Err entirely
Result core methods
let r: Result<i32, String> = Ok(10);
r.unwrap();  r.expect("msg");         // same panic-on-Err semantics as Option
r.map(|v| v * 2);                    // transforms the Ok value, Err passes through
r.map_err(|e| format!("wrapped: {e}")); // transforms the Err value, Ok passes through
r.and_then(|v| if v > 0 { Ok(v) } else { Err("neg".to_string()) }); // chain fallible ops
The ? operator
fn parse_one(s: &str) -> Result<i32, ParseErr> {
    s.parse().map_err(|_| ParseErr)
}
fn parse_two(a: &str, b: &str) -> Result<i32, String> {
    let x = parse_one(a)?;   // on Err, RETURNS EARLY — converts ParseErr -> String via From
    let y = parse_one(b)?;
    Ok(x + y)
}
? unwraps Ok/Some and continues, or does an early return Err(From::from(e)) / return None on failure. The automatic From::from() call is why a helper returning one error type can propagate cleanly into a caller with a different error type — as long as impl From<Inner> for Outer exists.
Custom error types
#[derive(Debug)]
enum MyError {
    NotFound,
    Invalid(String),
}

impl std::fmt::Display for MyError {
    fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result {
        match self {
            MyError::NotFound => write!(f, "not found"),
            MyError::Invalid(s) => write!(f, "invalid: {}", s),
        }
    }
}
impl std::error::Error for MyError {}

impl From<std::num::ParseIntError> for MyError {
    fn from(e: std::num::ParseIntError) -> Self { MyError::Invalid(e.to_string()) }
}
This trio (Display + Error + From<X>) is the standard shape interviewers expect — the From impl is what lets ? auto-convert a lower-level error (like ParseIntError) into your domain error.
Combining heterogeneous error types quickly
fn run() -> Result<(), Box<dyn std::error::Error>> {
    let n: i32 = "42".parse()?;       // ParseIntError -> Box<dyn Error> via a blanket From
    let _f = std::fs::read_to_string("x")?; // io::Error -> Box<dyn Error> too, no enum needed
    Ok(())
}
Trade-off: zero boilerplate, any error type that implements std::error::Error just works with ? — but callers lose the ability to match on a specific error variant; fine for main()/scripts/prototypes, weaker for library APIs.
is_some / is_none / is_ok / is_err
let x = Some(5);
if x.is_some() { /* ... */ }     // quick boolean check, no unwrapping/matching
let r: Result<i32, String> = Ok(1);
if r.is_err() { /* ... */ }
Handy for early-exit guard clauses, but if you find yourself calling is_some() then immediately unwrap()-ing, prefer if let Some(v) = x instead — one check, no risk of the two calls disagreeing.
as_ref() / as_mut()
let x: Option<String> = Some(String::from("hi"));
let len = x.as_ref().map(|s| s.len()); // Option<&String> -> peek without moving `x`
println!("{:?}", x);              // x is still usable — as_ref() didn't consume it
Without as_ref(), calling .map() directly on an Option<String> you don't own by value would move it out — as_ref()/as_mut() let you operate on the reference instead and keep the original binding alive.
Option::take()
let mut opt = Some(String::from("payload"));
let taken = opt.take();   // taken = Some("payload"), opt is now set to None in place
The standard way to move a value out of an Option field behind &mut self — this is exactly the trick linked-list reversal and other pointer-juggling patterns lean on constantly (see the Linked Lists section).
Don't blindly unwrap in production-style code
// fine for a throwaway script / a value you've already proven can't be None:
let first = v.first().unwrap();

// for real code: propagate, don't panic
let first = v.first().ok_or(MyError::NotFound)?;
Interviewers often probe this deliberately — panicking is fine for a quick LeetCode-style solution, but be ready to say out loud "in real code I'd propagate this with ? instead of unwrapping."
✓ Reach for this when
  • You need to chain several fallible/optional steps without a pyramid of nested match
  • You're writing a function boundary and need to decide between panicking, returning Option, or returning Result
  • You're propagating an error from a low-level call up through several layers — that's what ? and From are for
⚠ Watch out for
  • unwrap_or(expensive_call()) runs eagerly — use unwrap_or_else for anything non-trivial
  • .map() on an Option-returning closure gives Option<Option<T>> — you wanted .and_then()
  • ? only works inside a function whose return type is compatible (Result/Option) — you can't use it in fn main() unless main itself returns Result
✗ Common mistakes
  • Sprinkling .unwrap() everywhere and calling it done — always mention the production alternative
  • Defining a custom error enum but forgetting the From impls, then wondering why ? won't compile
  • Using Box<dyn Error> in a library's public API where callers actually need to match on error variants
// Common Code Patterns · Common Traits
Common Traits Reference — Use Cases & Key Methods
Traits are how Rust does polymorphism, and this small set covers ~90% of what shows up in interview code: knowing which one to derive, which one to hand-write, and what the derive actually requires of your fields is the difference between a 30-second answer and a stuck one.
Debug & Display
#[derive(Debug)]
struct Point { x: i32, y: i32 }
println!("{:?}", Point { x: 1, y: 2 });  // Point { x: 1, y: 2 } — programmer-facing, auto-derivable

impl std::fmt::Display for Point {
    fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result {
        write!(f, "({}, {})", self.x, self.y)
    }
}
println!("{}", Point { x: 1, y: 2 });    // (1, 2) — user-facing, ALWAYS hand-written
Debug is virtually always #[derive]d (used for {:?}, panics, and debugging); Display has no sensible default so it's always hand-implemented, and only exists for types with a genuine "user-facing string" representation.
Clone & Copy
#[derive(Clone)]          // gives you .clone() — always safe to derive, works for any type
struct Big { data: Vec<i32> }

#[derive(Clone, Copy)]    // Copy REQUIRES Clone too; assignment/passing becomes implicit-copy, not move
struct Small { x: i32, y: i32 }
#[derive(Copy)] only compiles if every field is itself Copy — a single String or Vec field anywhere in the struct makes Copy impossible to derive.
PartialEq & Eq
#[derive(PartialEq, Eq)]
struct Id(u32);
let a = Id(1); let b = Id(1);
assert!(a == b);   // PartialEq gives you == / !=
PartialEq alone is enough for ==; Eq is a marker adding the guarantee "equality is fully reflexive" (x == x always), required (alongside Hash) to use the type as a HashMap/HashSet key. f64 is PartialEq but NOT Eq, because NaN != NaN.
PartialOrd & Ord
#[derive(PartialEq, Eq, PartialOrd, Ord)]
struct Version { major: u32, minor: u32 }   // compares major FIRST, then minor — field declaration order = sort priority

let mut vs = vec![
    Version { major: 1, minor: 5 },
    Version { major: 2, minor: 0 },
    Version { major: 1, minor: 2 },
];
vs.sort();  // -> [1.2, 1.5, 2.0] — lexicographic by field order
Enables </>/.cmp()/.sort(), and lets the type live in a BinaryHeap or be a BTreeMap key. Reorder the fields in the struct definition to change sort priority — a common "sort by multiple keys" interview trick.
Default
#[derive(Default)]
struct Config { retries: u32, verbose: bool }  // -> Config { retries: 0, verbose: false }

let cfg = Config { retries: 3, ..Default::default() }; // struct-update syntax — override one field
let taken = std::mem::take(&mut cfg_field);        // mem::take relies on Default under the hood
Hash
#[derive(PartialEq, Eq, Hash)]   // Hash needs Eq alongside it to be a valid HashMap/HashSet key
struct UserId(u32);
let mut seen: std::collections::HashSet<UserId> = std::collections::HashSet::new();
seen.insert(UserId(7));
f64/f32 cannot derive Hash (no total equality, thanks to NaN) — if you truly need float-keyed lookups, wrap it in a newtype and hand-implement Hash/Eq using its bit pattern.
From & Into
struct Celsius(f64);
struct Fahrenheit(f64);

impl From<Celsius> for Fahrenheit {
    fn from(c: Celsius) -> Self { Fahrenheit(c.0 * 9.0 / 5.0 + 32.0) }
}
let f = Fahrenheit::from(Celsius(100.0));  // direct call
let f: Fahrenheit = Celsius(100.0).into();  // .into() works for free — blanket impl
Implement From once, get Into automatically — this is also exactly the mechanism the ? operator leans on to auto-convert error types between function boundaries (see the Error Handling section).
TryFrom & TryInto
use std::convert::TryFrom;
let big: i64 = 300;
let small: Result<i32, _> = i32::try_from(big);  // Ok(300) here, but...
let overflow: Result<i8, _> = i8::try_from(big);  // Err(TryFromIntError) — 300 doesn't fit in an i8
The fallible counterpart to From/Into — use for any conversion that can fail, most commonly narrowing integer casts where as would silently truncate instead of erroring.
Deref & DerefMut
struct Wrapper(Vec<i32>);
impl std::ops::Deref for Wrapper {
    type Target = Vec<i32>;
    fn deref(&self) -> &Vec<i32> { &self.0 }
}
let w = Wrapper(vec![1, 2, 3]);
println!("{}", w.len());  // calls Vec::len via deref coercion — no manual w.0.len() needed
This "deref coercion" is the exact mechanism behind Box<T>, Rc<T> acting like T, and String auto-coercing to &str. Only implement it for genuine smart-pointer-like types — abusing Deref for unrelated types is a well-known anti-pattern.
Drop
struct Guard(&'static str);
impl Drop for Guard {
    fn drop(&mut self) { println!("dropping {}", self.0); }
}
{
    let _g = Guard("resource");
    // ... use the resource ...
}  // "dropping resource" printed here, automatically, at end of scope
The foundation of RAII in Rust — file handles, mutex guards, and connection pools all rely on Drop for automatic cleanup with no explicit close() call needed.
Iterator & IntoIterator
struct Countdown(u32);
impl Iterator for Countdown {
    type Item = u32;
    fn next(&mut self) -> Option<u32> {
        if self.0 == 0 { None } else { self.0 -= 1; Some(self.0 + 1) }
    }
}
for n in Countdown(3) { println!("{n}"); }  // 3, 2, 1 — only fn next() had to be written
Implement just next() and you get every adapter (.map(), .filter(), .collect()...) for free. IntoIterator is the separate trait that a plain for x in my_thing actually requires — it's what Vec, HashMap, and ranges all implement to be loop-able.
AsRef & Borrow
fn greet<S: AsRef<str>>(name: S) -> String {
    format!("hello, {}", name.as_ref())
}
greet("world");              // &str works
greet(String::from("world")); // owned String works too
greet(&String::from("world")); // &String works too
Writing fn f<S: AsRef<str>> instead of fn f(s: &str) lets every caller pass whatever string type is convenient without an explicit & or .as_str() — the standard way to make a function ergonomic over "anything string-like".
Send & Sync
// marker traits, no methods — the compiler auto-derives them when every field qualifies
// Send: safe to MOVE this value to another thread
// Sync: safe to SHARE a &T of this value across threads simultaneously

use std::rc::Rc;
fn needs_send<T: Send>(_: T) {}
// needs_send(Rc::new(5));  // ERROR: Rc<T> is neither Send nor Sync (unsynchronized refcount)
You almost never write impl Send for X by hand — the compiler figures it out automatically from your fields. You only think about these traits when something DOESN'T implement them, most famously Rc<T> (use Arc<T> across threads instead).
Operator overloading
#[derive(Debug, Clone, Copy, PartialEq)]
struct Point { x: i32, y: i32 }

impl std::ops::Add for Point {
    type Output = Point;
    fn add(self, other: Point) -> Point {
        Point { x: self.x + other.x, y: self.y + other.y }
    }
}
let p3 = Point { x: 1, y: 2 } + Point { x: 3, y: 4 }; // Point { x: 4, y: 6 }
Same pattern for Sub, Mul, and Index/IndexMut (for custom my_matrix[(row, col)] syntax) — each is just one more trait in std::ops with a single required method.
✓ Reach for this when
  • You need `{:?}` for debugging (derive Debug) vs a real user-facing format (hand-write Display)
  • Your type needs to be a HashMap/HashSet key (PartialEq + Eq + Hash) or sortable/BinaryHeap-able (PartialOrd + Ord)
  • You're writing a conversion function — reach for `impl From` before a bespoke `fn to_x()`
⚠ Watch out for
  • `#[derive(Ord)]` compares fields in DECLARATION order — reorder fields to change sort priority
  • `#[derive(Copy)]` silently fails to compile the moment any field isn't Copy — no partial-Copy
  • Overusing `Deref` on non-smart-pointer types makes method resolution surprising for readers
✗ Common mistakes
  • Trying to derive Eq/Hash on a struct containing an f64 field — won't compile, need a newtype workaround
  • Forgetting Ord requires PartialOrd + Eq + PartialEq all be present/derived together
  • Assuming Rc is thread-safe because Arc "looks the same" — Rc is neither Send nor Sync on purpose
// Common Code Patterns · Smart Pointers
Smart Pointers & Interior Mutability
Smart pointers are how Rust gets you heap allocation, shared ownership, and "mutate through a shared reference" without giving up memory safety — each one trades away a different guarantee (single ownership, compile-time borrow checking, or thread-safety) so you have to pick the right one for the job.
Box<T>
enum List {
    Cons(i32, Box<List>),   // without Box, List would need infinite size (Cons contains a List contains a Cons...)
    Nil,
}
let list = List::Cons(1, Box::new(List::Cons(2, Box::new(List::Nil))));
The standard fix for "recursive type has infinite size" — Box<T> is just a heap pointer with a known, fixed size, so the recursion becomes indirect instead of literally nested inline.
Rc<T>
use std::rc::Rc;
let a = Rc::new(5);
assert_eq!(Rc::strong_count(&a), 1);
let b = Rc::clone(&a);          // cheap — increments a counter, no deep copy
assert_eq!(Rc::strong_count(&a), 2);
drop(b);
assert_eq!(Rc::strong_count(&a), 1);
Single-threaded shared ownership — the underlying value is dropped only once the strong count hits zero. Rc::clone(&a) and a.clone() are equivalent; the explicit form is idiomatic because it visually signals "cheap refcount bump", not a deep clone.
Arc<T>
use std::sync::Arc;
let shared = Arc::new(vec![1, 2, 3]);
let handle = Arc::clone(&shared);
std::thread::spawn(move || { println!("{:?}", handle); });
Same API shape as Rc, but the reference count is updated with atomic operations so it's safe to clone/drop from multiple threads — slightly slower than Rc, so don't reach for it in single-threaded code.
RefCell<T>
use std::cell::RefCell;
let cell = RefCell::new(vec![1, 2]);
cell.borrow_mut().push(3);        // borrow_mut() -> RefMut<Vec<i32>> guard
println!("{:?}", cell.borrow()); // borrow() -> Ref<Vec<i32>> guard

// let _a = cell.borrow_mut();
// let _b = cell.borrow_mut();  // PANICS at runtime: "already borrowed" — not a compile error!
Moves the borrow-checker's aliasing rule (many &T XOR one &mut T) from compile time to runtime — you get interior mutability through a shared &RefCell<T>, at the cost of a possible panic if you violate the rule while a guard is still alive.
Cell<T>
use std::cell::Cell;
let c = Cell::new(5);
c.set(10);
assert_eq!(c.get(), 10);
let old = c.replace(20);   // old = 10, cell now holds 20
Simpler and faster than RefCell, but only works for Copy types — since .get()/.set() always move a whole value in or out, there's never a live reference into the cell to worry about aliasing, so no runtime borrow checks are needed at all.
Weak<T>
use std::rc::{Rc, Weak};
let strong = Rc::new(5);
let weak: Weak<i32> = Rc::downgrade(&strong);  // doesn't bump strong_count, can't keep the value alive

assert!(weak.upgrade().is_some());   // Some(Rc<i32>) while `strong` is still alive
drop(strong);
assert!(weak.upgrade().is_none());   // None — the value is gone, upgrade fails safely
The standard fix for Rc reference cycles (memory leaks): in a parent/child tree, have children hold Weak<Parent> instead of Rc<Parent> so the parent can still be dropped even while children reference it. .upgrade() is the only way to (maybe) get a usable Rc back.
The Rc<RefCell<T>> pattern
let shared_state = Rc::new(RefCell::new(vec![1, 2, 3]));
let handle_a = Rc::clone(&shared_state);
let handle_b = Rc::clone(&shared_state);
handle_a.borrow_mut().push(4);   // both handles see the mutation
handle_b.borrow_mut().push(5);
The canonical "shared, mutable state, single-threaded" combo — a graph node, tree node, or observer list touched from multiple owners. Its multi-threaded equivalent is Arc<Mutex<T>> (see the Concurrency section) — same shape, different synchronization primitive.
When to reach for which
owned, heap-allocated, single owner        -> Box<T>
shared, immutable, single-threaded         -> Rc<T>
shared, immutable, multi-threaded          -> Arc<T>
shared, mutable, single-threaded           -> Rc<RefCell<T>>
shared, mutable, multi-threaded            -> Arc<Mutex<T>>
non-owning ref to break an Rc/Arc cycle    -> Weak<T>
✓ Reach for this when
  • You get "recursive type has infinite size" — wrap the recursive field in Box
  • Multiple owners genuinely need to share the same data — Rc (single-thread) or Arc (multi-thread)
  • You need to mutate through a shared reference — RefCell (or Cell for Copy-only data)
⚠ Watch out for
  • RefCell moves aliasing violations to a runtime panic — no compiler safety net, test your borrow scopes carefully
  • Rc reference cycles (parent -> child -> parent via Rc both ways) leak memory silently, since count never hits zero
  • Arc<Mutex<T>> needs `.lock().unwrap()` every access — forgetting to drop the guard before another lock attempt deadlocks
✗ Common mistakes
  • Using Rc/RefCell across threads (won't even compile — Rc isn't Send) instead of Arc/Mutex
  • Holding two live borrow_mut() guards at once (even briefly) and getting a surprise runtime panic
  • Forgetting Weak::upgrade() returns an Option — treating it like it always succeeds
// Common Code Patterns · Graphs
Graphs — Traversal & Shortest Paths
Graph problems all reduce to a handful of templates once you recognize the shape: adjacency-list build, then DFS/BFS/Dijkstra/DSU/topo-sort in some combination. Memorize these five skeletons cold — nearly every "graph interview question" is one of them wearing a costume.
Adjacency list representation
// unweighted: just neighbor indices
let mut graph: Vec<Vec<usize>> = vec![Vec::new(); n];

// weighted: (neighbor, weight) pairs
let mut wgraph: Vec<Vec<(usize, i32)>> = vec![Vec::new(); n];

fn build_undirected(n: usize, edges: &[(usize, usize)]) -> Vec<Vec<usize>> {
    let mut graph = vec![Vec::new(); n];
    for &(u, v) in edges {
        graph[u].push(v);
        graph[v].push(u); // undirected: BOTH directions!
    }
    graph
}
Gotcha: for a directed graph you only push graph[u].push(v). Forgetting the reverse push on an undirected graph is the single most common graph-setup bug — traversal will silently only ever go "one way."
Depth-first search (recursive)
fn dfs(u: usize, visited: &mut Vec<bool>, graph: &Vec<Vec<usize>>, order: &mut Vec<usize>) {
    visited[u] = true;
    order.push(u);
    for &v in &graph[u] {
        if !visited[v] {
            dfs(v, visited, graph, order);
        }
    }
}
Use for: cycle detection (track a "currently on the recursion stack" set for directed graphs), counting connected components (call dfs from every still-unvisited node), and topological sort — push each node to a result after all its neighbors finish (postorder), then reverse the result.
Breadth-first search with VecDeque
use std::collections::VecDeque;

fn bfs(start: usize, graph: &Vec<Vec<usize>>, visited: &mut Vec<bool>) -> Vec<usize> {
    let mut order = Vec::new();
    let mut queue = VecDeque::new();
    visited[start] = true;
    queue.push_back(start);
    while let Some(u) = queue.pop_front() {
        order.push(u);
        for &v in &graph[u] {
            if !visited[v] {
                visited[v] = true;
                queue.push_back(v);
            }
        }
    }
    order
}
Use for: shortest path in an unweighted graph (the first time BFS reaches a node IS the shortest path to it), level-order exploration (snapshot queue.len() at the top of the loop to know where one "generation" ends), and bipartite checking (2-color nodes as you BFS; any edge connecting two same-colored nodes means it's not bipartite).
Dijkstra's algorithm (BinaryHeap + Reverse)
use std::collections::BinaryHeap;
use std::cmp::Reverse;

fn dijkstra(start: usize, graph: &Vec<Vec<(usize, i32)>>, n: usize) -> Vec<i32> {
    let mut dist = vec![i32::MAX; n];
    dist[start] = 0;
    let mut heap = BinaryHeap::new();
    heap.push(Reverse((0, start)));

    while let Some(Reverse((d, u))) = heap.pop() {
        if d > dist[u] {
            continue; // stale entry -- a shorter path to u was already found
        }
        for &(v, w) in &graph[u] {
            let nd = d + w;
            if nd < dist[v] {
                dist[v] = nd;
                heap.push(Reverse((nd, v)));
            }
        }
    }
    dist
}
Gotcha: BinaryHeap is a max-heap by default — wrapping the tuple in Reverse(...) flips comparisons so the heap pops the smallest distance first. Requires non-negative edge weights (use Bellman-Ford if negatives are possible).
Union-Find / Disjoint Set Union (DSU)
struct DSU {
    parent: Vec<usize>,
    rank: Vec<usize>,
}

impl DSU {
    fn new(n: usize) -> Self {
        DSU { parent: (0..n).collect(), rank: vec![0; n] }
    }

    fn find(&mut self, x: usize) -> usize {
        if self.parent[x] != x {
            self.parent[x] = self.find(self.parent[x]); // path compression
        }
        self.parent[x]
    }

    fn union(&mut self, a: usize, b: usize) -> bool {
        let (ra, rb) = (self.find(a), self.find(b));
        if ra == rb {
            return false; // already connected
        }
        if self.rank[ra] < self.rank[rb] {
            self.parent[ra] = rb;
        } else if self.rank[ra] > self.rank[rb] {
            self.parent[rb] = ra;
        } else {
            self.parent[rb] = ra;
            self.rank[ra] += 1;
        }
        true
    }
}
Use for: cycle detection in an undirected graph — if union(u, v) returns false for an edge, u and v were already connected, so this edge closes a cycle. Also the backbone of Kruskal's MST: sort edges by weight, add each edge whose endpoints' union() returns true.
Topological sort — Kahn's algorithm
use std::collections::VecDeque;

fn topo_sort(n: usize, graph: &Vec<Vec<usize>>) -> Option<Vec<usize>> {
    let mut indegree = vec![0; n];
    for u in 0..n {
        for &v in &graph[u] {
            indegree[v] += 1;
        }
    }
    let mut queue: VecDeque<usize> = (0..n).filter(|&u| indegree[u] == 0).collect();
    let mut order = Vec::new();
    while let Some(u) = queue.pop_front() {
        order.push(u);
        for &v in &graph[u] {
            indegree[v] -= 1;
            if indegree[v] == 0 {
                queue.push_back(v);
            }
        }
    }
    if order.len() == n {
        Some(order)
    } else {
        None // fewer than n nodes processed -- the graph has a cycle
    }
}
Beyond the basics: this doubles as a free cycle detector. Nodes stuck in a cycle never reach in-degree 0, so if order.len() != n at the end, the graph is not a DAG — return None instead of a bogus partial ordering.
✓ Reach for this when
  • Modeling relationships or networks (dependency graphs, maps, social graphs)
  • You need shortest path — BFS for unweighted, Dijkstra for weighted non-negative
  • You need to group/merge items into connected sets (DSU)
  • You need a valid processing order under dependency constraints (topo sort)
⚠ Watch out for
  • Recursive DFS can stack-overflow on very deep/large graphs — use an explicit stack if size is unbounded
  • Dijkstra assumes non-negative weights — negative edges need Bellman-Ford instead
  • Undirected edges must be pushed in both directions or traversal silently misses half the graph
✗ Common mistakes
  • Marking a node visited AFTER popping instead of before pushing to the BFS queue — causes duplicate enqueues
  • Skipping the "stale entry" check in Dijkstra — still correct, but wastes time reprocessing outdated heap entries
  • Using DSU without path compression or union-by-rank on large inputs — degrades toward O(n) per operation
// Common Code Patterns · Linked Lists
Linked Lists — Ownership-Safe Patterns
Linked lists are where Rust's ownership model actually fights you — you can't have two &mut references into the same list, and you can't just null out a pointer C-style. The fix is always the same handful of moves: .take() to pull a value out of an Option field leaving None behind, and restructuring loops around ownership transfer instead of aliasing.
Defining ListNode
pub struct ListNode {
    pub val: i32,
    pub next: Option<Box<ListNode>>,
}

impl ListNode {
    fn new(val: i32) -> Self {
        ListNode { val, next: None }
    }
}
Box<ListNode> is the heap-owned next node — without it, ListNode would be infinitely sized (a struct can't contain itself directly). Option is what marks the end of the list: None means "no more nodes," standing in for a null pointer without any actual nullability.
Building a list from a Vec
fn from_vec(values: Vec<i32>) -> Option<Box<ListNode>> {
    let mut head = None;
    for &v in values.iter().rev() {
        let mut node = Box::new(ListNode::new(v));
        node.next = head;
        head = Some(node);
    }
    head
}
Why reversed: building front-to-back would require holding a mutable reference to the "current tail" while also owning the whole chain — a borrow-checker headache. Iterating the source Vec in reverse and always prepending sidesteps that entirely: no nested traversal, no dangling references.
Reversing iteratively
fn reverse_list(mut head: Option<Box<ListNode>>) -> Option<Box<ListNode>> {
    let mut prev = None;
    while let Some(mut node) = head.take() {
        head = node.next.take();
        node.next = prev;
        prev = Some(node);
    }
    prev
}
The canonical pattern: .take() replaces the field with None and hands you the owned value, so you never have two things pointing at the same node at once. No recursion, no unsafe, no fighting the borrow checker — just a prev/current pointer-swap done through ownership moves instead of pointer reassignment.
Detecting a cycle (Floyd's Tortoise and Hare)
fn has_cycle(head: &Option<Box<ListNode>>) -> bool {
    let mut slow = head;
    let mut fast = head;
    loop {
        fast = match fast {
            Some(n) => match &n.next {
                Some(n2) => &n2.next,
                None => return false,
            },
            None => return false,
        };
        slow = match slow {
            Some(n) => &n.next,
            None => return false,
        };
        if let (Some(s), Some(f)) = (slow, fast) {
            if std::ptr::eq(s.as_ref(), f.as_ref()) {
                return true;
            }
        }
    }
}
Why ptr::eq, not ==: ListNode doesn't derive PartialEq, and even if it did, == would compare values, not identity — two different nodes could coincidentally hold the same val. Walking with .as_ref() lets both pointers advance through shared (non-owning) references, so nothing is moved out of the list while merely checking it.
Merging two sorted lists
fn merge_two_sorted(
    l1: Option<Box<ListNode>>,
    l2: Option<Box<ListNode>>,
) -> Option<Box<ListNode>> {
    let mut dummy = Box::new(ListNode::new(0));
    let mut tail = &mut dummy;
    let (mut l1, mut l2) = (l1, l2);

    while l1.is_some() && l2.is_some() {
        let take_l1 = l1.as_ref().unwrap().val <= l2.as_ref().unwrap().val;
        let mut next_node = if take_l1 { l1.take().unwrap() } else { l2.take().unwrap() };
        if take_l1 { l1 = next_node.next.take(); } else { l2 = next_node.next.take(); }
        next_node.next = None;
        tail.next = Some(next_node);
        tail = tail.next.as_mut().unwrap();
    }
    tail.next = l1.or(l2);
    dummy.next
}
The dummy-head trick: a throwaway ListNode::new(0) at the front means the merge loop never needs a special case for "is this the first node I'm attaching?" — you always just do tail.next = Some(...) and advance tail. Return dummy.next, discarding the dummy itself.
Rust-specific pitfalls
// 1. Can't mutate through a shared &reference -- need ownership or `mut`
fn bad(node: &ListNode) { /* node.next = None; // compile error */ }
fn good(node: &mut Option<Box<ListNode>>) {
    if let Some(n) = node { n.next = None; } // needs &mut, or .take() ownership
}

// 2. Can't compare boxed nodes for identity with `==` -- need ptr::eq
// (`==` compares .val by value, not "is this literally the same node")

// 3. Nodes aren't Copy, and cloning is expensive -- each node is a separate
// heap allocation, so `list.clone()` deep-copies the ENTIRE chain
These three bite nearly everyone new to Rust linked lists at least once. Internalizing "ownership moves, not pointer copies" is 90% of getting comfortable with this data structure in Rust.
✓ Reach for this when
  • The interviewer explicitly gives you a ListNode-shaped problem (reverse, merge, cycle, etc.)
  • You need O(1) insertion/removal at a known position without shifting elements
  • Sequential access is all you need — no random indexing required
⚠ Watch out for
  • Deeply recursive traversal/drop of a very long list can blow the stack — prefer iterative solutions
  • Forgetting to null out a moved node's stale next pointer can accidentally re-attach an old sublist
  • RefCell<Rc<...>>-based lists (needed for genuinely doubly-linked structures) reintroduce runtime borrow checks — avoid unless the problem truly requires shared mutable ownership
✗ Common mistakes
  • Trying to hold two &mut references into the same list at once (won't compile — restructure around .take())
  • Using == instead of std::ptr::eq when the goal is identity, not value equality
  • Forgetting the dummy-head node when merging/building lists and special-casing the first element instead
// Common Code Patterns · Trees
Trees & Binary Trees
Tree problems are almost always "write the right recursive shape." Once you have the three DFS orders, level-order BFS, and the LCA/balance/BST templates memorized, most tree questions become "which of these do I combine, and what do I return from the recursion" rather than a blank-page problem.
Defining TreeNode
pub struct TreeNode {
    pub val: i32,
    pub left: Option<Box<TreeNode>>,
    pub right: Option<Box<TreeNode>>,
}

impl TreeNode {
    fn new(val: i32) -> Self {
        TreeNode { val, left: None, right: None }
    }
}
DFS: preorder / inorder / postorder
fn preorder(node: &Option<Box<TreeNode>>, out: &mut Vec<i32>) {
    if let Some(n) = node {
        out.push(n.val);          // root
        preorder(&n.left, out);  // left
        preorder(&n.right, out); // right
    }
}

fn inorder(node: &Option<Box<TreeNode>>, out: &mut Vec<i32>) {
    if let Some(n) = node {
        inorder(&n.left, out);   // left
        out.push(n.val);          // root
        inorder(&n.right, out);  // right
    }
}

fn postorder(node: &Option<Box<TreeNode>>, out: &mut Vec<i32>) {
    if let Some(n) = node {
        postorder(&n.left, out);  // left
        postorder(&n.right, out); // right
        out.push(n.val);           // root
    }
}
Key fact: running inorder on a BST always yields values in sorted order — this is the fastest way to validate a BST or convert one to a sorted array.
BFS: level-order traversal with VecDeque
use std::collections::VecDeque;

fn level_order(root: &Option<Box<TreeNode>>) -> Vec<Vec<i32>> {
    let mut result = Vec::new();
    let mut queue: VecDeque<&Box<TreeNode>> = VecDeque::new();
    if let Some(n) = root { queue.push_back(n); }

    while !queue.is_empty() {
        let mut level = Vec::new();
        for _ in 0..queue.len() {  // snapshot len BEFORE the loop -- that's one full level
            let node = queue.pop_front().unwrap();
            level.push(node.val);
            if let Some(l) = &node.left { queue.push_back(l); }
            if let Some(r) = &node.right { queue.push_back(r); }
        }
        result.push(level);
    }
    result
}
This is the standard building block for depth calculation, "is the tree complete" checks, and zigzag/spiral traversal (just reverse alternate levels before pushing them into result).
Lowest Common Ancestor (LCA)
fn lowest_common_ancestor<'a>(
    node: &'a Option<Box<TreeNode>>,
    p: i32,
    q: i32,
) -> Option<&'a TreeNode> {
    let n = node.as_deref()?;
    if n.val == p || n.val == q {
        return Some(n); // found one of the targets -- it can't be "below" itself
    }
    let left = lowest_common_ancestor(&n.left, p, q);
    let right = lowest_common_ancestor(&n.right, p, q);
    match (left, right) {
        (Some(_), Some(_)) => Some(n), // p and q on DIFFERENT sides -- n is the LCA
        (Some(l), None) => Some(l),
        (None, Some(r)) => Some(r),
        (None, None) => None,
    }
}
The classic pattern: if the current node is one of the targets, return it immediately; otherwise recurse both sides and let a non-None result on both sides identify the split point — that's the LCA. Otherwise just propagate whichever side found something.
Checking if a tree is height-balanced
fn balanced_height(node: &Option<Box<TreeNode>>) -> Option<i32> {
    match node {
        None => Some(0),
        Some(n) => {
            let lh = balanced_height(&n.left)?;   // `?` short-circuits on None
            let rh = balanced_height(&n.right)?;
            if (lh - rh).abs() > 1 {
                None // imbalance found -- bail out immediately
            } else {
                Some(1 + lh.max(rh))
            }
        }
    }
}

fn is_balanced(root: &Option<Box<TreeNode>>) -> bool {
    balanced_height(root).is_some()
}
Why Option<i32> and not just i32: encoding "already found an imbalance" as None lets the ? operator propagate the failure straight up through every level of recursion above it, avoiding a naive O(n²) solution that recomputes subtree heights over and over.
BST search and insert
fn search_bst<'a>(node: &'a Option<Box<TreeNode>>, target: i32) -> Option<&'a TreeNode> {
    let n = node.as_deref()?;
    if target == n.val {
        Some(n)
    } else if target < n.val {
        search_bst(&n.left, target)   // smaller -- go left
    } else {
        search_bst(&n.right, target)  // bigger -- go right
    }
}

fn insert_bst(node: &mut Option<Box<TreeNode>>, val: i32) {
    match node {
        None => *node = Some(Box::new(TreeNode::new(val))), // rewrite the None leaf in place
        Some(n) => {
            if val < n.val {
                insert_bst(&mut n.left, val);
            } else if val > n.val {
                insert_bst(&mut n.right, val);
            }
        }
    }
}
Taking &mut Option<Box<TreeNode>> (instead of returning a new tree) is what lets insert_bst mutate a None leaf directly via *node = Some(...) — no need to rebuild the path back to the root.
Max depth / diameter
fn max_depth(node: &Option<Box<TreeNode>>) -> i32 {
    match node {
        None => 0,
        Some(n) => 1 + max_depth(&n.left).max(max_depth(&n.right)),
    }
}
Diameter uses the same recursive shape as max_depth, but instead of returning the max height at the very top, it tracks left_height + right_height at every node along the way (updating a running "best" via a mutable accumulator) — the longest path doesn't have to pass through the root.
✓ Reach for this when
  • Data has a natural hierarchical/nested shape (file systems, ASTs, DOM, org charts)
  • You need ordered operations in O(log n) — BST search/insert when reasonably balanced
  • The problem statement literally hands you a TreeNode
⚠ Watch out for
  • An unbalanced BST degrades to O(n) — this packet's BST here does no self-balancing (no AVL/red-black rotations)
  • Recursive traversal of a very deep/skewed tree can blow the stack — convert to an explicit-stack iterative version if needed
  • Off-by-one snapshotting queue.len() at the wrong point breaks level-order grouping
✗ Common mistakes
  • Recomputing subtree height separately for every node when checking balance (O(n²)) instead of returning height + validity together
  • Forgetting inorder-on-a-BST-is-sorted, and hand-rolling a sort where one isn't needed
  • Confusing preorder/postorder when the problem actually wants "process children before parent" (postorder) vs. "process parent first" (preorder)
// Common Code Patterns · Algorithmic Idioms
Common Algorithmic Patterns
These templates cut across data structures — they're the "shape of the solution" you reach for once you've recognized the problem type, independent of whether it's an array, string, or list. Recognizing which pattern applies is usually 80% of solving a LeetCode-style question in an interview.
Two pointers — sorted pair sum
fn two_sum_sorted(nums: &[i32], target: i32) -> Option<(usize, usize)> {
    let (mut left, mut right) = (0, nums.len() - 1);
    while left < right {
        let sum = nums[left] + nums[right];
        if sum == target {
            return Some((left, right));
        } else if sum < target {
            left += 1;   // sum too small -- grow it
        } else {
            right -= 1;  // sum too big -- shrink it
        }
    }
    None
}
Only works because the input is sorted — moving left forward strictly increases the sum, moving right back strictly decreases it, so the search space shrinks monotonically. O(n) instead of the O(n²) brute-force pair check.
Sliding window (variable size)
use std::collections::HashSet;

fn longest_unique_substring(s: &str) -> usize {
    let chars: Vec<char> = s.chars().collect();
    let mut seen = HashSet::new();
    let mut left = 0;
    let mut max_len = 0;
    for right in 0..chars.len() {
        while seen.contains(&chars[right]) {
            seen.remove(&chars[left]); // shrink from the left until the violation clears
            left += 1;
        }
        seen.insert(chars[right]);
        max_len = max_len.max(right - left + 1);
    }
    max_len
}
The window only ever expands via right and shrinks via left — each index enters and leaves the window at most once, giving O(n) total instead of the naive O(n²) "check every substring."
Prefix sums
fn build_prefix_sums(nums: &[i32]) -> Vec<i32> {
    let mut prefix = vec![0; nums.len() + 1];
    for i in 0..nums.len() {
        prefix[i + 1] = prefix[i] + nums[i];
    }
    prefix
}

fn range_sum(prefix: &[i32], l: usize, r: usize) -> i32 {
    prefix[r + 1] - prefix[l] // inclusive [l, r], O(1) per query
}
The trade: O(n) one-time build cost buys O(1) range-sum queries forever after — versus the naive approach of summing nums[l..=r] fresh each time, which is O(n) per query. Pays off the moment you have more than a handful of queries.
Fast/slow pointers — find the middle
fn find_middle_index(nums: &[i32]) -> usize {
    let mut slow = 0;
    let mut fast = 0;
    while fast + 1 < nums.len() && fast + 2 < nums.len() {
        slow += 1;
        fast += 2;
    }
    slow
}
Same two-speed-pointer idea as linked-list cycle detection (see the Linked Lists section) — fast moves twice as fast as slow, so when fast reaches the end, slow is sitting exactly at the midpoint, found in a single pass with no length pre-computation.
Binary search on the answer
// search over POSSIBLE ANSWERS, not input positions -- works whenever
// can_do(x) is false...false...true...true as x increases (monotonic).
// e.g. "minimum ship capacity to deliver all packages within D days":
fn min_capacity(needs: &[i32], can_do: impl Fn(i32) -> bool) -> i32 {
    let mut lo = *needs.iter().max().unwrap();  // smallest capacity that could ever work
    let mut hi = needs.iter().sum::<i32>();      // definitely enough capacity
    while lo < hi {
        let mid = lo + (hi - lo) / 2;
        if can_do(mid) {
            hi = mid;       // mid works -- try to shrink further
        } else {
            lo = mid + 1;   // mid too small -- need more capacity
        }
    }
    lo // converges on the smallest x where can_do(x) first becomes true
}
The shape is what matters, not the specific can_do: binary search collapses lo..hi onto the exact boundary between "impossible" and "possible" in O(log(range)) calls to a — potentially expensive — feasibility check, instead of linearly testing every candidate answer.
Backtracking template — generate all subsets
fn subsets(nums: &[i32]) -> Vec<Vec<i32>> {
    let mut result = Vec::new();
    let mut current = Vec::new();
    backtrack(0, nums, &mut current, &mut result);
    result
}

fn backtrack(start: usize, nums: &[i32], current: &mut Vec<i32>, result: &mut Vec<Vec<i32>>) {
    result.push(current.clone()); // every prefix state along the way is itself a valid subset
    for i in start..nums.len() {
        current.push(nums[i]);                    // choose
        backtrack(i + 1, nums, current, result); // explore
        current.pop();                            // un-choose
    }
}
The "choose, explore, un-choose" skeleton is the universal backtracking shape — swap the base case and choice set to get permutations, combinations, N-Queens, or word search instead of subsets.
Monotonic stack — next greater element
fn next_greater_element(nums: &[i32]) -> Vec<i32> {
    let mut result = vec![-1; nums.len()];
    let mut stack: Vec<usize> = Vec::new(); // indices, values kept DECREASING bottom-to-top
    for i in 0..nums.len() {
        while let Some(&top) = stack.last() {
            if nums[top] < nums[i] {
                result[top] = nums[i]; // current element dominates the stacked index
                stack.pop();
            } else {
                break;
            }
        }
        stack.push(i);
    }
    result
}
Each index is pushed once and popped at most once, so despite the nested-looking loop this is O(n) overall. The stack always holds indices whose "next greater" hasn't been found yet, in decreasing value order.
✓ Reach for this when
  • Two pointers / sliding window: input is sorted (or you're scanning contiguous subarrays/substrings)
  • Prefix sums: many range-sum queries against a static array
  • Binary search on the answer: the problem asks for a minimum/maximum feasible value and feasibility is monotonic
  • Backtracking: the problem says "all subsets/permutations/combinations"
  • Monotonic stack: the problem mentions "next greater/smaller element" or "span until it drops"
⚠ Watch out for
  • Sliding window constraints that aren't simply "shrink until valid" — some variants need a HashMap of counts, not just a HashSet
  • Off-by-one errors in prefix sums (remember the `+1`-length array trick to avoid special-casing index 0)
  • Binary-search-on-answer bugs almost always come from an inconsistent `lo`/`hi` update — pick hi = mid vs lo = mid + 1 based on which direction "shrinks toward the true boundary"
✗ Common mistakes
  • Recomputing a sliding-window's sum/count from scratch each iteration instead of incrementally updating it
  • Backtracking without popping the last choice (`current.pop()`) — silently corrupts every subsequent branch
  • Building a monotonic stack that keeps increasing values when the problem needs decreasing (or vice versa) — always sanity check against a 3-element example first
// Common Code Patterns · Concurrency
Concurrency Quick Patterns
This is the fast-reach cheat-sheet layer, not the deep dive — full concurrency coverage (memory ordering, Send/Sync, more advanced synchronization) lives elsewhere in this packet. Here's just the "what do I type" muscle memory for the patterns that come up constantly.
Spawning threads and joining
let handle = std::thread::spawn(move || {
    2 + 2 // whatever this closure returns becomes the JoinHandle's output
});
let result = handle.join().unwrap(); // blocks until the thread finishes; Result<T, Box<dyn Any>>
.join() returns an Err only if the thread panicked — always decide deliberately whether .unwrap() (propagate the panic) or graceful handling is right for your use case.
Arc<Mutex<T>> shared counter
use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));
let mut handles = Vec::new();

for _ in 0..8 {
    let counter = Arc::clone(&counter); // bump the refcount, not a deep copy
    handles.push(thread::spawn(move || {
        let mut guard = counter.lock().unwrap(); // blocks until the lock is free
        *guard += 1;
    }));
}
for h in handles { h.join().unwrap(); }
This is the standard "share mutable state safely across threads" pattern: Arc gives shared ownership across threads, Mutex gives exclusive access to the value inside it. The lock is automatically released when guard goes out of scope.
mpsc channels
use std::sync::mpsc;
use std::thread;

let (tx, rx) = mpsc::channel();

for p in 0..3 {
    let tx = tx.clone();  // each producer gets its own cloned Sender
    thread::spawn(move || {
        for i in 0..5 { tx.send(p * 100 + i).unwrap(); }
    });
}
drop(tx); // drop the ORIGINAL sender too, or the channel never sees zero senders

let received: Vec<i32> = rx.iter().collect(); // blocks, then ends once every Sender is dropped
Gotcha: the classic producer/consumer pattern — multiple cloned Sender halves feed one Receiver. Iterating rx only terminates once every Sender clone (including the original) has been dropped; forgetting to drop the original tx after spawning is a common cause of a hang.
RwLock<T> vs Mutex<T>
use std::sync::RwLock;

let data = RwLock::new(vec![1, 2, 3]);
{
    let r1 = data.read().unwrap(); // many readers can hold this concurrently
    let r2 = data.read().unwrap();
    println!("{:?} {:?}", r1, r2);
}
{
    let mut w = data.write().unwrap(); // exclusive -- blocks out ALL readers and writers
    w.push(4);
}
RwLock allows many concurrent readers or one exclusive writer — worth it when reads vastly outnumber writes. Mutex is simpler and always exclusive, reader or not. Watch for write-starvation: on some platforms/implementations a constant stream of readers can indefinitely delay a waiting writer.
When to reach beyond std
// scoped threads (stable since 1.63) let you borrow non-'static data
// across threads safely, with NO Arc needed -- the scope guarantees
// every spawned thread finishes before the borrow ends.
let data = vec![1, 2, 3];
std::thread::scope(|s| {
    s.spawn(|| println!("{:?}", data)); // borrows `data` directly, no clone/Arc
});
Beyond what std comfortably covers: rayon for data-parallel iterators (parallelize a .map()/.filter() chain almost for free), and tokio for async I/O-bound concurrency (thousands of concurrent connections without one OS thread each).
✓ Reach for this when
  • CPU-bound work that can be split across cores — spawn threads and join
  • Shared mutable state across threads — Arc<Mutex<T>> (or RwLock if reads dominate)
  • Producer/consumer pipelines — mpsc channels
  • Borrowing local (non-'static) data across threads without cloning — scoped threads
⚠ Watch out for
  • Holding a Mutex guard longer than necessary — serializes work that could otherwise run in parallel
  • Forgetting to drop the original Sender — the channel's receiver iterator will never terminate
  • RwLock write-starvation under heavy read contention on some platforms
✗ Common mistakes
  • Forgetting move on a thread closure that needs to own captured variables — won't compile, but the fix is easy to miss under pressure
  • Calling .lock().unwrap() twice in the same scope on the same Mutex — deadlocks instantly (a single thread can't reacquire a lock it already holds)
  • Reaching for Arc<Mutex<T>> when scoped threads would let you just borrow the data directly
