TH1 · Multi-Tenant Billing & Invoices API
2–3 days Medium axum Postgres multi-tenant idempotency

You are building the billing core for a B2B SaaS called Ledgerly. Customers are organizations (tenants). Each org has members, subscription plans, usage meters, and invoices. Finance wants a clean HTTP API that other internal services can call; support wants auditability; engineering wants something that will not double-charge when a webhook retries.

The product brief is deliberately incomplete on edge cases (proration, tax, dunning). You are expected to make reasonable defaults, document them, and keep the domain model honest. Prefer an axum-style service with typed errors and a real database (Postgres or SQLite for the take-home).

Do not build a full Stripe clone. Focus on tenants, customers, invoices, line items, idempotent payment capture, and list/filter endpoints that feel production-ready.

Functional requirements
  • CRUD for Organization, Customer, Invoice, and invoice line items; invoices belong to a customer within an org.
  • Auth: bearer API keys scoped to an org; every request must be tenant-isolated (no cross-tenant reads/writes).
  • Idempotent POST /v1/invoices/{id}/pay via Idempotency-Key header; replay returns the original result.
  • Invoice lifecycle: draft → open → paid | void; illegal transitions return structured 409/422 errors.
  • List endpoints with cursor pagination, filter by status/created_at, and stable sort order.
  • OpenAPI (or equivalent) documenting request/response schemas and error shapes.
Non-functional requirements
  • All money as integer minor units + currency code (no floating point for amounts).
  • Request IDs in logs; structured JSON logging; health and readiness endpoints.
  • Migrations checked into repo; tests cover happy path + idempotency + tenant isolation.
  • p95 latency target for read endpoints under light load documented (even if measured locally).
Suggested milestones
  • Day 1: schema + migrations + org/customer CRUD + auth middleware.
  • Day 2: invoices, state machine, pay endpoint with idempotency store.
  • Day 3: pagination/filters, OpenAPI, integration tests, README + runbook notes.
Deliverables checklist
  • README with architecture diagram (ASCII OK), setup, env vars, sample curl flows.
  • Runnable HTTP API + DB migrations + seed script.
  • Automated tests (unit + at least a few HTTP integration tests).
  • Optional: Docker Compose for API + Postgres.
✓ Strong submission
  • Clear tenant boundary in DB + middleware
  • Correct idempotency under concurrent retries
  • Typed domain errors mapped to HTTP
  • Honest tradeoff notes in README
⚠ Stretch goals
  • Usage metering + invoice generation job
  • Webhook outbox for invoice.paid
  • Soft deletes + audit log table
✗ Evaluation red flags
  • Floats for money
  • No tenant checks on queries
  • Idempotency only in-memory / lost on restart
  • Giant god-handler with no modules
Rubric focus
Domain modeling, API ergonomics, correctness of idempotency and tenancy, Rust error handling style, and whether the candidate ships something an interviewer could run in under 10 minutes.

TH2 · Event-Sourced Task / Workflow Service
5–7 days Hard axum event sourcing CQRS-lite

Flowboard is an internal workflow product: users create tasks, assign them, comment, and transition status through a configurable board. Compliance asked for a full history of who changed what and when — not just the latest row.

Build a service where the write path appends domain events to an append-only log, and read models are projections. You may keep projections in the same database for the take-home. The point is to demonstrate event modeling, optimistic concurrency, and rebuildable state — not to invent Kafka.

Expose a REST (or JSON-over-HTTP) API for commands and queries. Include a way to rebuild a projection from events for a single aggregate or for the whole store.

Functional requirements
  • Commands: create task, assign, comment, transition status, archive; each produces one or more events.
  • Optimistic concurrency via expected version / stream revision; conflicts return 409.
  • Query: current task view, task history (event stream), list board with filters.
  • Admin: rebuild projection(s) from event store; document how you detect projection lag.
  • At least one async consumer path (same process OK) that updates a read model after append.
Non-functional requirements
  • Events immutable once written; schema version field on every event envelope.
  • Crash safety: restarting mid-projection must not corrupt read models (at-least-once + upsert OK).
  • Deterministic rebuild: same events → same projection content.
  • Bench or timing notes for append + rebuild of N events (e.g. 10k).
Suggested milestones
  • Phase 1: event envelope + store + command handlers for one aggregate.
  • Phase 2: projection worker + query API + concurrency tests.
  • Phase 3: rebuild tooling, schema versioning notes, load smoke test.
  • Phase 4: polish OpenAPI, failure modes in README, optional snapshotting.
Deliverables checklist
  • README explaining event types, concurrency model, and rebuild procedure.
  • HTTP API + persistence + tests including conflict cases.
  • Script or CLI subcommand to rebuild projections.
  • Optional: Docker Compose; metrics for append/project latency.
✓ Strong submission
  • Clean event vocabulary
  • Real optimistic concurrency
  • Rebuild path actually works
  • At-least-once projection handled
⚠ Stretch goals
  • Periodic snapshots
  • SSE/WebSocket live board updates
  • Multi-aggregate process manager
✗ Evaluation red flags
  • Events mutable / update-in-place
  • “Event sourcing” that is just an audit table after CRUD
  • No conflict handling
  • Projection only correct if never restarted
Rubric focus
Event modeling maturity, concurrency correctness, operational rebuild story, and whether CQRS boundaries are intentional rather than accidental dual writes.

TH4 · Embedded Key-Value Store with WAL
5–7 days Hard WAL storage durability

Build a small embedded KV engine (library + CLI) inspired by Bitcask/LMDB-lite ideas — not a wrapper around RocksDB. The selling point is crash-safe durability via a write-ahead log and a clear recovery procedure.

Keys and values are arbitrary bytes. Support get/put/delete, range scan (lexicographic), and controlled compaction or log recycling. Interviewers care about fsync policy, checksums, and what happens if power fails after WAL append but before memtable flush.

Functional requirements
  • put, get, delete, scan(start, end) with documented semantics for tombstones.
  • WAL append before acknowledging durable writes; configurable sync mode (none / batch / each).
  • Recovery rebuilds in-memory index (or on-disk index) from WAL + data files after crash.
  • Compaction or segment merge that reclaims space from deleted/overwritten keys.
  • CLI: put/get/delete/scan/compact/stats; library API usable from tests.
Non-functional requirements
  • Checksum each WAL record; detect torn writes on recovery.
  • Document durability guarantees per sync mode; never claim stronger than implemented.
  • Crash-injection or fault tests (kill process between steps) strongly preferred.
  • Basic benches: sequential put, random get, scan throughput.
Suggested milestones
  • Phase 1: WAL format + memtable + get/put recovery.
  • Phase 2: delete/tombstones + scan + sync modes.
  • Phase 3: compaction + stats + crash tests + benches.
  • Phase 4: README durability section + optional mmap read path.
Deliverables checklist
  • Rust library + CLI, file format spec in README, tests, bench notes.
  • Optional: hexdump examples of on-disk records.
✓ Strong submission
  • Honest sync/durability docs
  • Recovery from torn WAL
  • Space reclamation works
  • Property/crash tests
⚠ Stretch goals
  • Prefix compression
  • Bloom filter for gets
  • Multi-threaded readers
✗ Evaluation red flags
  • JSON lines file called a “WAL” with no recovery design
  • Silent data loss on crash
  • Wrapping RocksDB / sled as the whole submission
Rubric focus
Storage correctness under failure, clarity of on-disk format, and engineering judgment about fsync cost vs durability — classic systems interview signal in Rust shop take-homes.

TH7 · Durable Distributed Job Queue
5–7 days Hard queues workers at-least-once

Build Jobforge: a Redis/Sidekiq-inspired job queue in Rust. Producers enqueue jobs; workers lease them with visibility timeouts; failed jobs retry with backoff; dead-letter after N tries.

Single-node durable store is fine (Postgres/SQLite); demonstrate multiple worker processes competing safely. Emphasize lease fencing, idempotent handlers, and observability of queue depth/lag.

Functional requirements
  • Enqueue with queue name, payload JSON, delay, priority (at least two levels).
  • Lease/claim API with visibility timeout; heartbeat/extend; ack/nack.
  • Automatic requeue when lease expires; retry counts + exponential backoff + DLQ.
  • Worker binary with pluggable handler registry; graceful shutdown drains in-flight leases.
  • Admin: list queues, peek DLQ, requeue from DLQ, metrics endpoint.
Non-functional requirements
  • Safe under concurrent workers (no double-ack corruption; document at-least-once delivery).
  • Durability across broker restart; integration test with two worker processes.
  • Metrics: depth, oldest age, lease expiries, processed/failed rates.
Suggested milestones
  • Day 1–2: schema + enqueue/claim/ack.
  • Day 3–4: lease expiry sweeper + retries + DLQ.
  • Day 5–6: worker runtime + metrics + multi-worker tests.
  • Day 7: README ops guide + failure mode matrix.
Deliverables checklist
  • Broker service and/or library, worker binary, Compose optional, tests, metrics notes.
✓ Strong submission
  • Correct lease expiry
  • Multi-worker tests
  • Clear delivery semantics
  • Graceful shutdown
⚠ Stretch goals
  • Delayed schedules / cron
  • Exactly-once via outbox + handler keys
  • Priority starvation prevention
✗ Evaluation red flags
  • SELECT without row locks / skip-locked
  • Lost jobs on worker crash
  • Infinite retry storms
Rubric focus
Distributed correctness under failure, operational metrics, and pragmatic delivery guarantees — extremely common in backend Rust hiring loops.
