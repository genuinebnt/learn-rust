// OS 01
Processes, Address Spaces, Threads vs Tasks
Questions & model answers
Q1What is a process? What lives in its address space, and why do interviewers care?▼ answer
Model answer
A process is an OS abstraction for a running program: a private virtual address space, one or more threads of execution, open file descriptors, credentials, and scheduling/accounting state. The address space typically holds text (code), data/BSS, heap, stack(s), and memory-mapped regions (shared libs, mmap files). Isolation is the point — one process cannot casually read another's memory without explicit IPC/shared memory. Interviewers listen for: process = isolation + resources; thread = execution within that space; crash/segfault kills the process (shared fate), not just one logical "request." In Rust services, one binary is usually one process (or a few workers via fork/supervisor); Tokio tasks are not processes.
Q2Contrast OS threads and Tokio tasks. What is shared, what is scheduled, and when do you need a real thread?▼ answer
Model answer
An OS thread is a kernel-schedulable entity with its own stack and CPU context; the kernel can preempt it, migrate it across cores, and block it in syscalls. A Tokio task is a user-space future polled by a runtime on a pool of OS worker threads — cooperative at .await points, cheap to spawn (thousands–millions), and not visible to the kernel as separate threads. Tasks on the same worker share that thread's stack only while running; each task has its own future state machine heap allocation. Use a real thread / spawn_blocking when work is CPU-heavy without yield points, or when calling blocking syscalls/FFI that would stall the worker. Saying "async is free parallelism" is a trap — async multiplexes I/O concurrency; CPU parallelism still needs cores + non-blocking or properly offloaded work.
Q3What does fork vs clone/thread creation share? Why is forking risky in a multi-threaded Rust process?▼ answer
Model answer
Historically fork duplicates the process; modern Linux threads are clone with shared VM/files. After fork in a multi-threaded process, only the calling thread exists in the child — other threads vanish mid-critical-section, so mutexes can be left locked forever (classic deadlock after fork). Rust/Tokio services almost never fork for concurrency; prefer std::process::Command for subprocesses, or separate processes from a supervisor. If you must fork (e.g. prefork servers), do it before creating threads, or use posix_spawn / carefully designed single-threaded windows. Interview signal: know fork+threads is a footgun, not just "copy the process."
Q4Scenario: a Tokio service has 50k concurrent connections but only ~8 OS threads. How can that work, and what breaks it?▼ answer
Model answer
Connections are mostly waiting on I/O. Each connection is a task; the reactor (epoll/kqueue) wakes tasks when sockets are ready; workers poll ready tasks. At any instant only a handful of tasks run on the ~8 threads. It breaks when: (1) a task blocks the worker (sync mutex across .await, heavy CPU, blocking std::fs/std::net), (2) you hold a runtime lock while doing slow work, (3) you spawn unbounded CPU work without a blocking pool. Fixes: spawn_blocking, tokio::sync async mutexes when held across await, bound concurrency with a semaphore, separate CPU thread pools. Senior answer names "cooperative scheduling + readiness" and the "don't block the runtime" rule explicitly.
Q5When would you choose multi-process over multi-threaded / async in a Rust backend?▼ answer
Model answer
Prefer processes when you need fault isolation (a segfault/OOM in one worker must not kill all traffic), stronger security boundaries (separate privileges, seccomp profiles), or to work around global allocator / FFI / library state that is not thread-safe. Cost: higher memory (duplicated heaps, code pages shared via CoW), IPC instead of shared memory structures, harder shared caches. Multi-threaded async wins for shared in-memory state and connection density. Hybrid is common: N async worker processes behind a load balancer (Kubernetes replicas), each process internally Tokio. Interviewers want the isolation vs efficiency trade-off, not dogma.
// OS 02
User/Kernel Mode, Syscalls, Interrupts, Traps
Questions & model answers
Q1What is the difference between user mode and kernel mode? Why can't user code just touch devices?▼ answer
Model answer
CPUs enforce a privilege level: user mode runs applications with restricted instructions and no direct access to physical devices or other processes' memory; kernel mode runs the OS with full privileges. Transitions happen via controlled gates (syscalls, exceptions, interrupts). Without this, any program could corrupt disks, steal other apps' secrets, or hang the machine. Interviewers listen for: isolation + mediated resource access, not just "kernel is privileged." Rust unsafe does not enter kernel mode — it only relaxes the language's safety rules inside the process.
Q2What is a syscall? Walk through what happens on a read from Rust down to the kernel.▼ answer
Model answer
A system call is a controlled entry into the kernel to request a privileged service (I/O, mmap, clone, etc.). Path: Rust std/tokio → libc or direct syscall instruction → trap to kernel → validate args, perform work (or queue I/O) → return to user with result/errno. Context-switch costs matter: mode switch, possible scheduler run, TLB/cache effects. That is why batching (vectored I/O, io_uring, fewer larger reads) and avoiding chatty syscalls show up in perf work. Async does not remove syscalls; it avoids blocking a thread while waiting for completion/readiness.
Q3Contrast interrupts, traps/exceptions, and syscalls. Where do page faults fit?▼ answer
Model answer
Interrupts are asynchronous hardware signals (NIC packet, timer tick) that divert the CPU to a handler — independent of the current instruction stream. Traps/exceptions are synchronous, caused by the executing instruction (divide-by-zero, illegal opcode, breakpoint, page fault). Syscalls are deliberate traps for OS services. A page fault may be "minor" (map a page that was allocated but not yet faulted in, or CoW) or "major" (disk read from swap/file) — backends feel major faults as latency spikes. Good signal: timer interrupts drive preemptive scheduling; your Rust code rarely handles interrupts directly.
Q4Why do high-QPS Rust services care about syscall and context-switch rates? What do you measure?▼ answer
Model answer
Each syscall/mode switch costs latency and burns cache; under load, excessive read/write/futex/epoll_wait patterns show up as CPU in sys time with mediocre app throughput. Measure with perf stat (cycles, context switches, cache misses), strace -c / perf trace for hot syscalls, and runtime metrics (Tokio park rate, epoll wakeups). Mitigations: batching, io_uring, fewer threads (less scheduling noise), avoid needless fsync per request, use buffered/vectored I/O. Trap answer: "just add more pods" without looking at sys% vs user%.

CPU Scheduling — Fairness, Latency, CFS Intuition
Questions & model answers
Q1What does the CPU scheduler decide? Contrast throughput-oriented vs latency-oriented goals.▼ answer
Model answer
The scheduler picks which runnable thread runs on which CPU, for how long, and when to preempt. Throughput goals maximize useful work per second (batch jobs, compilers) — longer time slices, less switching. Latency / interactivity goals keep response times low (APIs, UIs) — shorter slices, prefer waking interactive tasks, avoid convoy behind CPU hogs. Real OS schedulers balance both with priorities/nice, fairness, and heuristics. Rust services care because a CPU-bound neighbor on the same machine (noisy neighbor, or your own spawn_blocking storm) can inflate p99 even if your code is "correct."
Q2Give a CFS (Completely Fair Scheduler) intuition. What does "nice" change?▼ answer
Model answer
Linux CFS approximates fair sharing of CPU among runnable tasks using a weighted virtual runtime: tasks that ran less recently (lower vruntime) are preferred. Think "each task gets a proportional fair slice of CPU over time," not strict round-robin of equal ticks. nice adjusts the weight — higher nice (lower priority) gets a smaller share; negative nice gets more. For containers, cgroups/CPU quotas add another layer (throttling when quota exhausted — classic latency cliffs in Kubernetes). Interview signal: fair share ≠ equal latency under overload; under saturation everyone slows. Pinning/affinity and isolating latency-critical threads are advanced levers.
Q3When do Rust services care about OS scheduling vs Tokio's scheduler?▼ answer
Model answer
Tokio schedules tasks onto worker threads (work-stealing, cooperative). The OS schedules those worker threads onto cores. You care about Tokio when tasks starve each other (blocking, missing yield, unfair locks). You care about the OS when: CPU throttling/cgroups, too many threads fighting for cores, priority of sidecar/agents, or realtime-ish needs. Rule of thumb: size Tokio workers ≈ CPU count; put blocking work on a bounded blocking pool; avoid creating thousands of OS threads. Mentioning both layers is the senior distinction.
Q4What is priority inversion? Where might it appear in a Rust service (even without RT priorities)?▼ answer
Model answer
Classic: high-priority task H waits on a lock held by low-priority L, while medium M runs and prevents L from releasing — H is stuck behind M. OS fix: priority inheritance. In ordinary Rust backends you may not use RT priorities, but the shape appears: a latency-critical request waits on a mutex held by a background task doing heavy work; or a Tokio task holds a sync mutex while the holder is scheduled off-CPU. Mitigations: short critical sections, don't do I/O under locks, prefer channels/sharding, use async-aware locks across await, separate latency classes onto different thread pools. Also watch false sharing: unrelated atomics on the same cache line cause ping-pong and look like "scheduler weirdness" under perf — pad hot counters (CachePadded).
Q5Scenario: p99 jumps every few minutes; CPU usage shows periodic throttling in the container. What do you check?▼ answer
Model answer
Suspect CFS bandwidth / cgroup CPU quota: the pod burns its burst, then is throttled (cpu.stat throttled periods). Correlate with GC-like batch work, compaction, or traffic spikes. Fixes: raise CPU limit/request, smooth work (rate-limit background jobs), reduce per-request CPU, avoid synchronized "thundering herd" timers across replicas. Also check noisy neighbors on the node and whether you oversubscribed threads. Strong candidates read cgroup metrics before rewriting business logic.

Synchronization Primitives & Deadlock Intro
Questions & model answers
Q1Define mutex, rwlock, semaphore, and condition variable. When do you pick each?▼ answer
Model answer
Mutex: exclusive ownership of a critical section — default for shared mutable state. RwLock: many readers or one writer — good when reads dominate and critical sections are short; write-heavy or long critical sections often lose to sharding. Semaphore: counting permit pool — bound concurrency (DB connections, in-flight requests) without "owning" a data structure. Condition variable: wait for a predicate under a mutex (producer/consumer); in async Rust you usually use channels / Notify / watch instead of raw condvars. Rust: std::sync::Mutex / parking_lot / tokio::sync::* — never hold a std mutex across .await.
Q2Why is busy-waiting usually wrong? When is a spinlock acceptable?▼ answer
Model answer
Busy-waiting burns CPU while waiting for a condition, hurts fairness, and on overloaded systems can delay the thread that would release the resource (self-inflicted priority inversion). Prefer blocking (futex-backed mutex) or async wait. Spinlocks can be OK for extremely short critical sections on multiprocessors when you know the holder is running and sleep cost exceeds spin cost — kernel and some lock-free designs. In userspace Rust services, default to mutex/channels; spinning in a loop checking an AtomicBool without backoff is a classic junior smell. If you spin, use parking_lot/std adaptive strategies or explicit core::hint::spin_loop with a clear bound — and measure.
Q3What is deadlock (quick definition)? Give a two-lock Rust sketch interviewers expect.▼ answer
Model answer
Deadlock: a set of threads/tasks permanently wait for each other's resources — no one can make progress. Classic: thread A holds lock1 waits lock2; thread B holds lock2 waits lock1. 
// Sketch — do NOT do this
// A: lock(a); lock(b);
// B: lock(b); lock(a);
fn transfer(a: &Mutex<Acct>, b: &Mutex<Acct>) {
    let _ga = a.lock().unwrap(); // acquire in address order instead
    let _gb = b.lock().unwrap();
}
Fix patterns: global lock order, try-lock with backoff, single mutex covering both, or message passing. Deeper Coffman conditions live in the next section — here they want the cycle intuition.
Q4Compare std::sync::Mutex, parking_lot::Mutex, and tokio::sync::Mutex. When does each belong?▼ answer
Model answer
std::sync::Mutex: poisoning on panic, adequate for sync code; do not hold across .await. parking_lot: often faster, no poisoning by default, still blocking — great inside CPU-bound or short sync sections. tokio::sync::Mutex: async-aware; tasks yield while waiting so workers are not blocked — use when the lock must be held across .await or waiters are async tasks. Prefer redesign (channels, shard, RwLock, atomics) over long-held async mutexes. Interview trap: wrapping everything in tokio::sync::Mutex "to be safe" and creating a global bottleneck.

Deadlock — Coffman, Detection, Prevention, Avoidance
Questions & model answers
Q1State the four Coffman conditions. Why does breaking any one prevent deadlock?▼ answer
Model answer
(1) Mutual exclusion — resources are not shareable. (2) Hold and wait — a task holds resources while waiting for more. (3) No preemption — resources cannot be forcibly taken back. (4) Circular wait — a cycle in the waits-for graph. Deadlock needs all four; remove one and cycles cannot stick. Practical lever in services is usually (4) lock ordering or (2) acquire-all-at-once / don't hold locks while awaiting other resources (including other services' RPCs — distributed deadlock).
Q2Contrast deadlock prevention, avoidance, and detection+recovery.▼ answer
Model answer
Prevention: design so a Coffman condition cannot hold (strict global lock order; no hold-and-wait by acquiring in one shot; timeout+release). Avoidance: runtime admits requests only if they keep the system in a safe state (Banker's algorithm — rarely used verbatim in app code). Detection: allow possible deadlock, find cycles (waits-for graph), then recover (kill a victim, abort transaction). Databases use detection/abort heavily; low-level Rust services usually prevent via ordering and timeouts. Saying "we'll just detect" without a recovery story is incomplete.
Q3What do practical deadlocks look like in Rust microservices (beyond two mutexes)?▼ answer
Model answer
(1) Async task holds tokio::sync::Mutex and .awaits an RPC that needs the same logical resource on another task. (2) Thread-pool exhaustion: all workers blocked on block_on/sync I/O waiting for tasks that need those workers (classic nested runtime / "async in async" antipattern). (3) Connection pool deadlock: handlers each hold one connection and wait for a second. (4) Distributed: service A waits on B while B waits on A (mitigate with timeouts, deadlines, hierarchical lock/resource ordering, circuit breakers). Interviewers love pool + lock stories as much as textbook two-lock cycles.
Q4How would you debug a suspected deadlock in a stuck Rust process in production?▼ answer
Model answer
Capture stacks: gdb/lldb thread apply all bt, or tokio-console / async-backtrace for task dumps; on Linux perf / eu-stack. Look for threads blocked on futex waits in lock patterns, or all Tokio workers parked while tasks wait each other. Reproduce with stress + RUST_BACKTRACE; add lock-order debug assertions in tests (parking_lot deadlock detection feature, or systematic ordering helpers). Temporary mitigation: timeouts on lock acquisition / request deadlines so the process degrades instead of wedging forever. Senior signal: distinguish deadlock from livelock and from simple overload.

Virtual Memory, Paging, Page Tables, TLB
Questions & model answers
Q1What is virtual memory? What problem do pages and page tables solve?▼ answer
Model answer
Virtual memory gives each process a large contiguous-looking address space while the OS maps those virtual pages to physical frames (or to disk). Benefits: isolation, relocation, sparse allocation, memory-mapped files, and overcommit/swap policies. Page tables store the translations (and permission bits: R/W/X, user/supervisor). Hardware walks them (or uses hardware page-walk with OS-maintained tables) on misses. Interviewers want: VA → PA translation + protection, not "virtual means fake RAM."
Q2What is the TLB? Why do large heaps / many mmap regions hurt performance?▼ answer
Model answer
The TLB (Translation Lookaside Buffer) caches recent VA→PA translations. A TLB miss forces a page-table walk — expensive. Huge working sets with poor locality, many small pages, or frequent context switches (different address spaces) increase miss rates. Huge pages (2MB/1GB) reduce TLB pressure for big heaps/caches — used by JVMs, databases, and some Rust services with large arenas. mmap of many tiny regions can also bloat page tables. Measuring: perf stat for dTLB loads/misses.
Q3Explain demand paging and copy-on-write. Where does Rust/Unix use CoW?▼ answer
Model answer
Demand paging: allocate virtual pages first; physical frames are assigned on first fault — speeds startup and keeps sparse heaps cheap until touched. Copy-on-write: after fork, parent and child share physical pages marked read-only; a write faults and copies the page. Also used for shared library text and some allocator patterns. Cost: first write after fork can storm faults. Rust apps that fork accidentally after allocating large heaps pay CoW taxes; containers that overcommit RAM can OOM when pages are finally dirtied.
Q4RSS vs VSZ vs "memory used" in a Rust service — what should you report in an interview?▼ answer
Model answer
VSZ (virtual size) is the mapped address space — can be huge with sparse mappings and is a weak OOMish signal. RSS is resident physical pages — better for "how much RAM am I using," but includes shared pages oddly depending on accounting. Also track file-backed vs anonymous, allocator heap stats (jemalloc/mimalloc metrics), and cgroup memory limits. A senior mentions that page cache is shared and not "my heap," and that dropping caches or mmap I/O can change RSS without a leak. For leaks: look at growth of anonymous RSS + allocator fragmentation, not VSZ alone.
// OS 07
Page Replacement, Thrashing, mmap & Page Cache
Questions & model answers
Q1What is page replacement? What is thrashing?▼ answer
Model answer
When physical memory is full, the OS must evict (replace) pages — write dirty ones to swap/file if needed — to free frames for new faults. Algorithms (approx LRU, CLOCK, etc.) try to evict cold pages. Thrashing is when the working set doesn't fit: the system spends most time paging rather than doing useful work — latency explodes, CPU looks "busy" in iowait/sys. Fix: more RAM, reduce working set, fix memory leaks, isolate noisy jobs. Interviewers want working-set language, not just "swap is bad."
Q2What is the page cache? How does it relate to read/write and mmap?▼ answer
Model answer
The kernel keeps file data in a page cache in RAM. Buffered read/write copy between user buffers and cache; disk I/O happens asynchronously (writeback) unless fsync/O_DIRECT changes the rules. mmap maps file pages into the process address space so access is via loads/stores + faults into the same cache — great for random reads / shared read-only data; trickier for writes (visibility, sync, SIGBUS on truncated files). Backends: sequential logs often prefer buffered writes + careful fsync; large read-mostly datasets may use mmap (search indexes) with awareness of cache pollution.
Q3Working set vs RSS — how do you reason about cache pressure for a Rust API host?▼ answer
Model answer
The working set is the set of pages actively touched in a time window. A service can have high RSS (cold caches, allocator freelists) but a smaller hot set — or the opposite under scan-heavy workloads that churn the page cache. Scanning large files through the page cache can evict useful pages (use O_DIRECT, posix_fadvise, or dedicated cache disks carefully). For Rust: avoid accidentally mmaping or reading multi-GB blobs on the request path; bound cache sizes in-process (moka/quick_cache) so you control eviction policy instead of fighting the kernel under memory pressure.
Q4Scenario: latency spikes correlate with disk activity; heap metrics look flat. Hypotheses?▼ answer
Model answer
(1) Major page faults / swap (memsteal). (2) writeback storms from dirty page cache (fsync or periodic flusher. (3) mmap'd index random access thrashing disk. (4) log rotation / compaction reading cold files through page cache. Check iowait, pgpgin/out, PSI memory, and whether cgroup memory limit is forcing reclaim. Fix direction: fit working set, rate-limit background I/O, tune fsync batching, isolate storage volumes. Flat heap rules out a Rust allocator leak but not kernel-mediated I/O pain.
// OS 08
Heap Allocation, Fragmentation, Allocators
Questions & model answers
Q1What does a heap allocator do? Contrast bump, freelist, and slab/size-class designs.▼ answer
Model answer
The allocator satisfies dynamic malloc/Box/Vec requests from arenas obtained via mmap/sbrk, tracking free/used regions. Bump: pointer only moves forward — blazing for arenas/ephemeral requests, no individual free (or free-all at once). Freelist: reuse freed blocks; simple but fragments. Size classes / slabs (jemalloc-style): round to size classes, per-class free lists/runs — good concurrency and lower fragmentation for many small objects. Interviewers want trade-offs: speed vs fragmentation vs multi-thread scalability, not a single "best" allocator.
Q2Internal vs external fragmentation — how do they show up in services?▼ answer
Model answer
Internal: allocator rounds up (ask 50B, get 64B class) — waste inside allocated blocks. External: free memory exists in scattered holes too small for a large request — RSS high while malloc fails or grows via new mmap. Services see this as RSS ratchet after spiky load (allocator keeps caches), or inability to allocate large contiguous buffers. Mitigations: reuse buffers (BytesMut pools), bound cache sizes, choose jemalloc/mimalloc, occasional process recycle for pathological fragmentation, avoid huge short-lived allocations on hot paths.
Q3How do Rust allocators fit? What is #[global_allocator], jemalloc, and allocator_api?▼ answer
Model answer
By default Rust uses the system allocator (often glibc malloc or macOS libmalloc). Many production services set #[global_allocator] to tikv-jemallocator or mimalloc for better multi-threaded behavior and introspection. Allocator trait / allocator APIs (still evolving in stable usage) let collections use custom arenas. Patterns: request-scoped bump arenas for parsing; object pools for connection buffers. Caution: mixing allocators across FFI boundaries; measuring with jemalloc stats (epoch/allocated/resident) beats guessing.
Q4Scenario: after a traffic spike, RSS stays high while request rate returns to baseline. Leak or allocator?▼ answer
Model answer
Often allocator caching / fragmentation, not a logical leak: freelists retain arenas for reuse. Confirm with jemalloc retained vs application-level metrics (cache entry counts, unbounded Vec/HashMap growth). True leaks grow without bound correlated with a specific allocation site (heaptrack, dhat, jemalloc profiling). Also check for forgotten JoinHandles, growing unbounded channels, or caches without eviction. Senior answer: hypothesize both, measure allocator vs app structures, don't restart pods as the only "fix" without understanding.

File Systems — Inodes, Journaling, fsync, Directories
Questions & model answers
Q1Inode vs dentry vs path — what does the kernel store?▼ answer
Model answer
An inode holds file metadata and data-block pointers (size, permissions, timestamps) — not the name. A directory maps names → inode numbers; a dentry is the kernel cache of that mapping. Multiple names (hard links) can point to one inode; symlinks store a path. Paths are looked up component-by-component with permission checks. Rust sees paths as strings/OsStr; the durable identity for an open file is the file descriptor / inode, which is why unlinking an open file still allows I/O until the last fd closes.
Q2What does journaling buy you? How does it relate to crash safety?▼ answer
Model answer
A journal (write-ahead log for FS metadata, sometimes data) lets the filesystem recover quickly after crash by replaying/rolling back incomplete operations — avoids long fsck and reduces metadata corruption risk. It does not by itself make your application durable: data you wrote may still sit in the page cache. Application durability needs explicit fsync/fdatasync (and often fsync of the parent directory after rename for atomic publish). Interview signal: separate FS journal from app WAL.
Q3Explain fsync durability pitfalls. What is the atomic-rename pattern?▼ answer
Model answer
write returns when data is in kernel cache, not necessarily on stable storage. fsync(fd) pushes file data+metadata; after creating a new file you often must also fsync the directory so the dirent is durable. Pattern for atomic config/replace: write file.tmp → fsync → rename to file → fsync dir. Trap: assuming rename alone is enough on all platforms/settings, or fsyncing every record synchronously and destroying throughput — batch commits instead. Rust: File::sync_all / sync_data; databases and queues obsess over this path.
Q4What is TOCTOU on files, and how do you avoid it in Rust services?▼ answer
Model answer
TOCTOU (time-of-check to time-of-use): you stat/access a path, then later open it — an attacker may have swapped the path (symlink races in /tmp). Fix: open first with safe flags, then fstat the fd; use O_NOFOLLOW/openat with directory fds; prefer random names in private dirs; never follow untrusted symlinks into sensitive targets. In Rust prefer operating on File/Dir descriptors over repeated path strings; be careful with std::fs helpers that re-open by path. Security interviews expect this vocabulary.
Q5Directories and large directory performance — what bites production systems?▼ answer
Model answer
Huge flat directories (millions of entries) make lookup/readdir slow depending on FS; classic anti-pattern is one directory per object store with no sharding. Mitigate with hierarchical prefixes (ab/cd/hash), separate metadata DB, or object storage APIs. Also: readdir + stat per file is a syscall storm — batch carefully. For queues on disk, prefer structured layouts and avoid unbounded directory growth.
// OS 10
I/O Models — Blocking to epoll to Async (mio/Tokio)
Questions & model answers
Q1Map blocking, nonblocking, multiplexed, and async I/O. Where do select/epoll fit?▼ answer
Model answer
Blocking: syscall sleeps the thread until data/space is available. Nonblocking: syscall returns immediately with EAGAIN if it would block — you must retry later. Multiplexed readiness: select/poll/epoll/kqueue tell you which fds are readable/writable so one thread can manage many connections. Async I/O (broader term): either readiness-based async (Tokio) or completion-based (io_uring, IOCP) where the kernel notifies when an operation finishes. epoll is readiness multiplexing on Linux; it is the substrate under mio/Tokio, not a competing application API you hand-roll in most services.
Q2How do mio and Tokio relate to epoll? What does a reactor do?▼ answer
Model answer
mio wraps OS readiness APIs portably (epoll/kqueue/IOCP). A reactor registers interest in fds, blocks in epoll_wait, then wakes the tasks/futures associated with ready events. Tokio's driver uses mio (or io_uring features when enabled): when you TcpStream::read().await, the task yields; on readability the runtime polls the future again. You rarely need raw mio unless building a custom runtime. Interview trap: thinking .await means zero syscalls — the readiness loop still uses epoll; you just amortize threads.
Q3Why is select historically limited, and why did epoll win for high connection counts?▼ answer
Model answer
select copies fd sets each call, scans them linearly, and traditionally caps at FD_SETSIZE (~1024) — O(n) per wait with large n. epoll keeps interest in-kernel, returns only ready events — scalable to tens/hundreds of thousands of idle connections. This is why the C10K problem pushed readiness APIs and why async Rust runtimes exist. Still: scalability of idle connections ≠ free CPU for active ones; hot connections still cost.
Q4Completion-based I/O (io_uring) vs readiness — when does it matter for Rust backends?▼ answer
Model answer
Readiness: "fd is readable" → you issue read (possible still partial). Completion: you submit a read buffer; kernel completes when filled — fewer syscalls, better batching, strong for disk and some socket workloads. Tokio is adding/using io_uring in places; specialized stacks (glommio, custom) lean in harder. For most CRUD APIs, Tokio readiness is enough; for storage engines / proxy data planes, completion I/O and syscall batching become interview-level differentiators. Mention copying vs registered buffers at the senior end.
Q5Why must you not call blocking std::fs / std::net on a Tokio worker?▼ answer
Model answer
Blocking parks the OS worker thread inside a syscall; other tasks scheduled on that worker cannot run until it returns — latency contagion under load. Use tokio::fs, async net types, or spawn_blocking / a dedicated pool for inherently blocking work (and bound that pool). Same class of bug: CPU-heavy loops without yield_now. This is one of the highest-signal Rust systems interview questions — map it explicitly to the OS blocking I/O model.
// OS 11
IPC — Pipes, Unix Sockets, Shared Memory, Signals
Questions & model answers
Q1Compare pipes, Unix domain sockets, and TCP localhost for local IPC.▼ answer
Model answer
Pipes (anonymous): unidirectional byte stream between related processes (shell pipelines); easy, no addressing. Unix domain sockets: bidirectional, filesystem or abstract-namespace addressed, support multiple clients, credential passing (SCM_CREDENTIALS), and often lower overhead than TCP loopback (no network stack framing). TCP localhost: same APIs as remote, easier to migrate off-box, but pays TCP/IP stack costs and port management. Rust: std::os::unix::net::UnixStream / tokio::net::UnixStream for local sidecars. Prefer Unix sockets for same-host service meshes/sidecars when you do not need IP routing.
Q2When is shared memory the right IPC? What synchronization is still required?▼ answer
Model answer
Shared memory (mmap of a shared region / shm_open) is for high-throughput, low-latency exchange of large data without copying through the kernel on each message — market data, telemetry rings, game engines. You still need synchronization: atomics, futex-backed locks, or single-producer single-consumer ring designs; also memory ordering and schema versioning. Danger: one corrupt writer can trash peers (weaker isolation). In Rust, shared memory is inherently unsafe territory — treat layouts like a wire format with care.
Q3What are signals? Why are they painful in Rust (and C) services?▼ answer
Model answer
Signals are async notifications (SIGINT, SIGTERM, SIGCHLD, SIGSEGV…) that interrupt a process. Handler restrictions are severe: only async-signal-safe functions; you can interrupt syscalls (EINTR); global handler state races with threads. Rust cannot safely do much in a classic handler — no heap allocation, no most std APIs. Best practice: use signal-hook / tokio::signal to convert signals into channel events or flags handled in normal async code (graceful shutdown on SIGTERM). Never println! from a raw handler. Interviewers listen for "signals as process control plane, not business logic pipe."
Q4Design a graceful shutdown for a Tokio service on SIGTERM — OS + runtime angle.▼ answer
Model answer
Register tokio::signal::unix::SignalKind::terminate() (and ctrl_c). On signal: stop accepting new connections, drain in-flight requests with a deadline, flush/fsync critical state, then exit. Coordinate with orchestrators (K8s terminationGracePeriodSeconds). Avoid work that can deadlock during drain (don't wait forever on stuck downstream). OS angle: SIGKILL cannot be caught — design so SIGTERM path is enough; persistent state must survive kill via WAL/fsync discipline. Strong answer ties signal handling to readiness/liveness probe behavior.

Putting It Together — Rust Service Perf Debug Checklist
Questions & model answers
Q1Give a first-pass checklist when a Rust service is "slow" — what axes do you split on?▼ answer
Model answer
Split: CPU (user vs sys, run queue), memory (RSS growth, reclaim, swap, cgroup OOM), I/O (disk/network latency, iowait, errnos), concurrency (lock contention, pool wait, scheduler throttling). Always establish: is it throughput collapse, latency spike (p99), or hard errors? Correlate with deploy, traffic shape, and saturation metrics. Interviewers want a structured triage, not a single favorite tool.
Q2CPU path: what do you check for a Tokio/Rust backend?▼ answer
Model answer
Profiles: perf/flamegraph/samply for on-CPU hot stacks; check whether time is in app code, allocator, serialization, or kernel. Watch for accidental Debug formatting, excessive cloning, hash brownian motion, compression on-request-path. Runtime: worker count, blocking pool saturation, tasks that never yield. OS: cgroup throttle, noisy neighbor, frequency scaling. False sharing on hot atomics shows as high cache-miss CPU without obvious app logic cost — pad contended counters.
Q3Memory path: leak vs cache vs fragmentation vs page cache — how do you tell?▼ answer
Model answer
App cache: bounded structures with hit-rate metrics. Leak: unbounded growth tied to connection/request IDs or forgotten tasks. Fragmentation/allocator retain: RSS high, app metrics flat — check jemalloc stats. Page cache: system-level, free memory low but reclaimable — not necessarily a process leak. Tools: allocator prof, /proc/self/smaps_rollup, cgroup memory.current vs limits, metrics for cache size. OOM kills under limit need the same split before "just increase the limit."
Q4I/O and lock contention paths — top symptoms and tools?▼ answer
Model answer
I/O: high iowait, slow fsync, DNS/connect timeouts, TCP retransmits, socket buffer stalls — use iostat, bpftrace/perf, app-level timing of connect/read/write, pool wait histograms. Locks: CPU in futex waits, threads blocked in pthread_mutex_lock, Tokio tasks waiting on the same Mutex, request latency with low CPU — use tokio-console, contention metrics, reduce critical sections, shard. Busy-waiting shows as high CPU with no progress — opposite of lock wait.
Q5Scenario: p99 is high, average CPU is low, error rate is near zero. Walk a senior investigation order.▼ answer
Model answer
Low CPU + high latency ⇒ waiting. Order: (1) latency histograms by stage (queue wait, DB, downstream, handler). (2) saturation: connection pools, semaphores, Tokio blocking threads, file descriptors. (3) lock/async contention and accidental sync I/O on workers. (4) external: DNS, GC on dependency, disk fsync, cgroup throttle (CPU throttle can also look odd — check throttled time even if average CPU looks low). (5) GC-like periodic jobs / cache stampede. (6) network RTT/retransmits. Propose one hypothesis at a time with a metric that would falsify it. That structured calm is the interview — not naming fifteen tools at once.
