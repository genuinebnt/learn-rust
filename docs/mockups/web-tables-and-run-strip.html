2 C++ / Rust comparison tables

Highlighted code, rows that line up, a copy button

These tables are the course’s main teaching device. Today the cells are plain inline code. Proposed: each cell goes through the same highlighters the code blocks already use (highlightCpp, highlightRust), both columns share a row height so the C++ line and its Rust line sit side by side, and hovering a cell shows copy. A first column names what each row compares.

  • Prose cells stay prose. Only cells that are entirely inline code are highlighted; a cell with words and a code fragment keeps its fragment as it is today.
  • Language per column comes from the header (C / C++ or Rust), which the renderer already detects to colour the headers.
  • The first column is optional: it appears when the markdown table has a third, unlabelled column, so no existing article needs rewriting.
  • Touch screens show the copy button all the time. Under 640px the table keeps horizontal scroll inside its box, as it does now.

3 Rust workspace: the result stays pinned above the test cases

Tests pane, with the last-run strip fixed at the top

Today the “Not run yet / 3 of 5” heading is the first thing inside the scrolling pane, so it scrolls out of sight as soon as a case is expanded. Proposed: it becomes a strip that stays at the top of the pane, with the Run button repeated in it and a count that updates while the tests run. Scroll the list to see it stay.

TestsOutput
  • Nothing is removed: the cases list, the visible-versus-hidden note and the Submit button are unchanged.
  • Failed cases are listed first and open, passed ones after them, the same order as the course Run tab, so the two screens agree.
  • Running shows one pulsing segment per case that has not finished (no motion with reduced-motion on).
  • Status uses icons as well as colour: a tick for pass, a cross for fail, a dashed ring for waiting.

Decisions

  1. Which of the four to build first? My order: the pinned run strip (small, in the workspace you use most), then the problem-table sort and filter with keys, then the comparison tables, then the course-page extras.
  2. Sort on the phone: a small “Sort” menu (drawn in my head, not here), or no sorting on phones? I would add the menu.
  3. Status icons replace the plain coloured squares on the track table and the course tree. OK to change both, or the track table only?

Per-test durations and grouping by stage are still left out, for the reason given on the Run-tab mockup: a reported run carries one total time, and stable cargo test does not measure per test.
