SD1 · Rate Limiter
Medium concurrency atomics distributed systems
Prompt
"Design a rate limiter for an API gateway that limits each client to N requests per second, running as a library inside a multi-threaded Rust service handling tens of thousands of requests per second across potentially millions of distinct client keys. Walk me through your data structure choice, algorithm, concurrency strategy, and how it would need to change if the service scaled to multiple instances."
Discussion — sub-questions & model answers
D1Which rate-limiting algorithm would you pick, and why not the alternatives?▼ answer
Model answer
Token bucket is the standard default: each client has a bucket holding up to N tokens, refilled continuously at rate N/second (or in discrete steps), and each request consumes one token, rejected if the bucket is empty. It naturally allows short bursts up to the bucket capacity while enforcing a steady-state average rate — closer to real client traffic patterns than a rigid per-second cutoff. Fixed window counter (reset a counter every second) is simpler to implement but has a well-known boundary problem: a client can send N requests at the very end of one window and another N at the very start of the next, achieving 2N requests in a short span while each window individually looks compliant. Sliding window log (store a timestamp per request) is the most precise but requires unbounded-ish per-client memory (a timestamp per request in the window) — usually not worth the memory cost compared to sliding window counter (a weighted approximation combining the current and previous fixed windows), which gets most of the accuracy of a sliding log with fixed, small memory per client. For most production API gateways, token bucket (or the closely related leaky bucket for output smoothing) is the pragmatic default; sliding window counter is the upgrade if boundary bursting is a genuine concern.
D2How do you represent "millions of distinct client keys" without unbounded memory growth, and what Rust types back this?▼ answer
Model answer
The core structure is a concurrent map from client key to bucket state: DashMap<ClientId, TokenBucket> (the dashmap crate, internally sharded — see the smart-pointers topic's discussion of sharded locking) is the pragmatic production choice over a single Mutex<HashMap<...>>, which would serialise every single request through one lock — a guaranteed bottleneck at "tens of thousands of requests per second." Each TokenBucket can be represented compactly as an atomic pair (or a packed AtomicU64 encoding both token count and last-refill timestamp, updated via a compare-and-swap loop) to avoid needing a per-client lock at all for the hot path. Unbounded memory growth is the real concern for "millions of distinct keys," most of which may be one-off or rarely-seen clients: the mitigation is a background eviction task (or a lazy, access-time-tracked eviction on insert) that removes buckets not accessed within some TTL — conceptually similar to an LRU/TTL cache, and worth explicitly connecting to that pattern if you've implemented one (see the LRU cache write-exercise in this packet). Bound the map's total size, or use a crate like moka which provides exactly this TTL-based concurrent cache semantics out of the box, rather than hand-rolling eviction.
D3Sketch how a single bucket's "check and consume a token" operation would be implemented safely with minimal contention.▼ answer
Model answer
struct Bucket { tokens: AtomicU64, last_refill_ns: AtomicU64 }

impl Bucket {
    fn try_consume(&self, capacity: u64, refill_per_ns: f64) -> bool {
        loop {
            let now = now_ns();
            let last = self.last_refill_ns.load(Ordering::Acquire);
            let current = self.tokens.load(Ordering::Acquire);
            let refilled = ((now - last) as f64 * refill_per_ns) as u64;
            let available = (current + refilled).min(capacity);
            if available == 0 { return false; }
            if self.tokens.compare_exchange(current, available - 1, Ordering::AcqRel, Ordering::Acquire).is_ok() {
                self.last_refill_ns.store(now, Ordering::Release);
                return true;
            }
            // CAS lost the race — another thread updated concurrently; retry
        }
    }
}
This is a lock-free CAS-retry loop, not a mutex — appropriate here because the critical section is tiny (a handful of arithmetic operations) and the operation is extremely hot (every single request touches it), so avoiding lock overhead entirely is worth the added complexity. Worth flagging explicitly: the two separate atomics (tokens and last_refill_ns) updated non-atomically-as-a-pair here has a subtle correctness gap under heavy contention (a race between reading one and the other) — a more rigorous implementation would pack both into a single AtomicU64 (e.g. tokens in the low 32 bits, a coarser timestamp in the high 32 bits) and CAS them together atomically, eliminating the gap entirely. Bringing this up unprompted — noticing your own sketch has a subtle correctness edge — is exactly the kind of self-review senior candidates should demonstrate.
D4The service now scales to multiple instances behind a load balancer. What breaks, and how do you fix it?▼ answer
Model answer
Everything above is per-instance, in-memory state — with M instances behind a load balancer, a client's requests get distributed across all M instances, and each instance independently enforces the full limit N, so the client can actually achieve up to M × N requests/second in aggregate, silently violating the intended global limit. Fix options, in order of complexity: (1) Sticky routing — route each client key consistently to the same instance (consistent hashing at the load balancer) so its state genuinely stays local; simplest, but creates hot-instance risk if key distribution is skewed and complicates instance scaling/failover. (2) Centralized store — Redis-backed limiter — move the token bucket state into Redis, using a Lua script (or Redis's own atomic INCR/EXPIRE primitives) to make the check-and-decrement atomic across all instances; this is the standard, most common production answer, at the cost of a network round-trip per request (mitigated with local caching of "definitely still has tokens" for very recently-checked clients, accepting slightly relaxed precision). (3) Approximate distributed limiting — each instance enforces N/M locally (simple but wastes capacity if load is uneven across instances) or periodically synchronises/gossips aggregate usage counts to approximate a global view without a centralized store, trading precision for lower latency and no single point of failure. The senior signal here: proactively raising this exact failure mode before being asked — many candidates design a perfectly correct single-instance limiter and simply don't think about what happens once you scale horizontally, which is precisely the scenario this system almost always runs in in production.
✓ Strong
  • Names token bucket vs sliding window trade-offs with the boundary-bursting failure mode
  • Proposes a sharded/lock-free structure instead of one global mutex without prompting
  • Proactively raises the multi-instance scaling problem before being asked
  • Notices subtle correctness gaps in their own CAS-loop sketch
⚠ Probe
  • Reaches for a single global Mutex<HashMap> without discussing contention
  • Only considers a single-instance design unless explicitly asked about scaling
✗ Concern
  • Cannot articulate why a fixed window counter has a boundary problem
  • Has no plan for unbounded memory growth with millions of client keys

SD2 · Connection Pool
Medium async RAII resource management
Prompt
"Design a generic async database connection pool for a Tokio-based service. It should hand out connections to callers, automatically return them to the pool when the caller is done, enforce a maximum pool size, and support a per-checkout timeout. Walk through the type design, how you'd guarantee connections are always returned even if the caller panics, and how you'd health-check idle connections."
Discussion — sub-questions & model answers
D1What does the checkout/return API look like, and how do you guarantee return happens even on panic or early return?▼ answer
Model answer
struct Pool { inner: Arc<PoolInner> }
struct PoolInner { semaphore: Semaphore, idle: Mutex<VecDeque<Conn>>, /* config, factory, ... */ }

struct PooledConn { conn: Option<Conn>, pool: Arc<PoolInner> }

impl Drop for PooledConn {
    fn drop(&mut self) {
        if let Some(conn) = self.conn.take() {
            self.pool.return_conn(conn); // pushes back into idle + releases semaphore permit
        }
    }
}
impl Deref for PooledConn { type Target = Conn; /* ... */ }
This is the same RAII guard pattern as a MutexGuard — checkout returns a PooledConn wrapper, not the raw connection, and returning it to the pool happens in PooledConn's Drop implementation. Because Drop runs unconditionally — on normal scope exit, on early return, on ?-propagated errors, and even during panic-driven unwinding — the connection is guaranteed to return to the pool regardless of how the caller's code path exits, with zero special-casing needed in caller code. This is precisely the same design principle discussed in the FFI topic's RAII-wrapper-around-a-C-handle pattern, applied to a higher-level resource instead of a raw pointer.
D2How do you enforce a maximum pool size and implement checkout timeout without blocking a Tokio worker thread?▼ answer
Model answer
tokio::sync::Semaphore initialized with max_size permits is the natural fit — acquiring a permit represents "I'm allowed to hold one connection," and it's specifically designed to be .await-ed rather than blocking a thread, unlike a plain counter guarded by a std mutex. Checkout becomes: let permit = semaphore.acquire().await, then either pop an idle connection from the pool or create a new one if none are idle (up to the size the semaphore allows). Timeout wraps the whole acquire-and-checkout future: tokio::time::timeout(Duration::from_secs(5), pool.checkout()).await — if the timeout fires first, the checkout future is dropped/cancelled (this is exactly the cancellation-safety topic from earlier: make sure a cancelled checkout doesn't leave a permit acquired-but-unaccounted-for; using an owned SemaphorePermit tied to the connection guard's lifetime, dropped together, handles this correctly by construction). Held permit needs to travel with the checked-out connection — typically stored inside the PooledConn guard itself alongside the connection, released together in the same Drop impl, ensuring the permit count and the idle-connection count never drift out of sync.
D3How would you health-check idle connections without adding checkout latency for every request?▼ answer
Model answer
Checking connection health synchronously on every checkout (e.g. sending a lightweight ping query before handing out the connection) adds latency to every single request, which is wasteful for connections that are almost always healthy. The better design: a background task, spawned once when the pool is created, that periodically (e.g. every 30 seconds) walks the idle connections and pings each one, evicting and replacing any that fail — this amortises the health-check cost across time instead of paying it on every checkout's critical path. Complementary lazy check: also validate a connection's "last used" timestamp on checkout — if a connection has been idle longer than some threshold (proactively suspecting the underlying DB/network may have silently closed it), do a cheap check specifically for that connection rather than blindly handing out a possibly-stale connection. On checkout failure (the actual query using the "healthy" connection fails with a connection-level error, not a query-level error), the pool should distinguish "this connection is broken, discard it and don't return it to the idle pool" from "this was a transient query error, the connection itself is fine" — mixing these up either leaks a permanently-broken connection back into rotation (silent, hard-to-diagnose failures downstream) or wastefully discards perfectly good connections.
D4What happens under a connection-storm scenario — the database becomes briefly unavailable and hundreds of requests are simultaneously trying to check out or create new connections?▼ answer
Model answer
Without care, every one of those hundreds of waiting requests independently retries creating a new connection the moment the DB seems reachable again, all at once — a thundering herd that can itself overwhelm a database that's just recovering, potentially causing it to fail again immediately (a self-inflicted cascading failure pattern). Mitigations: (1) the semaphore-based design already provides natural backpressure — only max_size connection-creation attempts can be in flight at once, since everyone else is queued waiting for a permit, rather than every waiter racing to create a connection independently; (2) add exponential backoff with jitter to connection-creation retries specifically (not checkout timeout — a distinct retry policy for "the DB itself seems down" vs "the pool is just momentarily saturated") so retries spread out over time rather than synchronising; (3) consider a circuit breaker around connection creation — after N consecutive connection failures, stop attempting new connections for a cooldown period and fail fast instead, giving the database room to recover rather than being immediately re-hammered the moment it comes back; (4) surface this state via metrics (checkout wait time distribution, active connection-creation failures) so on-call engineers can distinguish "the pool is saturated because traffic is high" from "the pool is saturated because the database is down" — these require completely different responses and look identical from the caller's perspective (a slow or failing checkout) without that visibility.
✓ Strong
  • Designs an RAII guard whose Drop returns the connection, connects it to MutexGuard/FFI patterns
  • Uses tokio::sync::Semaphore rather than a busy-poll or blocking counter for capacity limiting
  • Distinguishes background health-checking from per-checkout latency cost
  • Proactively raises thundering-herd / circuit-breaker concerns under DB outage
⚠ Probe
  • Health-checks every connection synchronously on every checkout
  • Hasn't considered what happens to the semaphore permit if checkout is cancelled via timeout
✗ Concern
  • Relies on the caller to manually call a "release" method instead of RAII/Drop
  • No plan at all for connection-storm / cascading failure scenarios

SD3 · Thread Pool Sizing & Work Distribution
Medium threading scheduling performance
Prompt
"You're building a service that does a mix of CPU-bound image processing and I/O-bound calls to downstream services. How many threads/worker pools do you provision, how do you decide the size of each, and how do you route work to the right pool? Assume this runs on an 8-core machine."
Discussion — sub-questions & model answers
D1Why is one shared thread pool for both kinds of work the wrong design, even though it seems simpler?▼ answer
Model answer
CPU-bound and I/O-bound work have opposite optimal pool-sizing rules. A CPU-bound workload saturates the CPU with useful work continuously — the optimal thread count is close to the number of physical cores (N or slightly more to absorb scheduling gaps), since more threads than cores just adds context-switch overhead without added throughput. An I/O-bound workload spends most of its time waiting (network round-trips) rather than computing, so a much larger thread/task count than the core count is not only fine but necessary to keep enough requests in flight concurrently to saturate the actual bottleneck (the network or downstream service), not the CPU. If you mix both in one pool sized for one workload's rule, you get it wrong for the other: size for I/O-bound (large pool) and the CPU-bound image processing tasks now oversubscribe the cores with wasteful context switching between CPU-bound threads competing for the same cores; size for CPU-bound (small, core-count-sized pool) and I/O-bound requests queue up and stall behind slow-but-not-CPU-intensive work, starving unrelated I/O -bound throughput even though the CPU itself is mostly idle. This is exactly the same class of mismatch as the "blocking calls inside async fn" problem discussed in the async/Tokio topic — the fix there and here is the same principle: separate pools sized for their actual workload's bottleneck.
D2Concretely, what pools would you provision on this 8-core machine, and how would you size each?▼ answer
Model answer
Pool 1 — Tokio's async runtime (I/O-bound downstream calls, request handling): default multi-threaded scheduler with worker count roughly equal to core count (Tokio's default is num_cpus) — since these workers handle many concurrent tasks each mostly waiting on I/O, not CPU, the actual concurrency achieved is far higher than the worker thread count itself, governed by how many tasks are in flight, not by thread count. Pool 2 — CPU-bound image processing: a separate pool, ideally sized to roughly num_cpus (or num_cpus - 1 to leave headroom for the async runtime's own threads and OS scheduling, especially if both pools genuinely run concurrently under load) — implemented via rayon's global thread pool (which defaults to core count and is purpose -built for exactly this kind of CPU-bound parallel work), or tokio::task::spawn_blocking for one-off CPU-heavy operations dispatched from async handlers (Tokio's blocking pool is sized differently — much larger, for blocking I/O, not CPU work — so using it for sustained CPU-bound work is itself a design smell worth naming: it works but isn't purpose-sized for CPU-bound throughput the way rayon is). Routing: an async handler receiving an image-processing request should hand the actual computation off to rayon (via a oneshot channel bridging rayon's sync world back into the async handler awaiting the result) rather than doing it inline on the Tokio worker thread — this is the same "don't block a Tokio worker" principle from the async topic, generalized to CPU-bound work instead of blocking I/O.
D3How would you validate that your sizing choices are actually correct, rather than just theoretically reasonable?▼ answer
Model answer
Theoretical sizing rules (core count for CPU-bound, larger for I/O-bound) are a reasonable starting point, not a guarantee — the correct approach is the same measurement-first discipline from the performance topic: load-test the actual service under a realistic mix of both workload types and measure end-to-end latency/throughput while varying each pool's size independently, rather than assuming the textbook formula is exactly right for this specific workload's characteristics (e.g. actual downstream call latency distribution, actual image sizes/processing cost). Instrument both pools with metrics — queue depth/wait time before a task starts executing, and utilization (% time actually busy vs idle) — a CPU-bound pool that's consistently near 100% utilized with a growing queue is under-provisioned; an I/O-bound pool where tasks spend most of their time waiting on a lock or queue slot rather than on the actual network call suggests the pool itself, not downstream latency, has become the bottleneck. The senior framing: pool sizing is a hypothesis to validate under load, not a formula to compute once and trust forever — and it should be revisited whenever the workload mix or downstream latency characteristics meaningfully change in production.
✓ Strong
  • Articulates the opposite sizing rules for CPU-bound vs I/O-bound work with the underlying reason
  • Names rayon specifically for CPU-bound parallel work, distinct from Tokio's blocking pool
  • Proposes bridging CPU-bound work out of async handlers via spawn_blocking or a channel to rayon
  • Insists on load-testing and instrumenting queue depth/utilization rather than trusting a formula
⚠ Probe
  • Proposes separate pools but can't justify specific sizes beyond "more for I/O, less for CPU"
  • Uses tokio::task::spawn_blocking for sustained CPU-bound work without noting rayon would be more purpose-built
✗ Concern
  • Proposes one shared thread pool for everything with no sizing rationale
  • Cannot explain why I/O-bound and CPU-bound workloads need different-sized pools at all

SD4 · Backpressure-Aware Streaming Pipeline
Hard async streams channels backpressure
Prompt
"Design a data pipeline with three stages: (1) ingest events from a network source faster than they can be processed, (2) transform/enrich each event with an async call to another service, (3) write batches of processed events to storage. Producers can occasionally spike to 10x the sustained processing rate. Design this so it never runs out of memory and never silently drops data under sustained overload — walk through how backpressure propagates from stage 3 back to stage 1."
Discussion — sub-questions & model answers
D1What primitive connects each stage, and how does it create backpressure rather than just being a buffer?▼ answer
Model answer
Each stage is connected by a bounded channel — tokio::sync::mpsc::channel(capacity) — deliberately not unbounded. The key mechanism: an unbounded channel lets a fast producer keep pushing forever regardless of whether the consumer keeps up, which is exactly how you run out of memory under sustained overload (the "never runs out of memory" requirement directly rules out unbounded channels anywhere in the pipeline). A bounded channel's .send(item).await call itself .awaits (suspends, does not busy-loop) until there is room in the channel — meaning the producer for that stage is automatically slowed down to match the consumer's actual processing rate, with zero explicit coordination code needed. This naturally propagates end-to-end: if stage 3 (storage writes) is the slowest link, its inbound channel (stage 2 → stage 3) fills up, which makes stage 2's sends to that channel block, which means stage 2 stops pulling from its own inbound channel (stage 1 → stage 2) as quickly, which fills that channel, which in turn slows stage 1's sends — the slowdown ripples backward through the whole pipeline automatically, purely as an emergent property of each stage using bounded channels and normal blocking sends. This is the single most important design insight for the whole exercise, and a strong candidate should articulate it explicitly and early.
D2Stage 1 ingests from an external network source that can't itself be "blocked" the way an internal channel can. What happens there specifically when the pipeline is backed up?▼ answer
Model answer
This is the crux of the "never silently drops data" requirement, and it depends heavily on what the actual ingest source is. If the source itself supports backpressure (e.g. a TCP connection, or a message queue like Kafka with consumer-driven pull semantics), stage 1 simply stops pulling/reading from the source when its outbound channel to stage 2 is full — TCP's own flow control (or the queue's own offset-based consumption model) then naturally applies backpressure all the way back to whatever is sending the data, with no data loss, since the sender-side buffer holds the not-yet-read data. If the source cannot be backpressured (e.g. inbound UDP packets, or a push-based webhook receiver that must respond immediately regardless of downstream state), you genuinely cannot avoid data loss under sustained overload without unbounded memory growth — this is a real, unavoidable trade -off, not something clever channel design can solve away. The honest answer here: (1) size an internal buffer generously enough to absorb the stated "occasional 10x spike" (bounded, but large enough that a transient spike drains without loss, sized based on spike duration × rate, a genuinely measurable/testable quantity) — this handles bursts without handling sustained overload; (2) for genuinely sustained overload beyond the buffer's capacity, you must choose an explicit, deliberate degradation policy — drop with logging/metrics (visible data loss, at least not silent), shed load by returning an explicit backpressure signal to the sender if the protocol supports it (e.g. HTTP 429), or persist overflow to a durable overflow log/queue for later reprocessing rather than in-memory-only. Explicitly separating "burst absorption via sizing" from "sustained overload requires an explicit, chosen trade-off" is the senior -level distinction — many candidates conflate the two and think a big-enough buffer solves both.
D3Stage 3 batches events before writing to storage. How does batching interact with the bounded-channel backpressure design, and what's the failure mode if you get the batching logic wrong?▼ answer
Model answer
Batching introduces a time/size trade-off that channel backpressure alone doesn't resolve: stage 3 should write a batch either when it reaches some target size or when a maximum wait time elapses (whichever comes first) — using a target-size-only policy means a slowdown upstream (exactly the backpressure scenario) could leave stage 3 waiting indefinitely for a batch to fill that never completes, while events sit unwritten and channel capacity stays consumed by items stage 3 hasn't drained yet, which actually worsens the backpressure it's supposed to relieve — a subtle, easy-to-miss interaction. The standard implementation: tokio::select! between "the batch reached its size threshold" and "a timeout elapsed since the batch started accumulating," flushing on whichever fires — the tokio-stream crate's chunks_timeout combinator implements exactly this pattern directly on a stream. Failure mode if this is done wrong (e.g. size-only batching with a very large threshold under low/bursty traffic): events accumulate correctly under high load, but under low or bursty load, individual events can sit unflushed for a very long time, which for many use cases (freshness-sensitive analytics, alerting pipelines) is functionally equivalent to that data being unavailable/lost from the consumer's perspective even though it's technically "safe" in the channel — naming this specific interaction between batching policy and end-to-end data freshness is a solidly senior observation that goes beyond the backpressure mechanics alone.
D4How would you observe this pipeline's health in production — what metrics would immediately tell you it's degraded, before it fails outright?▼ answer
Model answer
Channel occupancy / queue depth at each stage boundary is the single most important leading indicator — a channel that's consistently near-full is the earliest visible sign of a downstream bottleneck, well before anything actually fails or drops. Tokio's mpsc channel doesn't expose depth directly out of the box, so this typically means wrapping sends with an atomic counter incremented/ decremented around each send/receive, or switching to a channel implementation that exposes this (some crates do). Per-stage processing latency (time from receiving an item to handing it to the next stage) — a rising trend here, independent of queue depth, tells you a specific stage is genuinely slowing down rather than just being backed up by something further downstream. Backpressure-wait time — specifically, how long .send().await itself blocks due to a full channel — directly quantifies how much each stage is being throttled by the stage after it, which is the most direct measurement of the backpressure mechanism actually engaging (as opposed to inferring it indirectly from queue depth alone). Drop/overflow counters at stage 1's ingest boundary specifically — since that's the one place actual data loss can occur under the design discussed above, this metric needs to be non-zero-alerted, not just dashboarded, since any nonzero value there represents real lost data. Naming all four of these, and specifically distinguishing "queue depth" from "backpressure-wait time" as two different signals telling you different things, is a mark of having actually operated a system like this rather than just designed one on a whiteboard.
✓ Strong
  • Explains backpressure as an emergent property of bounded channels + blocking sends, propagating backward automatically
  • Distinguishes burst absorption (buffer sizing) from sustained overload (requires an explicit trade-off) rather than conflating them
  • Catches the batching/backpressure interaction where size-only batching can worsen backpressure
  • Names specific, distinct observability signals (queue depth vs backpressure-wait time vs drop counters)
⚠ Probe
  • Uses unbounded channels "to be safe" without recognizing the memory-growth risk that creates
  • Proposes a big buffer as a universal fix without distinguishing burst vs sustained overload
✗ Concern
  • Doesn't know how backpressure would actually propagate between stages at all
  • Assumes unbounded channels are fine "since Rust manages memory automatically"

SD5 · Distributed Lock / Lease
Hard distributed systems correctness clock skew
Prompt
"Multiple instances of a Rust service need to ensure only one of them runs a particular scheduled job at a time (e.g. a nightly cleanup task). Design a distributed lock/lease mechanism for this using an external store (assume Redis or a similar key-value store is available). Walk through failure modes — what happens if the instance holding the lock crashes, or if it's just slow?"
Discussion — sub-questions & model answers
D1Why is a lease (a lock with an expiry) necessary instead of a plain lock, given that instances can crash?▼ answer
Model answer
A plain lock — a key that exists until explicitly deleted by whoever set it — has a fatal failure mode in a distributed setting: if the instance holding the lock crashes before releasing it (process crash, node failure, network partition), the lock is held forever, since there's no other instance with permission to remove it and the crashed instance obviously can't do so itself — this is a permanent deadlock requiring manual intervention to recover from. A lease attaches a TTL (time-to-live) to the lock — e.g. SET lock_key instance_id NX EX 30 in Redis, atomically setting the key only if it doesn't already exist, with automatic expiry after 30 seconds — so even if the holder crashes and never explicitly releases it, the lock is guaranteed to become available again within the TTL window without any manual recovery step. The holder is expected to periodically renew the lease (extend the TTL) while still actively working, and a crash simply means renewal stops happening, letting the lease expire naturally.
D2What is the classic "slow holder" failure mode with leases, and why is it actually more dangerous than the crash case?▼ answer
Model answer
Consider: instance A acquires the lease and begins the cleanup job, but experiences a long GC pause, scheduler starvation, or network partition (unable to renew the lease in time, but its process is still running and will resume eventually) — the lease expires due to the missed renewal, another instance B correctly acquires it (from the store's perspective, this is completely correct behaviour — the lease genuinely expired), and B starts running the same job concurrently. Then A's pause ends and A resumes execution, believing it still holds the lease — it has no way of knowing time passed without it — and now A and B are both actively running the "exclusive" job simultaneously, which is exactly the correctness violation the whole lock was meant to prevent. This is more dangerous than the crash case specifically because nothing looks wrong from any single instance's point of view — A never received an error, never observed the lease had expired, and has no signal telling it to stop; the violation only becomes visible externally, e.g. as double-processed data or a corrupted result from two writers touching the same resource concurrently. This is the canonical scenario used to argue that distributed locks require more careful design than "just add a TTL," and is discussed at length in the well-known "How to do distributed locking" analysis (Martin Kleppmann's critique of Redlock) — bringing this scenario up by name or by description unprompted is a strong senior/staff-level signal.
D3How do you actually defend against the slow-holder scenario, given that the instance itself can't be trusted to know it lost the lease?▼ answer
Model answer
Fencing tokens are the standard, robust answer: every successful lease acquisition returns a monotonically increasing token (e.g. Redis INCR on a separate counter key, returned alongside the lease) rather than trusting the holder's own belief that it still owns the lease. Critically, the resource being protected (the actual database row, file, or API being written to during the job) must itself check and enforce that the token presented with any write is >= the highest token it has already seen, rejecting writes from stale (lower-numbered) tokens. Concretely: when A acquires the lease it gets token 5; A stalls; B acquires (after A's lease expires) and gets token 6; B writes to the resource, which records "highest token seen: 6"; A resumes and tries to write with its stale token 5 — the resource rejects it outright, because 5 < 6, regardless of whether A itself still believes it holds a valid lease. The critical insight to state explicitly: this pushes the actual correctness guarantee onto the resource itself checking tokens, not onto the lock service or the holder's own good behaviour — the lock/lease mechanism alone, no matter how carefully built, cannot fully solve this problem without cooperation from whatever is being protected. If the protected resource can't be made to check tokens (e.g. it's a legacy system with no such support), the fundamental race is unavoidable, and you'd need a different strategy entirely (e.g. making the job itself idempotent so double-execution is harmless rather than trying to prevent it).
D4If you can't easily add fencing-token support to the protected resource, what's the pragmatic fallback for this specific "nightly cleanup job" use case?▼ answer
Model answer
For a use case specifically like a scheduled cleanup job (as opposed to, say, protecting a financial transaction), the pragmatic senior answer is often to reduce the blast radius of double-execution rather than trying to eliminate it entirely: (1) design the cleanup job itself to be idempotent — deleting already-deleted rows, or recomputing an already-correct aggregate, should be harmless no-ops rather than causing corruption or duplication, which sidesteps the whole fencing-token problem for this specific job type; (2) size the lease TTL generously relative to the job's expected duration (with margin, e.g. 3–5x expected runtime) specifically to make the slow-holder race genuinely rare in practice, while accepting it's not eliminated in theory; (3) add monitoring/alerting for "lease was acquired by two different instances within a short window" as a detectable symptom, even if you can't prevent it outright, so you at least know when it happens rather than it being entirely silent; (4) explicitly document the accepted risk and why — this is a legitimate, common trade-off for lower-stakes scheduled jobs, and articulating "we accepted this risk because the job is idempotent and low-stakes, versus we would need real fencing tokens for a payment-processing job" demonstrates the actual senior skill here: matching the rigor of the solution to the actual stakes of the problem, rather than either over-engineering a low-stakes job or under-engineering a high-stakes one.
✓ Strong

  • Independently identifies or recognizes the slow-holder / GC-pause race condition
  • Names fencing tokens and explains that the protected resource, not the lock service, must enforce them

D1How do structured logging, metrics, and distributed tracing differ in what question each answers, and why do you need all three rather than picking the "best" one?▼ answer
Model answer
Metrics answer "what is the aggregate behaviour of the system right now/over time" — request rate, error rate, latency percentiles, connection pool utilization — cheap to store and query over long time ranges, ideal for dashboards and alerting thresholds, but they lose all per-request detail (you can see p99 latency spiked, but not which specific requests or why). D1Clarify requirements first — what must you nail down before drawing boxes?▼ answer

D2How do you generate short codes — base62 of what, and how do you handle collisions / custom aliases?▼ answer
Model answer
Two common generation strategies: (1) auto-increment ID → base62 — allocate a monotonic u64 (DB sequence, Redis INCR, or a Snowflake-style ID) and encode with alphabet 0-9A-Za-z. Collision-free by construction; length grows with ID space; reverse lookup is just decode → primary key. (2) hash of the long URL (e.g. first N chars of base62(sha256)) — natural idempotency for the same URL, but hash collisions and truncation collisions are real: on insert conflict, append a salt / counter and rehash, or fall back to a random code. Random u64 → base62 with "insert if not exists" retry is also fine at low collision probability. Custom aliases are a separate namespace: validate charset/length, reject reserved words (api, health), and INSERT … ON CONFLICT DO NOTHING (or equivalent) returning 409 if taken — never overwrite. In Rust, keep encode/decode as pure functions over &[u8; 62] alphabet; avoid allocating on the hot redirect path beyond the lookup itself. 
fn to_base62(mut n: u64) -> String {
    const A: &[u8] = b"0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz";
    if n == 0 { return "0".into(); }
    let mut buf = [0u8; 11]; // enough for u64 in base62
    let mut i = buf.len();
    while n > 0 { i -= 1; buf[i] = A[(n % 62) as usize]; n /= 62; }
    String::from_utf8_lossy(&buf[i..]).into_owned()
}

D4Design the single-node Rust service and the hot redirect path with caching.▼ answer
Model answer
axum (or actix-web) in front of a persistence layer: Postgres for durable mappings, or sled/rocksdb for a simpler single-node embedded store. Senior signal: treat the redirect path as a cache problem with a boring durable source of truth, not as a clever distributed consensus problem.

SD9 · Distributed Job Queue
Hard queues retries exactly-once
Prompt
"Design a distributed job queue for background work (email sends, image processing, webhooks): producers enqueue jobs; a pool of workers claims, executes, acks, and retries on failure, with a dead-letter queue for poison messages. Cover visibility timeouts, at-least-once vs exactly-once, and two Rust-friendly backends — Redis Streams and Postgres FOR UPDATE SKIP LOCKED — plus how Tokio workers are structured."
Discussion — sub-questions & model answers
D1What are the core operations and the job state machine?▼ answer
Model answer
Operations: enqueue(payload, opts), claim() / lease, ack(id), nack(id) / retry, extend_lease(id) for long jobs, admin peek into DLQ. States: pending → in_flight (leased) → succeeded | pending (retry) | dead. Each job carries id (UUID), queue, payload (bytes/JSON), attempts, max_attempts, available_at (for backoff/delay), lease_owner, lease_expires_at, optional dedupe_key. Visibility timeout / lease: after claim, the job is invisible to other workers until the lease expires; if the worker crashes without ack, the lease times out and the job becomes claimable again — this is the same lease idea as SD5, applied to work units. Heartbeat/extend_lease for jobs that may run longer than the default visibility window.
D2At-least-once vs exactly-once — what can you actually promise?▼ answer
Model answer
The queue itself almost always provides at-least-once delivery: a worker may process a job, crash before ack, and another worker will process it again after the visibility timeout. Exactly-once end-to-end requires the handler to be idempotent (or a transactional outbox / dedupe store keyed by job_id or dedupe_key). Pure "exactly-once queue semantics" without idempotent side effects is a myth in the crash-failure model — you can get exactly-once effects by combining at-least-once delivery with idempotent processing (e.g. INSERT … ON CONFLICT DO NOTHING on a processed_jobs table inside the same DB transaction as the business write). Senior answer: promise at-least-once from the queue; require idempotent handlers; optionally offer "at-most-once" (no retry) as an explicit footgun for lossy work.
D3Compare Redis Streams vs Postgres SKIP LOCKED as backends.▼ answer
Model answer
Redis Streams: XADD enqueue, consumer groups with XREADGROUP claim, XACK on success; pending entries (XPENDING/XCLAIM) implement visibility timeout for crashed consumers. Fast, simple ops story, great for high throughput ephemeral workloads; durability depends on Redis persistence/config; complex job queries (admin UI by status) are awkward. Postgres FOR UPDATE SKIP LOCKED: 
-- claim batch
UPDATE jobs SET status='in_flight', lease_expires_at=now()+interval '30s', …
WHERE id IN (
  SELECT id FROM jobs
  WHERE status='pending' AND available_at <= now()
  ORDER BY available_at
  FOR UPDATE SKIP LOCKED LIMIT 10
) RETURNING *;
Concurrent workers don't block each other on the same rows — locked rows are skipped. Excellent when jobs and business data share a transaction (transactional enqueue with the app write); richer querying; lower raw throughput than Redis. Pick Postgres when you already have it and need transactional enqueue; pick Redis Streams when job volume is high and payloads are independent of OLTP transactions. SQS-style external queues are also valid — same lease/ack mental model.
D4How do you structure Tokio workers, retries, and the DLQ?▼ answer
Model answer
Run N worker tasks (or a semaphore-limited pool) that loop: claim batch → for each job tokio::spawn or concurrently process with a bound → on success ack; on failure increment attempts, compute backoff (available_at = now + exp_backoff(attempts) with jitter), requeue; if attempts >= max_attempts, move to DLQ (separate stream/table) and alert. Wrap handler execution in tokio::time::timeout so hung handlers don't pin leases forever — on timeout, nack/allow lease expiry. Cancellation safety: if the worker task is cancelled mid-handler, prefer not acking (at-least-once redo) rather than half-applying side effects. Use a separate reaper task that periodically requeues jobs whose lease_expires_at < now() still marked in_flight (needed for Postgres; Redis XCLAIM fills this role). Metrics: queue depth, claim latency, processing time, retry rate, DLQ rate — DLQ depth should page a human.
D5What scaling and poison-pill failure modes matter most?▼ answer
Model answer
Poison messages that always panic/fail must hit max_attempts and land in DLQ — without this, they block the head of a FIFO forever (head-of-line blocking). Prefer per-queue concurrency limits and separate queues by latency class (interactive email vs bulk resize). Hot keys: one noisy tenant flooding a shared queue — fair scheduling via per-tenant queues or weighted claims. Clock skew affecting lease_expires_at — use DB/Redis server time, not worker wall clocks, when possible. Dual delivery after a slow worker that eventually finishes and acks after a reclaimer already gave the job to someone else: this is why idempotency is mandatory, and why lease extension + conservative timeouts matter. Scale workers horizontally; scale the store by partitioning queues (one stream/table partition per shard key).

  • Includes DLQ, backoff+jitter, and a reaper/XCLAIM path for expired leases
⚠ Probe
  • Retries forever with no DLQ / max attempts
  • Uses SELECT FOR UPDATE without SKIP LOCKED and serializes all workers
✗ Concern

  • Cannot explain what happens when a worker dies mid-job

SD10 · Key-Value Store
Hard storage engines LSM replication
Prompt
"Design a durable embedded key-value store API: put, get, delete. Cover the durability story (WAL), storage engine choice (LSM vs B-tree), compaction, and a simple replication story. Tie your reasoning to this packet's write exercises on LSM trees (W56) and B-trees (W52). Call out Rust-specific buffer ownership — who owns the bytes on the read and write paths."
Discussion — sub-questions & model answers
D1What does the public API and durability contract look like?▼ answer
Model answer
Minimal API: put(key: Bytes, val: Bytes), get(key) -> Option<Bytes>, delete(key), optionally scan(start, end), sync() / put with WriteOptions { fsync: bool }. Durability levels: (a) acknowledged after OS page cache write (fast, risk on power loss), (b) acknowledged after WAL fsync (standard "durable put"), (c) acknowledged after replica quorum (distributed). Clarify value size assumptions (fit in memory vs large values/blob indirection), concurrency (single-writer vs concurrent reads), and whether delete is tombstone-based. In Rust, prefer borrowing on get via Bytes (refcounted) or returning Guard that pins an mmap/arena — avoid mandatory Vec<u8> copies on every read. 
trait KvStore {
    fn put(&self, key: Bytes, val: Bytes) -> io::Result<()>;
    fn get(&self, key: &[u8]) -> io::Result<Option<Bytes>>;
    fn delete(&self, key: &[u8]) -> io::Result<()>;
}
D2LSM vs B-tree — when do you pick each? (Connect to W56 / W52.)▼ answer
Model answer
B-tree (W52 mental model): point updates go to leaf pages; good for read-heavy / update-in-place / range scans with predictable latency; write amplification from page splits and fsync of modified pages; familiar Postgres/InnoDB shape. LSM (W56 mental model): writes append to a memtable + WAL, flush to immutable sorted SSTables, reads merge memtable + levels (with bloom filters to skip files); excellent sustained write throughput; pay with read amplification and compaction write amplification / background IO. Pick LSM for write-heavy telemetry/ingest-style KV (RocksDB/sled class); pick B-tree when you need stable read latency and update-heavy hot keys without compaction storms. Strong candidates explicitly say "I'd reuse the invariants from W56/W52" — memtable ordering, tombstones, level compaction vs page-split balancing — rather than inventing a third engine from scratch.
D3Walk the put/get path for an LSM-style design, including compaction and tombstones.▼ answer
Model answer
Put: append WAL record → insert/update memtable (e.g. BTreeMap or crossbeam skiplist) → return after fsync policy. When memtable hits size threshold, freeze it, rotate WAL, flush to L0 SSTable on a background thread/task (spawn_blocking for heavy encode/IO). Delete: write a tombstone; compaction eventually drops covered keys. Get: check memtable → immutable memtables → L0 → lower levels; bloom filter negative checks avoid disk reads; first live value wins (newest seqno). Compaction: merge overlapping SSTables, drop obsolete versions/tombstones when safe, write new files, atomically swap manifest — classic space vs write-amp tradeoff (size-tiered vs leveled). Crash recovery: replay WAL into memtable from last flushed sequence. This is exactly the W56 pipeline at system-design zoom.
D4How does Rust ownership of buffers show up on hot paths?▼ answer
Model answer
Writes: accept Bytes (or Vec<u8>) so the caller can hand off ownership without copy; the WAL encoder may need an owned buffer or write vectored I/O from borrowed slices — avoid double-copy (once into memtable, once into WAL) by sharing Bytes refcounts across both if lifetimes allow. Reads: returning Bytes from an mmap-backed SSTable block cache lets many readers share one allocation; a naive Vec copy per get kills throughput. Lifetime traps: you cannot return a &[u8] into an SSTable file if compaction might unmap/delete that file — either refcount blocks (Arc<[u8]>/Bytes), epoch GC, or copy out. Concurrent readers + compactors need a table file refcount or MVCC manifest; this is where "Rust makes me model the ownership the engine already needed" is the right narrative — the borrow checker is reflecting real use-after-free hazards against recycled SST files.
D5Sketch a simple replication / scale-out story and its failure modes.▼ answer
Model answer
Single-primary async replication: primary appends to WAL, streams records to replicas; replicas apply to their memtable/SST. Ack to client: primary-only (RPO > 0 on primary death) vs quorum fsync (higher latency). Discussion — sub-questions & model answers
D1What clarifying requirements would you pin down first, and what API shape do you propose for resumable chunked upload?▼ answer
Model answer
Clarify: max object size / concurrency per tenant, whether clients can compute checksums upfront, allowed content types, retention of incomplete sessions, and whether the virus scanner is synchronous (block publish) or async (quarantine then promote). API sketch: POST /uploads creates a session (upload_id, recommended chunk_size, expiry); PUT /uploads/{id}/chunks/{n} with body bytes + per-chunk checksum; GET /uploads/{id} returns which chunk indices are already acknowledged (the resume contract); POST /uploads/{id}/complete with the ordered chunk list / composite checksum; optional DELETE /uploads/{id} to abort. D2How do checksums and multipart S3-style upload compose, and where do you verify integrity?▼ answer
Model answer
Three layers, each catching different failures: (1) per-chunk checksum (CRC32C or BLAKE3) validated on receipt so a flaky TCP/HTTP body cannot poison a part — reject and let the client retry that index only; (2) multipart ETags / part numbers when calling UploadPart / CompleteMultipartUpload against S3 — the object store's own integrity for each part; (3) whole-object checksum (SHA-256 or BLAKE3 tree hash) computed incrementally as parts land, compared at complete against a client-supplied digest so reordered/missing parts cannot assemble a silently wrong object. Store chunk_index → (etag, size, checksum) in the session row; complete is idempotent and only succeeds when the set is contiguous 0..N-1. Rust angle: hash with a streaming hasher (blake3::Hasher / sha2) updated from each buffered chunk read — never read_to_end the whole file. Prefer verifying the chunk checksum before calling UploadPart so bad network data never burns multipart part slots or scan quota.
D3How do you stream request bodies in Rust with backpressure, and what goes wrong if you buffer naively?▼ answer
Model answer
async fn put_chunk<S>(
    body: S,
    expected_len: usize,
    hasher: &mut blake3::Hasher,
    sink: &mut impl AsyncWrite + Unpin,
) -> Result<(), Error>
where
    S: Stream<Item = Result<Bytes, Error>> + Unpin,
{
    let mut body = StreamReader::new(body);
    let mut limited = (&mut body).take(expected_len as u64);
    let mut buf = vec![0u8; 64 * 1024];
    loop {
        let n = limited.read(&mut buf).await?;
        if n == 0 { break; }
        hasher.update(&buf[..n]);
        sink.write_all(&buf[..n]).await?; // awaits when S3/client slow
    }
    Ok(())
}
Treat the HTTP body as AsyncRead (via StreamReader over axum/hyper Body) and pipe with a fixed-size buffer — typically 64 KiB–1 MiB — into the object-store upload stream. write_all(...).await applies backpressure: if S3 or the multipart client slows, the write future stays pending, which stops pulling from the request body, which stalls TCP window advancement and naturally slows the client. Loading an entire multi-GB body into Bytes/Vec<u8> defeats the design (OOM under concurrency). Cap Content-Length / enforce chunk size, reject unexpected trailing bytes after take(expected_len), and bound concurrent in-flight chunks per upload_id with a semaphore so one tenant cannot open thousands of half-open streams.
D4Where does the virus-scan hook sit in the lifecycle, and how do you avoid publishing unscanned bytes?▼ answer
Model answer
Keep a strict state machine: receiving → assembled → scanning → clean | quarantined | failed. Multipart CompleteMultipartUpload lands the object under a non-public key (or with a bucket policy that denies public ACL until promoted). Enqueue a scan job (upload_id, object key, checksum) on a durable queue; the scanner streams from object storage (again AsyncRead, not download-to-tmp-on-API-pod) and writes a verdict. Only on clean do you copy/move to the public prefix or flip a metadata flag / CDN purge token that makes the object readable. Never return a final download URL from complete until scan finishes unless the product explicitly accepts async publish with a "processing" state the client polls. Timeouts and scanner outages need a policy: leave in scanning with alert, auto-fail after SLA, and never default-open. Idempotent scan workers + store verdict with the content checksum so retries after redelivery do not double-promote.
D5What failure modes matter for resume, expiry, and orphaned multipart uploads?▼ answer
Model answer
Clients disconnect mid-chunk: that chunk is simply missing from the session bitmap — resume re-PUTs the same index (idempotent overwrite if you allow; or reject duplicate with same checksum). Session TTL must abort both DB state and the S3 multipart upload (AbortMultipartUpload) via a sweeper, or you leak part storage costs indefinitely — a classic ops footgun. Clock skew between instances matters less if expiry is absolute server time in the DB. Partial complete after a crash: make completion a compare-and-swap on session status so two completers cannot race one scan job and one public promote. For at-least-once chunk PUTs, store checksum so a retried PUT with different bytes is rejected rather than silently replacing a good part. Cap outstanding incomplete uploads per user to stop abuse via abandoned multipart sessions.

  • Streams with AsyncRead + bounded buffers and names backpressure via awaited writes
  • Layers per-chunk, multipart, and whole-object checksums with clear failure domains
  • Keeps unscanned objects non-public and aborts orphaned multipart uploads on TTL
⚠ Probe
  • Resumability described only as "HTTP Range" without a session/chunk index contract
  • Virus scan mentioned but still returns a public URL immediately from complete
✗ Concern
  • Buffers entire multi-GB bodies into Vec/Bytes in the API process
  • No plan for AbortMultipartUpload / leaked incomplete uploads

D2What does the Rust verification hot path and axum middleware/extractor look like?▼ answer

struct AuthContext {
    tenant_id: TenantId,
    principal_id: PrincipalId,
    scopes: ScopeSet,
    key_id: KeyId,

struct Authenticated(AuthContext);

#[async_trait]
impl<S> FromRequestParts<S> for Authenticated
where S: Send + Sync {
    type Rejection = AuthError;
    async fn from_request_parts(parts: &mut Parts, state: &S) -> Result<Self, Self::Rejection> {
        let raw = bearer_from(parts)?;
        let (key_id, secret) = split_key(&raw)?;

    }

Tables: Job (id, cron expr or interval, timezone, payload ref, enabled, shard key), JobSchedule materialised fields next_run_at, last_run_at, and JobRun (id, job_id, scheduled_for, status, attempt, lease_owner, fence_token). "Due" means next_run_at <= now() and job enabled. On successful schedule tick, compute the next fire from the cron library in the job's timezone (not the server's local TZ — classic bug). Store scheduled_for as the logical fire instant so catch-up and dedupe key off that timestamp, not "whenever the worker happened to wake." Idempotency key: (job_id, scheduled_for) unique in JobRun.
D2How do leader election / shard ownership work, and how does this relate to SD5 leases?▼ answer
Model answer
Two common designs: (1) single leader evaluates all crons and enqueues runs — simple, limited scale; (2) sharded ownership — hash job_id into N shards; each scheduler instance holds leases on a subset of shards (DB row or Redis key per shard with TTL), renewing while alive (SD5 lease pattern). Only the shard owner scans next_run_at for its shard and creates JobRun rows. Use fencing tokens (SD5) on shard leases so a slow owner that wakes late cannot keep enqueueing after a new owner took over — stamp runs with the fence token and reject stale enqueues. Pure in-process tokio::time timers alone are insufficient across a fleet: timers are for local wakeups; truth of ownership and due-ness lives in the DB. Pattern: lease loop renews shards; a tick loop (tokio::time::interval) per owned shard queries due jobs in batches; workers separately claim runs.
D3How do you approach exactly-once firing semantics in practice?▼ answer
Model answer
True exactly-once across distributed systems is usually at-least-once delivery + idempotent execution. Mechanically: insert JobRun(job_id, scheduled_for) with a unique constraint — only one enqueuer wins; workers UPDATE ... SET status='running', owner=$self WHERE id=$id AND status='pending' (optimistic claim). Handlers must be idempotent for that scheduled_for (or use fencing tokens against side effects, per SD5). Distinguish schedule exactly-once (one run row per logical tick) from side effects exactly-once (requires idempotency keys in the downstream). Missed leases should not create a second row for the same scheduled_for. Retries increment attempt on the same run id rather than creating a new logical fire.
D4How does catch-up after downtime work without stampedes?▼ answer
Model answer
Policies per job: skip (set next_run_at to next future cron tick), fire_once (one catch-up run for the missed window), or backfill_all (generate runs for each missed tick — dangerous for every-minute jobs after a day of downtime). Cap backfill fan-out (max N missed runs) and rate-limit enqueue per shard. After a partition, a newly elected owner should compute missed ticks from last_run_at/next_run_at using the cron iterator, apply the job's catch-up policy, and avoid looping "while due" without a bound — that is how you create a thundering herd into workers. Prefer catch-up on the scheduler (materialise run rows) with worker concurrency limits rather than synchronically executing all missed work on the owner thread.

D2Fan-out on write vs fan-out on read — when do you pick each?▼ answer

D1What is the double-entry ledger data model, and what invariants must always hold?▼ answer

D2How do idempotency keys give you "exactly-once money movement" in practice?▼ answer
Model answer

Discussion — sub-questions & model answers
D1What is the Snowflake bit layout, and what throughput does it imply?▼ answer
Model answer
Classic 64-bit layout (sign bit unused): 41 bits timestamp (ms since custom epoch) ~ 69 years; 10 bits node id (often 5 datacenter + 5 worker = 1024 nodes); 12 bits sequence = 4096 IDs/ms/node. At full tilt one node can mint ~4M IDs/sec; the cluster scales with unique node ids. Persist the epoch and bit splits as constants — changing them breaks ordering/decoding. 
struct Snowflake { node_id: u16, sequence: u16, last_ms: u64 }
// id = (ms << 22) | ((node_id as u64) << 12) | sequence
Expose fn next_id(&mut self) -> Result<u64, WaitOrClockError> (or mutex/atomics for shared generators). Prefer one generator per process/thread shard to avoid lock contention.
D2How are datacenter / worker bits assigned without collisions?▼ answer
Model answer
Node id must be unique for the lifetime of concurrent generators. Options: (1) static config / Kubernetes downward API ordinal; (2) small lease from ZooKeeper/etcd/Redis on startup (TTL heartbeat) mapping to a worker slot; (3) derive from carefully managed host inventory. Colliding node ids ⇒ duplicate IDs under same ms+sequence — silent data corruption risk. On shutdown, release the lease; on steal, fence old processes. Do not hash hostname into 10 bits and hope — birthday collisions happen. Multi-DC: encode DC in high node bits so operators can decode origin; still require per-DC worker uniqueness.
D3How do you handle clock skew, NTP backwards jumps, and sequence exhaustion?▼ answer
Model answer
Keep last_ms. If now < last_ms (clock moved backwards): either wait until clock catches up, refuse with error (safe), or — carefully — increment logical time while tracking max skew tolerance (risky if skew is large). Never blindly emit decreasing timestamps if consumers rely on roughly-ordered IDs. If now == last_ms and sequence would overflow 4096, spin/sleep to next millisecond. Prefer monotonic clocks for elapsed waits (Instant) but Snowflake still needs wall clock for the timestamp field — document NTP dependency. After long pauses, don't allow huge leaps without ops visibility (metric on backward-jump count). VM pauses / live migration are real producers of jumps.
D4When would you choose ULID or UUID v7 instead of Snowflake?▼ answer
Model answer
UUID v4: random, no coordination, but random B-tree inserts and no time order. ULID / UUID v7: 128-bit, timestamp-ordered, sortable as strings/bytes, easy in browsers and any language, no node-id registry — trade larger keys and slightly weaker packing vs 64-bit Snowflake. Prefer ULID/v7 when IDs leave your service boundary (public APIs, client-generated ids) or when ops cost of worker-id assignment dominates. Prefer Snowflake when you need compact u64 PKs, high ingest locality in MySQL/Postgres indexes, and you already run a disciplined node-id allocator. DB sequences / HiLo are simpler for single-primary databases but don't work across independent writable regions without ranges.

Export metrics: ids_issued, wait_for_next_ms, clock_rollback_events. In async services, don't hold a global mutex across .await — generate IDs synchronously under a short lock or use thread-local generators.

Prompt
"Design a multi-tier caching architecture for a read-heavy Rust backend fronted by a CDN: browser/CDN edge, regional reverse-proxy cache, and application / Redis caches in front of Postgres. Discussion — sub-questions & model answers
D1What are the tiers, and what data belongs at each?▼ answer
Model answer
CDN / edge: public, cacheable HTTP responses (images, CSS, anonymized pages) with Cache-Control / surrogate keys; not per-user private JSON unless carefully varied. Regional reverse proxy (Varnish/NGINX/FO): shared hot GETs closer to origin. App-local memory (moka / Arc<Swap<...>>): ultra-hot keys, feature flags, JWKS. Redis / Memcached: shared cross-instance cache for session fragments, rendered feed slices, object blobs by id. Origin DB: source of truth. Rule: the farther from origin, the more coarse-grained and more public the data; private user data stays behind auth and usually skips shared CDN or uses Vary / cookie-busting carefully.
D2How do you approach cache coherence — TTL vs explicit invalidation?▼ answer
Model answer
Pure TTL is simple and eventually consistent; unacceptable alone when users must see edits immediately. Explicit invalidation: on write, delete/update cache keys and purge CDN via surrogate keys / tags (Purge: user-123. Versioned keys (user:123:v={version}) avoid coordinated deletes — bump version in DB, readers naturally miss old keys. Pub/sub invalidation to app-local caches (same idea as SD17 flag snapshots) for process memory. Accept a coherence matrix: CDN may lag seconds; Redis invalidated on write path; local memory soft-TTL + invalidate listener. Document the worst-case stale window as an SLO, not an accident.
D3How do you prevent cache stampede when a hot key expires?▼ answer
Model answer
Classic stampede: popular key TTL ends → N Rust pods simultaneously miss → N identical expensive DB queries. Mitigations: (1) singleflight / request coalescing per key (DashMap<K, Shared<Response>> or tokio oneshot broadcast so one fetches and others await; (2) probabilistic early expiration / soft TTL (XFetch) so refresh is staggered; (3) stale-while-revalidate — serve stale under a lock while one refresher runs; (4) locking in Redis (SET nx px) for cross-node singleflight; (5) never set identical TTLs on millions of keys created together — jitter TTLs. Seniors pick at least two of these and know singleflight alone doesn't help across many pods without a distributed lock or shared cache fill.
D4What is the write path that updates origin and keeps caches honest?▼ answer
Model answer
Preferred: write-through origin, then invalidate (or write-behind only for explicitly loss-tolerant data). Order: commit DB → enqueue invalidation / purge → optionally pre-warm hot key. Invalidating before commit races with readers refilling from old DB snapshots. For CDN, purge by tag after commit; for Redis, DEL or version bump in the same request as success response when possible. If using outbox (SD20 style), commit outbox invalidation events transactionally with the write. Avoid dual-writing DB and cache as two truths — cache is a projection.

}
D5How do TTLs, negative caching, and memory bounds interact?▼ answer
Model answer
Short TTLs for volatile data; long TTLs + explicit invalidation for stable assets. Negative cache 404s briefly to stop hammering origin on missing ids — but keep TTL short and invalidate on create. Bound in-process caches (max entries, max bytes); Redis with maxmemory + LRU/LFU eviction — treat eviction as a miss, not an error. Compress large values; store ids + fetch bodies from object storage when blobs are huge. Watch cardinality: caching per personalized feed key can explode memory — cache shared fragments instead (ties to SD19).

Model answer
Metrics: hit ratio by tier, origin QPS, fill latency, purge latency, stampede lock contention, stale serve rate. Prefer fail-open to origin with strict concurrency limits rather than serving corrupt cross-tenant data. Senior answer names who is allowed to be stale under each failure.

D2Why is delivery at-least-once, and how should customers verify authenticity?▼ answer

D3How do retries, backoff, and DLQ work without hammering a bad endpoint?▼ answer
Model answer
Retry on 5xx, 429, and network errors; typically do not retry 2xx (success) or most 4xx except 408/429. Exponential backoff with jitter (e.g. 1m, 5m, 30m, 2h, …) capped; after N attempts move to DLQ / dead status and alert the customer. Circuit-break / disable an endpoint after consecutive failures to protect your worker fleet (automatic cooldown). Respect Retry-After. Per-endpoint concurrency limits so one slow customer cannot monopolize the pool (bulkhead). Store response bodies truncated for debugging — not unbounded.

Model answer

Bounded concurrency (Semaphore) globally and per endpoint key. Use a dedicated client with connection pools; never unlimited tokio::spawn per delivery. Cancel safety: if timed out, leave lease to expire (at-least-once) rather than acking. Metrics: delivery lag, attempt outcomes, endpoint error rates, pool wait time.

Prompt
"Design a collaborative document editor backend in Rust: multiple users edit concurrently with low latency, see each others' cursors (presence), and reload durable document state after refresh. Choose CRDT vs OT, explain merge/persistence, and explicitly connect the design to the packet's CRDT write exercises — W78 (G/PN-Counter), W79 (OR-Set), and W80 (vector clocks). Discussion — sub-questions & model answers
D1CRDT vs OT for a collaborative doc — which do you pick and why?▼ answer
Model answer
OT (Operational Transform): central server transforms concurrent ops against a linear history; hard to get right, historically used by Google Docs-style systems; needs a strongly ordered op log and careful transform functions. CRDT: commutative/associative/idempotent merges so peers can apply updates in any order and converge — friendlier for decentralized/offline edits and for reasoning in interviews. For a greenfield Rust service, prefer a document CRDT (e.g. RGA/WoOT/Yjs- style text CRDT, or Automerge) with a relay server that does not interpret transforms — it persists and fans out opaque updates. Tie to packet theory: W78/W79 are state-based join-semilattices; text CRDTs are the same algebra at richer types. OT is acceptable if the candidate deeply knows transform correctness and central sequencing — probe that they aren't hand-waving.
D2How do W78–W80 primitives show up inside a real doc system?▼ answer
Model answer
W78 G/PN-Counter: per-replica counters for lamport-ish op counters, reaction tallies, or "chars inserted" analytics — merge via element-wise max (never sum two replica states). Composition (PN = two G-Counters) mirrors composing doc CRDTs from maps/lists. W79 OR-Set: model collaborative presence sets, comment threads, or sticky "open tabs" where concurrent add/remove must be add-wins for unobserved tags — tombstones grow, same GC pressure as doc tombstones. W80 vector clocks: causal metadata on updates; compare → Concurrent flags true conflicts for sibling branches when you layer application-level conflict UI on top of CRDT automatic merge; also used to know when tombstones are safe to GC (all replicas have observed add+remove). Senior candidates map exercises upward rather than treating CRDTs as a library-shaped black box.
D3What is the real-time path: clients, relay, and fan-out?▼ answer
Model answer
Each editor holds local CRDT doc state. On keystroke, client generates an update (state delta or op), applies locally (optimistic), sends to a doc room over WebSocket. Server: authz → append update to durable log → broadcast to other connection actors (SD8 pattern: per-socket Tokio task, broadcast / room pub/sub). Peers merge updates (doc.merge(remote)) — order-independent. Snapshots periodically compact the log so reconnects don't replay forever. Multi-node: Kafka/NATS room topic keyed by doc_id. Use Arc<[u8]> for fan-out of opaque update blobs.

D4How do presence and persistence differ from document convergence?▼ answer
Model answer
Presence (cursors, selections, "user X viewing"): ephemeral, high-churn, usually not in the durable CRDT — broadcast with short TTL / heartbeat; model online users as an OR-Set- like soft state (W79 intuition) that expires on disconnect debounce (SD8 presence). Persisting every cursor move is waste. Document persistence: append-only update log + periodic snapshot blob in object storage/DB; source of truth is the merged CRDT state recoverable from snapshot+tail. On reconnect: load snapshot, apply buffered updates after seq, then join live room. At-least- once WS delivery ⇒ merges must be idempotent (CRDT property; W78 self-merge).
D5What are the hard production issues: tombstones, compaction, and conflicts?▼ answer
Model answer
Deleted characters leave tombstones so concurrent inserts at the same position still converge — documents grow without bound unless compacted. Compaction must preserve CRDT semantics (or freeze a snapshot and reset ids carefully). GC requires causal knowledge that all replicas have seen the delete (vector clocks, W80). Concurrent edits that CRDTs auto-merge may still be semantically wrong (two users rewrite the same sentence) — product may surface branches when CausalOrder::Concurrent on higher-level intents. Large docs: shard by block/fragment CRDTs; avoid single multi-MB merge on every keystroke. Offline edits: queue local updates; merge on reconnect; never require a single global lock for correctness if you chose CRDTs.
D6What security, scale, and testing signals matter?▼ answer
Model answer
Authz per doc on WS upgrade and every update; size-cap updates; rate-limit presence storms. Encrypt payloads at rest if docs are sensitive. Scale: room ownership sticky vs bus fan-out; snapshot workers separate from realtime relays. Testing: property tests that random concurrent update interleavings converge to the same state (same spirit as W78 commutativity tests); fuzz merge idempotence. Observability: merge CPU, room fan-out lag, snapshot age, tombstone ratio. Explicitly refuse to "just last-write-wins the whole file" — that silently loses concurrent edits (anti-pattern vs W80 concurrent detection).
