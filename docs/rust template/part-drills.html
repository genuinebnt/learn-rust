D1FizzBuzz: for n, return "Fizz" if divisible by 3, "Buzz" if by 5, "FizzBuzz" if both, else the number as a string.▼ reveal
Idiomatic solution
fn fizzbuzz(n: u32) -> String {
    match (n % 3, n % 5) {
        (0, 0) => "FizzBuzz".to_string(),
        (0, _) => "Fizz".to_string(),
        (_, 0) => "Buzz".to_string(),
        _ => n.to_string(),
    }
}
Idiomatic tell
Matching a tuple (n % 3, n % 5) in one exhaustive match instead of a chain of nested if/else if is the small detail that signals fluency — it's the same "match on a composite key" instinct you'll reuse constantly in real Rust code.
D2Reverse a string, correctly handling multi-byte UTF-8 characters.▼ reveal
Idiomatic solution
fn reverse_string(s: &str) -> String {
    s.chars().rev().collect()
}
Idiomatic tell
There's no way to index a String by integer position (s[3] doesn't compile) — Rust strings are UTF-8 byte sequences, and slicing at an arbitrary byte offset can split a multi-byte character, which would panic. .chars() iterates by Unicode scalar value, not byte, so .rev() is always safe here. Caveat worth naming out loud: this still isn't fully grapheme-cluster correct for things like combined emoji — that needs the unicode-segmentation crate.
D3Check if a string is a palindrome, ignoring case and non-alphanumeric characters.▼ reveal
Idiomatic solution
fn is_palindrome(s: &str) -> bool {
    let chars: Vec<char> = s.chars()
        .filter(|c| c.is_alphanumeric())
        .map(|c| c.to_ascii_lowercase())
        .collect();
    let n = chars.len();
    (0..n / 2).all(|i| chars[i] == chars[n - 1 - i])
}
Idiomatic tell
Iterator::all() short-circuits on the first mismatch and reads as a direct statement of the palindrome property itself ("for every front/back pair, they're equal") — much cleaner than a manual two-pointer while loop with a mutable bool flag, though that's a perfectly valid alternative if asked to avoid the extra allocation from .collect().
D4Valid Anagram: determine if two strings are anagrams of each other.▼ reveal
Idiomatic solution
use std::collections::HashMap;

fn is_anagram(a: &str, b: &str) -> bool {
    fn counts(s: &str) -> HashMap<char, i32> {
        let mut m = HashMap::new();
        for c in s.chars() { *m.entry(c).or_insert(0) += 1; }
        m
    }
    counts(a) == counts(b)
}
Idiomatic tell
Two things worth having automatic: the entry().or_insert(0) pattern for "increment a counter that might not exist yet" (versus manually checking contains_key then branching), and the fact that HashMap already implements PartialEq comparing contents regardless of insertion order — so counts(a) == counts(b) Just Works without you writing any comparison logic yourself.
D5Group Anagrams: given a list of strings, group the ones that are anagrams of each other.▼ reveal
Idiomatic solution
use std::collections::HashMap;

fn group_anagrams(strs: Vec<String>) -> Vec<Vec<String>> {
    let mut groups: HashMap<Vec<char>, Vec<String>> = HashMap::new();
    for s in strs {
        let mut key: Vec<char> = s.chars().collect();
        key.sort_unstable();  // order doesn't matter for a key — unstable sort is faster, no reason to pay for stability
        groups.entry(key).or_default().push(s);
    }
    groups.into_values().collect()  // drops the keys, yields owned Vec groups directly
}
Idiomatic tell
Using a sorted Vec<char> as the hash key itself — rather than, say, re-sorting and comparing strings pairwise — is the classic anagram-bucketing trick, and it works because Vec<char> automatically derives Eq + Hash when its element type does. Reaching for .into_values() instead of .into_iter().map(|(_, v)| v) is a small but real "have they used HashMap enough to know its full API surface" signal.
D6Longest Substring Without Repeating Characters.▼ reveal
Idiomatic solution
use std::collections::HashMap;

fn length_of_longest_substring(s: &str) -> usize {
    let chars: Vec<char> = s.chars().collect();  // materialize once — can't do O(1) char-index into &str
    let mut last_seen: HashMap<char, usize> = HashMap::new();
    let mut start = 0;
    let mut max_len = 0;

    for (i, &c) in chars.iter().enumerate() {
        if let Some(&prev) = last_seen.get(&c) {
            if prev >= start { start = prev + 1; }
        }
        last_seen.insert(c, i);
        max_len = max_len.max(i - start + 1);
    }
    max_len
}
Idiomatic tell
Note the prev >= start guard — without it, a repeated character seen before the current window's start would incorrectly shrink the window based on stale information. This is the exact bug that separates "memorized the sliding-window shape" from "actually understands why each line is there." Also note the Vec<char> pre-collect for O(1) positional access — &str has no cheap "give me the i-th character" operation.
D7Valid Parentheses: check if a string of brackets ()[]{} is properly balanced and nested.▼ reveal
Idiomatic solution
fn is_valid(s: &str) -> bool {
    let mut stack = Vec::new();
    for c in s.chars() {
        match c {
            '(' | '[' | '{' => stack.push(c),
            ')' => if stack.pop() != Some('(') { return false; },  // compare Option directly — no unwrap
            ']' => if stack.pop() != Some('[') { return false; },
            '}' => if stack.pop() != Some('{') { return false; },
            _ => {}
        }
    }
    stack.is_empty()
}
Idiomatic tell
stack.pop() returns Option<char> — comparing it directly against Some('(') avoids an unwrap() that would panic on an empty stack (unmatched closing bracket) entirely for free, rather than needing a separate empty-check branch.

D8Two Sum: return the indices of the two numbers in an array that add up to a target.▼ reveal
Idiomatic solution
use std::collections::HashMap;

fn two_sum(nums: &[i32], target: i32) -> Option<(usize, usize)> {
    let mut seen: HashMap<i32, usize> = HashMap::new();
    for (i, &n) in nums.iter().enumerate() {
        if let Some(&j) = seen.get(&(target - n)) {
            return Some((j, i));
        }
        seen.insert(n, i);
    }
    None
}
Idiomatic tell
Returning Option<(usize, usize)> rather than panicking or returning a sentinel (usize::MAX, usize::MAX) is itself a small design signal — it makes "no answer exists" a type-checked case the caller must handle, not a documented-but-unenforced convention. One hash-map pass (O(n)) beats the naive O(n²) nested-loop translation from other languages.
D9Merge Intervals: given a list of (start, end) pairs, merge all overlapping intervals.▼ reveal
Idiomatic solution
fn merge_intervals(mut intervals: Vec<(i32, i32)>) -> Vec<(i32, i32)> {
    intervals.sort_by_key(|iv| iv.0);
    let mut merged: Vec<(i32, i32)> = Vec::new();

    for (start, end) in intervals {
        if let Some(last) = merged.last_mut() {  // mutate the last element in place — no pop+push dance
            if start <= last.1 {
                last.1 = last.1.max(end);
                continue;
            }
        }
        merged.push((start, end));
    }
    merged
}
Idiomatic tell
Vec::last_mut() hands back Option<&mut (i32, i32)>, letting you extend the most recent merged interval in place — a candidate reaching for merged.pop() then reconstructing and re-pushing a new tuple is doing extra, unnecessary work that a quick "is there a `_mut` version of this method" instinct avoids.
D10Move Zeroes: given a mutable array, move all zeroes to the end in place, preserving the relative order of non-zero elements.▼ reveal
Idiomatic solution
fn move_zeroes(nums: &mut Vec<i32>) {
    let mut insert_pos = 0;
    for i in 0..nums.len() {
        if nums[i] != 0 {
            nums.swap(insert_pos, i);
            insert_pos += 1;
        }
    }
}
Idiomatic tell
slice::swap(a, b) exchanges two elements by index internally without you needing to fight the borrow checker over holding two mutable references at once (let tmp = nums[i]; nums[i] = nums[j]; nums[j] = tmp; works too, but .swap() is the one-line, harder-to-get-wrong version every experienced Rust dev reaches for automatically).
D11Product of Array Except Self: return an array where each element is the product of all other elements — no division allowed.▼ reveal
Idiomatic solution
fn product_except_self(nums: &[i32]) -> Vec<i32> {
    let n = nums.len();
    let mut result = vec![1; n];

    let mut prefix = 1;                        // pass 1: prefix products, left to right
    for i in 0..n {
        result[i] = prefix;
        prefix *= nums[i];
    }

    let mut suffix = 1;                        // pass 2: fold in suffix products, right to left
    for i in (0..n).rev() {
        result[i] *= suffix;
        suffix *= nums[i];
    }
    result
}
Idiomatic tell
(0..n).rev() for a backward index walk is the idiomatic replacement for the C-style for (int i = n-1; i >= 0; i--) — and it sidesteps a genuine Rust-specific trap: with usize indices, writing the naive translation as let mut i = n - 1; while i >= 0 can underflow-panic (in debug) or infinite-loop (usize can never be negative, so the condition is always true) once i would go below zero.
D12Binary Search: find the index of a target in a sorted array, or report it's absent.▼ reveal
Idiomatic solution
fn binary_search(arr: &[i32], target: i32) -> Option<usize> {
    let mut lo = 0usize;
    let mut hi = arr.len();               // half-open [lo, hi) — hi = len(), never len() - 1
    while lo < hi {
        let mid = lo + (hi - lo) / 2;
        if arr[mid] == target { return Some(mid); }
        else if arr[mid] < target { lo = mid + 1; }
        else { hi = mid; }
    }
    None
}
Idiomatic tell
This is a genuinely Rust-specific gotcha: because usize is unsigned, an empty array (arr.len() == 0) means arr.len() - 1 would underflow — in debug builds that's an immediate panic, in release it silently wraps to usize::MAX. Using the half-open range [lo, hi) with hi = arr.len() (never len() - 1) avoids ever needing that subtraction at all. This exact trap doesn't exist in a signed-integer version of this algorithm in C/C++/Python.
D13Maximum Subarray: find the contiguous subarray with the largest sum (Kadane's algorithm).▼ reveal
Idiomatic solution
fn max_subarray(nums: &[i32]) -> i32 {
    let mut max_ending_here = nums[0];
    let mut max_so_far = nums[0];

    for &n in &nums[1..] {
        max_ending_here = n.max(max_ending_here + n);
        max_so_far = max_so_far.max(max_ending_here);
    }
    max_so_far
}
Idiomatic tell
Calling n.max(other) as an inherent method on the numeric type reads more naturally in a chain than std::cmp::max(n, other) as a free function — both compile to the same thing, but which one a candidate reaches for by default is a small, honest tell about how much Rust they've actually written versus transliterated from another language.

D14Reverse a singly linked list, defined as Option<Box<Node<T>>>, iteratively (no recursion).▼ reveal
Idiomatic solution
struct Node<T> { val: T, next: Option<Box<Node<T>>> }

fn reverse<T>(mut head: Option<Box<Node<T>>>) -> Option<Box<Node<T>>> {
    let mut prev = None;
    while let Some(mut node) = head {
        head = node.next.take();   // pull the rest of the list out, leaving node.next = None
        node.next = prev;         // point this node backward at what we've reversed so far
        prev = Some(node);          // this node is now the new head of the reversed portion
    }
    prev
}
Idiomatic tell
Option::take() is the crux of this entire drill — it replaces the field with None and hands you the original value owned, which is exactly what you need to move node.next out while you still hold node itself. Without .take() you'd be fighting the borrow checker trying to partially move out of a field you don't fully own yet — recognizing .take() as the escape hatch here is one of the single most useful Option methods to have memorized cold.
D15Detect a cycle in a linked list (Floyd's tortoise and hare) — but first: can this Option<Box<Node>> list even have a cycle in idiomatic Rust?▼ reveal
Idiomatic solution
This is the highest-value trick question in this whole drill set. A list built from Option<Box<Node<T>>> owns its nodes exclusively — ownership in Rust forms a strict tree/DAG, so it is structurally impossible for node.next to ever point back to an ancestor of node without either unsafe raw pointers or shared-ownership types. The "detect a cycle" question only makes sense once you pick a representation that can express one: 
struct ArenaNode { val: i32, next: Option<usize> }

fn has_cycle(nodes: &[ArenaNode], head: usize) -> bool {
    let mut slow = head;
    let mut fast = head;
    loop {
        slow = match nodes[slow].next { Some(n) => n, None => return false };
        fast = match nodes[fast].next.and_then(|n| nodes[n].next) {
            Some(n) => n,
            None => return false,
        };
        if slow == fast { return true; }
    }
}
Idiomatic tell
Nodes live in a flat Vec<ArenaNode> "arena" and reference each other by plain usize index instead of pointer — indices are freely Copy-able and comparable, so a cycle is just "two indices become equal," with zero unsafe anywhere. The other two valid answers, worth naming even if not coding live: Rc<RefCell<Node>> with deliberately-created strong-reference cycles (the same shape as the Rc-cycle-leak bug elsewhere in this packet, just intentional this time), or raw pointers under unsafe. Naming this distinction before writing any code is a far stronger senior signal than jumping straight to Floyd's algorithm on an impossible data shape.
D16Binary tree inorder traversal, recursive.▼ reveal
Idiomatic solution
struct TreeNode { val: i32, left: Option<Box<TreeNode>>, right: Option<Box<TreeNode>> }

fn inorder(node: &Option<Box<TreeNode>>, out: &mut Vec<i32>) {
    if let Some(n) = node {
        inorder(&n.left, out);
        out.push(n.val);
        inorder(&n.right, out);
    }
}
Idiomatic tell
Taking &Option<Box<TreeNode>> (a borrow) rather than the owned value means traversal never destroys the tree — obvious once you think in borrows, but candidates coming from pointer-heavy C/C++ backgrounds sometimes reach for consuming ownership out of habit and then can't figure out why the tree "disappeared" after one traversal call.
D17Binary tree inorder traversal, iterative — with an explicit stack, no recursion.▼ reveal
Idiomatic solution
fn inorder_iterative(root: &Option<Box<TreeNode>>) -> Vec<i32> {
    let mut stack: Vec<&TreeNode> = Vec::new();
    let mut current = root.as_deref();   // &Option> -> Option<&T>, no cloning, no unwrap
    let mut out = Vec::new();

    loop {
        while let Some(node) = current {
            stack.push(node);
            current = node.left.as_deref();
        }
        match stack.pop() {
            Some(node) => {
                out.push(node.val);
                current = node.right.as_deref();
            }
            None => break,
        }
    }
    out
}
Idiomatic tell
Option::as_deref() is the tool most candidates forget under pressure: it turns &Option<Box<T>> into Option<&T> in one call, which is exactly the type you need to walk a boxed tree using only plain references — without it you end up writing awkward nested match/.as_ref().map(|b| b.as_ref()) chains to get the same result.
D18Binary tree level-order traversal (BFS), returning each level as its own Vec.▼ reveal
Idiomatic solution
use std::collections::VecDeque;

fn level_order(root: &Option<Box<TreeNode>>) -> Vec<Vec<i32>> {
    let mut result = Vec::new();
    let mut queue: VecDeque<&TreeNode> = VecDeque::new();
    if let Some(node) = root.as_deref() { queue.push_back(node); }

    while !queue.is_empty() {
        let level_size = queue.len();   // snapshot BEFORE the inner loop — this is what separates levels
        let mut level = Vec::with_capacity(level_size);
        for _ in 0..level_size {
            let node = queue.pop_front().unwrap();
            level.push(node.val);
            if let Some(l) = node.left.as_deref() { queue.push_back(l); }
            if let Some(r) = node.right.as_deref() { queue.push_back(r); }
        }
        result.push(level);
    }
    result
}
Idiomatic tell
Capturing level_size = queue.len() before the inner for loop starts pushing this level's children into the same queue is the one line that makes level-separation correct — skip it and you'll iterate a moving target and lose the level boundaries entirely. Same VecDeque + as_deref() combo as the earlier drills, now composed together.

D19Write a generic function largest that returns the largest element in a slice, for any orderable type.▼ reveal
Idiomatic solution
fn largest<T: PartialOrd + Copy>(list: &[T]) -> T {
    let mut max = list[0];
    for &item in list.iter() {
        if item > max { max = item; }
    }
    max
}
Idiomatic tell
PartialOrd, not Ord — this is what lets the function also work for f64/f32, which can't implement total Ord because NaN isn't comparable to anything, including itself. The Copy bound is what justifies max = item instead of needing Clone and a .clone() call — knowing exactly which trait bound unlocks which operation, without an IDE's inline error to guide you there, is the whole point of this drill.
D20Manually implement Display and Debug for a Point { x: i32, y: i32 } struct — no #[derive(...)].▼ reveal
Idiomatic solution
use std::fmt;

struct Point { x: i32, y: i32 }

impl fmt::Display for Point {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "({}, {})", self.x, self.y)
    }
}

impl fmt::Debug for Point {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        f.debug_struct("Point").field("x", &self.x).field("y", &self.y).finish()
    }
}
Idiomatic tell
The exact signature — fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result — is one of the most-forgotten-under-pressure signatures in Rust precisely because you almost never write it by hand in real projects (#[derive(Debug)] covers 95% of cases). Using f.debug_struct(...).field(...).finish() for the manual Debug impl mirrors exactly what the derive macro itself generates — a strong "read the derived output before" signal versus hand-writing a raw write! call for Debug too.
D21Implement a fallible TryFrom<i32> and an infallible From<Direction> conversion for an enum Direction { North, East, South, West }.▼ reveal
Idiomatic solution
enum Direction { North, East, South, West }

impl TryFrom<i32> for Direction {
    type Error = String;
    fn try_from(v: i32) -> Result<Self, Self::Error> {
        match v {
            0 => Ok(Direction::North),
            1 => Ok(Direction::East),
            2 => Ok(Direction::South),
            3 => Ok(Direction::West),
            other => Err(format!("invalid direction: {other}")),
        }
    }
}

impl From<Direction> for &'static str {
    fn from(d: Direction) -> Self {
        match d {
            Direction::North => "N", Direction::East => "E",
            Direction::South => "S", Direction::West => "W",
        }
    }
}
Idiomatic tell
Choosing TryFrom (with an associated Error type) for the integer-to-enum direction specifically because not every i32 is a valid Direction, versus plain From for enum-to-&str because that direction is always infallible, is exactly the judgment call this drill is testing — reaching for the wrong one of the pair (e.g. panicking inside a From impl instead of using TryFrom) is a real, common mid-level mistake.
D22Model a traffic light as an enum state machine with a next(self) -> Self transition method.▼ reveal
Idiomatic solution
enum TrafficLight { Red, Yellow, Green }

impl TrafficLight {
    fn next(self) -> Self {
        match self {
            TrafficLight::Red => TrafficLight::Green,
            TrafficLight::Green => TrafficLight::Yellow,
            TrafficLight::Yellow => TrafficLight::Red,
        }
    }
}
Idiomatic tell
next(self) takes self by value, not &self — a state transition replaces the state entirely rather than mutating in place, so consuming the old state and returning the new one is the honest signature (this is the same consuming-self instinct behind the builder pattern). Also deliberately no wildcard _ => ... arm: an exhaustive match means adding a new light color later forces a compile error here until you decide what it transitions to — the compiler becomes a checklist for you.
D23Roman numeral to integer conversion (e.g. "MCMXCIV" → 1994).▼ reveal
Idiomatic solution
fn roman_to_int(s: &str) -> i32 {
    fn value(c: char) -> i32 {
        match c {
            'I' => 1, 'V' => 5, 'X' => 10, 'L' => 50,
            'C' => 100, 'D' => 500, 'M' => 1000,
            _ => 0,
        }
    }

    let chars: Vec<char> = s.chars().collect();
    let mut total = 0;
    for i in 0..chars.len() {
        let curr = value(chars[i]);
        if i + 1 < chars.len() && curr < value(chars[i + 1]) {
            total -= curr;   // smaller numeral before a larger one — subtractive notation (IV, IX, XC...)
        } else {
            total += curr;
        }
    }
    total
}
Idiomatic tell
A bounds-checked one-ahead peek (i + 1 < chars.len() && ...) is perfectly idiomatic here and arguably clearer than reaching for a Peekable iterator — knowing when the "fancier" iterator abstraction is not worth it, versus reflexively reaching for one every time, is itself a mark of practical judgment rather than syntax showing-off.

D24Write double_n_times, generic over a closure parameter bounded by Fn(i32) -> i32, that applies the closure to a value n times.▼ reveal
Idiomatic solution
fn double_n_times<F>(start: i32, n: u32, f: F) -> i32
where
    F: Fn(i32) -> i32,
{
    let mut value = start;
    for _ in 0..n { value = f(value); }
    value
}
Idiomatic tell
F is declared as its own generic parameter, then constrained in a where clause (or inline as F: Fn(i32) -> i32 in the angle brackets — both are equally correct) — the closure parameter itself, f: F, is never mutable here since Fn only ever needs &self to call. Forgetting the generic parameter entirely and trying to write f: Fn(i32) -> i32 directly as a "concrete type" is the single most common syntax slip under pressure — Fn(i32) -> i32 is a trait, not a type, and can only appear behind &dyn/Box<dyn _> or as a generic bound.
D25Write count_calls, taking a boxed, owned FnMut(i32) -> i32 trait object as its parameter, and call it exactly twice with the running result.▼ reveal
Idiomatic solution
fn count_calls(start: i32, mut f: Box<dyn FnMut(i32) -> i32>) -> i32 {
    let once = f(start);
    f(once)
}

fn main() {
    let mut calls = 0;
    let closure: Box<dyn FnMut(i32) -> i32> = Box::new(move |x| { calls += 1; x + 1 });
    println!("{}", count_calls(0, closure));  // 2
}
Idiomatic tell
Box<dyn FnMut(i32) -> i32> is taken by value, not by reference, since the function owns and fully consumes it here — and the parameter needs its own mut f: binding (shadowing/rebinding as mutable) to legally call a FnMut more than once, exactly like the plain generic case. Note also the closure itself needs move to take ownership of calls before it's boxed and handed off — without move, the closure would try to borrow calls, and a boxed trait object with a borrowed capture can't outlive the function it was created in as easily as an owned one.
D26Read a text file into a Vec<String>, one entry per line, using buffered I/O.▼ reveal
Idiomatic solution
use std::fs::File;
use std::io::{self, BufRead, BufReader};

fn read_lines(path: &str) -> io::Result<Vec<String>> {
    let file = File::open(path)?;
    BufReader::new(file).lines().collect()
}
Idiomatic tell
.lines() yields io::Result<String> per line, not a bare String — but Iterator<Item = Result<T, E>>::collect() can target Result<Vec<T>, E> directly (via the FromIterator impl for Result), short-circuiting on the first error — this is why the whole function body can be just BufReader::new(file).lines().collect() with no explicit loop or error handling at all, and it's one of the most useful "collect into a Result" tricks to have memorized cold.
D27Write a Vec<String> to a file, one entry per line, using buffered I/O — and make sure a write failure is actually observable.▼ reveal
Idiomatic solution
use std::fs::File;
use std::io::{self, BufWriter, Write};

fn write_lines(path: &str, lines: &[String]) -> io::Result<()> {
    let mut writer = BufWriter::new(File::create(path)?);
    for line in lines {
        writeln!(writer, "{line}")?;
    }
    writer.flush()  // returns io::Result<()> directly — the function's final expression, no trailing Ok(()) needed
}
Idiomatic tell
File::create (not File::open) is what creates-or-truncates for writing — mixing these two up is a common slip. Ending the function with writer.flush() as the final expression (rather than calling it with ? and then a separate Ok(())) works because flush() already returns exactly the io::Result<()> the function needs — a small but genuine "do you reach for the minimal correct code" tell.

use std::pin::Pin;

trait Fetcher {

D29Write a function generic over R: BufRead that counts how many lines contain a given substring — then call it with both a BufReader<File> and a plain &[u8], unchanged.▼ reveal
Idiomatic solution
use std::io::{self, BufRead};

fn count_matching_lines<R: BufRead>(reader: R, needle: &str) -> io::Result<usize> {
    let mut count = 0;
    for line in reader.lines() {
        if line?.contains(needle) {
            count += 1;
        }
    }
    Ok(count)
}

fn main() -> io::Result<()> {
    let file_reader = io::BufReader::new(std::fs::File::open("log.txt")?);
    count_matching_lines(file_reader, "ERROR")?;

    let in_memory: &[u8] = b"ok\nERROR: oops\nok\n";  // &[u8] implements BufRead directly — same function, zero changes
    assert_eq!(count_matching_lines(in_memory, "ERROR")?, 1);
    Ok(())
}
Idiomatic tell
Bounding the parameter by R: BufRead rather than accepting a concrete BufReader<File> is the entire point — &[u8] implements BufRead natively (no wrapping needed), so the exact same function that scans a real log file also drives a unit test with an in-memory byte slice and zero I/O. Reaching for the trait bound instead of the concrete type "just because that's what the file-handling example used" is the mid-to-senior line this drill is drawing.
D30Connect to a TCP server, send one line, read one line back — using TcpStream plus buffered I/O, no async runtime.▼ reveal
Idiomatic solution
use std::io::{self, BufRead, BufReader, Write};
use std::net::TcpStream;

fn send_and_receive(addr: &str, message: &str) -> io::Result<String> {
    let mut stream = TcpStream::connect(addr)?;
    writeln!(stream, "{message}")?;  // write the request over the raw stream — no BufWriter needed for one line

    let mut reader = BufReader::new(stream);  // only one direction needed after the write, so no try_clone() required here
    let mut reply = String::new();
    reader.read_line(&mut reply)?;
    Ok(reply)
}
Idiomatic tell
Order matters: the write happens on the plain stream before it's moved into BufReader::new(stream) — once wrapped, BufReader owns it. Because this drill only needs to read after it's done writing (a strict request/response, not interleaved read-while-write like the echo server exercise), there's no need for try_clone() at all — recognizing when the split is unnecessary is just as important a signal as knowing how to do it when it is.
D31Sort a Vec<Employee> (with department: String, salary: f64 fields) by department alphabetically, then by salary descending within each department — using sort_by, not a hand-rolled sorting algorithm.▼ reveal
Idiomatic solution
struct Employee { name: String, department: String, salary: f64 }

fn sort_employees(employees: &mut Vec<Employee>) {
    employees.sort_by(|a, b| {
        a.department
            .cmp(&b.department)  // primary key: department, ascending, via Ord on String
            .then_with(|| b.salary.partial_cmp(&a.salary).unwrap())  // secondary key: salary, DESCENDING (b vs a, reversed)
    });
}
Idiomatic tell
Two things have to be right: .then_with(...) chains a secondary comparator that only runs when the primary one reports Equal — this is the idiomatic way to express "sort by A, then by B" without manually nesting match arms. Second, salary is f64, which does not implement Ord (only PartialOrd, because NaN compares unequal to everything, breaking Ord's total-ordering requirement) — so .partial_cmp(...).unwrap() is required, and reversing the two operands (b.salary.partial_cmp(&a.salary) instead of a vs b) is the correct, idiomatic way to get descending order without a separate .reverse() call bolted on afterward. sort_by (not sort_unstable_by) is also the right default here specifically because employees with identical department and salary should keep their original relative order — a stability guarantee sort_unstable_by does not make.
