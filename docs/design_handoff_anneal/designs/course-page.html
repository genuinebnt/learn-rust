2B · STAGE 04/EASY/~10 MIN/5 TESTS

hash_to_directory_index: the top bits.

By the end you can keep the top or the low k bits of a u32, and you know why a shift by the full width panics in Rust and is undefined behaviour in C.

01 · THE PROBLEM

Which directory does a hash go to?

An extendible hash table has three levels: a header page, up to 2max_depth directory pages, and buckets. Every lookup starts at the header, which has one job: pick a directory from the top max_depth bits of the hash.

Why the top? Each directory later splits itself on the low bits, one at a time, as it grows. Using opposite ends means the two levels never compete for the same bits. Try it:

CHECK YOURSELF

With max_depth = 3, which directory does 0x6000_0000 go to?

0x6 is 0110, so the top three bits are 011: directory 3.

02 · THE INTERFACE

What you start with

Your starter code already has the method. You wrote max_depth() in stage 3, so call it here.

Two tools do all the work. x >> n drops the low n bits of x, so to keep the top k bits of a u32 you shift by 32 - k. And match lets one value take its own path.

In depthShifting by the full width in C, C++ and Rust

What is x >> 32 for a 32-bit x? Not 0, in any of the three:

C, C++Undefined behaviour. x86 masks the amount to 5 bits, so you get x back.
Rust, debugPanics: attempt to shift right with overflow.
Rust, releaseMasked like x86: x >> 0, which is x.

The obvious C++, hash >> (32 - max_depth_), has this bug at depth 0: on x86 it quietly returns the whole hash. Rust's debug build turns the same line into a panic a test catches.

Porting rule: every shift whose amount comes from data needs a look at 0 and at the type's width.

Hint 1Which shift keeps the top bits?

Shifting right by n drops the low n bits. To keep the top max_depth bits, drop the other 32 - max_depth.

Hint 2Why does depth 0 need care?

At depth 0 that is a shift by 32, which panics in a debug build. Give 0 its own match arm, or use checked_shr and fall back to 0.

Common mistakes

1
Keeping the low bits instead of the top

hash & ((1 << d) - 1) is the directory's rule (stage 6), not the header's. Fails every test except a_depth_of_zero….

2
No case for depth 0

hash >> (32 - d) panics at depth 0: "attempt to shift right with overflow".

3
Shifting by d instead of 32 - d

That drops only the low d bits, so the answer is far too big.

4
Casting to i32 first

A signed right shift copies the sign bit in, so 0x8000_0000 comes out negative. Stay in u32.
