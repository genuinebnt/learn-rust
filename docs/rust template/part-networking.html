OSI/TCP Mental Model for Rust Engineers
Questions & model answers
Q1Map the OSI / Internet layers to what a Rust backend engineer actually touches. Where do sockets live?▼ answer
Model answer
Practical stack: L3 IP (routing, NAT), L4 TCP/UDP (ports, connections/datagrams), L5–7 as application protocols (TLS, HTTP, gRPC, custom framing). You rarely configure L2; you care about MTU/fragmentation when debugging. A socket is the kernel API endpoint for L4: bind/listen/accept or connect, then read/write byte streams (TCP) or datagrams (UDP). In Rust, std::net::TcpStream / TcpListener wrap OS sockets; tokio::net::TcpStream is the async equivalent registered with the reactor. TLS and HTTP sit above the socket as byte transformers — rustls + hyper/axum do not replace TCP; they speak over it. Interview signal: separate "connection" (TCP) from "request" (HTTP) and "stream" (HTTP/2).
Q2What does TCP give you as a byte stream, and what does it deliberately not provide?▼ answer
Model answer
TCP provides reliable, ordered, congestion-controlled delivery of a bidirectional byte stream between two endpoints. It does not preserve message boundaries — one write can arrive as multiple reads and vice versa (coalescing). It does not encrypt, authenticate peers, or define application framing. Application must: (1) frame messages, (2) handle partial reads, (3) decide idempotency for app-level retries after reconnect. Saying "TCP is message-oriented" is a common junior mistake; seniors talk about stream + framing + connection lifecycle (TIME_WAIT, half-close with shutdown).
Q3Contrast blocking sockets, non-blocking + readiness (mio), and async (Tokio). When would you still touch mio?▼ answer
Model answer
Blocking: read/write park the OS thread until complete — simple, but one thread per connection does not scale. Non-blocking + readiness: set O_NONBLOCK, use epoll/kqueue/IOCP; when the kernel says readable/writable, try the syscall; on EAGAIN wait again. mio is Rust's portable readiness layer. Async (Tokio): tasks yield at .await; the runtime multiplexes many connections on few worker threads using mio (or io_uring on Linux when enabled) under the hood. Prefer Tokio for almost all services. Touch mio directly for custom reactors, embedding in non-Tokio event loops, or ultra-specialized runtimes — and know that tokio::net types must not be used from blocking contexts without spawn_blocking / proper runtime entry. Never call blocking std::net I/O on a Tokio worker thread.
Q4Walk through accept → read → write on tokio::net::TcpListener. Where do backpressure and cancellation show up?▼ answer
Model answer
use tokio::net::TcpListener;
use tokio::io::{AsyncReadExt, AsyncWriteExt};

let listener = TcpListener::bind("0.0.0.0:8080").await?;
loop {
    let (mut socket, _addr) = listener.accept().await?;
    tokio::spawn(async move {
        let mut buf = [0u8; 4096];
        loop {
            let n = socket.read(&mut buf).await?; // 0 = EOF / peer half-close
            if n == 0 { break; }
            socket.write_all(&buf[..n]).await?;
        }
        Ok::<(), std::io::Error>(())
    });
}
accept awaits readiness then accepts; unbounded spawn per connection can DoS your process — bound with a Semaphore. read/write_all await socket readiness; if the peer is slow, write_all applies TCP backpressure by not completing. Task cancellation (dropping the future, select timeout) aborts the in-flight syscall wait; ensure protocol state machines treat cancel as connection teardown. Prefer framed codecs over raw echo loops for real protocols.
Q5Scenario: p99 latency spikes only under load, CPU is low. What networking hypotheses do you check first?▼ answer
Model answer
Low CPU + high latency often means waiting: (1) accept queue / file-descriptor limits (ulimit -n, somaxconn), (2) worker exhaustion from accidental blocking on the runtime, (3) downstream connection pool saturation, (4) TCP retransmits / buffer bloat, (5) DNS or TLS handshake storms on new connections, (6) unbounded fan-out without concurrency limits. Check accept RPS vs active connections, Tokio busy/idle metrics, pool wait time, and TcpStream connect timeouts separately from app timeouts. Strong candidates separate "slow handler" from "slow network path" before rewriting business logic.

TCP Reliability, Nagle, Delayed ACK, Keepalive
Questions & model answers
Q1How does TCP achieve reliability? What failure modes still leak to the application?▼ answer
Model answer
Sequence numbers, ACKs, retransmits, and checksums recover lost/reordered packets within a live connection. Congestion control (slow start, cwnd) throttles senders. What still leaks up: connection reset (ECONNRESET, timeout (no ACK within RTO budget), half-open connections after silent middlebox drops, and "write succeeded locally but peer never processed" after a crash between TCP ACK and app commit. Reliability is transport delivery to the peer kernel buffer, not exactly-once application processing. APIs still need idempotency keys and application ACKs for critical mutations.
Q2What is Nagle's algorithm, and when does it bite request/response APIs?▼ answer
Model answer
Nagle coalesces small writes to reduce tiny packets: it may delay sending a small segment until an ACK arrives or a full MSS accumulates. Combined with delayed ACK (receiver waits ~40ms before ACKing hoping to piggyback), you get classic 40ms latency cliffs on chatty protocols that write header then body as separate syscalls. Fix: enable TCP_NODELAY (socket.set_nodelay(true)? on tokio::net::TcpStream / hyper clients, and batch logical writes (one buffer / vectored write) so you are not relying on Nagle for efficiency. Use Nagle only when you intentionally send many tiny writes and care more about packet count than latency — rare for RPCs.
Q3TCP keepalive vs application heartbeats — which should an API use?▼ answer
Model answer
SO_KEEPALIVE probes idle connections at OS timescales (often hours by default; tunable via idle/interval/count). Good as a last-resort cleanup of dead peers through NATs, but too slow for UX or load-balancer draining. Application heartbeats (WebSocket ping, gRPC keepalive, Redis PING, custom idle frames) detect death in seconds and keep NAT mappings fresh. For HTTP APIs: idle timeouts on servers/proxies matter more than TCP keepalive; clients should reconnect with jitter. In Rust, set TcpStream::set_keepalive if available/platform-supported, but design protocol-level pings for long-lived streams (tonic/h2 settings, axum WebSocket ping).
Q4Scenario: a Rust microservice sees occasional stuck clients for ~40ms on tiny POSTs. How do you confirm Nagle/delayed-ACK and fix it?▼ answer
Model answer
Capture with tcpdump/Wireshark: look for small PSH segments waiting for ACK before the next send. Check whether the client library writes headers and body separately. Confirm TCP_NODELAY is off (getsockopt). Fix on both ends if needed: nodelay + single-buffer writes; ensure HTTP/1.1 clients use keep-alive properly so you are not also paying handshake costs. Measure before/after at p50/p99 — a true Nagle issue shows a sharp ~40ms mode, not a smooth shift. Mentioning packet captures + nodelay is the senior signal; guessing "add more pods" is not.

Framing Protocols & Tokio Codecs
Questions & model answers
Q1Why must every TCP application protocol define framing? Compare length-prefix, delimiter, and HTTP-ish framing.▼ answer
Model answer
Because TCP is a byte stream, the receiver must know where message N ends and N+1 begins. Length-prefix: u32 BE length + payload — binary-friendly, O(1) boundary, needs max-length caps. Delimiter: newline/NULL terminated — easy for text; fails if payload can contain the delimiter unless escaped. HTTP-ish: headers until \r\n\r\n, then body sized by Content-Length or chunked encoding — rich but complex (trailers, pipelining, smuggling). Prefer length-prefix for internal binary RPC; use battle-tested HTTP stacks (hyper) rather than hand-rolling HTTP.
Q2How does tokio_util::codec::{Decoder, Encoder, Framed} work? Sketch a length-prefix decoder.▼ answer
Model answer
Decoder::decode inspects a BytesMut buffer, returns Ok(None) if it needs more bytes, Ok(Some(frame)) when a full frame is split off, or Err on protocol violation. Framed/FramedRead repeatedly fills the buffer from the socket and calls decode. Example sketch: 
impl Decoder for LenPrefix {
    type Item = Bytes;
    type Error = std::io::Error;
    fn decode(&mut self, src: &mut BytesMut)
        -> Result<Option<Bytes>, Self::Error> {
        if src.len() < 4 { return Ok(None); }
        let n = u32::from_be_bytes(src[..4].try_into().unwrap()) as usize;
        if n > self.max { return Err(...); }
        if src.len() < 4 + n { return Ok(None); }
        src.advance(4);
        Ok(Some(src.split_to(n).freeze()))
    }
}
Always enforce max before waiting for n bytes — otherwise a malicious length allocates you into OOM (see NET12).
Q3What are common framing bugs in interviews and production?▼ answer
Model answer
(1) Assuming one read = one message. (2) Using u32 length without endianness agreement. (3) Forgetting that length includes/excludes the header inconsistently across peers. (4) Delimiter protocols without escaping. (5) Reusing a buffer incorrectly so remaining bytes from message N+1 are discarded. (6) Blocking decode on incomplete data instead of returning "need more". Codecs + property tests with split reads (proptest partial chunks) catch most of these. Prefer tokio_util::codec::LengthDelimitedCodec when it fits before inventing a format.
Q4When do you choose custom framing vs gRPC/HTTP? Rust ecosystem callouts.▼ answer
Model answer
Custom framing for latency-sensitive binary meshes, game/replication protocols, or constrained devices — you own versioning, auth, and observability. Prefer HTTP/2 + gRPC (tonic) or HTTP + axum when you want intermediaries, tracing headers, load balancers, and boring security defaults. Middle ground: length-prefix + protobuf over TLS. Ecosystem: tokio_util::codec, asynchronous-codec, prost/parity-scale-codec for payloads; never claim custom TCP RPC is "simpler" without counting auth, retries, and ops tooling.

UDP / Datagrams — When to Use
Questions & model answers
Q1What does UDP provide vs TCP? Name real systems that correctly choose UDP.▼ answer
Model answer
UDP is connectionless datagrams: best-effort, unordered (in practice often mostly ordered but not guaranteed), no congestion control or retransmission at L4. Each recv_from is one datagram (up to size limits) — message boundaries are preserved, unlike TCP. Good fit: DNS queries, DHCP, voice/video (with app codecs), game state, telemetry/metrics fan-in, QUIC (reliability built in userspace over UDP), and some discovery protocols. Bad fit: "I want TCP but without the handshake" for banking transfers without redesigning reliability.
Q2How do you use tokio::net::UdpSocket correctly? What about connected UDP?▼ answer
Model answer
Bind, then recv_from/send_to with buffers sized to expected MTU (often 1500 minus headers; beware jumbo/path MTU). Truncation: if the buffer is smaller than the datagram, data is cut — detect via APIs that report size. Connected UDP (connect on a UDP socket) filters peer address and lets you use send/recv; it is not a TCP-like session — still no reliability. For fan-in servers, one socket + many peers is typical; for clients, connected mode simplifies icmp error delivery on some OSes. Always handle WouldBlock via async awaits; never spin.
Q3If you need reliability on UDP, what do you reinvent — and when should you just use QUIC?▼ answer
Model answer
Homegrown reliability needs: sequence numbers, ACKs/NACKs, retransmit timers, congestion control, RTT estimation, connection IDs for NAT rebinding, and ideally encryption — i.e. most of QUIC/TCP. Prefer QUIC (quinn in Rust) when you want multiplexed streams, TLS 1.3-integrated security, and modern loss recovery without head-of-line blocking across streams. Roll your own only for tiny constrained domains (e.g. loss-tolerant state snapshots where latest wins) and document which properties you intentionally skip.
Q4Scenario: metrics agent sending counters over UDP drops under load. What do you change?▼ answer
Model answer
UDP drops are expected when kernel buffers fill — increase SO_RCVBUF/SO_SNDBUF, batch/aggregate metrics client-side, sample, or switch hot paths to a reliable channel (TCP/gRPC) for critical counters. Add sender-side non-blocking send with drop counters (metric about metrics). Do not "fix" silent loss without making loss visible. Interviewers like: "UDP is best-effort; SLOs must either tolerate loss or change transport."

TLS with rustls — Handshake, Certs, ALPN
Questions & model answers
Q1What does a TLS handshake establish, and where does rustls sit relative to TCP?▼ answer
Model answer
TLS runs over a reliable stream (usually TCP) or is integrated into QUIC. Handshake negotiates version/ciphers, authenticates the server (and optionally the client) via certificates, and derives symmetric keys for encryption/integrity of application data. rustls is a pure-Rust TLS implementation: you feed it bytes from the socket and it emits plaintext / wants ciphertext written — typically via tokio-rustls wrapping TcpStream. It does not replace TCP; failed handshakes look like connection errors before any HTTP request is parsed.
Q2Explain server cert validation, SANs, and common misconfigurations in Rust clients.▼ answer
Model answer
Clients verify: chain to a trusted root (webpki roots / custom CA), validity period, and hostname against certificate SANs (DNS/IP). Mistakes: disabling verification in prod ("just for staging" that ships), pinning the wrong CA, using IP connect while cert only has DNS SAN, forgetting intermediate certs on the server, and clock skew failing NotBefore/NotAfter. In rustls, build a ClientConfig with proper root store; for mTLS add client cert resolver on the client and server_config.client_verifier on the server. Never leave dangerous() verifier helpers enabled outside tests.
Q3What is ALPN and why does HTTP/2 care?▼ answer
Model answer
ALPN (Application-Layer Protocol Negotiation) lets the TLS handshake advertise protocols like h2 and http/1.1. HTTP/2 over TLS requires ALPN h2; without it, clients fall back to HTTP/1.1. gRPC over TLS similarly depends on h2. In rustls, set ClientConfig::alpn_protocols / server ALPN lists; hyper/tonic wire this when configured. Debugging "why am I on HTTP/1.1?" often ends at missing ALPN or a middlebox that does not forward it.
Q4Session resumption, 0-RTT risks, and cert rotation — what should a senior mention?▼ answer
Model answer
Tickets/PSK resumption cut handshake RTTs for repeat connections — important for short-lived clients and mobile. TLS 1.3 0-RTT data can be replayed; only send idempotent requests in 0-RTT (most HTTP stacks disable or carefully gate it). Cert rotation: overlap old/new certs, automate with ACME, reload server config without dropping long-lived connections if possible (graceful config swap). rustls configs are typically rebuilt and swapped under an Arc; hot-reload strategies matter at the acceptor. Mention OCSP/CRL sparingly; stapling and short-lived certs are the modern direction.

HTTP/1.1 vs HTTP/2 vs HTTP/3 (QUIC) for Service Design
Questions & model answers
Q1Contrast HTTP/1.1 connection usage with HTTP/2 streams for backend fan-out.▼ answer
Model answer
HTTP/1.1: one request at a time per connection (pipelining exists but is cursed); browsers open many connections; servers see connection churn and head-of-line blocking at the HTTP layer. Keep-Alive reuses connections but concurrency needs a pool of sockets. HTTP/2: many streams multiplexed on one TLS+TCP connection, binary framing, HPACK headers — better for many parallel RPCs to one host, but TCP loss still blocks all streams (transport HOL). Rust: hyper supports both; axum servers typically speak h1/h2 based on ALPN; tonic needs h2.
Q2What problems does HTTP/3 / QUIC solve that HTTP/2-over-TCP does not?▼ answer
Model answer
QUIC runs on UDP with userspace loss recovery and encryption by default (TLS 1.3 integrated). Independent streams avoid TCP-wide head-of-line blocking when packets drop. Connection IDs survive NAT rebinding (mobile networks). Handshake often combines transport+TLS in 1-RTT (0-RTT optional). Costs: UDP blocked on some networks (fallback to h2), more complex middleboxes/load balancers, different tuning knobs. For public edge/mobile, H3 can win; for east-west datacenter gRPC over h2/TCP remains dominant and simpler ops.
Q3How do these choices affect timeouts, retries, and load balancing?▼ answer
Model answer
H1 pools: many conns → LB sees fine-grained distribution; idle timeouts kill unused sockets. H2/H3: fewer conns, long-lived → imbalance if LB is conn-based (need L7 or careful power-of-two choices); a single stalled connection hurts many streams. Retries: safe only for idempotent requests; gRPC/HTTP retry policies must avoid thundering herds (jitter). Timeouts: separate connect, TLS, request headers, and body/streaming deadlines — hyper/tower layers make this explicit. Do not use one giant 30s timeout for everything.
Q4Scenario: internal gRPC mesh vs public REST. Which HTTP version story do you tell?▼ answer
Model answer
Internal: tonic/gRPC over HTTP/2 + mTLS (or mesh sidecar), connection pooling per destination, deadlines as first-class metadata, protobuf contracts. Public: REST/JSON over HTTPS (h1/h2, maybe h3 at CDN edge), axum/hyper, CDN caching where possible, stricter auth and rate limits. Avoid exposing raw gRPC to browsers without grpc-web/proxy. Strong answer names trade-offs (streaming, codegen, human debuggability) rather than "gRPC is always faster."

Backpressure: Socket → Application (Tokio)
Questions & model answers
Q1What is backpressure in a network service, and why do unbounded queues hide it?▼ answer
Model answer
Backpressure means a slow consumer forces producers to slow down rather than buffering without bound. TCP does this via receive windows; async apps often break it by reading sockets as fast as possible into unbounded channels/vecs — memory grows, latency explodes, OOM kills the process while TCP still looks "healthy." Correct design: bounded buffers at every stage so fullness propagates to TCP window / HTTP refusal / load shedding.
Q2How do you wire socket → worker backpressure with Tokio primitives?▼ answer
Model answer
Pattern: accept loop acquires a Semaphore permit before spawn (limits concurrent connections or in-flight requests). Per connection: Framed reads only when the next stage can accept — use tokio::sync::mpsc with capacity N, and send().await so a full channel pauses the reader (which then pauses socket reads → TCP backpressure). For fan-out, prefer broadcast/watch carefully (they drop/lag differently). Avoid unbounded_channel on request paths. BufferUnordered(n) in futures streams is another concurrency bound.
Q3Where does hyper/axum apply backpressure, and where must you add it yourself?▼ answer
Model answer
hyper won't read an unbounded body into memory unless you ask — use body size limits and stream large uploads. Request concurrency is not magically global-limited; under Accept flood you still need tower ConcurrencyLimit, load shedders, or reverse-proxy limits. Axum extractors that collect full bodies (Bytes, large JSON) are app-level buffers — cap them. Downstream clients: bounded connection pools and tower concurrency limits so one hot route cannot exhaust the runtime.
Q4Scenario: channel between decoder and DB workers is size 10_000 and RSS climbs. Diagnose and fix.▼ answer
Model answer
10k large messages is still unbounded-ish memory. Shrink bound to what SLO latency allows (often tens), scale DB workers, and add explicit load shedding when wait time exceeds budget (fail fast 503). Measure queue depth and wait latency — depth alone without age is misleading. Ensure slow DB does not get "help" from ever-larger buffers. Senior answer: pick bound from latency math (bound ≈ target_concurrency, not from "big enough to never block."
// NET 08
Load Balancing & Connection Pooling (L4/L7)
Questions & model answers
Q1L4 vs L7 load balancing for Rust services — what changes for the app?▼ answer
Model answer
L4 balances TCP/UDP flows; TLS may pass through; app sees real or NAT'd client IPs depending on topology. L7 terminates HTTP, can route by path/header, retry GETs, inject headers (X-Forwarded-For, X-Request-Id). Axum apps behind L7 must trust proxy headers only from known hops (SetTrueClientIp patterns / forwarded middleware). Idle timeouts on LB and app must align or you get random 502s on long polls.
Q2How should HTTP and DB connection pools be sized in a Tokio service?▼ answer
Model answer
Pool size ≈ concurrent in-flight work that productively uses the resource, not "threads × something." For Postgres via sqlx/deadpool: start from DB max_connections / number of app replicas, leave headroom for admin/migrations, measure wait time. For hyper clients: pool per upstream host, cap idle connections, set connect timeouts. Too large → DB overload; too small → queueing latency. Prefer explicit tower concurrency limits in front of the pool so waits are visible as 429/503 rather than silent latency.
Q3Why can HTTP/2 to backends create load imbalance? What mitigations exist?▼ answer
Model answer
Few long-lived H2 connections → L4 hashing pins a lot of traffic to one pod; others idle. Mitigations: L7 balancing per request, shorter connection lifetimes with jittered reconnect, more connections in the pool (trade memory), ORCA/load reports, or client-side P2C (power of two choices) with EWMA latency. Envoy/service mesh often owns this; tonic/hyper clients need careful pool settings when talking directly.
Q4Health checks, connection draining, and graceful shutdown — Rust callouts.▼ answer
Model answer
Readiness fails before shutdown so LB stops new sends; in-flight requests drain with a timeout; then drop listen socket. In axum/hyper: catch signal, with_graceful_shutdown, track in-flight via WaitGroup/counters, close idle pooled clients. Fail readiness if dependency pools are exhausted only if that matches product policy — sometimes better to shed load while still "alive." Sticky sessions: avoid unless necessary; if needed, terminate affinity at L7 with explicit cookie/hash and document failover behavior.

DNS, Service Discovery, Timeouts & Retries (Tower)
Questions & model answers
Q1How does DNS interact with long-lived connection pools in Rust clients?▼ answer
Model answer
Resolve-at-connect means a pool may pin stale IPs after DNS TTL changes (deploys, failover). Clients need periodic re-resolve, connection max-age, or a discovery layer that pushes endpoints. getaddrinfo blocking calls must not run on Tokio workers — use async resolvers (hickory-dns/trust-dns) or spawn_blocking. Caching resolvers can hide updates; set TTLs consciously. Kubernetes ClusterIP vs headless services change whether you load-balance at DNS or kube-proxy/mesh.
Q2Design a timeout hierarchy for an outbound HTTP call from an axum handler.▼ answer
Model answer
Separate: DNS lookup, TCP connect, TLS handshake, full request (headers+body), and optional per-stream idle timeouts. The handler's client timeout should be less than the inbound request deadline so you fail fast and return a controlled error. Propagate deadlines (gRPC) / cancel tokens so work stops. tower: Timeout layer; hyper client builder timeouts; never rely only on OS TCP retransmit timeouts (far too long for UX).
Q3How do you implement retries safely with tower? What must never be retried blindly?▼ answer
Model answer
Retry only idempotent requests or those with idempotency keys; use exponential backoff + full jitter; cap attempts; classify errors (connect timeout / 503 / RESET vs 400 / 401). tower Retry + Policy / Budget (retry budget) prevents retry storms amplifying outages. Hedge cautiously (tail latency) — it doubles load. Combine with circuit breakers (tower::limit / custom failure gates). Non-idempotent POST without keys: no automatic retry at the HTTP client; application-level compensation instead.
Q4Service discovery options: DNS, env, Consul/etcd, mesh. When is each enough?▼ answer
Model answer
Static/env for small deployments; Kubernetes DNS + ClusterIP for many services; headless + client LB for sticky/StatefulSets; Consul/etcd when you need richer health and KV outside k8s; service mesh when you want mTLS, retries, and stats without app changes. Rust apps should treat discovery results as changing sets — watch or poll, rebuild pools, and avoid assuming a single IP forever. Strong candidates discuss failure: empty endpoints, partial AZ loss, and stale caches.

Proxies, NAT & WebSocket Upgrade Pitfalls
Questions & model answers
Q1What does NAT do to connections, and why do keepalive/heartbeats matter?▼ answer
Model answer
NAT rewrites addresses/ports and maintains a mapping table entry with an idle timeout. Silent TCP connections can be dropped without RSTs reaching both peers → half-open zombies. Heartbeats refresh mappings; on failure, reconnect. Symmetric NAT and CGNAT make inbound peer-to-peer hard — prefer server-relayed designs. QUIC connection IDs help path migration; plain TCP needs rediscovery.
Q2Forward proxy vs reverse proxy vs transparent — what does each mean for TLS and headers?▼ answer
Model answer
Forward: client-chosen proxy to the outside world (corp egress). Reverse: sits in front of your services (nginx/Envoy/ALB) — TLS often terminated here. Transparent: intercepts without client config — surprising MTU/TLS issues. After TLS termination, apps see HTTP and must reconstruct client IP via forwarded headers carefully. End-to-end TLS (passthrough) preserves client→app encryption but loses L7 routing unless using SNI. Document trust boundaries explicitly.
Q3Walk through the WebSocket handshake and common proxy pitfalls with axum.▼ answer
Model answer
Client sends HTTP/1.1 upgrade: Connection: Upgrade, Upgrade: websocket, Sec-WebSocket-Key; server responds 101 Switching Protocols, then frames take over. Pitfalls: L7 proxies that buffer or do not allow Upgrade; wrong idle timeouts killing quiet sockets; sticky sessions required when state is in-memory per pod; missing ping/pong → NAT drop; trying to run WebSocket over HTTP/2 incorrectly (browsers use h1 upgrade or H2 extended CONNECT in newer stacks — know your proxy). In axum, use the WebSocket extractor/upgrade APIs; ensure reverse proxy proxy_http_version 1.1 and upgrade headers (nginx) are set.
Q4Scenario: WebSockets work locally but die every ~60s behind a cloud LB. What do you check?▼ answer
Model answer
Idle timeout on the LB/listener (classic 60s), missing app-level pings, proxy not forwarding upgrades, or draining during deploys without graceful reconnect. Fix: protocol pings every 20–30s, align idle timeouts, implement client reconnect with jitter and resume tokens if needed. Confirm whether the LB supports WebSocket at all (some need explicit annotation). Packet captures at client vs server show who sent FIN/RST.
// NET 11
Observability for Network Paths
Questions & model answers
Q1Which network signals belong in RED/USE dashboards for a Rust service?▼ answer
Model answer
Request Rate / Errors / Duration (RED) at the HTTP/gRPC layer; Utilization / Saturation / Errors (USE) for sockets, pools, and runtime. Add: connect failures, TLS handshake failures, DNS errors, pool wait time, active connections, bytes in/out. Separate client-perceived latency from handler time to spot proxy/network inflation. tracing + OpenTelemetry spans across outbound calls beat ad-hoc logs alone.
Q2RTT, retransmits, and error classes — how do you use them in an interview debugging story?▼ answer
Model answer
Rising RTT / retransmit rates (from kernel TCP_INFO, eBPF, or cloud NIC metrics) point to congestion or bad paths — app retries will worsen it. Error classes: timeouts vs connection refused vs reset vs TLS alert vs application 5xx — each maps to a different fix. Never aggregate all failures into one "error rate" without labels. For Tokio, also track task schedule delay to distinguish runtime overload from network RTT.
Q3How do you instrument outbound calls with tower/hyper without drowning in cardinality?▼ answer
Model answer
Low-cardinality labels: destination service, method, status class (2xx/4xx/5xx), error kind — not raw URLs or user ids. Use histograms for latency with sensible buckets. Sample traces; keep spans for queue wait vs DB vs outbound HTTP. Metrics crates (metrics, prometheus) plus tracing spans is the usual Rust stack. Exemplars linking a slow trace to a histogram bucket are a staff-level flourish.
Q4Scenario: p99 is high but p50 is fine; dependency p99 looks fine too. Where is the time?▼ answer
Model answer
Check queueing before the handler (accept/semaphore), Tokio worker saturation, head-of-line on H2 connections, GC-less but allocator contention, lock contention, DNS spikes on reconnect storms, or retry amplification on a subset of hosts. Distributed traces with span events for "got pool permit" / "DNS done" / "TLS done" / "first byte" localize the gap. Strong answer invents a latency waterfall, not a single average.
// NET 12
Correct Protocol Parsers without DoS (Limits & Slowloris)
Questions & model answers
Q1What parser/resource limits belong in every length-prefixed protocol?▼ answer
Model answer
Max frame size (reject before allocate), max nested depth (JSON/protobuf recursion), max concurrent connections, max in-flight requests per connection, read/write idle timeouts, and absolute handshake deadlines. Prefer incremental parsing from BytesMut over read_to_end. On violation: close the connection with a metric — do not try to "helpfully" skip giant frames.
Q2Explain Slowloris-style attacks against HTTP and how Rust servers mitigate them.▼ answer
Model answer
Attacker opens many connections and dribbles headers/body bytes slowly, holding server resources (tasks, buffers, sockets). Mitigations: header/body timeouts, minimum data rates, connection/request concurrency caps, reverse-proxy buffering limits, and kernel SYN cookies / backlog tuning at the edge. hyper/axum: configure server timeouts; put nginx/Envoy with aggressive timeouts in front for public exposure; never leave accept loops unbounded.
Q3How do you write a Decoder that is safe against length = u32::MAX?▼ answer
Model answer
After reading the length field, compare to MAX_FRAME immediately and return a protocol error before reserving buffer space or looping until src.len() >= 4 + n. Cap BytesMut reservations; use reserve carefully. Same idea for HTTP: Content-Length limits, and for chunked encoding a total body cap. Fuzz with cargo fuzz on the decode path — networking parsers are prime fuzz targets.
Q4HTTP request smuggling / header abuse — what should a Rust interviewer hear?▼ answer
Model answer
Ambiguous Content-Length vs Transfer-Encoding across proxy and origin can desync connections — use one well-maintained parser (hyper) on both sides or normalize at a trusted proxy; disable rare TE features if unused. Reject obs-fold headers, absurd header counts/sizes, and duplicate CL. Don't roll a custom HTTP parser for production edges. Mention security advisories and keeping hyper/rustls updated — dependency hygiene is part of network safety.
Q5Scenario: design acceptance tests that prove your codec resists DoS. What do you automate?▼ answer
Model answer
(1) Frame length > max → immediate error, constant memory. (2) Slow drip of bytes under timeout → connection closed, worker freed. (3) Thousands of concurrent idle conns → accept semaphore rejects or sheds. (4) Partial frames left in buffer across reads still decode correctly (correctness under split). (5) Fuzz corpus for panics/OOM. Tie tests to metrics assertions where possible. This is the difference between a demo codec and a production-ready one in staff interviews.
