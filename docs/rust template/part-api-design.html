// API Design 01 · 25 min
API1 · REST Resource Modeling & URI Design
Medium REST URI design axum routing
Prompt
"You're designing the public HTTP API for a multi-tenant project management product (orgs, projects, tasks, comments, memberships). Walk me through how you'd model resources and URIs, which relationships are nested vs top-level, how you'd name collections and actions that aren't CRUD, and how that maps cleanly onto axum routers and typed path extractors in Rust."
Discussion — sub-questions & model answers
D1How do you choose between nested URIs (/orgs/{org_id}/projects/{project_id}/tasks) and flat ones (/tasks/{task_id})?▼ answer
Model answer
Nest when the child is scoped by and only meaningful under the parent for list/create — e.g. listing tasks in a project: GET /orgs/{org_id}/projects/{project_id}/tasks. Prefer a canonical top-level URI for the resource itself once it has a stable global id: GET /tasks/{task_id} (and optionally keep the nested form as an alias if clients already use it). Deep nesting beyond two levels (.../tasks/{id}/comments/{id}/reactions) becomes painful for clients, caches, and auth checks — flatten leaf resources. Collections are plural nouns (/tasks); path segments are lowercase kebab-case or snake_case and stay consistent across the API. Avoid verbs in paths for CRUD (/createTask); reserve verbs or RPC-style sub-resources for non-CRUD actions (POST /tasks/{id}/assignees or POST /tasks/{id}:archive — pick one convention and stick to it).
D2Model memberships and "add user to project" — is that a resource or an action?▼ answer
Model answer
Prefer a first-class membership (or role-binding) resource: POST /projects/{project_id}/members with body { "user_id": "...", "role": "editor" }, GET /projects/{project_id}/members, DELETE /projects/{project_id}/members/{user_id} (or /members/{membership_id} if memberships have their own id). That gives you listability, pagination, auditability, and clear authz ("can manage members"). An RPC-style POST /projects/{id}/addMember works but hides the collection and makes idempotent retries and "list who has access" awkward. Many-to-many relationships almost always want an explicit join resource rather than stuffing arrays into parent PATCH bodies.
D3How does this map to axum routers and typed extractors? Sketch a nested router layout.▼ answer
Model answer
use axum::{Router, routing::{get, post}, extract::Path};

async fn list_tasks(
    Path((org_id, project_id)): Path<(Uuid, Uuid)>,
) -> Result<Json<Vec<Task>>, ApiError> { /* ... */ }

fn app() -> Router {
    Router::new()
        .nest("/orgs/{org_id}/projects/{project_id}",
            Router::new()
                .route("/tasks", get(list_tasks).post(create_task)))
        .route("/tasks/{task_id}", get(get_task).patch(update_task))
}
Use Path<T> with a tuple or a serde-deserializable struct for multi-segment ids; keep org_id in the path (or a tenant middleware) so authorization can verify the project belongs to that org before touching the DB. Nest routers with .nest / .merge so each bounded context owns its routes. Prefer typed newtypes (struct ProjectId(Uuid)) at the domain boundary even if the path extractor starts as Uuid.
D4What about filtering, sorting, and partial updates — query params vs body?▼ answer
Model answer
Safe, cacheable reads use query parameters: GET /tasks?status=open&assignee=u_123&sort=-updated_at, extracted with Query<ListTasksParams> and serde field defaults. Keep filter vocabularies documented and reject unknown filter keys in public APIs if you want strict contracts. Partial updates use PATCH with a JSON Merge Patch or explicit optional fields (Option<Option<T>> or a custom patch type to distinguish "omit" vs "set null") — not a kitchen-sink PUT that forces full replacement unless the resource is small and replacement is intentional. Avoid encoding complex filters as POST bodies for ordinary lists; reserve POST /tasks/search for truly large or sensitive query payloads.
D5Rust callouts — what mistakes show up in axum REST APIs?▼ answer
Model answer
Common pitfalls: (1) leaking internal DB ids or composite keys inconsistently; (2) using verbs as path segments for every mutation; (3) nesting so deep that path extractors become 5-tuples; (4) returning different shapes for the same resource from nested vs flat routes; (5) forgetting that Path<(Uuid, Uuid)> order must match the template. Strong candidates mention stable resource identifiers, consistent collection naming, and a single canonical GET URI per entity for caching and webhooks.
✓ Strong
  • Separates nested list/create scope from canonical flat resource URIs
  • Models memberships as resources, not verb endpoints
  • Maps cleanly to axum nest/Path/Query with typed ids
  • Has a coherent PATCH vs PUT and query-filter story
⚠ Probe
  • Nests three or more levels without discussing client/auth pain
  • Uses RPC verbs everywhere without justifying why REST resources fail
✗ Concern
  • Cannot explain plural nouns, id placement, or collection vs instance
  • No plan for authorization scoping via org/project in the path or middleware
// API Design 02 · 25 min
API2 · Pagination — Offset vs Cursor for Large Lists/Feeds
Medium pagination feeds sqlx
Prompt
"Your API must list millions of events / feed items. Design pagination for both an admin table UI (jump to page N, show total counts) and a mobile infinite-scroll feed (stable under inserts). Compare offset and cursor pagination, show response shapes, and sketch how you'd implement cursor pages in Rust with sqlx."
Discussion — sub-questions & model answers
D1When is offset pagination acceptable, and what are its failure modes at scale?▼ answer
Model answer
Offset (?page=50&per_page=50 or ?offset=2500&limit=50) is fine for small/stable result sets, admin tools, and when clients need "page 7 of 12" with a total count. Failure modes: (1) OFFSET deep pages scan/skip prior rows — cost grows with offset; (2) inserts/deletes while paging cause duplicates or skipped rows; (3) COUNT(*) on huge filtered tables is expensive. Cap limit (e.g. max 100), default sensibly, and avoid offering huge offsets on hot public feeds.
D2Design a cursor scheme for a feed ordered by (created_at DESC, id DESC).▼ answer
Model answer
Opaque cursor encoding the sort key of the last item, e.g. base64url(JSON {"t":"2024-01-15T12:00:00Z","id":"..."}) or a signed token. Next page query: WHERE (created_at, id) < ($t, $id) ORDER BY created_at DESC, id DESC LIMIT n+1 (use the extra row to compute has_more). Always include a unique tie-breaker (id) so equal timestamps don't stall. Return { "data": [...], "next_cursor": "...", "has_more": true } — not bare arrays. Prefer opaque cursors so you can change encoding without breaking clients; never encourage clients to invent cursors from raw fields unless it's an internal API.
D3Sketch Rust request/response types and a sqlx query shape.▼ answer
Model answer
#[derive(Deserialize)]
struct ListParams {
    #[serde(default = "default_limit")]
    limit: u32,
    cursor: Option<String>,
}

#[derive(Serialize)]
struct Page<T> {
    data: Vec<T>,
    next_cursor: Option<String>,
    has_more: bool,
}

// decode cursor -> (created_at, id); fetch limit+1; encode next from last returned
let rows = sqlx::query_as!(Event,
    r#"SELECT * FROM events
       WHERE project_id = $1
         AND (created_at, id) < ($2, $3)
       ORDER BY created_at DESC, id DESC
       LIMIT $4",
    project_id, t, id, (limit + 1) as i64
).fetch_all(&pool).await?;
Clamp limit in one place. Invalid cursors → 400 with a clear error code, not a empty 200 that looks like end-of-stream.
D4How do totals, bidirectional paging, and real-time inserts change the design?▼ answer
Model answer
Feeds usually drop exact totals (or show approximate/"99+" counts). Bidirectional paging needs prev_cursor/next_cursor and carefully defined inequalities for ASC vs DESC. For live feeds, cursor stability under inserts at the head is a strength of keyset pagination — new items appear on a refresh of the first page, not by mutating the current cursor window. If the admin UI truly needs jump-to-page, offer offset only on bounded queries (indexed filters, recent time windows) and document that deep pages are unsupported or slow.
D5What do you put in HTTP headers vs JSON body for pagination?▼ answer
Model answer
Either is fine if consistent: GitHub-style Link headers, or JSON next_cursor (more common for mobile/SPA clients and easier in axum without custom header plumbing). If using headers, still return a structured body. Expose RateLimit-* separately — don't overload pagination headers. Document whether cursors expire (e.g. signed with TTL) for security on sensitive listings.
✓ Strong
  • Contrasts offset drift/cost vs keyset/cursor stability with a unique sort key
  • Uses opaque cursors, limit clamps, and limit+1 for has_more
  • Picks offset for admin UX and cursors for feeds without being prompted
⚠ Probe
  • Cursor is just an offset integer renamed — misses keyset semantics
  • No tie-breaker when sorting by timestamp alone
✗ Concern
  • Unbounded limit / no invalid-cursor behavior
  • Assumes COUNT(*) on every feed page at millions of rows
// API Design 03 · 30 min
API3 · Idempotency Keys for POSTs / Payments
Hard idempotency payments exactly-once UX
Prompt
"Clients will retry POST /v1/payments on timeouts. Design an idempotency-key mechanism so retries don't double-charge. Cover header contract, storage, in-flight races, response replay, key TTL, and how you'd implement the critical section in a Rust service with Postgres."
Discussion — sub-questions & model answers
D1What is the client-facing contract for idempotency keys?▼ answer
Model answer
Client sends Idempotency-Key: <client-generated-string> (UUID/ULID) on unsafe methods that create side effects — especially payments and order creation. Same key + same request body → same result (replay stored status/body). Same key + different body → 409 Conflict (or Stripe-style mismatch error). Keys are scoped per API key / account, not globally across tenants. Document TTL (e.g. 24h), required header on payment routes, and that GET/PUT (already idempotent by HTTP semantics) usually don't need keys. Safe retries: client must reuse the same key for a logical operation.
D2How do you store keys and win the in-flight race when two retries hit at once?▼ answer
Model answer
Table roughly: (tenant_id, idempotency_key) PK, request hash, status (in_progress | completed | failed, response code/body (or pointer), created_at. Flow: (1) BEGIN; (2) try insert row as in_progress; (3) on unique violation, SELECT and either replay completed response, wait/retry if in_progress, or 409 on hash mismatch; (4) perform payment; (5) store response and mark completed; COMMIT. Use INSERT ... ON CONFLICT or SELECT ... FOR UPDATE so only one request executes the side effect. In-progress timeout: if a worker dies, expire stale in_progress after N seconds and allow retry, or use a lease.
D3Sketch the Rust/Postgres critical path.▼ answer
Model answer
// Pseudocode — single transaction owns the side effect
let mut tx = pool.begin().await?;
let inserted = sqlx::query!(
    r#"INSERT INTO idempotency_keys (tenant_id, key, request_hash, status)
       VALUES ($1,$2,$3,'in_progress')
       ON CONFLICT (tenant_id, key) DO NOTHING",
    tenant, key, hash
).execute(&mut *tx).await?.rows_affected();

if inserted == 0 {
    let row = fetch_for_update(&mut tx, tenant, key).await?;
    if row.request_hash != hash { return Err(ApiError::IdempotencyMismatch); }
    if row.status == "completed" { return Ok(replay(row)); }
    // else: wait, 409 Conflict, or 425/503 with Retry-After
}
let outcome = charge(&mut tx, body).await?;
store_completion(&mut tx, tenant, key, &outcome).await?;
tx.commit().await?;
Ok(outcome)
Hash the canonical request (method, path, body). Persist enough of the response to replay bytes/status faithfully — including error responses if the first attempt failed in a non-retryable way (policy choice: some APIs only replay successes and allow retry on failure).
D4What must be idempotent at the payment provider boundary too?▼ answer
Model answer
Your DB unique key alone isn't enough if you call Stripe/Adyen after commit or outside the transaction. Pass the provider's idempotency key (often derived from yours) on the outbound charge call, and store the provider payment id locally before confirming success to the client. Pattern: local record in pending → provider call with idempotency → update to succeeded/failed. Timeouts after provider accept need reconciliation jobs, not blind re-POSTs without keys.
D5TTL, storage size, and security considerations?▼ answer
Model answer
Retain keys long enough for legitimate retries (24–72h for payments; shorter for cheaper POSTs). Cap stored response body size; store large payloads in object storage with a pointer. Keys are secret-ish in that guessing another client's key shouldn't leak responses — always scope by tenant/auth. Rate-limit distinct keys per account to stop table flooding. Don't use monotonically sensitive data as keys.
✓ Strong
  • Covers mismatch-on-body, in-flight race, and response replay
  • Uses DB uniqueness / row locks; mentions provider-side idempotency
  • Defines TTL and tenant scoping without prompting
⚠ Probe
  • Only caches success in a HashMap — no durability across restarts
  • Ignores concurrent duplicate in-flight requests
✗ Concern
  • Says "just retry POST" with no key — accepts double charge risk
  • Cannot explain why timeouts are the hard case vs clear 500s

API4 · Error Model — problem+json & Typed Enums in axum
Medium errors RFC 7807 axum
Prompt
"Design a consistent error model for a public axum API. Cover HTTP status mapping, machine-readable codes, human messages, validation details, and whether you'd use RFC 7807 problem+json. Show a Rust error enum and how it becomes a response via IntoResponse."
Discussion — sub-questions & model answers
D1What belongs in a public error response, and what must never leak?▼ answer
Model answer
Public body: stable type / code, short title, optional detail, status, optional instance / request id, and structured errors[] for field validation. Never leak: raw SQL, panic messages, filesystem paths, internal service names, or stack traces. Log the full error with request_id server-side; return the same request_id to the client for support. Distinguish client mistakes (4xx, actionable codes) from server faults (5xx, generic message).
D2RFC 7807 problem+json vs a custom JSON envelope — trade-offs?▼ answer
Model answer
problem+json (application/problem+json) standardizes type, title, status, detail, instance and allows extension members — good for public/partner APIs and HTTP-native tooling. A custom envelope ({ "error": { "code": "...", "message": "...", "details": [] } }) is fine and common for SPAs you control; consistency matters more than the RFC badge. Either way: stable machine codes (task_not_found, idempotency_mismatch that clients can switch on — don't force clients to parse English detail strings.
D3Sketch a typed error enum and axum IntoResponse mapping.▼ answer
Model answer
#[derive(Debug, thiserror::Error)]
enum ApiError {
    #[error("not found")]
    NotFound { resource: &'static str },
    #[error("validation failed")]
    Validation(Vec<FieldError>),
    #[error("unauthorized")]
    Unauthorized,
    #[error("conflict: {0}")]
    Conflict(String),
    #[error(transparent)]
    Internal(#[from] anyhow::Error),
}

impl IntoResponse for ApiError {
    fn into_response(self) -> Response {
        let (status, code, title, detail, fields) = match &self {
            ApiError::NotFound { .. } =>
                (StatusCode::NOT_FOUND, "not_found", "Not Found", self.to_string(), None),
            ApiError::Validation(f) =>
                (StatusCode::UNPROCESSABLE_ENTITY, "validation_error", "Validation Failed", "...".into(), Some(f)),
            ApiError::Unauthorized =>
                (StatusCode::UNAUTHORIZED, "unauthorized", "Unauthorized", "...".into(), None),
            ApiError::Conflict(d) =>
                (StatusCode::CONFLICT, "conflict", "Conflict", d.clone(), None),
            ApiError::Internal(_) =>
                (StatusCode::INTERNAL_SERVER_ERROR, "internal", "Internal Error",
                 "unexpected error".into(), None),
        };
        // log internals for Internal; serialize ProblemBody { type, title, status, detail, code, errors }
        (status, Json(body)).into_response()
    }
}
Handlers return Result<T, ApiError>. Use thiserror for domain errors; map sqlx RowNotFound → NotFound at the edge, not by leaking sqlx types in signatures.
D4How do you map validation (serde/validator) and auth failures specifically?▼ answer
Model answer
JSON syntax errors → 400 with code invalid_json. Schema/field validation → 422 (or 400 — pick one, document it) with per-field pointers (/amount, messages, and reason codes. Missing/invalid credentials → 401; authenticated but not allowed → 403 (don't conflate). Rate limits → 429 + Retry-After. For axum, a custom Rejection handler for Json<T> / Query<T> keeps extractor failures in the same problem+json shape as handler errors.
D5Layered errors: domain vs transport — how do you avoid a mega-enum?▼ answer
Model answer
Keep domain crates returning rich errors (PaymentError::InsufficientFunds) without HTTP knowledge; at the API layer map with From<PaymentError> for ApiError or explicit map_err. That preserves reusable domain logic for gRPC/workers. Avoid ApiError::Sqlx(sqlx::Error) in the public enum — downcast/map at boundaries. Strong candidates mention stable codes as part of the API version surface (renaming codes is a breaking change).
✓ Strong
  • Stable machine codes + correct 401/403/404/409/422/429 mapping
  • IntoResponse enum that hides internal error details on 5xx
  • Maps domain errors at the edge; unified rejection handling
⚠ Probe
  • Returns anyhow/string errors directly to clients
  • Uses 500 for not-found or validation failures
✗ Concern
  • Leaks SQL/panic text in JSON bodies
  • No request id / no distinction between authn and authz failures

API5 · API Versioning Strategies
Medium versioning compatibility axum
Prompt
"You're about to ship breaking changes to a public REST API consumed by external partners. Walk through versioning strategies (URL path, header, media type), how you'd evolve without a big-bang v2, how axum routing would host two versions, and when you'd refuse to version at all."
Discussion — sub-questions & model answers
D1Compare path (/v1/...), header, and Accept media-type versioning.▼ answer
Model answer
Path prefix /v1 — most common, highly visible, easy to route and document, works in browsers and dumb clients; downside: looks like resources moved. Header (X-API-Version: 2024-06-01 (Stripe-style dated versions) — keeps URIs stable, supports fine-grained evolution; harder to try in a browser and cache keys must include the header. Accept application/vnd.myapp.v2+json — pure REST aesthetics, awkward DX and tooling. Recommendation for partner HTTP APIs: path /v1 for major breaks + additive changes in-place; or dated header versions if you need long parallel compatibility like Stripe.
D2What changes are additive vs breaking — and how do you avoid v2?▼ answer
Model answer
Additive (usually safe): new optional fields, new endpoints, new optional query params, new error codes (if clients ignore unknown). Breaking: remove/rename fields, change types/meaning, make optional fields required, change auth, alter status codes for the same condition, default behavior changes. Prefer expand/contract: add display_name, dual-write, deprecate name, remove later with a sunset header (Deprecation / Sunset). Don't bump major versions for every field tweak — versioning is expensive (test matrix, docs, SDKs).
D3How would you host v1 and v2 in axum without duplicating the world?▼ answer
Model answer
fn app(state: AppState) -> Router {
    Router::new()
        .nest("/v1", v1::router())
        .nest("/v2", v2::router())
        .with_state(state)
}

// shared domain services; version modules only adapt DTOs + HTTP mapping
mod v1 { /* TaskV1 serde shapes, handlers */ }
mod v2 { /* TaskV2 shapes; call same TaskService */ }
Keep business logic version-agnostic. Duplicate only request/response DTOs and mapping layers. For small deltas, a single handler with version-aware serializers is possible but gets messy — prefer explicit modules once responses diverge. Integration tests per version; contract tests (schemathesis/pact) on published OpenAPI.
D4When should you not version, and how do you sunset v1?▼ answer
Model answer
Internal-only APIs behind a BFF you deploy atomically may skip formal versioning and ship breaking changes with the frontend. Mobile/partner APIs need versions because clients aren't updated in lockstep. Sunset: announce, emit Deprecation: true and Sunset: <date>, metrics on v1 traffic, migrate SDKs, then return 410 Gone after the date. Overlap period measured in months for external partners.
D5Rust-specific callout — serde and versioned DTOs.▼ answer
Model answer
Don't reuse one struct for v1 and v2 with a tangle of #[serde(skip)] flags — separate types. Use #[serde(alias = "...")] sparingly for read-compatible renames. For dated versions, middleware can parse the version header into an extension type extracted by handlers. OpenAPI generation (utoipa/aide) should publish distinct specs per major version.
✓ Strong
  • Knows additive vs breaking and expand/contract without always jumping to v2
  • Separates versioned DTOs from shared domain services in axum
  • Has a concrete deprecation/sunset plan
⚠ Probe
  • Only knows URL /v2 and treats every field change as a new version
  • Duplicates entire service crates per version
✗ Concern
  • No notion of breaking change — renames fields in place for public clients
  • Cannot explain cache/proxy implications of header versioning

API6 · Authn/z — API Keys, JWT/Session, Scopes & Extractors
Hard auth JWT middleware
Prompt
"Design authentication and authorization for a Rust API that serves first-party web sessions, third-party API keys, and user JWTs with OAuth-like scopes. Explain middleware vs extractors in axum, how you'd represent AuthContext, and how handlers declare required scopes."
Discussion — sub-questions & model answers
D1When do you choose API keys vs JWT vs server sessions?▼ answer
Model answer
API keys — service-to-service / partner automation; long-lived, revocable, stored hashed (like passwords), often paired with coarse scopes and IP allowlists. JWTs (Bearer) — stateless access tokens for SPAs/mobile after OAuth/OIDC login; short TTL + refresh tokens; validate signature/issuer/audience/exp. Server sessions (cookie + sid in Redis) — first-party browsers where you want instant revoke and no token theft via localStorage; use Secure/HttpOnly/SameSite cookies CSRF-protected for cookie auth. Many products use sessions for the web app and API keys/JWT for programmatic access — don't force one mechanism.
D2How should axum middleware and extractors split responsibilities?▼ answer
Model answer
Middleware: parse credentials, authenticate identity, attach AuthContext to request extensions (or reject with 401). Extractors: pull AuthContext in handlers and optionally enforce authorization (RequireScope("tasks:write")). Pattern: 
struct AuthUser { user_id: Uuid, scopes: HashSet<String>, auth_via: AuthVia }

struct RequireScope(&'static str);

impl<S> FromRequestParts<S> for AuthUser { /* read extensions; else 401 */ }

async fn create_task(
    user: AuthUser,
    _scope: RequireScope, // constructed to require "tasks:write"
    Json(body): Json<CreateTask>,
) -> Result<impl IntoResponse, ApiError> { /* ... */ }
Prefer failing closed. Keep JWT validation (jwks cache, clock skew) in one module. Don't do heavy authz (per-resource ACL) only in middleware — middleware lacks path-specific resource ids; do RBAC/scope checks early, ABAC/resource checks in the handler/service after loading the entity.
D3How do you store and validate API keys safely?▼ answer
Model answer
Show the key once at creation (pk_live_... prefix for environment). Store only a hash (HMAC or salted hash); lookup by key id prefix + verify hash. Attach scopes, tenant id, rate-limit tier, and optional expiry. Support rotation (two valid keys during overlap). Never log full keys; redact Authorization headers. Constant-time compare for secrets.
D4Scopes vs roles vs resource policies — how do they compose?▼ answer
Model answer
Scopes (OAuth): what the token is allowed to do (tasks:read) — especially for delegated third-party apps. Roles: who the user is in a tenant (admin, member). Resource policy: whether this user can mutate this project. A request must satisfy all layers: valid authn → scope/role gate → resource membership check. Map scopes to permissions carefully; don't treat JWT role: admin as gospel without server-side checks for sensitive ops if roles can change before token expiry (or keep access tokens short).
D5Common Rust/auth footguns in interviews?▼ answer
Model answer
Accepting alg: none, skipping aud/iss, storing JWTs in localStorage without XSS discussion, confusing 401/403, putting shared secrets in the repo, and doing authorization only in the UI. Strong candidates mention tower middleware layering, JWKS caching with tokio, and testing extractors with crafted request parts.
✓ Strong
  • Picks mechanisms by client type; hashed API keys; short-lived JWTs
  • Clear middleware (authn) vs extractor/service (authz) split
  • Scopes + resource checks; 401 vs 403 correct
⚠ Probe
  • One global "is logged in" middleware with no scope model
  • Stores API keys plaintext in Postgres
✗ Concern
  • Cannot explain JWT validation claims or session CSRF for cookies
  • Authorizes solely from client-supplied user id in the body
// API Design 07 · 25 min
API7 · gRPC vs REST vs WebSocket — When to Pick Which (tonic)
Medium gRPC tonic WebSocket
Prompt
"You're building a platform with a public developer API, internal microservice calls, and a collaborative editor that needs live presence. Choose among REST/JSON (axum), gRPC (tonic), and WebSockets — justify each boundary, and call out Rust/ecosystem trade-offs."
Discussion — sub-questions & model answers
D1When is REST/JSON the right default?▼ answer
Model answer
Public/partner APIs, browser clients, webhooks to customer endpoints, anything that benefits from HTTP caching, CDNs, easy curl/OpenAPI, and broad client generation. Resource-oriented CRUD maps naturally. Cost: chatty APIs, weaker streaming, looser contracts unless you discipline OpenAPI. For a public developer platform, REST (or REST + optional GraphQL) is usually the exterior façade even if internals are gRPC.
D2When do you pick gRPC/tonic for service-to-service?▼ answer
Model answer
Internal RPC with schema-first protobuf contracts, streaming (server/client/bidi), compact binary payloads, deadlines/cancellations, and polyglot services. tonic gives async Rust stubs/services generated from .proto. Prefer gRPC when many services call each other with strict types and you control both ends. Caveats: browser support needs grpc-web/proxy; human debuggability worse than JSON; load balancers must understand HTTP/2; error model is status codes + rich details, not problem+json.
D3When are WebSockets (or SSE) warranted instead?▼ answer
Model answer
WebSockets — low-latency bidirectional chatter: collaborative editing, games, live agent tooling. SSE — server→client streams over plain HTTP (notifications, token streams) when client→server is ordinary REST. Don't use WebSockets for ordinary CRUD; they complicate auth, scaling (sticky sessions or pub/sub fanout), reconnects, and backpressure. In Rust: axum WebSocketUpgrade, or tonic bidi streams for internal realtime between services.
D4Sketch a sensible split for this product and a tonic service surface.▼ answer
Model answer
Public edge: axum REST (+ API keys, webhooks). Internal: tonic services for billing/search/workflow. Editor clients: WebSocket gateway that talks to a presence service (possibly via gRPC bidi or NATS). 
// proto
service Tasks {
  rpc GetTask (GetTaskRequest) returns (Task);
  rpc ListTasks (ListTasksRequest) returns (stream Task);
}

// tonic impl implements Tasks for TaskService
#[tonic::async_trait]
impl Tasks for TaskService {
    async fn get_task(&self, req: Request<GetTaskRequest>)
        -> Result<Response<Task>, Status> { /* map Auth to Status::unauthenticated */ }
}
Share domain logic; don't let protobuf types permeate your core if you also expose REST — map at edges.
D5What operational concerns tip the decision?▼ answer
Model answer
Mesh/LB HTTP/2 support, timeout propagation (tonic metadata + contexts), observability (gRPC status vs HTTP), mobile battery/proxies (WS through corp proxies), and team skills (protobuf CI breaking-change detection with buf). Strong candidates mention BFF: REST/WS at the edge, gRPC inside.
✓ Strong
  • Clear exterior REST vs interior gRPC vs WS for realtime only
  • Knows tonic/protobuf trade-offs and browser/grpc-web limits
  • Maps domain at edges instead of one transport type everywhere
⚠ Probe
  • Defaults to WebSockets for all APIs
  • Picks gRPC for public partner APIs without a gateway story
✗ Concern

API8 · Webhook Delivery — Signed Payloads, Retries, Ordering
Hard webhooks retries signing
Prompt
"Design outbound webhooks for domain events (payment.captured, task.updated). Customers register HTTPS endpoints. Cover signing, retry/backoff, ordering guarantees (or lack thereof), deduplication on the receiver side, and how a Rust worker would implement delivery safely."
Discussion — sub-questions & model answers
D1What should the webhook HTTP contract look like (headers + body)?▼ answer
Model answer
POST JSON envelope: id (event delivery id), type, created_at, data. Headers: Content-Type: application/json, Webhook-Id, Webhook-Timestamp, Webhook-Signature (e.g. HMAC-SHA256 over timestamp.payload, Svix/Stripe style). Receivers verify signature + timestamp skew (replay protection), then return 2xx quickly. Provide a secret per endpoint; support rotation with multiple valid secrets.
D2Retry, backoff, and failure isolation — how do you design the delivery system?▼ answer
Model answer
Persist outbox events; workers claim deliveries. On non-2xx or timeout: exponential backoff with jitter (e.g. 1m, 5m, 30m, … up to 24h), capped attempts, then mark dead and notify the customer. Isolate per endpoint (one slow customer must not stall the fleet — concurrency limits per destination). Treat 410/404 as disable-endpoint signals. Idempotency: same Webhook-Id may be redelivered — receivers must dedupe by event id.
D3What ordering guarantees do you give, and what do you explicitly not promise?▼ answer
Model answer
Usually at-least-once, mostly ordered per resource, not globally. Strict total order across all events is expensive and breaks under concurrency/retries. Document: events for the same task_id are best-effort ordered; consumers should use version vectors / updated_at / monotonic resource_version in the payload to apply updates correctly if reordered. Never promise exactly-once delivery over HTTP webhooks — promise idempotent processing instead.
D4Sketch Rust delivery + HMAC signing.▼ answer
Model answer
fn sign(secret: &[u8], timestamp: i64, body: &[u8]) -> String {
    let mut mac = HmacSha256::new_from_slice(secret).unwrap();
    mac.update(timestamp.to_string().as_bytes());
    mac.update(b".");
    mac.update(body);
    format!("v1={}", hex::encode(mac.finalize().into_bytes()))
}

// worker: claim row -> reqwest POST with timeout -> update attempt / next_run_at
// use outbox table written in the same DB transaction as the domain event
Transactional outbox avoids "DB committed but webhook never enqueued." SSRF: validate customer URLs (HTTPS only, block link-local/metadata IPs) when they register endpoints.
D5How do customers verify and debug deliveries?▼ answer
Model answer
Offer a delivery log UI/API (request headers, response status, next retry time), manual "redeliver," and signed test pings. Document clock skew tolerance and which signatures to accept during rotation. Rust callout: never use String compare for MAC equality — use constant-time subtle::ConstantTimeEq on the receiver side examples you publish.

API9 · Rate Limiting & Quotas at the API Edge
Medium rate limiting token bucket quotas
Prompt
"Design rate limiting and quotas for a multi-tenant public API. Tie your answer to token-bucket semantics, explain response headers and 429 behavior, distinguish burst vs sustained vs monthly quotas, and describe where enforcement lives in a Rust axum edge (and when Redis is required)."
Discussion — sub-questions & model answers
D1How do token buckets express API rate limits, and what headers do clients see?▼ answer
Model answer
Each tenant/API key has a bucket: capacity = burst, refill rate = sustained rps (or rpm). Each request costs one token (or a weighted cost for expensive search endpoints). On success/failure of the limit check, return headers such as RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset (IETF draft style) or legacy X-RateLimit-*. When empty → 429 Too Many Requests with Retry-After and a stable error code rate_limit_exceeded. Token bucket allows short bursts (good DX) while enforcing average rate — call out fixed-window boundary burst as the reason you didn't pick naïve per-second counters.
D2Rate limits vs quotas — how do they differ in product semantics?▼ answer
Model answer
Rate limits protect the system (per-second/minute abuse and fairness). Quotas are billing/product entitlements (10k jobs/month, 5 seats). Quotas are usually counted durably (Postgres/billing meter) and may return 402/403/429 depending on product language; rate limits are hot-path and often approximate. Design both: a customer can be within monthly quota but still 429 on burst, or pass rate limits but exhaust monthly quota. Weight expensive routes (e.g. export costs 10 tokens).
D3Where do you enforce in axum, and when is Redis mandatory?▼ answer
Model answer
Tower middleware / early layer after auth (keyed by API key or user id, not raw IP alone for authenticated APIs — IP still useful for anonymous/login endpoints). Single instance: in-memory sharded map of buckets (DashMap + atomic bucket, as in SD1). Multiple instances: Redis (Lua token bucket) or Envoy/API gateway limits, else each replica allows the full rate. Local memory as a cache in front of Redis can cut latency with slight over-admit risk. Rust: keep the limiter async-friendly; don't hold a std mutex across await points.
D4How do you rate-limit fairly across tenants and protect expensive endpoints?▼ answer
Model answer
Per-key buckets with plan tiers (free/pro). Separate buckets for write vs read if needed. Global shedder for overload (load shedding) distinct from per-tenant fairness. Cost-based limiting for search/ report endpoints. Return which limit was hit in the error body. Consider concurrent request limits (semaphore per key) in addition to rate — slow requests can exhaust workers without exceeding rps.
D5Testing and observability callouts?▼ answer
Model answer
Deterministic clock injection for bucket refill tests; metrics: rate_limit_rejections_total{tier,route}; structured logs with key id hash. Document limits in OpenAPI. Shadow-mode (log would-reject) before enforcing new limits. Strong candidates connect this discussion back to the token-bucket system-design exercise explicitly.

  • Separates rate limits from monthly quotas; weighted costs
  • Calls out multi-instance Redis/gateway requirement
⚠ Probe
  • Only IP throttling for authenticated APIs
  • In-memory limiter with no horizontal scaling story
✗ Concern
  • Drops requests without 429 semantics or client guidance
  • Cannot explain why fixed windows allow 2x burst at boundaries

API10 · Public API Compatibility & Schema Evolution
Medium serde compatibility schema evolution
Prompt
"Your public JSON API must evolve for years without breaking SDKs. Discuss compatibility rules, OpenAPI as a contract, and the serde trade-off of deny_unknown_fields on request vs response types — including how that choice affects forward/backward compatibility for clients and servers."
Discussion — sub-questions & model answers
D1What are the golden rules of JSON API compatibility?▼ answer
Model answer
Servers should accept older clients (backward compatible reads of requests) and clients should tolerate newer servers (ignore unknown response fields). Safe server changes: add optional request fields with defaults, add response fields, add new endpoints. Unsafe: remove fields, change types/meaning, make optional required, change defaults that alter behavior, reuse URLs with different semantics. Enum evolution: add enum variants carefully — old clients may break if they exhaustively match; prefer open enums / unknown fallbacks in SDKs. Document compatibility explicitly in the API guidelines and enforce via OpenAPI diff CI (breaking-change detectors).
D2Explain deny_unknown_fields on request DTOs — when is it good or harmful?▼ answer
Model answer
#[derive(Deserialize)]
#[serde(deny_unknown_fields)]
struct CreateTaskRequest {
    title: String,
    #[serde(default)]
    priority: Priority,
}
On server request types: rejecting unknown fields catches client typos and prevents silent ignore of fields the client thinks are honored — great for internal/strict APIs. Harm for public evolving APIs: if you later add an optional field and an old server build is still running, a new client sending that field gets 400 — you break forward-compatible rollout (new clients talking to old servers). For public APIs, many teams do not deny_unknown_fields on requests so unknown fields are ignored (Protobuf-style tolerance), and rely on docs/SDK generation for correctness. Alternatively, deny unknowns only in test/staging or on explicitly versioned strict content types.
D3What about response deserialization in Rust SDKs / clients?▼ answer
Model answer
Client response structs should not use deny_unknown_fields — servers must be able to add fields without breaking old SDKs. Default serde ignores unknown fields, which is what you want for responses. Use #[serde(default)] for new optional fields when reading older responses. For truly closed enums from the server, include an #[serde(other)] Unknown variant so new variants don't fail deserialize. Mirror this guidance in generated clients.
D4How do you evolve fields in practice (rename, optional→required, type change)?▼ answer
Model answer
Rename: publish both fields for a deprecation window (#[serde(alias = "old_name")] on deserialize; serialize both or only the new name with docs). Optional→required: only after metrics show all clients send it, or introduce a new version. Type change: add a new field (amount_cents) rather than changing amount from float to int; dual-read, then sunset. Nullability changes are breaking. Prefer additive DTOs and expand/contract migrations over in-place semantic shifts.
D5Contract testing / OpenAPI — what does "done" look like in a Rust shop?▼ answer
Model answer
Generated OpenAPI from utoipa/aide (or hand-maintained with CI drift checks) is the source of truth for public shape. Breaking-change CI fails PRs that remove fields or change types. Pact/schemathesis or golden JSON fixtures catch serde mismatches. Document the unknown-field policy explicitly so SDK authors and server authors don't disagree. Strong signal: articulating that deny_unknown_fields is a compatibility policy knob, not just a validation nicety.
✓ Strong
  • States ignore-unknown-on-responses; nuanced deny_unknown_fields on requests
  • Expand/contract for renames and type changes; open enums in SDKs
  • Ties OpenAPI/CI breaking-change detection to the policy
⚠ Probe
  • Enables deny_unknown_fields everywhere without rollout implications
  • Renames fields in place and calls it compatible because "it's better"
✗ Concern
  • Believes adding response fields always requires a major version
  • Uses deny_unknown_fields on client response types — guaranteed breakages
