// Closing question
Senior Readiness Assessment
Ask this after the write exercise — highest signal moment
"If you joined our team next week and inherited a mid-sized async Rust service, what are the first three things you'd want to look at — in the codebase, in its dependencies, or in how it's operated — to judge whether it's actually production-solid? And separately: what's a Rust decision you made in a past project that you're genuinely still unsure was the right call?"
Strong answer
  • ✓ Names concrete, checkable things: unwrap()/panic! density, blocking calls inside async fns, unsafe block audit trail, error-handling consistency, dependency count/audit status
  • ✓ Mentions operational signals too, not just code — metrics/tracing coverage, graceful shutdown behavior, how panics are surfaced in production
  • ✓ Gives a genuinely specific, second-guessed past decision (e.g. "I chose Arc<Mutex<_>> where a channel-based design would have avoided lock contention entirely") — not a generic platitude
  • ✓ Shows genuine intellectual humility about trade-offs rather than defending every past choice as obviously correct
Weak answer
  • ✗ Vague — "I'd read through the code and see if it looks good" without any specific, checkable criteria
  • ✗ Claims "if it compiles and passes clippy, it's basically fine" — overstates what Rust's guarantees actually cover (logic bugs, deadlocks, and unsound unsafe code all still compile cleanly)
  • ✗ Can't name a single past decision they're unsure about — implies either limited real experience or lack of reflection
  • ✗ Focuses entirely on syntax-level nitpicks (formatting, naming) rather than architectural or concurrency-level concerns

Quick-reference — decision matrix to probe during the closing discussion
Concurrency primitive choice
Single counter/flag → Atomic*
Multiple related fields updated together → Mutex
Many readers, rare writers → RwLock
Handoff between tasks → channel (mpsc, oneshot)
Shared read-mostly state, single-thread → Rc<RefCell<_>>
Shared read-mostly state, cross-thread → Arc<Mutex<_>> or Arc<RwLock<_>>
Async vs threads vs unsafe
I/O-bound, high concurrency → async/Tokio task
CPU-bound, parallel → OS threads / rayon
CPU-bound work inside async → spawn_blocking
Need a stable interface for many types → generics or dyn Trait (perf-critical → generics)
Reaching for unsafe → only with a documented invariant, never for convenience
Cross-language interop → FFI + bindgen, audit thread-safety explicitly
