Threading & Sync Primitives
Questions & model answers
Q1What are Send and Sync? Give an example of a type that is Sync but not Send, or explain why that combination is rare.▼ answer
Model answer
Send: a type is safe to move to a different thread — ownership transfer across a thread boundary is sound. Sync: a type is safe to access via &T from multiple threads concurrently — equivalently, T is Sync if and only if &T is Send. Both are auto-traits: the compiler derives them automatically for any type whose fields are all Send/Sync, and you almost never implement them manually (doing so requires unsafe impl, since you're asserting a property the compiler can't verify). Rc<T> is neither Send nor Sync (non-atomic refcount). Mutex<T> is Sync even if T is only Send — locking serialises access, making concurrent &Mutex<T> access safe regardless of whether T itself could handle concurrent access unsynchronised. Sync-but-not-Send example: genuinely rare in practice because most types that are safe to share by reference across threads are also safe to move — one textbook example is a MutexGuard-like type tied to OS-level thread-locking semantics (some lock APIs require the same OS thread that acquired the lock to be the one that releases it) — such a guard could be Sync in some designs while being unsound to hand off entirely to a different thread for the unlock. In practice this combination is the least common of the four (Send+Sync, Send-only, Sync-only, neither) and mostly shows up in low-level synchronisation primitive implementations, not everyday application code.
Q2What's the difference between thread::spawn's 'static requirement and how std::thread::scope (Rust 1.63+) relaxes it? Why couldn't earlier Rust do this safely?▼ answer
Model answer
thread::spawn(f) requires f: FnOnce() + Send + 'static — the closure cannot borrow anything from the spawning function's stack frame, because spawn returns a JoinHandle immediately and the spawned thread may still be running long after the parent function (and its local stack frame) has returned; the compiler has no way to guarantee the spawned thread finishes before the borrowed data goes away, so it forbids borrowing entirely. std::thread::scope(|s| { s.spawn(...) }) introduces a scope whose API statically guarantees that every thread spawned within it is joined before the scope call returns — the closure passed to scope cannot return until all its spawned threads have finished. Because that guarantee is enforced by the API's own structure (not merely a runtime convention), the borrow checker can soundly allow scoped threads to borrow local variables from the enclosing function — the data is provably still valid for the entire time any spawned thread could be using it. Why not always allowed: before scoped threads existed in std (crates like crossbeam::scope provided this earlier), there was no way for the type system to see the "guaranteed to join before returning" property — thread::spawn's API shape alone can't express that constraint, so the conservative, always-sound rule ('static only) was necessary in the absence of a scoping API.
Q3Explain the difference between std::sync::mpsc::channel and crossbeam_channel. What's missing from the standard library's channel that makes crossbeam the common production choice?▼ answer
Model answer
std::sync::mpsc provides a multi-producer, single-consumer channel — multiple Senders, exactly one Receiver. It's functionally adequate but has known gaps: (1) no true select! over multiple channels simultaneously (waiting on "whichever of these N channels has data first") — std's channel API has no equivalent; (2) historically weaker/less predictable performance under contention compared to crossbeam's implementation (crossbeam uses more sophisticated lock-free/low-contention techniques); (3) no MPMC (multi-producer multi-consumer) support at all in std — if you need multiple worker threads all pulling from one queue, std's channel can't do it directly (you'd wrap the single receiver in a Mutex, which partially defeats the purpose of a lock-free channel). crossbeam_channel provides both MPSC and true MPMC channels, a select! macro for multiplexing several channels and/or timeouts, and generally better throughput under contention. In practice, most production Rust concurrent code reaches for crossbeam_channel (for sync/thread-based code) or tokio::sync::mpsc/broadcast/watch (for async code) rather than std's channel, which mostly persists in codebases for simple, low-throughput one-shot signalling or in examples/teaching material.
Q4Name the four Coffman conditions for deadlock and describe two concrete strategies a Rust codebase can use to avoid lock-ordering deadlocks in a large service with many mutexes.▼ answer
Model answer
(1) Mutual exclusion — a resource can only be held by one holder at a time. (2) Hold and wait — a thread holds one resource while waiting for another. (3) No preemption — a held resource can't be forcibly taken away. (4) Circular wait — a cycle of threads each waiting on a resource the next one holds. Rust's type system doesn't prevent deadlock (unlike data races, this is a logic-level problem, not a memory-safety one) — you need discipline. Strategy 1 — global lock ordering: establish a canonical order (e.g. by a stable ID, or by documenting "always lock A before B" in a comment next to both mutex definitions) and enforce it via code review or a lint; some teams encode the order into the type system by wrapping mutexes in newtypes that can only be acquired via an API that takes them in a fixed sequence. Strategy 2 — reduce the surface area for holding multiple locks at once: design APIs so a thread rarely, if ever, needs two locks held simultaneously — e.g. copy out the data you need under lock A, release it, then acquire lock B, instead of holding both. Strategy 3 (tooling): use parking_lot's optional deadlock-detection feature in debug/CI builds, or write loom-based tests that exhaustively explore thread interleavings for lock-acquisition code paths, catching potential deadlocks and ordering bugs before they ever reach production traffic. In a system-design interview, explicitly naming "we'd want a documented lock hierarchy plus loom tests for the tricky bits" reads as considerably more senior than describing a single fix for one specific deadlock.
Q5Your team has a hot function with a coarse-grained Mutex<HashMap<K, V>> that's become a contention bottleneck under load. Walk through your options in order of increasing complexity.▼ answer
Model answer
1. Measure first — confirm via profiling (e.g. perf, or simply instrumenting lock wait time) that the mutex itself is the bottleneck and not, say, the work done inside the critical section, or an unrelated allocation. Don't optimise a hunch. 2. Shrink the critical section — often the map operation itself is fast but unrelated work (serialisation, logging, an I/O call) is incorrectly happening while the lock is held; moving that work outside the lock is usually the single highest-leverage, lowest-risk fix. 3. Swap to parking_lot::Mutex — smaller and often meaningfully faster than std's mutex in the contended case, essentially a drop-in replacement with no design change. 4. Switch to RwLock if read-heavy — verify actual read/write ratio first; this only helps if reads dominate and critical sections aren't tiny (see the RwLock caveats discussed elsewhere in this packet). 5. Shard the map — replace one Mutex<HashMap> with N Mutex<HashMap> shards, routing each key to a shard via hash(key) % N (this is exactly what dashmap does internally, and reaching for the dashmap crate directly is often the pragmatic move rather than hand-rolling sharding). 6. Lock-free structures — for extreme cases, a concurrent hash map with fine-grained or lock-free bucket-level synchronisation (again, dashmap, or for specialised needs a hand-rolled structure validated with loom) — reserve this for when sharding has been tried and measured insufficient, since lock-free code has a much higher bug surface and maintenance cost. The senior signal here is the ordering: measure, then cheap/low-risk fixes, then structural changes, then exotic solutions — not jumping straight to "let's write a lock-free hash map."
Q6A single N-worker thread pool needs to run arbitrarily many different jobs over its lifetime — some returning i32, some returning String, some returning nothing — and hand each caller back exactly that job's result. Why can't the pool itself be generic over the job/result type, and what design actually works?▼ answer
Model answer
Making ThreadPool<T> generic over the result type would only ever let one pool instance run jobs that all return that same, fixed T — the opposite of what a general-purpose pool needs, which is to serve many different job/result-type combinations over its lifetime from one shared set of worker threads. The standard fix is type erasure at the queue boundary, generics at the call boundary: 
type Job = Box<dyn FnOnce() + Send + 'static>;  // the ONE shape every job gets erased down to

fn execute<T: Send + 'static, F: FnOnce() -> T + Send + 'static>(&self, job: F) -> mpsc::Receiver<T> {
    let (result_tx, result_rx) = mpsc::channel();  // a FRESH channel per call — one job, one dedicated result path
    let wrapped: Job = Box::new(move || { let _ = result_tx.send(job()); });
    self.sender.send(wrapped).unwrap();
    result_rx
}
execute is generic per call (each call can have a totally different T), but the shared queue every worker thread pulls from only ever sees the single erased shape Box<dyn FnOnce() + Send + 'static> — the specific T is confined entirely to a private, per-call mpsc channel that the caller holds onto. This is precisely why one pool instance can run an i32-returning job and then, on the very next call, a String-returning job, with no changes to the pool itself. The result channel's send uses let _ = ... rather than .unwrap() deliberately — the caller may have already dropped the receiver (they stopped caring about the result), and that's not an error condition worth panicking a worker thread over.
Q7Design a simple in-process pub/sub message queue: publish(msg) should fan a message out to every currently-subscribed listener. What data structure backs the subscriber list, and what has to happen when a subscriber stops listening?▼ answer
Model answer
struct MessageQueue<T: Clone> { subscribers: Mutex<Vec<mpsc::Sender<T>>> }

impl<T: Clone> MessageQueue<T> {
    fn subscribe(&self) -> mpsc::Receiver<T> {
        let (tx, rx) = mpsc::channel();
        self.subscribers.lock().unwrap().push(tx);
        rx
    }
    fn publish(&self, msg: T) {
        let mut subs = self.subscribers.lock().unwrap();
        subs.retain(|tx| tx.send(msg.clone()).is_ok());  // send() fails exactly when the paired Receiver was dropped
    }
}
A Vec<Sender<T>> behind a Mutex is the simplest correct backing store — one mpsc::Sender per subscriber, cloning the message into each subscriber's own channel (hence the T: Clone bound). The critical detail is what happens when a subscriber drops their Receiver (they've stopped listening, gone out of scope, or their task panicked): the matching Sender::send call starts returning Err — not panicking, just failing gracefully — which is exactly the signal publish uses via Vec::retain to prune that subscriber from the list on the very next publish. Without this, the subscriber list would grow forever with dead senders that publish keeps uselessly trying (and failing) to send to — a slow, easy-to-miss memory leak in any long-running service with churny subscribers (e.g. WebSocket connections coming and going). At real scale (many subscribers, high publish rate, or needing delivery across process boundaries), this pattern is what you'd reach for a dedicated broker (Kafka, NATS, Redis pub/sub) to replace, rather than continuing to scale a single in-process, mutex-protected Vec.

Candidates who conflate the two haven't internalised what Rust's safety guarantees actually cover.

Atomics & Memory Ordering
Questions & model answers
Q1Why can't you just use a plain static mut counter: i32 incremented from multiple threads? What does AtomicI32 give you that a mutex would also give you, but more cheaply?▼ answer
Model answer
A plain i32 increment (x += 1) compiles to separate load, add, and store instructions — if two threads interleave these steps on the same memory location with no synchronisation, you get a data race, which is undefined behaviour, and updates can be silently lost. Accessing static mut at all requires an unsafe block specifically because the compiler cannot verify you're not doing exactly this. AtomicI32 (and friends) wrap the value so that operations like .fetch_add(1, Ordering::SeqCst) compile to a single indivisible hardware instruction (e.g. LOCK XADD on x86, or a load-link/store-conditional loop on ARM) — no other thread can observe or interleave a partial update. Compared to a Mutex<i32>: both are correct, but the mutex requires acquiring a lock (which, even in the best case with no contention, is more expensive than one atomic instruction — it involves at minimum a compare-and-swap on the lock state, and under contention can involve OS-level blocking/futex syscalls), whereas an atomic operation is a single CPU instruction with no possibility of blocking. Atomics are the right tool specifically for simple, single-value operations (counters, flags, sequence numbers); a mutex is still necessary once you need to update multiple related values together as one logical unit.
Q2List the five memory orderings available on Rust atomics and give a one-line use case for each of Relaxed, Acquire/Release, and SeqCst.▼ answer
Model answer
Weakest to strongest: Relaxed (atomicity only — no ordering constraint relative to other memory operations), Acquire (a load: prevents subsequent reads/writes from being reordered before it), Release (a store: prevents preceding reads/writes from being reordered after it), AcqRel (both — for read-modify-write ops that need both properties), SeqCst (sequentially consistent — a single global total order all threads agree on, the strongest and most expensive guarantee, and Rust's atomics default recommendation when unsure). Relaxed use case: a metrics counter that's only read at shutdown/reporting time, where you need atomicity (no lost increments) but don't care about ordering relative to any other memory access. Acquire/Release use case: a "data ready" flag — the producer writes some non-atomic data, then does a Release store to a flag; the consumer does an Acquire load of the flag and, if true, is guaranteed to see all the producer's writes that happened before the release — this is the fundamental building block of lock-free publish/subscribe and the pattern underlying how Mutex itself is implemented at a lower level. SeqCst use case: when multiple atomics are involved and you need a globally consistent view of the order of operations across all of them (e.g. some lock-free algorithms genuinely require this to remain correct) — or simply as the safe default when you haven't yet proven a weaker ordering is sufficient and correct.
Q3Explain the ABA problem in lock-free programming with compare-and-swap. Give one concrete mitigation.▼ answer
Model answer
A CAS-based algorithm reads a value A from a shared location, does some work, then tries to CAS it from A to a new value — succeeding only if the location still holds A. The ABA problem: between the read and the CAS, another thread could change the value A → B → A — the location holds A again by the time the CAS runs, so the CAS succeeds, even though the underlying state genuinely changed in between (e.g. in a lock-free stack, the exact node object with address A could have been popped, freed, reused for a new allocation that happens to land at the same address, and pushed back — the CAS can't distinguish "nothing changed" from "changed and changed back to something that looks identical"). This can corrupt data structures in ways that are extremely hard to reproduce and debug. Mitigation — tagged/versioned pointers: pair the pointer with a monotonically-incrementing generation counter, packed into a wider CAS (e.g. 128-bit double-word CAS on x86-64, or splitting bits within a 64-bit word) — A at generation 5 is distinguishable from A at generation 7 even though the pointer bits are identical, so the CAS correctly fails in the ABA scenario. Other real mitigations include hazard pointers (threads publish which nodes they're currently dereferencing so memory reclamation waits until no one holds a hazard pointer to it) and epoch-based reclamation (what the crossbeam-epoch crate implements) — both sidestep ABA by deferring memory reuse until it's provably safe, rather than only guarding the CAS itself.
Q4Explain why the Rust standard library's atomic types are conceptually similar to C++'s std::atomic, and what guarantees you as a Rust engineer get "for free" that a C++ engineer writing the equivalent lock-free code does not.▼ answer
Model answer
Rust's atomic types and memory-ordering enum map almost 1:1 onto C++11's std::atomic<T> and its memory_order enum — same relaxed/acquire/release/acq_rel/seq_cst vocabulary, same underlying hardware model (both ultimately target the C/C++11 memory model that most modern CPU architectures and compilers agree on). The genuine Rust-specific advantage is everything surrounding the atomic operations themselves: in C++, nothing stops you from also touching the same memory location with a plain, non-atomic read/write from another thread — mixing atomic and non-atomic access to the same location is a silent data race and undefined behaviour that the type system has no way to catch. In Rust, if a piece of memory needs to be accessed atomically from multiple threads, it has to actually be an AtomicUsize/etc — you cannot accidentally take a plain &mut usize to it from another thread while it's shared, because the ownership/borrowing rules (and Sync) would already have forced you to reach for the atomic type or a lock in the first place. In other words: C++ gives you the same atomic primitives, but nothing stops the rest of your codebase from bypassing them by accident; Rust's broader ownership discipline is what actually keeps the atomic operations meaningful and not undermined elsewhere. The atomics themselves aren't more powerful in Rust — the surrounding safety net is what changes.
Q5Explain what loom does and why you'd reach for it when writing a custom lock-free data structure, instead of relying on manual testing under load.▼ answer
Model answer
The fundamental problem with testing concurrent code by "run it under heavy load and see if it breaks" is that thread interleavings are effectively infinite and non-deterministic — a genuine race condition might only manifest one time in a billion runs on your specific CPU's specific scheduler behaviour, meaning your test suite can pass thousands of times in CI while a real bug lurks, only to surface unpredictably in production under different hardware or load patterns. loom is a permutation-testing library: it replaces std's threading/atomic primitives with instrumented versions and, for a given test, exhaustively (or systematically, with pruning) explores every possible thread interleaving the C11 memory model permits, checking your code's invariants hold under every one — effectively turning "probably fine after N runs" into "provably correct for all interleavings the model allows, within the bounded model checked." The trade-off: loom tests run your code many times over (combinatorially, for every interleaving), so they must be written for small, focused test cases (not full integration tests) and can take much longer to run than a standard unit test. The senior signal: someone who's written a custom queue, spinlock, or other lock-free primitive and reaches for loom specifically for that code path — rather than shipping something "tested under load and seemed fine" — demonstrates a properly calibrated level of paranoia for exactly the class of code where that paranoia is warranted.

Async/Await & Tokio
Questions & model answers
Q1What does an async fn actually compile down to? Why does calling one do nothing until it's awaited or polled?▼ answer
Model answer
async fn foo() -> T desugars into a regular function returning impl Future<Output = T>. The compiler generates an anonymous state machine struct that captures all the local variables that need to stay alive across .await points, plus a discriminant tracking which .await point execution is currently paused at. This struct implements the Future trait's single required method, poll(self: Pin<&mut Self>, cx: &mut Context) -> Poll<T>, which either returns Poll::Ready(value) (done) or Poll::Pending (not done yet — and registers a "wake me up later" callback via the provided Context's waker). Calling an async function just constructs this state-machine value — no code inside the function body actually runs yet, exactly analogous to how calling .map() on an iterator just builds an adapter. Nothing executes until something drives the future forward by repeatedly calling .poll() — either the executor (Tokio's runtime) after you .await it inside another async context, or a top-level block_on() call. This is why an unawaited async call, similar to an unconsumed iterator, produces a compiler warning about an unused future that does nothing.
Q2Why is blocking (e.g. calling std::thread::sleep or synchronous file I/O) inside an async fn running on Tokio's default runtime a serious problem, and not just "a bit slower"?▼ answer
Model answer
Tokio's default multi-threaded runtime runs many independent async tasks cooperatively multiplexed onto a small, fixed pool of OS worker threads (typically one per CPU core) — each task is expected to run only briefly between .await points, voluntarily yielding control back to the executor so it can run other tasks on that same OS thread. A blocking call (synchronous sleep, blocking disk I/O, a long CPU-bound loop with no .await) doesn't yield — it monopolises the underlying OS thread for its entire duration. Since that thread is one of only N worker threads shared by potentially thousands of concurrent tasks, blocking it means every other task scheduled onto that same worker thread is stalled, not just the offending task — this can cause cascading latency spikes or even apparent "hangs" across unrelated requests in a web server, and under enough concurrent blocking calls can starve the runtime entirely (all worker threads blocked, nothing else can run at all). This is categorically different from "a bit slower" — it's a correctness-adjacent problem that can take down a whole service's responsiveness from what looks like one innocuous blocking call deep in a rarely -hit code path. The fix: use tokio::task::spawn_blocking to move blocking work onto a separate, dedicated blocking-thread pool that Tokio manages specifically for this, or use the async equivalent (tokio::time::sleep, tokio::fs) wherever one exists.
Q3Compare tokio::sync::Mutex with std::sync::Mutex. When should you actually use the async version, and why is "just use the async mutex everywhere in async code" a common but wrong instinct?▼ answer
Model answer
std::sync::Mutex's .lock() blocks the OS thread while waiting — exactly the problem described above if used carelessly inside async code with a contended lock. tokio::sync::Mutex's .lock().await instead yields control back to the executor while waiting, letting other tasks run on that thread in the meantime — safe to hold across an .await point, and its guard is Send so it can technically be held across await points (unlike the sync mutex's guard, which is deliberately not Send in many cases specifically to discourage this misuse). The common wrong instinct: using the async mutex reflexively everywhere in async code, on the assumption that "async code needs async primitives." In practice, if your critical section is short and never itself awaits anything inside the lock — e.g. just updating an in-memory counter or map — a plain std::sync::Mutex (ideally parking_lot::Mutex) held very briefly is faster and simpler, because the async mutex has real overhead (it interacts with the task scheduler, involves constructing/registering wakers) that a lock held for a handful of nanoseconds doesn't need. The actual rule: reach for tokio::sync::Mutex specifically when you need to .await something while still holding the lock (e.g. locking a connection object and then awaiting a network call on it) — otherwise, a short, synchronous lock is the better and more idiomatic choice, and the Tokio docs themselves say this explicitly.
Q4Explain cancellation in Tokio — what happens when you drop a future/task mid-execution, and why is "cancellation safety" a real design concern for async code that isn't a problem for synchronous code?▼ answer
Model answer
A Tokio future can be cancelled at any .await point — for example, via tokio::select! choosing a different branch, a tokio::time::timeout firing, or simply dropping the JoinHandle/future. Cancellation is implemented as a plain drop — the future's state-machine struct (and all its captured local variables) is dropped exactly where it was paused, running normal Drop impls for anything it owns, but with no chance to run any further code inside the async function body itself — there's no "finally" block that executes; execution simply stops mid-function at the last await point and everything local gets dropped. Why this matters: if an async function does something like "increment a counter, await a network call, then decrement the counter back" — and it's cancelled while awaiting the network call — the decrement never runs, leaving the counter permanently incremented. This kind of bug has no synchronous equivalent, because synchronous code only "stops" via a panic (which at least runs destructors during unwinding) or process termination — there's no routine, expected mechanism for a synchronous function to simply vanish mid-body the way async cancellation works. Cancellation-safe design means structuring async code so a mid-await cancellation never leaves shared state inconsistent — e.g. using RAII guards whose Drop impl performs the cleanup (so it runs even on cancellation, unlike code written directly in the function body after the await), or designing operations to be atomic from an external observer's perspective (nothing observable changes until the whole operation completes). This is one of the most frequently-cited "gotchas" senior Tokio users bring up unprompted, and specifically distinguishes people who've shipped real async services from people who've only completed async tutorials.
Q5Design the shutdown sequence for a Tokio-based service that's processing in-flight requests, has background tasks (e.g. a metrics flusher), and needs to drain gracefully on SIGTERM. What primitives do you reach for?▼ answer
Model answer
1. Signal handling: use tokio::signal::unix::signal(SignalKind::terminate()) (or the cross-platform ctrl_c() for simpler cases) to get an async stream that resolves when SIGTERM arrives — this becomes one branch of a top-level tokio::select!. 2. Broadcast the shutdown signal: use tokio::sync::watch (a single-value, "latest wins" channel good for broadcasting a boolean "shutting down" flag to many listeners) or a CancellationToken (from tokio_util) — every long-running task holds a clone and checks/selects on it, e.g. inside a request-handling loop: tokio::select! { _ = token.cancelled() => break, req = accept_next() => handle(req) }. 3. Stop accepting new work immediately on shutdown signal — close the listening socket / stop pulling new items off the intake queue — while letting in-flight requests finish. 4. Track in-flight work — a common pattern is an Arc'd counter (or a tokio::sync::Semaphore's permit count, or a JoinSet tracking all spawned request -handler tasks) that lets the shutdown routine await until all in-flight work has genuinely completed, not just been signalled to stop. 5. Grace period + forceful cutoff: wrap the drain-wait in tokio::time::timeout(Duration::from_secs(N), drain_future) — if in-flight work hasn't finished within a reasonable grace period, log it and exit anyway rather than hanging indefinitely on shutdown (important for orchestrators like Kubernetes that will SIGKILL after their own grace period regardless). 6. Background tasks last — only after request-serving tasks have drained, signal background tasks (metrics flush, etc.) to do their final flush and exit; a JoinSet or explicit .await on their handles ensures the process doesn't exit while a final flush is still in flight, losing that data. Mentioning CancellationToken, JoinSet, and a bounded grace period unprompted signals real production experience with this exact problem, which comes up in nearly every non-trivial Tokio service.
Q6What does #[tokio::main] actually expand to? What's the difference between the multi-thread and current-thread runtime flavors, what does tokio::spawn return, and what does tokio::select! do?▼ answer
Model answer
// This attribute macro...
#[tokio::main]
async fn main() { run().await; }

// ...desugars to roughly this — build a Runtime, then block_on() the async body
fn main() {
    tokio::runtime::Builder::new_multi_thread()
        .enable_all()
        .build()
        .unwrap()
        .block_on(async { run().await; });
}
#[tokio::main] is sugar for constructing a tokio::runtime::Runtime and calling its synchronous block_on() — the one place a sync context bridges into the async world by driving a single top-level future to completion, blocking the calling OS thread until it's done. Runtime flavors: the default is multi-thread — a work-stealing scheduler across a pool of OS worker threads (defaults to the number of CPU cores), which is what lets independent tasks actually run in parallel, not just concurrently. #[tokio::main(flavor = "current_thread")] runs everything on the single thread that called block_on — no parallelism, lower overhead, and the right choice for CLI tools, tests, or anywhere you deliberately don't want a thread pool spun up. tokio::spawn(fut) hands a future to the runtime to run independently and immediately returns a JoinHandle<T> — itself a future that resolves to Result<T, JoinError> when the spawned task finishes (the Result wraps the possibility that the task panicked, which is caught and reported through the handle rather than crashing the whole runtime — one task panicking doesn't take down unrelated tasks). Critically, a spawned task starts running independently even if you never .await its JoinHandle — dropping the handle just means you stop being able to observe its result, it doesn't cancel the task (use handle.abort() for that). tokio::select! polls multiple futures concurrently and proceeds with whichever branch becomes ready first, dropping (cancelling) all the other branches' futures — the standard building block for "whichever happens first: a response, or a timeout" or "handle the next request, or shut down if a cancellation signal fires," and the reason cancellation-safety (Q4) matters so much in practice, since every unselected branch is cancelled mid-flight on every single call.

Questions & model answers
Q1Name the main Rust web frameworks in common use today and roughly how they differ in philosophy (axum vs actix-web).▼ answer
Model answer
axum: built by the Tokio team, on top of tower/hyper — leans heavily on the type system for its "extractor" pattern (handler function parameters are extracted from the request by type — Json<T>, Path<T>, State<T> — rather than an imperative "get param" call), and composes middleware via the generic tower::Layer/Service abstractions shared with the rest of the Tokio ecosystem (meaning gRPC via tonic, load balancers, retries, etc. all interoperate through the same middleware model). No macros required for routing. actix-web: older, historically the higher-raw-throughput option in early benchmarks (much less true today), has its own actor-model runtime heritage though modern actix-web is mostly just a fast async framework at this point, uses attribute macros for handlers (#[get("/users/{id}")]) and its own middleware trait rather than tower. Other notable options: rocket (very ergonomic, macro-heavy, historically nightly-only though now stable-compatible), warp (filter-based composition, an early influence on axum's design), and poem/salvo as newer entrants. For a new project today, axum is the most common default recommendation specifically because of its tower ecosystem interoperability and close alignment with Tokio.
Q2In axum, what is an "extractor," and why does parameter order matter for extractors that consume the request body?▼ answer
Model answer
An extractor is any type implementing axum's FromRequest (or FromRequestParts) trait — used as a handler function parameter type, axum automatically constructs it from the incoming request before calling your handler: 
async fn create_user(
    State(pool): State<PgPool>,      // pulls shared state
    Path(org_id): Path<u64>,        // pulls a path param
    Json(payload): Json<CreateUserReq>, // deserialises the body
) -> impl IntoResponse { /* ... */ }
Why order matters: the HTTP request body is a single-consumption stream — once something reads it, it's gone. Extractors that need the body (like Json<T>, Bytes, String, or a raw Request) implement FromRequest, which consumes the whole request; extractors that only need metadata (headers, path params, extensions, state) implement the more restrictive FromRequestParts, which only borrows the request's parts, not the body. axum's design constraint (enforced by the trait signatures themselves) is that at most one body-consuming extractor can appear, and it must be the last parameter — trying to put Json<T> before a Path<T> parameter is actually fine order-wise since Path doesn't need the body, but you cannot have two separate body-consuming extractors in the same handler, and the compiler enforces the "body extractor must be last" constraint via the trait bounds on the handler-registration machinery — getting this wrong is a compile error, not a runtime surprise, which is a nice example of axum pushing an HTTP-semantics constraint into the type system.
Q3How do you implement custom error handling in axum so that your application's error enum automatically converts into an appropriate HTTP response?▼ answer
Model answer
Implement axum's IntoResponse trait for your application error type — this is the trait axum uses to turn any handler return value into an actual HTTP response, and handlers are commonly written to return Result<T, AppError> where T: IntoResponse: 
#[derive(thiserror::Error, Debug)]
enum AppError {
    #[error("not found")] NotFound,
    #[error("unauthorized")] Unauthorized,
    #[error(transparent)] Internal(#[from] anyhow::Error),
}

impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        let (status, msg) = match &self {
            AppError::NotFound     => (StatusCode::NOT_FOUND, self.to_string()),
            AppError::Unauthorized => (StatusCode::UNAUTHORIZED, self.to_string()),
            AppError::Internal(e)   => { tracing::error!(%e, "internal error"); (StatusCode::INTERNAL_SERVER_ERROR, "internal error".into()) }
        };
        (status, Json(json!({ "error": msg }))).into_response()
    }
}
The key design points worth calling out: (1) never leak internal error details to the client for the internal/500 case — log the real error server-side with full detail (via tracing), return a generic message externally; (2) the ? operator now works seamlessly in handlers thanks to the #[from] conversion, so a handler calling a fallible database function just writes let user = get_user(id).await?; and the whole error-to-response pipeline is handled once, centrally, rather than repeated per-handler.
Q4Design middleware for a production axum service that needs: request-id propagation, structured logging, and rate limiting. How do these compose, and in what order should they be layered?▼ answer
Model answer
In axum/tower, middleware is applied via .layer(), and layers wrap outside-in — the last .layer() call is the outermost, seeing the request first and the response last. Order (outermost to innermost): (1) Request-ID generation — must be outermost so every subsequent layer (including logging) can access the ID; typically implemented via tower_http::request_id::SetRequestIdLayer plus a matching PropagateRequestIdLayer to echo it back in the response headers. (2) Tracing/structured logging span — tower_http::trace::TraceLayer, configured to pull the request ID into every log line's structured fields (via tracing spans) for the rest of the request's lifetime — this needs to wrap everything downstream so it can measure total latency and capture the final response status. (3) Rate limiting — placed after logging so rate-limited (429) responses are still logged with full context, but before the actual handler/business logic so limited requests never reach expensive application code; typically keyed by a header/IP/API key via a custom tower::Layer or the tower_governor crate. Handler is innermost. Cross-cutting concern to raise: where does rate-limit state live? For a single-instance service, an in-memory sharded counter (e.g. token-bucket per key, similar to the rate -limiter system-design exercise elsewhere in this packet) suffices; for a multi-instance deployment behind a load balancer, the limiter needs to be backed by a shared store (Redis) or you accept per-instance limits that are effectively N× more permissive than intended — a detail worth surfacing proactively rather than waiting to be asked, since it's the kind of thing that quietly breaks in production once the service scales past one instance.
Q5How would you structure a moderately large axum service's codebase — module boundaries, shared state, and where business logic lives relative to HTTP handlers?▼ answer
Model answer
Keep HTTP concerns and business logic in separate layers. A common, effective structure: handlers/ (thin — extract inputs, call into the service layer, map the result/error to an HTTP response; no actual business logic here), services/ or domain/ (the real logic — validation rules, orchestration across repositories, pure business decisions — deliberately has no dependency on axum types at allrepositories/ or storage/ (database/external-service access, returning domain-level errors, not raw SQL errors), and a shared AppState struct (holding the DB pool, config, and any shared clients) injected via axum's State extractor. Why this separation matters concretely: (1) you can unit test business logic without spinning up an HTTP server or mocking request/response types at all; (2) if the framework changes (axum major version bump, or migrating to a different framework entirely) only the thin handler layer needs rewriting; (3) it keeps the "what does this error mean to an HTTP client" decision (status codes, response shape) cleanly separated from "what does this error mean to the business logic" (retry? escalate? is this even an error or an expected outcome?) — the same layered error-handling design discussed in the error-handling topic. For workspace organisation at real scale, many teams go further and split the domain logic into its own crate within a Cargo workspace, with the axum-based HTTP binary crate depending on it — enforcing the separation at the compiler/dependency-graph level rather than just by convention.

  • Implements IntoResponse correctly, distinguishing client-facing messages from internally-logged detail
  • Reasons about middleware layering order and its outside-in semantics correctly
  • Separates HTTP handlers from business logic as distinct, independently testable layers
⚠ Probe
  • Has used a web framework but can't explain how middleware layering order affects behaviour
  • Puts business logic directly inside handler functions
✗ Concern
  • Has never used a Rust web framework
  • Returns raw internal error details (e.g. SQL errors) directly to HTTP clients

Q1What does serde actually do, and why is #[derive(Serialize, Deserialize)] so much faster at runtime than a typical reflection-based JSON library in other languages?▼ answer
Model answer
serde ("serialize/deserialize") is a generic serialization framework, deliberately decoupled from any specific data format — the core crate defines the Serialize/ Deserialize traits and a generic "data model" both sides agree on; separate crates (serde_json, bincode, serde_yaml, toml, rmp-serde for MessagePack, etc.) implement the actual format encoding/decoding against that shared model — meaning a single #[derive(Serialize, Deserialize)] on your struct works with any supported format with zero extra code. Why it's fast: the derive macro generates ordinary, monomorphised Rust code at compile time that directly calls serializer.serialize_field(name, &self.field) for each field in sequence — there is no runtime reflection at all (Rust has essentially no runtime type reflection to begin with, unlike Java/Python/Go, which typically use runtime reflection to enumerate a struct's fields when (de)serializing generically). The generated code is exactly what you'd write by hand, and the compiler can inline and optimise it like any other function — this is a major reason Rust JSON (de)serialization consistently benchmarks far ahead of reflection-based libraries in other languages.
Q2What problem does rayon solve, and how does par_iter() relate to the regular Iterator trait? Why is it described as "data parallelism" rather than "task parallelism"?▼ answer
Model answer
rayon provides effortless CPU-bound parallel iteration — converting collection.iter().map(f).sum() into collection.par_iter().map(f).sum() automatically splits the work across a work-stealing thread pool (sized to the number of CPU cores by default), with rayon handling all the chunking, load-balancing, and result-merging internally. ParallelIterator mirrors much of the standard Iterator API surface (map, filter, fold, etc.) but processes items across multiple threads instead of sequentially on one — the mental model shift is small precisely because the API is deliberately familiar. It's "data parallelism" because the same operation is applied independently to many pieces of data in parallel (think SIMD-at-the-thread-level) — contrasted with "task parallelism" (what Tokio provides), where many different, independent units of work (HTTP requests, background jobs) run concurrently, often I/O-bound and not CPU-bound. The rule of thumb interviewers look for: rayon for CPU-bound, parallelisable batch computation (image processing, parsing a large dataset, numerical simulation); Tokio for I/O-bound concurrency (many concurrent network connections, most of each task's wall-clock time spent waiting, not computing) — mixing them up, or trying to use rayon for thousands of concurrent network connections, is a common early-career mistake.
Q3What is tracing and how does it differ conceptually from the older log crate? What is a "span" and why does it matter for async code specifically?▼ answer
Model answer
log provides simple, flat, leveled log lines (info!(), error!()) with no built-in notion of structure or causality beyond the text of the message itself. tracing generalises this with two key additions: (1) structured fields — tracing::info!(user_id = %id, latency_ms = elapsed, "request completed") attaches typed key-value data to each event rather than baking everything into a formatted string, letting downstream log aggregators (e.g. shipping to a JSON-log pipeline) filter/query on those fields directly. (2) Spans — a span represents a period of time with a beginning and end (e.g. "handling this HTTP request," "processing this batch job"), and events emitted while a span is active are automatically nested/associated with it, forming a call-tree-like structure of context. Why spans matter specifically for async code: a single OS thread in an async runtime interleaves work from many concurrently-running tasks — a plain thread-local "current context" approach (which works fine in traditional synchronous, one-task-per-thread systems) breaks down completely, because ten different tasks' log lines could all be interleaved on the same thread. tracing's spans are explicitly entered/exited around .await points (the #[tracing::instrument] attribute macro automates this for whole functions), so even though the underlying thread is shared across many tasks, each log event is still correctly attributed to the specific request/task span it logically belongs to — this is the foundational piece that makes distributed tracing and per-request log correlation possible in an async service, and it's a problem the older log crate's model has no answer for.
Q4Compare sqlx and diesel as database access approaches for a Rust service. What is compile-time query checking, and what does it actually verify?▼ answer
Model answer
diesel: a full-featured, non-async-native ORM/query-builder — you construct queries using a Rust DSL that mirrors SQL structurally (users.filter(id.eq(5)).select(name)), and diesel's macro system generates a Rust-level schema representation from your database schema, giving strong compile-time type checking of queries built through the DSL. Historically async support was secondary/bolted-on (via diesel-async), which mattered a lot for Tokio-based services. sqlx: async-native from the ground up, and takes a different approach to safety — you write actual SQL strings (not a Rust DSL), but its macros (sqlx::query!, query_as!) connect to a real database at compile time (or use an offline-cached schema snapshot in CI, via sqlx-cli prepare, to avoid needing a live DB during every build) and verify the query actually parses, the referenced tables/columns exist, and infers/checks the Rust types of each selected column against your target struct — a typo'd column name or a type mismatch between a SQL column and your Rust struct field becomes a compile error, not a runtime panic or silent bug discovered in production. What it does NOT verify: query logic correctness (a syntactically valid query that returns the wrong rows compiles fine) and it can't catch issues that only manifest with production data distributions (e.g. a query that's correct but catastrophically slow without an index — that's still a runtime/observability concern, not something the macro checks). Choice: sqlx is generally preferred for greenfield async services specifically for that async-native design and because many engineers prefer writing real SQL over learning a DSL; diesel appeals to teams who want the DSL's composability for building complex, programmatically-constructed queries and stronger enforcement of schema consistency across a codebase without needing a live DB connection during compilation.
Q5A candidate says "I always add anyhow, tokio, serde, and tracing to every new project by default." Evaluate this instinct — when is it right, and when should a senior engineer push back on default crate choices?▼ answer
Model answer
The instinct is reasonable as a starting default for a typical async service — these four are genuinely close to universal for that category of project, and reaching for known-good, widely-audited crates instead of reinventing basic infrastructure is generally the right call. Where a senior engineer should push back on blind defaults: (1) anyhow in a library crate — as covered elsewhere, a published library should generally expose typed errors (thiserror) since downstream consumers need to match on failure modes; pulling in anyhow by default for a crate meant to be a dependency of other crates is often wrong. (2) tokio in a CLI tool or CPU-bound batch job with no actual concurrent I/O — pulling in a whole async runtime adds compile time, binary size, and cognitive overhead for a program that's fundamentally synchronous; this is a surprisingly common case of cargo-culting a "modern Rust" stack onto a project that doesn't need it at all. (3) Compile-time and dependency-tree cost — every crate added multiplies transitive dependencies and compile time; for a small, latency-sensitive CLI tool, minimal dependencies is a real design goal, and even serde's compile-time cost (proc-macro heavy) is worth questioning if you're only parsing one simple config file (toml_edit's manual parsing, or a hand-rolled parser, might be genuinely lighter-weight). The senior framing to state explicitly: defaults are a reasonable prior, but the actual decision should always be justified by the project's real requirements — "does this project have genuine concurrent I/O" and "will this be depended on by other crates" are the two questions that most often flip the default answer, and being able to articulate that instead of reciting a fixed crate list is the differentiator.
