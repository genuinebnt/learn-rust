// W3 01
Accounts, Keys & Signatures
Questions & model answers
Q1What is an account on EVM vs Solana at a backend level, and what identifiers do APIs actually expose?▼ answer
Model answer
On EVM, an externally owned account (EOA) is identified by a 20-byte address derived from a secp256k1 public key (Keccak-256 of the uncompressed pubkey, last 20 bytes). Contract accounts share the same address space but hold code and storage. On Solana, an account is a keyed data blob owned by a program; the "wallet" address is typically an ed25519 pubkey (32 bytes, base58-encoded). Backends expose checksummed hex (0x… / EIP-55) for EVM and base58 pubkeys for Solana — never raw private keys. Strong interview answers separate identity (who can sign) from state location (where balances/NFTs live): EVM balances live on the account; Solana balances often live in associated token accounts (ATAs) that your indexer must resolve. Rust: alloy_primitives::Address, solana_sdk::pubkey::Pubkey, and typed newtypes at API boundaries so you never mix chains.
Q2Contrast ECDSA (secp256k1) and ed25519 for signing. What must a Rust backend verify, and what must it never store?▼ answer
Model answer
ECDSA/secp256k1 (Ethereum, Bitcoin-flavoured): signatures are (r, s, v) or compact 65-byte forms; recovery lets you derive the signer address from message hash + signature (used heavily for off-chain auth and mempool gossip). ed25519 (Solana, many Cosmos chains): deterministic, faster verify, no public-key recovery from signature alone — you need the claimed pubkey and check verify(pubkey, msg, sig). Interview must-say: backends verify signatures over a canonical message (EIP-191 / EIP-712 typed data, or Solana message bytes), check domain separators / chain id / expiry, and reject malleable or replayable payloads. Never store raw private keys in app DBs, logs, or env dumps — use HSM/KMS, MPC, or keep signing in the wallet/client; server-side hot keys (relayers, custodial flows) go in KMS with audit and least privilege. Rust crates: k256/alloy-signer for secp256k1, ed25519-dalek / solana_sdk::signature for ed25519; prefer zeroize on any ephemeral secret material.
Q3Explain EIP-191 vs EIP-712. When would you require typed data for an API auth or permit flow?▼ answer
Model answer
EIP-191 personal_sign prefixes "\x19Ethereum Signed Message:\n" + len + message so signatures cannot be reused as raw transaction hashes — fine for simple "prove you control this address" challenges. EIP-712 structured typed data hashes a domain separator (name, version, chainId, verifyingContract) plus a typed struct — wallets show human-readable fields, and signatures are bound to a specific app/chain/contract. Use EIP-712 (or equivalent) for gasless permits, off-chain order books, and any authorization that could move value or grant allowances; use EIP-191 only for low-risk session challenges if you still bind nonce + expiry + audience yourself. Rust: build digests with alloy sol types / eip712 helpers; never hand-roll hashing without tests against known vectors — one wrong ABI encode and every signature verifies against the wrong thing.
Q4How do HD wallets (BIP-32/39/44) and account abstraction change what your backend assumes about "the user"?▼ answer
Model answer
HD wallets derive many addresses from one seed via paths (m/44'/60'/0'/0/n for ETH). Users may rotate addresses; your product identity should not assume one address forever — link addresses via verified signatures or a custody provider mapping. Account abstraction (ERC-4337, EIP-7702, native AA on some L2s) means the "signer" may be a smart contract validating custom logic (multisig, passkeys, session keys). Backends must: (1) resolve whether an address is EOA or contract, (2) accept UserOperations / sponsored txs where gas payer ≠ user, (3) not equate tx.from with economic actor without reading the AA flow. Rust services usually treat addresses as opaque verified identities after signature/SIWE, store user_id ↔ address[] with verification timestamps, and keep derivation/seed material entirely out of the service.

Transactions, Nonces & Gas / Fees
Questions & model answers
Q1What fields define an EVM transaction a backend must reason about? Contrast legacy, EIP-1559, and EIP-4844 fees at a mental-model level.▼ answer
Model answer
Core fields: nonce, to/data/value, gas limit, chain id, and signature. Fee market evolution: legacy single gasPrice; EIP-1559 splits maxFeePerGas and maxPriorityFeePerGas against a protocol baseFee that burns — users bid tip for inclusion, base fee is algorithmic. EIP-4844 blobs add a separate data-availability fee market for L2 batch posting (blob gas) — app backends rarely set blob fields unless they operate a rollup poster. Interview framing: gas limit is computational budget; gas price/fee is market bid; effective cost ≈ gasUsed × effectiveGasPrice. Rust: model with alloy::consensus tx types / TransactionRequest; never assume gasPrice exists on all txs when decoding receipts.
Q2Explain the EVM nonce. How do stuck transactions and replacement work, and what bugs do APIs cause around nonces?▼ answer
Model answer
The account nonce is a strictly increasing counter of transactions from an EOA; the next executable tx must use pendingNonce (or create a gap that parks later txs). A stuck tx has too-low fees; later nonces wait. Replacement: resubmit same nonce with higher fees (nodes typically require a minimum bump, e.g. +10%). Common API bugs: (1) reading only latest nonce while another process has pending txs; (2) parallel workers both claiming the same nonce; (3) treating "submitted" as "confirmed"; (4) not tracking local nonce state when you operate a hot wallet. Relayers need a nonce manager (DB lease + pending set + replacement policy). Solana uses recent blockhashes / durable nonces instead of per-account sequential nonces — different concurrency model. Rust: serialize signing per key with a lease in Postgres/Redis; use alloy provider get_transaction_count with BlockNumberOrTag::Pending carefully.
Q3How should a Rust backend estimate gas and fees for user-facing "submit tx" or meta-tx flows?▼ answer
Model answer
Estimate gas limit via eth_estimateGas (or simulate with revm / alloy call) then add a safety buffer (10–30%) for state drift; never hardcode gas for complex contracts. Estimate fees from eth_feeHistory / oracle percentiles for tip and max fee, capped by policy. Surface both "likely cost" and "max authorization" to users. For sponsored txs, the backend pays and must budget, rate-limit, and simulate for reverts before broadcasting. Fail closed on estimation reverts — they usually mean the tx would fail on-chain. Cache fee suggestions briefly; do not cache gas estimates across materially different calldata or block state. Strong candidates mention simulation at the pending state and handling "out of gas" vs application revert distinctly in UX and metrics.
Q4Solana fees and compute units — what is the analogue of gas, and how do backends set priorities?▼ answer
Model answer
Solana charges a base fee per signature and optional priority fees (price × compute units requested). Programs consume compute units (CU); exceeding the budget fails the tx. Backends estimate CU (simulation via simulateTransaction), set ComputeBudgetInstruction limits and price, and refresh a recent blockhash before send. Unlike EVM nonces, many Solana txs can be prepared concurrently as long as accounts and blockhash rules allow — but account locks and write conflicts still serialize execution. Rust: solana_sdk::compute_budget, RpcClient::simulate_transaction; treat blockhash expiry (~60–90s) as a first-class retry reason in your submitter.

JSON-RPC, HTTP + WebSocket Node APIs
Questions & model answers
Q1What is Ethereum JSON-RPC? Which methods does a typical Rust backend actually use day-to-day?▼ answer
Model answer
JSON-RPC 2.0 over HTTP (request/response) and WebSocket (plus subscriptions). Common methods: eth_chainId, eth_blockNumber, eth_getBlockByNumber, eth_getTransactionReceipt, eth_call, eth_estimateGas, eth_sendRawTransaction, eth_getLogs, eth_getBalance/eth_getCode, and fee helpers (eth_feeHistory, eth_gasPrice). Subscriptions: eth_subscribe for newHeads, logs, sometimes newPendingTransactions. Rust: prefer alloy providers (RootProvider, WsConnect) over hand-rolled serde envelopes — but know the wire shape (method, params, id, error.code) for debugging provider quirks. Batch requests exist but many hosts limit or disable them.
Q2How do you design a node client layer for rate limits, retries, and multi-provider failover?▼ answer
Model answer
Treat RPC as an unreliable dependency: timeouts, 429s, inconsistent results across providers. Patterns: (1) per-provider rate limiters (token bucket) and concurrency caps; (2) retry with jitter on idempotent reads; (3) do not blindly retry eth_sendRawTransaction without checking if the tx is already known; (4) hedged requests for latency-critical reads; (5) sticky vs fanout — writes to one primary, reads from a pool with quorum checks for critical paths; (6) circuit breakers when error rate spikes. Tag metrics by provider + method. Rust: tower layers for retry/timeout/limit around an alloy transport, or a small internal RpcPool that picks healthy endpoints. Always pin chainId at boot and refuse mismatched providers.
Q3What is a reorg, and how should HTTP APIs and indexers react differently than a wallet UI?▼ answer
Model answer
A reorg replaces a previously accepted chain tip with another fork; transactions can flip from included → excluded or move to a different block/index. Depth is usually small on healthy L1s but can be larger under stress; L2s have their own safe/finalized notions. Wallet UIs can show "pending / 1 conf / finalized". Backend indexers must: process blocks with a confirmation lag or reorg-rewind (delete/mark invalidated rows for orphaned blocks), prefer safe/finalized tags when business logic allows, and emit compensating events to downstream systems. Never treat a single eth_getTransactionReceipt success as irreversible settlement for high-value actions. Subscribe to newHeads and detect parent-hash discontinuities as reorg signals.
Q4HTTP vs WebSocket for chain ingestion — trade-offs, and how do you keep a WS subscription correct?▼ answer
Model answer
HTTP polling is simpler, cacheable at the edge for some reads, and easier to load-balance — but laggy and costly at high frequency. WebSocket subscriptions push heads/logs with lower latency but drop on disconnects, need heartbeat/pong handling, and can silently stall. Production pattern: WS for low-latency tips + periodic HTTP backfill/gap-fill by block number; on reconnect, resume from last durable checkpoint, not from "now". Deduplicate by block hash / log unique key. Rust: tokio task with supervised reconnect, alloy pubsub, and a cursor in Postgres. Watch provider-specific limits on filter lifetime and max log range for eth_getLogs (often 2k–10k blocks).

Mempools & Transaction Lifecycle
Questions & model answers
Q1Walk through the lifecycle of a transaction from signed bytes to finalized inclusion.▼ answer
Model answer
(1) Client/backend builds and signs → raw bytes / tx hash. (2) eth_sendRawTransaction (or Solana sendTransaction) propagates to a node. (3) Node validates signature, nonce, balance/fees, intrinsic gas → admits to mempool (txpool). (4) Gossip to peers (public mempool) or private relay. (5) Block builder/validator selects txs → included in a block. (6) Receipt available: status, gas used, logs. (7) Confirmations accumulate; eventually safe/finalized per chain rules. Failure modes at each step: RPC reject, eviction from mempool, replace-by-fee, dropped on low tip, on-chain revert (still included), reorg. Your API should model states explicitly: signed → submitted → pending → mined → confirmed → finalized / failed / replaced.
Q2What is a mempool, and why do many modern Ethereum flows bypass the public one?▼ answer
Model answer
The mempool is the node's pool of valid but not-yet-included transactions, ordered by local policy (fees, account nonces, size limits). It is not a global consistent queue — each node sees a different set. Post-PBS / MEV-aware Ethereum, searchers and sophisticated users often send via private orderflow (builder relays, MEV-Share, protected RPCs) to reduce frontrunning. Backends that broadcast sensitive swaps through a default public RPC expose users to sandwich risk. Interview signal: distinguish "tx is known to our node" from "tx is safely private" and from "tx is finalized on-chain."
Q3How do you track submission status reliably in a Rust service without busy-polling forever?▼ answer
Model answer
Persist tx hash + metadata at submit time. Watcher loop: poll receipt with exponential backoff, and/or subscribe to heads and check inclusion; timeout into dropped_or_unknown and trigger resubmit/replace policy. Use eth_getTransactionByHash to distinguish "unknown" vs "pending" vs "mined". Idempotency keys on your API map to at most one in-flight signed tx per user action. Metrics: time-to-mine, replace count, revert rate. Rust: a dedicated tokio worker reading from a queue (SQS/NATS/Postgres SKIP LOCKED), calling alloy provider methods, writing state transitions transactionally with the business effect (credit user only on sufficient confirmations).
Q4Local vs public mempools on Solana — what does "processed / confirmed / finalized" mean for API design?▼ answer
Model answer
Solana RPCs expose commitment levels: processed (leader saw it), confirmed (supermajority voted), finalized (rooted / irreversible under normal assumptions). TPU / QUIC ingest and leader scheduling differ from Ethereum's gossip mempool model; landing depends on leader schedule, CU price, and sometimes staked connections. APIs should let callers choose commitment for reads, default writes' success criteria to confirmed or finalized based on value, and never promise finality at processed. Rust: CommitmentConfig on RpcClient / solana_client; surface commitment in your own JSON so clients do not assume Ethereum-style "12 confirmations."

Smart Contracts vs Indexing — What Backends Build
Questions & model answers
Q1What do Web3 backend engineers usually build, if not the chain or the Solidity itself?▼ answer
Model answer
Most Rust roles are chain-adjacent: indexers, APIs over indexed data, wallets/relayers, trading bots, risk engines, oracle publishers, bridge watchers, and infra (RPC proxies, simulators). Smart contracts define on-chain truth; backends make it queryable, enforce product rules off-chain, assemble transactions, and integrate fiat/KYC/notifications. Saying "I'd put that in a contract" for every feature is a smell — storage cost, upgradeability, and latency matter. Conversely, never invent off-chain balances that disagree with chain state without a clear custody model. Interview framing: contracts for settlement and adversarial integrity; backends for UX, aggregation, search, and policy.
Q2When do you eth_call / simulate vs read from your indexer DB?▼ answer
Model answer
Indexer DB: historical queries, joins, full-text, portfolio views, analytics — fast and rich, but eventually consistent and only as complete as your pipeline. Live RPC / eth_call: current allowance, precise preview of a swap, "what would this tx do now," admin checks against tip state. Hybrid is normal: list NFTs from DB, verify ownership with a fresh ownerOf before a sensitive action. Rust: alloy sol! bindings for typed calls; sqlx/sea-orm for indexed tables. Document freshness SLAs ("indexed within N blocks") in your API.
Q3What is ABI / IDL and how do Rust services bind to contracts without shipping a full node?▼ answer
Model answer
An ABI (EVM) describes functions/events and how to encode calldata and decode logs/returns. Solana IDL (Anchor) describes accounts and instructions similarly. Backends depend on RPC + ABI bindings, not on executing the VM for ordinary reads (unless simulating). Rust: alloy sol! macro or sol!{ ... } from artifacts; legacy ethers-rs abigen; Solana anchor-client / hand-built instruction data with borsh. Pin contract addresses per chain id; version your bindings when contracts upgrade. Strong candidates mention immutable event layouts vs upgradeable proxies and why event indexing must key by proxy address + implementation awareness.
Q4Where does revm fit for a backend team? When is local EVM simulation worth it?▼ answer
Model answer
revm is a Rust EVM implementation used for simulation, fuzzing, custom tracers, and building tooling (Foundry uses it). Backend uses: pre-flight simulate user txs against a forked state, MEV/strategy research, decode complex revert data, or run deterministic tests without a full geth. It is overkill for CRUD APIs over indexed transfers. If you simulate in production, you need state provider integration (alloy db / fork at block), gas metering parity awareness, and strict resource limits — simulation can be CPU heavy. Interview gold: "we simulate to reduce failed on-chain spends; we index for query path."

Event Logs, Receipts & Indexing Pipelines
Questions & model answers
Q1What is an event log vs a receipt? How do you uniquely identify a log line?▼ answer
Model answer
A receipt is per-transaction inclusion metadata: status, gas used, cumulative gas, logs bloom, logs[]. Each log has address (emitter), topics[0]=event signature hash, indexed topics, and data payload. Unique key in practice: (block_hash, tx_hash, log_index) or (block_number, block_hash, log_index) with reorg handling — tx_hash + log_index alone can be ambiguous across chains/reorgs if you multi-chain. Decode with ABI: non-indexed fields live in data; indexed dynamic types are hashed (you cannot recover the original string from the topic). Rust: alloy event types + decode_log; store raw topics/data too for re-decoding after ABI upgrades.
Q2Sketch a production indexing pipeline from blocks to API-ready tables.▼ answer
Model answer
Classic stages: ingest (WS heads + HTTP backfill) → decode (ABI apply) → transform (domain entities: Transfer, Swap, Position) → write (Postgres/ClickHouse) → publish (webhooks/Kafka). Maintain a cursor (block_number, hash); on parent mismatch, rewind N blocks and delete orphaned rows or use versioned validity intervals. Partition eth_getLogs requests by address/topic and block range to respect provider limits. Idempotent upserts on natural keys. Separate "fast unconfirmed" lane from "finalized" lane if product needs speed. Rust: tokio workers, alloy for RPC, sqlx for writes, exactly-once-ish via DB transactions + deterministic ids. Tools like Subsquish/The Graph exist; interviewers still want you to know the rewind/cursor mechanics.
Q3How do you handle reorgs and finality in the database schema?▼ answer
Model answer
Options: (1) confirm lag — only index blocks older than K; simple, latency trade-off. (2) rewind — store block_hash, on reorg delete where block_number >= reorg_point and replay. (3) bitemporal / invalidate flags — mark rows is_orphaned for audit. Always store block hash with every derived row. Downstream consumers need tombstones or version vectors. For payments, gate business side-effects on finalized (or chain-specific safe head). Test reorgs explicitly on a local anvil chain by mining competing blocks — not only happy-path backfills.
Q4Solana indexing differences: accounts vs logs, and why "getProgramAccounts" is a trap at scale.▼ answer
Model answer
Solana programs emit logs, but much state lives in accounts that mutate in place — you often index account updates (Yellowstone gRPC / Geyser plugins) plus transaction metadata, not only EVM-style receipt logs. getProgramAccounts scans and is expensive/rate-limited — fine for rare admin tools, bad as a hot path. Prefer streaming account updates, store by pubkey, and reconstruct dashboards from your DB. Decode with borsh/Anchor layouts; handle discard of inner instructions carefully when parsing token balances. Rust ecosystem: solana_client, geyser proto clients, carbon/yellowstone-grpc style pipelines — same cursor/rewind discipline as EVM.

DEX Mechanics for Backend Engineers
Questions & model answers
Q1Contrast AMM and order-book DEXes. What data does each force your backend to track?▼ answer
Model answer
AMM (Uniswap-style): pool reserves / liquidity positions determine price via a curve (x*y=k or concentrated liquidity ticks. Backend indexes Swap/Mint/Burn events, pool state, and optionally tick bitmaps for quoting. Quotes can be computed from reserves + fee tier (or off-chain quoter). Order book (on-chain like Serum/OpenBook, or hybrid): resting orders at price levels; backend tracks order placement/cancel/fill events, maintains an off-chain book mirror for speed, reconciles to chain. AMM indexing is event + slot/block state; books need sequence numbers and gap repair. Neither requires you to reimplement matching in the API — but market-data APIs must state whether prices are indexed, simulated, or live RPC.
Q2What is slippage, price impact, and mid price — and how should a quote API present them?▼ answer
Model answer
Price impact: move along the AMM curve caused by trade size. Slippage: difference between expected and executed price due to impact + competing trades before inclusion. Quote APIs should return amount-in/out, fee, route legs, estimated execution price, and a minOut / maxIn bound the user signs (deadline + slippage bps). Never silently default to unlimited slippage. For multi-hop routes, show per-hop pools and aggregate. Rust quoting services often run pure functions over cached pool state with periodic refresh, then verify with eth_call before suggesting a signature. Document quote TTL — stale quotes are a leading cause of revert spam.
Q3How do aggregators (0x, Uniswap router, Jupiter) change backend design?▼ answer
Model answer
Aggregators split routes across venues and return calldata + allowance targets. Your backend may: call their HTTP APIs, cache routes briefly, simulate calldata, and present unified UX. Trust boundaries matter — verify chain id, spender addresses against allowlists, and simulate for unexpected token movements. For Solana, Jupiter-style routes return serialized transactions you may partially sign or sponsor. Treat aggregator outages as dependency failures with fallback routes. Rust: typed HTTP clients (reqwest + serde), strict allowlists for to/spender, and revm/RPC simulation before broadcast.
Q4Concentrated liquidity (Uniswap v3) — what indexer complexity appears that v2 did not have?▼ answer
Model answer
v3 positions are NFTs with tick ranges; swaps cross ticks and update liquidity in-range. Indexers must handle tick-crossing events, position fees growth, and sparse tick state — pool "reserves" alone are insufficient for accurate quoting. Historical PnL needs fee snapshots per position. Many teams index Swap events for volume charts but call a Quoter contract or maintain a tick cache for executable quotes. Mentioning ticks, positions as NFTs, and fee growth globals is a strong senior DEX signal without writing a full v3 clone.

Consensus & Finality for App Backends
Questions & model answers
Q1What does "finality" mean for an application backend, in practical terms?▼ answer
Model answer
Finality is the point after which your product will not unwind a state transition under normal operation — credits, shipments, completed withdrawals. Probabilistic PoW-style finality ("after k confirmations") differs from economic/protocol finality (Casper FFG justified/finalized checkpoints on Ethereum). Backends should map chain concepts onto product policies: low-value UX can follow safe; high-value settlement waits for finalized or a risk-scored confirmation depth. Do not recite HotStuff internals — show you gate side effects on the right head.
Q2Explain Ethereum latest vs safe vs finalized for RPC reads.▼ answer
Model answer
latest: current tip — can reorg. safe: under honest-majority assumptions, unlikely to reorg (still not finalized). finalized: justified by consensus finality gadgets — treated as irreversible for app purposes. Also pending for txpool-inclusive views (nonces, calls). Indexers often ingest latest for speed but only mark business-final at finalized. Always specify the block tag in eth_call when correctness matters; default provider tags differ. Rust alloy: BlockNumberOrTag::Finalized etc. on provider calls.
Q3How do L2s change the finality story (optimistic vs ZK, sequencer risk)?▼ answer
Model answer
Many L2s have fast soft confirmations from a sequencer (centralized soft finality) and slower L1-settled finality. Optimistic rollups add challenge windows for withdrawals; ZK rollups wait for validity proofs posted to L1. App backends must distinguish: (1) tx confirmed on L2 RPC, (2) batched to L1, (3) L1 finalized, (4) bridge withdrawal completed. Cross-chain credit should key off the bridge's security model, not merely an L2 receipt. Mention sequencer downtime / reorg policies of the specific L2 when designing SLOs.
Q4What finality/commitment knobs matter on Solana for a payments API?▼ answer
Model answer
Return and persist the commitment level used when you declared success. For merchant payments, prefer confirmed minimum and finalized for settlement/ledger close. Handle the rare rollback cases with explicit reconciliation jobs. Expose these in webhooks: payment.confirmed vs payment.finalized so accountants and risk systems can subscribe appropriately. This is the Solana analogue of Ethereum confirmation policies — same product idea, different RPC vocabulary.

Wallets, Sessions & SIWE-Style API Auth
Questions & model answers
Q1How does Sign-In with Ethereum (SIWE / EIP-4361) work end-to-end for a Rust API?▼ answer
Model answer
Flow: (1) backend issues a challenge nonce bound to address + expiry; (2) client signs a SIWE message (domain, uri, chain id, nonce, issued-at, statement); (3) backend verifies EIP-191 signature recovers the claimed address, checks domain/nonce/expiry/chain binding, consumes nonce; (4) issues an application session (JWT/session cookie) for subsequent HTTP calls — not re-signing every request. SIWE authenticates wallet control, not KYC identity. Rust: parse/verify with a SIWE crate or careful hand parser + alloy signature recovery; store nonces in Redis with TTL; use axum middleware for Bearer/session.
Q2What security checks are non-negotiable in SIWE-style auth?▼ answer
Model answer
Bind domain and URI to your frontend origin (prevent phishing signatures reused elsewhere). Single-use nonce, short expiry, matching chainId if chain-specific. Reject malleable signatures / wrong version; constant-time compare where relevant; rate-limit verification. After login, authorize by session user id mapped to verified addresses — do not trust a client-supplied address header alone. For Solana, analogous "sign message" login with ed25519 verify and the same nonce/domain discipline. Rotate session tokens; provide logout/revocation. Never log full signed messages with secrets if you embed them; nonces are not passwords but still treat the store as sensitive.
Q3Session keys, permits, and delegated signing — how do they differ from SIWE login?▼ answer
Model answer
SIWE proves control for authentication. ERC-2612 permits / DAI permits authorize token allowances via signature (state-changing intent). Session keys (AA, gaming wallets) grant limited on-chain powers for a period. Backends must not conflate "logged in" with "can move funds." Store capability scopes separately. If your API sponsors txs, enforce allowlisted selectors, spending caps, and simulation. Interview clarity on authn vs authz vs on-chain authorization is a senior signal.
Q4How would you design multi-address users and wallet linking without creating account-takeover bugs?▼ answer
Model answer
Linking requires a fresh SIWE (or chain equivalent) from the new address while an authenticated session already exists for the primary user — or a dual-signature ceremony. Never link solely because a tx was seen from an address. Support unlink with re-auth. Beware signature reuse across your staging/prod domains. For custodial/embedded wallets, the auth primary may be email/OAuth with wallets as secondary deposit addresses — document which key is authoritative. Rust services: transactional DB constraints on address uniqueness globally, and audit log every link/unlink.

MEV & Frontrunning Awareness for API Designers
Questions & model answers
Q1What is MEV in one paragraph a backend interviewer expects?▼ answer
Model answer
MEV (maximal extractable value) is profit from controlling inclusion and ordering of transactions in a block — arbitrage, liquidations, sandwiches. Searchers bid via priority fees or builder auctions (PBS). App backends care because user trades can be frontrun/backrun if broadcast publicly, and because your own liquidations/oracles may be raced. You do not need to write a searcher; you need to design APIs and submit paths that do not unnecessarily leak valuable, time-sensitive intent.
Q2How does a sandwich attack work, and what API/UX mitigations exist?▼ answer
Model answer
Attacker sees a victim swap in the mempool, inserts a buy before and a sell after, extracting value via price impact; victim's minOut still holds but they get worse price within slippage. Mitigations: tight slippage + short deadline, private RPCs / MEV protection relays, RFQ/quotes with firm off-chain market makers, batch auctions, and avoiding broadcasting intent before binding constraints. API design: default safe slippage, warn on high impact, do not return unsigned "exact executable route" in public logs, and offer protected submission endpoints.
Q3What must you avoid logging or exposing in trading/relayer APIs because of MEV?▼ answer
Model answer
Avoid publishing pending transaction hashes/calldata of high-value strategies to public websockets, predictable liquidation cron schedules with exact targets, or mempool-visible "intent" APIs without commit-reveal / privacy. Rate-limit quote APIs that reveal inventory. Treat internal orderflow as confidential. Even debug logs with full calldata can leak to centralized log vendors — redact or sample. Rust services should classify fields at the tracing layer (tracing sensitive fields) and gate admin endpoints.
Q4How do PBS / builders and private orderflow change what "sendTransaction" means in product copy?▼ answer
Model answer
Users think "broadcast to the network"; often the tx goes to a builder via a relay with privacy until inclusion. Your API should label submission routes: public RPC vs protected. Failures differ (relay reject vs mempool eviction). Inclusion guarantees are probabilistic; always watch receipts. For Solana, priority fees and leader-aware landing services are the rough analogue — same product need, different plumbing. Strong answer: MEV-aware design is about information leakage and submission path, not implementing Flashbots.

Solana vs EVM — Mental Models for Rust Engineers
Questions & model answers
Q1List the top mental-model differences that bite EVM engineers moving to Solana (and vice versa).▼ answer
Model answer
(1) Accounts: Solana data lives in explicit accounts you pass to instructions; EVM storage is keyed inside the contract. (2) Programs are stateless; state is in accounts they own. (3) Parallelism: Solana schedules non-overlapping account locks in parallel; EVM is largely sequential per block execution mental model. (4) Fees: CU + prioritization vs gas metering. (5) Signatures: ed25519 vs secp256k1; many signers per tx common on Solana. (6) Tokens: SPL token accounts / ATAs vs ERC-20 balances in contract storage. (7) RPCs / commitment vocabulary differs. Rust engineers often feel at home on Solana's native Rust programs, but backend indexing and ATA resolution are the usual footguns.
Q2What is an Associated Token Account (ATA), and why do backends care?▼ answer
Model answer
An ATA is a deterministic PDA for (wallet, mint) holding SPL token balances. Transfers fail if the destination ATA is missing — wallets/relayers often createAssociatedTokenAccount first. Indexers must map mint+owner → ATA pubkey; portfolio APIs sum token accounts, not the system account balance alone (SOL rent/balance is separate from SPL). Rust: spl_associated_token_account derivations; never assume one token account per wallet without checking.
Q3How do PDAs and instruction account metas affect API/tx builders in Rust?▼ answer
Model answer
PDAs (program-derived addresses) are deterministic keys programs can sign for via invoke_signed; backends derive the same seeds to fetch accounts and build instructions. Each instruction lists accounts with is_signer/is_writable metas — wrong flags cause runtime failures. Tx builders assemble instructions + recent blockhash + signers. Rust: solana_sdk::instruction::Instruction, Pubkey::find_program_address. Contrast EVM: one to + calldata; Solana txs are more like explicit capability lists.
Q4EVM tooling map for Rust engineers: alloy vs ethers-rs vs revm vs Foundry — when to cite each?▼ answer
Model answer
alloy: modern RPC/types/providers/signers (ethers-rs successor direction). ethers-rs: legacy but still seen in codebases — know migration points. revm: embeddable EVM for sim/fuzz. Foundry (forge/anvil/cast): Solidity-centric test/deploy tooling that Rust backends call as processes or mirror via anvil endpoints. Solana side: solana_sdk, solana_client, Anchor for programs, litesvm/banks client for tests. Citing the right tool for RPC vs simulation vs contract test shows practical experience.

Testing: Anvil, Localnets, Forks & Parsers
Questions & model answers
Q1How do you test a Rust indexer or relayer against a local EVM?▼ answer
Model answer
Run anvil (Foundry) or geth dev mode; deploy contracts with known ABIs; emit events; point the indexer at http://127.0.0.1:8545; assert DB rows. Use fixed mnemonic/keys from anvil for signers. Reset between tests or use unique chain ids / snapshots (evm_snapshot/evm_revert). Prefer deterministic block times. Rust integration tests: spawn anvil as std::process::Command or testcontainers, drive with alloy, then assert via sqlx. Keep unit tests pure for decode logic without RPC.
Q2What are fork tests, and when are they worth the cost?▼ answer
Model answer
Fork tests run anvil/Hardhat against a pinned mainnet/L2 block via RPC, so you interact with real contract bytecode and state (Uniswap pools, tokens). Great for route simulation, allowance quirks, and proxy layouts. Costs: flaky providers, slow CI, mainnet state drift if unpinning. Pin fork_block_number, cache RPCs where possible, and reserve forks for a thin suite — not every unit test. Rust: alloy provider against forked anvil; or revm with a forked database backend for tighter in-process tests.
Q3How do you property-test ABI/Borsh parsers and why does it matter?▼ answer
Model answer
Encoding bugs are silent fund-loss risks. Use proptest to generate field values, encode → decode → assert equality; also test known vectors from Foundry/cast and hostile inputs (truncated data, oversized lengths). For logs, fuzz topic counts and ensure unknown events are safely skipped. For JSON-RPC, fuzz serde of hex quantities (U256, leading zeros) — Ethereum hex quirks are classic production incidents. Rust: proptest + alloy_primitives strategies; corpus tests for raw mainnet log samples.
Q4Solana localnets and banks/litesvm — what does a solid test pyramid look like for a Rust backend?▼ answer
Model answer
Pyramid: (1) pure unit tests for borsh layouts, PDA seeds, ATA derivation; (2) litesvm / solana-program-test / banks client for instruction-level program interaction without full validators; (3) solana-test-validator integration for RPC commitment and ws flows; (4) slim mainnet-beta read-only tests behind a feature flag. Assert commitment behavior and blockhash expiry retries explicitly. CI should not depend on public mainnet write access. Same idea as EVM: mock RPC for unit speed, localnet for protocol fidelity, fork/mainnet samples for realism.
