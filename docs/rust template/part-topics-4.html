Macros & Unsafe Rust
Questions & model answers
Q1What does the unsafe keyword actually turn off? What does it emphatically not turn off?▼ answer
Model answer
unsafe unlocks exactly five extra capabilities the compiler otherwise forbids: (1) dereferencing a raw pointer, (2) calling an unsafe fn, (3) accessing/mutating a static mut, (4) implementing an unsafe trait, (5) accessing fields of a union. That's the entire list — nothing more. What it does not turn off: the borrow checker still runs inside unsafe blocks for ordinary safe operations; the type checker is fully active; integer overflow checks in debug builds still apply to normal arithmetic; move semantics and drop glue are unaffected. unsafe is best understood as "I am now personally responsible for upholding invariants the compiler would otherwise check for me" for those five specific operations — it's a promise to the compiler, not a mode that disables Rust's usual rules wholesale. This is why the common phrase "unsafe doesn't mean incorrect, it means unchecked" is accurate: well-written unsafe code is exactly as correct as safe code, it just required the human, not the compiler, to prove it.
Q2What is the difference between a declarative macro (macro_rules!) and a procedural macro? Name the three kinds of proc macros.▼ answer
Model answer
macro_rules! (declarative macros) work by pattern matching on token trees and substituting into a template — you declare patterns like ($($x:expr),*) => { ... } and the macro expands by textual-ish substitution of matched fragments, hygienic with respect to variable names to avoid accidental capture. They're relatively limited in what shapes of input they can match/transform, but simple to write and don't require a separate crate. Procedural macros are functions written in ordinary Rust that receive a token stream and return a token stream — full programmatic control over the transformation, typically using the syn crate to parse the input into an AST and quote to generate output tokens. They must live in a separate crate marked proc-macro = true in Cargo.toml, because they run at compile time as a plugin the compiler invokes. Three kinds: (1) derive macros — #[derive(MyTrait)], generates additional code (usually a trait impl) alongside the item, cannot modify the original item itself. (2) attribute macros — #[my_attribute], can arbitrarily transform the item it's attached to (this is how #[tokio::main] rewrites your async fn main() into a synchronous fn main() that spins up the runtime and blocks on your original body). (3) function -like macros — my_macro!(...), similar to macro_rules! call syntax but with the full power of a proc macro (e.g. sqlx::query!, which needs to actually talk to a database at compile time — something declarative macros could never do).
Q3What invariant must you uphold when implementing unsafe fn get_unchecked(&self, index: usize) -> &T on a custom collection? What happens if you violate it, concretely?▼ answer
Model answer
The function's safety contract (which must be documented, conventionally via a /// # Safety doc section) is: the caller must guarantee index < self.len() before calling — the function itself skips the bounds check the safe .get(index) would otherwise perform, trusting the caller instead. Concretely, if violated: the function computes a pointer via pointer arithmetic (self.ptr.add(index)) and dereferences it without checking — if index is out of bounds, this reads memory outside the buffer's allocation. This is immediate undefined behaviour, not a graceful failure: it might read garbage data that happens to look plausible (silent data corruption propagating through your program with no crash at all, the worst case for debuggability), might read unmapped memory and segfault, or — since the compiler is permitted to assume UB never happens — might cause the optimiser to make transformations elsewhere in the program that assume this code path is unreachable, producing behaviour that appears completely unrelated to the out-of-bounds access itself. This is precisely the class of bug cargo miri run is designed to catch during testing (it detects out-of-bounds raw-pointer access even when it happens not to crash on a given run), and why any custom unsafe API needs to be paired with either exhaustive testing of the boundary conditions or a miri-based test suite before shipping.
Q4What does "sound" mean when describing an unsafe abstraction? Give an example of an API that is memory-safe in every test you can write but is nonetheless unsound, and explain why soundness, not testing, is the actual bar.▼ answer
Model answer
A safe function/API built on top of unsafe internals is sound if it is impossible to trigger undefined behaviour through its safe public interface, no matter what otherwise-valid arguments a caller supplies — soundness is a universal claim over all possible inputs and usage patterns, not a claim that it happened to work for the inputs you tried. Concrete example of unsound-but-passes-your-tests: 
fn get_two_mut<T>(v: &mut Vec<T>, a: usize, b: usize) -> (&mut T, &mut T) {
    unsafe {
        let ptr = v.as_mut_ptr();
        (&mut *ptr.add(a), &mut *ptr.add(b)) // BUG: no check that a != b!
    }
}
This compiles, and calling it with a=1, b=3 on a length-5 vector "works fine" in every test — but calling it with a=2, b=2 produces two live &mut T aliasing the same memory location — a direct violation of Rust's core aliasing guarantee, exactly the class of bug the borrow checker exists to prevent, now smuggled past it through an unsafe block. This is unsound: there exists a valid, safe-looking call (no out-of-bounds index, nothing exotic) that produces UB, purely because the function forgot to check a != b. Why soundness, not testing, is the real bar: you can run this function against thousands of random valid indices and never happen to hit a == b, so it would appear "well-tested" and correct — but the bug is latent, waiting for exactly the input the tests didn't cover, in code the type system offers zero protection against once you're inside unsafe. Reviewing unsafe code requires proving the safety argument covers every possible input, not sampling a representative few — this is precisely why unsafe code review is treated as a qualitatively different, higher-bar activity than ordinary code review in serious Rust teams.
Q5Your team is reviewing a PR that adds an unsafe block to bypass a bounds check for a 3% throughput improvement in a hot loop. Walk through how you'd evaluate whether to approve it.▼ answer
Model answer
1. Demand the benchmark, not the intuition. Verify the 3% number with a reproducible criterion benchmark, on realistic data — bounds-check elimination is one of the most commonly overestimated optimisations in Rust, since LLVM already eliminates many redundant bounds checks automatically when it can prove an index is in range from surrounding code (e.g. iterating 0..v.len() — the compiler frequently proves this safe already, without needing unsafe at all). Ask: does simply restructuring the loop to iterate via .iter() directly instead of indexing achieve the same speedup safely, since that sidesteps bounds checks entirely without unsafe? 2. Demand an explicit, written safety argument. Every unsafe block should have a comment stating precisely which invariant makes it sound and why that invariant provably holds at this call site — if the author can't write this down convincingly, that's itself a strong signal the code isn't actually sound yet, even if it currently "works." 3. Ask whether it's covered by miri or a proptest/fuzzing setup exercising edge cases (empty inputs, boundary indices, unusual data), not just the happy-path benchmark inputs. 4. Weigh the trade-off explicitly, out loud, as a team decision — 3% in a genuinely hot, profiled bottleneck for a latency-critical service might be worth the added maintenance burden and risk surface; 3% in a code path that runs once per request in a service where the network round-trip dominates by 100x is very likely not worth it. The senior-level point to make explicitly: unsafe code is not free even when correct — it's a permanent tax on every future reviewer and refactor of that code, since any change nearby must be re-checked against the original safety argument. The right default posture is scepticism, not "well it compiles and the benchmark shows a gain" — approve only once the safety argument, test coverage, and actual measured benefit under realistic conditions all justify it.

  • Treats unsafe PR review as demanding a written safety argument, not just a passing benchmark

The single highest-leverage senior signal on this whole page: does the candidate treat "it passed all my tests" and "it's sound" as two different, separate claims? Almost every real-world unsafe-code incident comes from conflating these two. If they say this distinction unprompted, take note.
// Topic 17
Memory Layout & Performance
Questions & model answers
Q1What's the difference between #[repr(Rust)] (the default), #[repr(C)], and #[repr(packed)]?▼ answer
Model answer
#[repr(Rust)] (the implicit default): the compiler is free to reorder struct fields, choose enum discriminant representations, and apply layout optimisations (like the null-pointer optimisation for Option) however it decides is best — there is no stable, guaranteed layout across compiler versions or even between two compilations, and you should never assume a specific byte layout for a default-repr type. #[repr(C)]: forces the same field-ordering and padding rules a C compiler would use — fields laid out in declaration order, with standard alignment-driven padding, no reordering — required whenever a struct crosses an FFI boundary (passed to/from C code) since C code needs a stable, predictable layout to interpret the bytes correctly. #[repr(packed)]: removes inter-field padding entirely, packing fields as tightly as possible — saves memory but at the cost of potentially unaligned field access, which is undefined behaviour to do via a normal reference on some architectures (you must read packed fields via ptr::read_unaligned or copy them out by value first) — this is a genuinely dangerous repr that should only be reached for with a specific, well-understood reason (e.g. matching an exact wire/file format), never as a casual memory-saving trick.
Q2Given struct Foo { a: bool, b: u64, c: bool }, what is size_of::<Foo>() likely to be, and how would you reduce it?▼ answer
Model answer
With the default repr, the compiler is free to reorder fields for compactness, so it will likely place both bools adjacent to each other and the u64 separately, giving 16 bytes total (8 for the u64 + 1 + 1 for the two bools + 6 bytes of trailing padding to keep the overall struct's size a multiple of its largest field's alignment, 8) — rather than the naive 24 bytes you'd get from padding each field to 8-byte alignment independently in declaration order (which is what #[repr(C)] would actually produce for this exact declaration order, since C repr preserves order: bool+7 padding, u64, bool+7 padding = 24 bytes). The general technique for reducing size by hand (relevant when you do need #[repr(C)], or want to help the default repr's reordering along, or are just being deliberate): order fields from largest alignment to smallest (largest types first) to minimise padding holes, and consider whether small flags/enums can be packed into a single byte or bitflags instead of several separate bools. In practice with default repr, hand-ordering rarely matters since the compiler already reorders — but knowing std::mem::size_of and std::mem::align_of as the verification tools, and being able to explain why a given size arises, is the actual skill being tested here, not memorising the exact byte count for every case.
Q3What is false sharing? How would you use #[repr(align(64))] (or a padding field) to fix it in a per-thread counters array?▼ answer
Model answer
False sharing occurs when two logically-independent variables happen to reside on the same CPU cache line (typically 64 bytes) — even though two threads are writing to entirely different variables with no actual data dependency between them, every write invalidates the whole cache line in the other core's cache (the cache-coherence protocol operates at cache-line granularity, not per-variable), forcing repeated cross-core cache-line transfers that can degrade throughput to far worse than a single-threaded version — despite the algorithm being logically perfectly parallel with zero real contention. A classic trigger: [AtomicU64; N] where each thread increments its own index — the array's elements are only 8 bytes apart, so up to 8 counters share one 64-byte cache line. Fix: pad each element out to a full cache line: 
#[repr(align(64))]
struct PaddedCounter(AtomicU64);
let counters: [PaddedCounter; N] = /* ... */;
// each PaddedCounter now occupies its own 64-byte-aligned cache line — no cross-talk
#[repr(align(N))] forces the compiler to align (and pad) every instance of the type to an N-byte boundary. The standard library exposes std::hint::likely... no — more precisely, exposes std::mem::size_of::<CacheLine>-style constants via the unstable #[repr(align)] approach shown above, and crates like crossbeam-utils provide a ready-made CachePadded<T> wrapper that does exactly this padding for you, which is what most production code reaches for in practice rather than hand-rolling the repr attribute.
Q4Explain why iterating a Vec<Box<LargeStruct>> can be significantly slower than iterating a Vec<LargeStruct>, even though both are technically "O(n)." What's the general principle called, and when would you actually prefer the boxed version despite the cost?▼ answer
Model answer
Vec<LargeStruct> stores every struct's bytes directly, contiguously in the vector's single heap buffer — sequential iteration streams through memory linearly, which the hardware prefetcher predicts and pre-loads extremely well, maximising cache-line utilisation. Vec<Box<LargeStruct>> stores a contiguous array of pointers, each pointing to a separate, independent heap allocation potentially scattered anywhere in the address space — iterating means chasing a pointer to a effectively random location for every single element, causing a cache miss (and often a full round-trip to main memory, ~100ns+ vs ~1ns for an L1 cache hit) on nearly every access, with no useful prefetching possible since the addresses aren't predictable. This general principle — arranging data so that fields/elements accessed together are stored physically near each other, to maximise cache-line utilisation and prefetcher effectiveness — is often called data-oriented design or, more specifically here, the "array of structs vs struct of arrays" and "pointer chasing vs contiguous access" considerations. When boxing is still the right call despite this cost: when the structs are extremely large and you're frequently moving/reordering them within the collection (sorting, shuffling) — moving a Box pointer is a cheap pointer-swap regardless of the pointee's size, while moving a giant inline struct means memcpy-ing the whole thing on every swap; when elements need stable addresses that survive the Vec reallocating/growing (a raw inline struct's address changes on reallocation, a boxed one's heap address doesn't); or when the struct is polymorphic (Box<dyn Trait>) and there's genuinely no fixed size to store inline at all. The senior framing: this is a real trade-off with a right answer that depends on access pattern (sequential scan vs frequent reordering vs need for stable addresses), not a universal "avoid boxing" or "always box large types" rule.
Q5Walk through how you'd profile a Rust service that's using more CPU than expected in production, from first principles — tools, in order, and what each tells you that the previous one didn't.▼ answer
Model answer
1. Confirm you're profiling a release build with debug symbols ([profile.release] debug = true in Cargo.toml) — profiling an unoptimised debug build tells you almost nothing useful about production behaviour, and forgetting this is the single most common profiling mistake. 2. Sampling CPU profiler first — perf record / cargo flamegraph. This gives you a flame graph showing which functions consume wall-clock/CPU time in aggregate, cheaply and with low overhead, without needing any code changes — almost always the right first step to find "where is the time actually going" before hypothesising. 3. If the flame graph points at allocation-heavy code — heaptrack or dhat-rs. Excessive small allocations, unexpected clones, or fragmentation often show up as surprisingly hot malloc/free frames in the flame graph — a heap profiler then tells you exactly which call sites are allocating and how much. 4. If contention/lock waiting is suspected — tokio-console (for async services) or instrumenting lock-wait time directly. A CPU profiler alone can be misleading for concurrency-bound problems since a thread blocked waiting for a lock isn't "using CPU" in the way a sampling profiler measures — you need visibility into wait time and task scheduling specifically, which tokio-console provides for async task polling/wake patterns. 5. Micro-benchmark the specific hot function in isolation with criterion once you've identified a candidate, to validate a proposed fix actually helps before shipping it, and to catch performance regressions in CI going forward. 6. Only after all of the above, consider perf stat hardware counters (cache misses, branch mispredictions, instructions-per-cycle) if you need to distinguish "this function is slow because of algorithmic complexity" from "this function is slow because of cache behaviour" — this is the deepest, most specialised level and rarely the first tool reached for. The senior signal here is the ordering and hypothesis-driven approach — starting broad and cheap (flame graph) and only going deeper once the broad view has narrowed the search space, rather than guessing and reaching straight for exotic tools.
Q6What is memory-mapping a file, how do you do it in Rust (the memmap2 crate), and when does it actually beat reading the file into a buffer with BufReader? What are the safety caveats?▼ answer
Model answer
use memmap2::Mmap;
use std::fs::File;

fn scan_for_pattern(path: &str, pattern: &[u8]) -> std::io::Result<bool> {
    let file = File::open(path)?;
    let mmap = unsafe { Mmap::map(&file)? };  // unsafe: file could be mutated externally underneath us
    Ok(mmap.windows(pattern.len()).any(|w| w == pattern))  // mmap derefs to &[u8] — slice ops just work
}
What it is: instead of copying a file's bytes into a heap buffer you manage (read_to_string, BufReader), mmap asks the OS to map the file's pages directly into your process's virtual address space — the returned Mmap derefs to a plain &[u8], but behind the scenes reads are satisfied by the OS's page cache and page faults, not an explicit read() syscall per access; pages are loaded lazily, only when actually touched. When it wins over buffered reads: (1) huge files where you only need random access to small portions — mmap avoids paying to load the entire file when you might touch 1% of it (a database engine or log-indexing tool accessing arbitrary offsets is the classic case); (2) avoiding double-buffering — a normal read copies data from the OS page cache into your own user-space buffer, a second copy that mmap skips entirely, since your "buffer" and the page cache are the same physical memory; (3) sharing pages between processes — multiple processes mmap-ing the same file share the same physical pages in the OS page cache, useful for large shared read-only datasets/models loaded by multiple worker processes. When it's the wrong tool: small files (the mmap setup/syscall overhead isn't worth it for a config file you read once), or genuinely sequential full-file processing, where a well-buffered streaming read is just as fast and far simpler. Safety caveats — why Mmap::map is unsafe: the mapped memory is only "just a slice" as long as nothing else mutates the underlying file while it's mapped — if another process (or your own code via a different file handle) truncates or overwrites the file concurrently, your &[u8] can observe changing data underneath a supposedly-immutable borrow, or in the truncation case, accessing now-invalid pages can raise a SIGBUS that Rust's safe abstractions cannot recover from — a real, if narrow, soundness hole inherent to the OS-level mechanism, which is exactly why the API is marked unsafe despite the resulting type looking like an ordinary safe slice. MmapMut (via memmap2::MmapMut) additionally lets you write through the mapping directly back to the file, useful for in-place binary file editing without a read-modify-write-whole-file cycle.
Q7Two performance/correctness questions that come up together whenever you're hand-rolling a binary format: why does endianness matter when you write u32::from_le_bytes/to_be_bytes, and why does Vec::with_capacity matter when building a byte buffer incrementally?▼ answer
Model answer
Endianness. A multi-byte integer's in-memory representation isn't universal — little-endian machines (essentially all mainstream x86/ARM hardware today) store the least-significant byte first, big-endian machines the opposite. u32::to_ne_bytes/from_ne_bytes use whatever the current machine's native order happens to be — fine for scratch data that never leaves the process, but a real bug the moment those bytes are written to a file, sent over a network, or read back on a different architecture. Any wire format or file format needs to pick one fixed convention independent of the machine — to_be_bytes/from_be_bytes ("network byte order," the traditional convention for internet protocols) or to_le_bytes/from_le_bytes (common in modern binary formats since most hardware is little-endian anyway) — and apply it consistently in both directions. Using the wrong pair on the decode side doesn't error out; it silently produces a wrong-but-plausible-looking number, which is exactly why this class of bug is dangerous — it can hide for a long time before something notices the values are off. Capacity planning. Vec::pushing into a Vec::new() (capacity 0) works correctly regardless, but each time the Vec outgrows its current capacity it must allocate a new, larger backing buffer and copy every existing byte into it — this happens roughly O(log n) times for n total pushes thanks to geometric (typically doubling) growth, so the total copying work across all reallocations is still amortised O(n), but with real, avoidable constant-factor cost. If the final size is knowable or computable upfront — as it almost always is when serialising a known collection into bytes — Vec::with_capacity(exact_size) performs exactly one allocation for the whole operation, and pairing it with extend_from_slice (a single bulk copy per chunk) instead of a byte-by-byte push loop is the natural, idiomatic combination for building a buffer you already know the size of.

// Topic 18
Testing, Benchmarking & Tooling
Questions & model answers
Q1What's the difference between unit tests (#[cfg(test)] mod tests), integration tests (tests/ directory), and doc-tests? When does each run?▼ answer
Model answer
Unit tests live inside the same file as the code they test, in a #[cfg(test)] mod tests { ... } submodule — the #[cfg(test)] attribute means this module is compiled only when running cargo test, never in a normal release build, adding zero footprint to production binaries. Because they live inside the crate, they can test private functions and internal implementation details directly. Integration tests live in a top-level tests/ directory — each file there is compiled as its own separate crate that depends on your library as an external consumer would, so it can only exercise your crate's public API, which makes these tests a genuine check that your public interface actually works as an outside user would use it (and they catch "I forgot to make this function pub" issues unit tests inside the crate never would). Doc-tests are code blocks inside /// documentation comments — cargo test actually compiles and runs every one of them by default, which means your documentation examples are continuously verified to still compile and behave as documented; a code example in a doc comment that goes stale/wrong after a refactor is caught automatically rather than silently misleading future readers, which is a distinctly Rust-ecosystem practice not common in most other languages' documentation conventions.
Q2What is property-based testing (via the proptest or quickcheck crates), and how does it differ from writing example-based unit tests? Give a concrete property you'd test for a sorting function.▼ answer
Model answer
Example-based unit tests assert specific input → specific expected output (assert_eq!(sort(&[3,1,2]), [1,2,3])) — you have to think of every interesting case yourself, and you'll systematically miss edge cases you didn't think to consider. Property-based testing instead asserts a general property that should hold for all valid inputs, and the testing library generates hundreds or thousands of random inputs (with smart strategies biasing toward likely-to-break edge cases: empty collections, very large/small values, duplicates) to try to find a counterexample violating that property. When a failure is found, most implementations automatically "shrink" the failing input down to the smallest/simplest case that still reproduces the failure, so instead of debugging a 400-element random vector, you're handed the minimal 2-element case that breaks your invariant. Concrete properties for a sort function: (1) the output has the same length as the input (catches accidental element loss/duplication); (2) the output is a permutation of the input (same multiset of elements — catches subtle corruption bugs, not just reordering bugs); (3) the output is actually sorted (every adjacent pair satisfies a[i] <= a[i+1]); (4) idempotence — sorting an already-sorted list should return it unchanged. Property tests are especially valuable for exactly this kind of algorithmic code, parsers, and serialization round-tripping (deserialize(serialize(x)) == x), where the space of "interesting" inputs is large and easy to under-sample by hand.
Q3What is fuzzing (e.g. via cargo-fuzz), and how does it complement property-based testing? What kind of bug is fuzzing uniquely good at finding in Rust specifically?▼ answer
Model answer
Fuzzing (cargo-fuzz, built on libFuzzer) also generates random inputs, but the key difference from property testing is coverage-guided mutation: the fuzzer instruments your code to track which branches/basic blocks execute for a given input, then uses that feedback to intelligently mutate inputs toward exploring new, previously-unreached code paths — it's actively searching the input space guided by your program's own control flow, rather than sampling somewhat-randomly (as most property-testing strategies do) or requiring you to specify what a "valid" property even looks like. This makes fuzzing extremely effective at finding inputs that trigger code paths a human never thought to test, run continuously (sometimes for hours/days in CI) rather than a bounded number of test-run iterations. What it's uniquely good at finding in Rust: panics and unsafe-code memory violations reachable from a public API given adversarial or malformed input — a parser that panics on malformed input isn't a memory-safety bug (safe Rust can't corrupt memory), but it's still a real denial-of-service vector if that parser is exposed to untrusted data (e.g. parsing network protocol data or file formats) — fuzzing routinely finds these panic-on-bad-input cases that neither example-based nor typical property tests happen to construct. Combined with cargo fuzz + cargo miri, it's also one of the most effective ways to find latent unsafe-code memory bugs before they ever reach production, since the fuzzer explores far more input combinations than any hand-written test suite realistically could.
Q4How do you set up a meaningful CI pipeline for a production Rust crate — beyond just cargo test? What checks catch problems that tests alone won't?▼ answer
Model answer
A senior-level CI pipeline for a serious Rust project layers several distinct checks, each catching a different class of problem: cargo build + cargo test — correctness of the code you wrote, obviously. cargo fmt --check — enforces consistent formatting so code review focuses on substance, not style bikeshedding. cargo clippy -- -D warnings — catches non-idiomatic patterns, likely logic bugs (needless clones, redundant comparisons, integer casts that could lose data), and performance footguns the compiler itself doesn't flag; treating clippy warnings as build failures (-D warnings) keeps the codebase clean by construction rather than accumulating debt. cargo audit — scans dependencies against the RustSec advisory database for known CVEs, catching supply-chain risk that no amount of your own testing would reveal. cargo deny check — enforces license compliance and can ban specific problematic dependencies/duplicate-version bloat across the tree. cargo test --doc (usually implied by plain cargo test) — keeps documentation examples honest. MSRV check — building against your published minimum-supported-Rust-version toolchain in CI (not just the latest stable) if you're a library, since it's trivially easy to accidentally use a newer API and silently break MSRV compliance without noticing on your own up-to-date local toolchain. For unsafe-heavy crates specifically: a cargo miri test job, and potentially a scheduled (not per-PR, since it's slow) fuzzing job that runs continuously and reports new crashes. The senior framing: each of these is genuinely catching a different failure mode — tests alone would miss every one of the others — and a mature pipeline is deliberately layered rather than "just run the test suite and call it done."
Q5You wrote a criterion benchmark showing your new implementation is 40% faster than the old one — but a teammate is skeptical of microbenchmark results in general. What pitfalls would you specifically check for before trusting the number?▼ answer
Model answer
1. Dead-code elimination / constant folding. If the benchmarked function's result isn't actually used, LLVM may optimise away some or all of the real work being measured — criterion provides black_box() specifically to prevent the optimiser from seeing that a value is unused/constant and eliminating the computation; forgetting to wrap inputs/outputs in black_box is the single most common way to get a meaningless "impossibly fast" benchmark number. 2. Unrepresentative input data. A benchmark using a tiny, uniformly-distributed, or already-sorted dataset can behave completely differently from production data distributions (e.g. a hash map benchmark with sequential integer keys can look artificially fast/slow compared to real-world string keys with different hash distribution behaviour). 3. Warm cache / warm allocator effects that won't hold in a cold-start production request path, or conversely, benchmarking steady-state throughput when the real concern is tail latency (criterion reports mean/median by default — check whether p99 or worst-case behaviour is actually what matters for this change). 4. CPU frequency scaling / thermal throttling / other processes on the benchmarking machine introducing noise — running benchmarks on a shared CI runner or a laptop under load produces unreliable numbers; ideally benchmark on a dedicated, pinned-frequency machine, and always look at criterion's reported confidence intervals, not just the point estimate, before claiming a real difference. 5. Does the microbenchmark reflect the actual bottleneck in the full system? A function that got 40% faster in isolation might contribute 0.1% of end-to-end request latency in production — always connect a microbenchmark improvement back to a real, measured system-level impact (e.g. an actual before/after production latency measurement or load test) before treating the optimisation as validated. Raising all of this proactively, rather than just presenting the 40% number, is exactly the kind of rigor that distinguishes senior performance work from "I benchmarked it and it's faster."

FFI & Interop
Questions & model answers
Q1What does extern "C" mean on a function, and why is it necessary for calling into or being called from C code?▼ answer
Model answer
Rust's default calling convention (how arguments are passed — which registers, stack layout, name mangling for linking) is unspecified and can change between compiler versions — it's an internal implementation detail, not a stable ABI. extern "C" on a function declares that it should use the platform's standard C calling convention instead — a stable, well-defined ABI every language's FFI tooling agrees on. This is required in both directions: a Rust function meant to be called from C code must be declared extern "C" fn foo(...) (plus #[no_mangle] to prevent Rust's default name-mangling so the linker can find it by its plain name), and declaring the signature of a C function you want to call from Rust (extern "C" { fn some_c_function(x: i32) -> i32; }) tells the Rust compiler to generate a call using that same stable convention rather than assuming a Rust-internal one. Without this, the two sides would disagree about register usage/stack layout and calls would corrupt data or crash unpredictably.
Q2What is bindgen and what problem does it solve? Contrast it with writing FFI bindings by hand.▼ answer
Model answer
bindgen parses a C/C++ header file and automatically generates the corresponding Rust extern "C" function declarations, matching #[repr(C)] struct definitions, and constant/enum bindings — typically run as a build-time step (build.rs) so bindings stay in sync with the actual header used at build time, rather than being a one-time manual transcription that silently drifts out of sync as the C library evolves. Hand-writing bindings is error-prone specifically because getting a struct's field order, types, and padding exactly right is required for FFI safety (a mismatched field type or missing padding byte causes silent memory corruption, not a compile error, since the Rust compiler has no visibility into what the actual C struct layout is) — a manual transcription mistake is exactly the kind of bug that's invisible until it corrupts data in a way that's very hard to trace back to its root cause. bindgen eliminates this entire class of error by generating bindings directly from the authoritative header, and automatically re-generates them whenever the header changes, catching upstream C API changes at Rust compile time instead of at runtime. The trade-off: bindgen-generated bindings are often extremely low-level/unsafe (matching the raw C API 1:1) — real crates almost always wrap the raw bindgen output in a hand-written, safe, idiomatic Rust API layer (the common "sys crate" + "high-level wrapper crate" pattern seen throughout the ecosystem, e.g. libgit2-sys + git2).
Q3You're wrapping a C library that returns error codes via an out-parameter and expects the caller to eventually free returned pointers. Design the safe Rust wrapper API around it.▼ answer
Model answer
Error codes → Result: the raw FFI signature might look like extern "C" fn c_open(path: *const c_char, out: *mut *mut Handle) -> c_int; — the safe wrapper translates the integer return code into a proper Rust error enum, and returns the out-parameter's value as the Ok payload instead of leaving it as a raw pointer parameter for the caller to manage: fn open(path: &str) -> Result<SafeHandle, CError>. Owned resources → RAII wrapper with Drop: wrap the raw pointer in a newtype struct and implement Drop to call the C library's corresponding free/close function — struct SafeHandle(*mut Handle); impl Drop for SafeHandle { fn drop(&mut self) { unsafe { c_close(self.0) } } } — this guarantees the resource is released exactly once, deterministically, even if the caller panics or forgets to explicitly close it, mirroring how std::fs::File wraps a raw OS file descriptor. CString/CStr for string boundaries: any &str passed to a C function expecting a null-terminated string must go through CString::new(s) (which also validates there are no interior null bytes, returning an error if so — a real and easy-to-forget failure mode for arbitrary Rust strings passed across the boundary). Never expose the raw pointer in the public API — keep it entirely private inside the wrapper struct, so users of your safe crate have no way to misuse it, double-free it, or use it after the wrapper has dropped it; the entire point of the wrapper layer is that its public surface should be impossible to misuse into memory unsafety, with all the unsafe contained and justified inside the small number of FFI call sites rather than leaked to callers.
Q4What does it mean for a callback-based C API to require a Rust closure to cross the FFI boundary? Walk through the userdata/trampoline pattern used to make this work.▼ answer
Model answer
C callback APIs universally expect a plain function pointer plus (by convention, in well-designed C APIs) a void* userdata parameter that the C library promises to pass back unchanged on every invocation — this is C's idiom for smuggling "context" across an interface that has no concept of closures. As established earlier in this packet, a capturing Rust closure cannot coerce to a bare fn pointer — there's nowhere in a raw function pointer to store captured state. The trampoline pattern bridges this: (1) box the actual Rust closure: let boxed: Box<dyn FnMut(Event)> = Box::new(my_closure);; (2) cast the box into a raw pointer and pass that as the C API's userdata: let raw = Box::into_raw(boxed) as *mut c_void;; (3) define a small, non-capturing extern "C" function — the actual trampoline — matching the C callback signature exactly, whose entire body reconstructs a reference to the boxed closure from the userdata pointer and calls it: 
extern "C" fn trampoline(event: CEvent, userdata: *mut c_void) {
    let closure = unsafe { &mut *(userdata as *mut Box<dyn FnMut(Event)>) };
    closure(event.into());
}
(4) pass trampoline (a plain, non-capturing function — perfectly valid as a bare fn pointer) as the callback, and the raw pointer from step 2 as userdata; (5) critically, reconstruct and drop the Box via Box::from_raw(...) once the callback is no longer needed (e.g. when unregistering, or when the wrapping struct itself drops) — forgetting this leaks the boxed closure and its captured state forever, since the raw pointer conversion opted out of Rust's automatic drop tracking for that allocation. This pattern — box, leak the raw pointer across the boundary, non-capturing trampoline reconstructs and calls it, explicitly reclaim ownership later to free it — is the standard, necessary answer whenever a Rust closure needs to satisfy a C-style callback API, and articulating all five steps correctly is a strong senior FFI signal.
Q5What additional considerations come into play when the FFI boundary needs to be thread-safe — e.g. a C library that isn't documented as thread-safe, being wrapped for use from a multi-threaded Rust service?▼ answer
Model answer
The Rust compiler has zero visibility into the C library's actual thread-safety — raw pointers are neither Send nor Sync by default specifically because the compiler can't verify anything about what they point to, but that default is a conservative "don't know" more than an active protection; if you write an unsafe impl Send for MyWrapper {} to make your wrapper usable across threads, you are personally certifying something the compiler cannot check at all — this is exactly the kind of soundness claim discussed in the unsafe topic, except now the claim depends on an entirely separate codebase's (the C library's) internal implementation, which you may not be able to fully audit. Concrete due diligence before doing this: (1) check the C library's own documentation explicitly for thread-safety guarantees — many C libraries are thread-hostile by design (global mutable state, non-reentrant functions) and this is not always obvious from the header alone; (2) if the library is genuinely not thread-safe, the correct wrapper design is to serialise all access through a single Rust-side Mutex around the entire handle, converting the C library's requirement into an enforced Rust-level invariant — do not mark the type Send/Sync without this, and definitely don't assume it's fine because "it hasn't crashed yet"; (3) watch specifically for C libraries with global/static state (not just per-handle state) — even if each individual handle looks independent, shared global state inside the C library can silently corrupt across handles used from different threads, something no amount of per -handle Rust-side locking alone will fix, requiring a single global lock for the whole library instead. Being able to reason about a dependency's thread-safety that lives entirely outside Rust's type system, and translating that external contract into an enforced Rust invariant deliberately rather than by assumption, is a distinctly senior/staff-level FFI skill.
✓ Strong
  • Explains extern "C" as a stable ABI necessity, not just required syntax
  • Designs RAII wrappers around raw C handles with Drop-based cleanup
  • Can walk through the full box/trampoline/userdata callback pattern from memory
  • Treats unsafe impl Send/Sync on an FFI wrapper as a serious, externally-dependent soundness claim
⚠ Probe
  • Has used bindgen-generated bindings but never written the safe wrapper layer around them
  • Hasn't considered CString null-byte validation when passing strings to C
✗ Concern
  • Exposes raw pointers directly in a "safe" public API
  • Marks an FFI wrapper Send/Sync without investigating the underlying C library's thread-safety

FFI questions are a great way to test whether "unsafe" understanding is theoretical or practiced — the trampoline pattern and the RAII-wrapper-around-a-C-handle pattern both come up constantly in real systems work and are very hard to fake convincingly without having actually built one.

Architecture & Design Patterns
Questions & model answers
Q1What is the builder pattern in Rust, and why is it especially common given Rust has no function overloading or default parameter values?▼ answer
Model answer
let client = HttpClient::builder()
    .timeout(Duration::from_secs(30))
    .retries(3)
    .build()?;
The builder pattern uses a chain of methods, each consuming and returning self (or &mut self), to incrementally configure an object before a final .build() call constructs it. It's especially prevalent in Rust specifically because Rust has neither function overloading nor default parameter values — languages with those features can express "construct this with mostly-default settings, just override one or two fields" via an overloaded constructor or named/default arguments; Rust cannot express that directly on a plain fn new(a, b, c, d, e) constructor without forcing every caller to specify every argument. The builder sidesteps this entirely: each configuration option becomes an optional, independently-callable method, callers only call the ones they care about, and sensible defaults live in the builder's own Default implementation. This is also why the pattern often pairs with the typestate pattern discussed earlier — a builder can use generic type parameters to track which required fields have been set, making .build() only callable (at compile time) once all mandatory configuration has actually been provided.
Q2What is the "newtype" pattern used for beyond just type-safety (covered earlier)? Specifically, how does it help you work around the orphan rule when implementing a foreign trait for a foreign type?▼ answer
Model answer
The orphan rule forbids impl ForeignTrait for ForeignType — you can only implement a trait for a type if you own the trait, the type, or both — this exists to guarantee coherence (exactly one implementation of a given trait for a given type exists anywhere in the dependency graph, so trait resolution is never ambiguous regardless of which crates are combined). If you want to implement, say, serde::Serialize (foreign trait, from the serde crate) for chrono::DateTime (foreign type, from the chrono crate) directly, the orphan rule blocks it — neither type nor trait is yours. The newtype workaround: define struct MyDateTime(chrono::DateTime<Utc>); — now the type MyDateTime is yours, so impl serde::Serialize for MyDateTime is perfectly legal, and you implement Serialize by delegating to the inner value's own formatting logic. The cost: you now have a wrapper type that needs Deref/explicit unwrapping or delegate methods to feel ergonomic to use, and any function expecting the original foreign type needs an explicit conversion at the boundary — a real but usually small ergonomic tax in exchange for coherence, which is a much more valuable, structural property for the entire ecosystem (no crate can ever silently "fight" another crate's trait impl for the same type). This is one of the most commonly-hit "why won't this compile" moments for engineers moving from languages without an orphan-rule-equivalent restriction.
Q3Compare a "visitor pattern"-style approach with matching on an enum directly for processing a tree of heterogeneous node types. When would you reach for one over the other in Rust specifically?▼ answer
Model answer
Direct enum + match: represent the node types as an enum (enum Node { Literal(i64), Add(Box<Node>, Box<Node>), ... }) and process it with match in each function that needs to operate on it. This benefits enormously from Rust's exhaustiveness checking (covered earlier) — adding a new node variant forces a compile error at every match site that needs updating, which is a huge correctness win for evolving a small, closed, stable set of node types. The downside: every new operation (pretty-print, evaluate, type-check, optimise) requires a new function that matches on every variant, and if you have many operations, the "match arms scattered across many functions" style can become harder to navigate than a more object-oriented "one method per operation, grouped by type" organisation. Trait-object-based visitor pattern: define a Visitor trait with one method per node type, and a Node trait with an accept(&self, visitor: &mut dyn Visitor) method each concrete node type implements to call back the right visitor method — this groups all logic for one operation together (implement one Visitor per operation), at the cost of losing exhaustiveness checking (adding a new node type requires you to remember to add a corresponding method to the Visitor trait and implement it everywhere — nothing forces this the way match does) and adding dynamic dispatch overhead. Rust-specific guidance: because Rust's enum exhaustiveness is such a strong compile-time safety net, the enum+match approach is idiomatically preferred by default in Rust far more often than in languages like Java/C++ where the visitor pattern is the conventional answer to "avoid a giant if-else chain checking types" — reach for the trait-object visitor specifically when the set of node types is genuinely open-ended/extensible by third parties (plugin-style extensibility), which is exactly the scenario where you'd want new node types addable without needing to modify a closed, exhaustively-matched enum at all.
Q4You're designing a moderately large service as a Cargo workspace with multiple crates. What principles guide how you split crate boundaries, and what mistakes do teams commonly make when first adopting workspaces?▼ answer
Model answer
Guiding principles: (1) split along compile-time and reuse boundaries, not just conceptual ones — a crate boundary is valuable specifically because Cargo caches and parallelises compilation per-crate; splitting a pure-logic domain crate out from an HTTP-serving api crate means changing an HTTP handler doesn't force recompiling the domain logic (and vice versa), which meaningfully improves iteration speed in a large codebase. (2) dependency direction should point one way — lower-level crates (domain logic, shared types) should never depend on higher-level crates (the HTTP binary, a specific storage backend) — this is enforced automatically by Cargo's dependency graph (a cyclic crate dependency simply doesn't compile), which is a nice structural guardrail against architectural erosion that's easy to accidentally violate in a single monolithic crate with only module-level (not crate-level) separation. (3) expose a minimal public surface per crate — use pub(crate) visibility liberally within a crate, and only mark genuinely cross-crate-needed items fully pub, so refactoring internals of one crate doesn't ripple outward. Common mistakes: (1) splitting too early, before the boundaries are clear — premature crate-splitting based on a guessed-at architecture often needs re-splitting later once real usage patterns emerge; many experienced teams start with a single crate and split out workspace members only once a genuine reuse or compile-time need materialises. (2) one shared "utils" or "common" crate that becomes a dependency-graph bottleneck — everything depends on it, so any change to it forces a full rebuild of the whole workspace, defeating much of the incremental-compilation benefit workspaces are meant to provide; it's usually better to have several small, focused shared crates than one large grab-bag. (3) forgetting to unify dependency versions across workspace members — without care, two member crates can end up depending on different semver-incompatible versions of the same external crate, bloating the build and occasionally causing confusing type-mismatch errors when a type from some-crate 1.x doesn't unify with the "same" type from some-crate 2.x; a shared [workspace.dependencies] table (Cargo's newer built-in mechanism for this) helps enforce consistency deliberately rather than by accident.
Q5Argue both sides: should a Rust service's core business logic be written against concrete types (e.g. a specific database pool type) or behind trait abstractions (a repository trait) for testability? What's your actual recommendation and why?▼ answer
Model answer
Case for trait abstraction (dependency inversion): business logic depending on a trait UserRepository { fn find(&self, id: UserId) -> Result<User, Error>; } rather than a concrete PgPool lets you write fast, deterministic unit tests using an in-memory fake implementation, with no database required — this can make the majority of business-logic tests run in milliseconds instead of requiring a real (or containerized) database, and decouples the logic from a specific storage technology if it ever needs to change. Case against (over-abstraction cost): introducing a trait for every dependency "just in case" adds real indirection cost — an extra trait definition, an extra impl, and (if using dyn) dynamic dispatch and heap allocation for something that in practice will only ever have one real implementation in production. Rust's culture also somewhat pushes back against Java/C#-style "interface for everything" architecture as unidiomatic ceremony when it isn't earning its cost, and generic trait bounds are only free (statically dispatched) if you're willing to make business logic generic over the repository type, which itself adds complexity (an extra generic parameter propagating through every function that touches it). Actual recommendation: abstract at the boundary genuinely likely to vary or need substitution — a database/storage layer is a very common, legitimate candidate (multiple storage backends across environments, integration tests wanting an in-memory fake) — but don't reflexively abstract every single dependency. For the cases you do abstract, prefer testing with a real lightweight instance where practical (a real SQLite/Postgres in a testcontainer) over a hand -written fake, since fakes drift from real behaviour over time and can pass tests while the real implementation has diverged; reserve pure in-memory fakes for genuinely slow/expensive/hard-to-provision dependencies (an external third-party API, a message queue) where a real instance in every test run isn't practical. Articulating this nuanced trade-off, rather than dogmatically defending "always abstract dependencies" or "never add unnecessary indirection," is what a staff-level architecture discussion actually sounds like.
Q6The Strategy pattern is "encapsulate an interchangeable algorithm/behavior so it can be swapped at runtime." In classic OOP that's an interface with several implementing classes. What's the idiomatic Rust equivalent, and when do you still reach for a real trait instead of just a closure parameter?▼ answer
Model answer
A large fraction of "Strategy pattern" needs in Rust are served directly by passing a closure or impl Fn(...) rather than defining a formal trait Strategy with several struct implementors — Vec::sort_by(|a, b| ...), a retry_with_backoff(strategy: impl Fn(u32) -> Duration), or a validation pipeline taking impl Fn(&str) -> bool are all, structurally, the Strategy pattern with dramatically less ceremony than trait BackoffStrategy { fn delay(&self, attempt: u32) -> Duration; } plus multiple structs implementing it — appropriate whenever the "strategy" really is just one function of some inputs to an output, with no state beyond what a closure's own captures already provide. Reach for an actual trait instead when: (1) the strategy needs multiple related methods, not one callable operation (a trait CompressionStrategy { fn compress(...); fn decompress(...); } pairing that must stay in sync); (2) the strategy carries meaningfully complex configuration/state that reads far more clearly as a named struct than as a closure's opaque captures; or (3) you need a heterogeneous, runtime-selected collection of strategies (Vec<Box<dyn Strategy>>, or picking one by name from a config value) — a closure can't be "looked up by name" the way a match over an enum, or a registered trait-object factory, can. Whether the chosen strategy is generic (fn f<F: Fn(...)>(strategy: F)) or boxed (Box<dyn Fn(...)>) follows the same static-vs-dynamic-dispatch trade-off as everywhere else: generic when the concrete strategy is known at each call site and zero-cost monomorphisation is worth it, boxed dyn when the strategy is chosen at runtime and needs to be stored without its concrete type being known ahead of time.
Q7RAII isn't a classic GoF pattern, but it's arguably the single most pervasive design pattern in idiomatic Rust. Name 2-3 places the standard library itself relies on it, then sketch your own scope-guard type for a resource needing custom cleanup — e.g. temporarily flipping a flag and restoring it on scope exit.▼ answer
Model answer
Std examples: MutexGuard (returned by Mutex::lock()) releases the lock in its Drop impl the instant it goes out of scope — impossible to forget to unlock, even across an early return or a panic mid-critical-section. File closes its OS file descriptor on drop. thread::scope's scope guard blocks on drop until every thread spawned inside it has finished, which is precisely what lets thread::scope soundly allow borrowing local stack data (covered in the threading topic) — the borrow-checker-visible scope and the actual-thread-joining both end at the same Drop. Custom scope guard: 
struct ResetOnDrop<'a> { flag: &'a AtomicBool, original: bool }

impl<'a> Drop for ResetOnDrop<'a> {
    fn drop(&mut self) { self.flag.store(self.original, Ordering::SeqCst); }  // runs on every exit path, including panics
}

fn temporarily_enable(flag: &AtomicBool) -> ResetOnDrop<'_> {
    let original = flag.swap(true, Ordering::SeqCst);
    ResetOnDrop { flag, original }
}
// caller: let _guard = temporarily_enable(&some_flag);  ... restored automatically at end of scope
This is exactly what the scopeguard crate's defer! macro generalises for one-off cleanup without writing a dedicated struct+Drop impl each time. The interview-worthy insight: Drop::drop runs even during a panic-triggered unwind (barring a second panic inside drop itself, or a panic = "abort" profile) — RAII guards give you the cleanup-on-every-exit-path guarantee that other languages need an explicit try/finally or defer block to express, entirely for free, without the guard needing to know anything about how control left the scope.
Q8Earlier we covered modelling a state machine as an enum with runtime variants. There's a second, compile-time flavor of the typestate pattern using generic phantom markers — e.g. a Connection<Disconnected> that has no .send() method until .connect() turns it into a Connection<Connected>. Sketch it and explain the trade-off against the enum approach.▼ answer
Model answer
struct Disconnected;
struct Connected;

struct Connection<State> { socket: Option<TcpStream>, _state: PhantomData<State> }

impl Connection<Disconnected> {
    fn connect(self, addr: &str) -> io::Result<Connection<Connected>> {
        let socket = TcpStream::connect(addr)?;
        Ok(Connection { socket: Some(socket), _state: PhantomData })  // returns a DIFFERENTLY-TYPED connection
    }
}

impl Connection<Connected> {
    fn send(&mut self, data: &[u8]) -> io::Result<()> {  // this method simply doesn't exist on Connection
        self.socket.as_mut().unwrap().write_all(data)
    }
}
Calling .send() on a Connection<Disconnected> is a compile error — there's no such method — rather than a runtime "not connected yet" error or panic you'd get from one struct with a runtime state: ConnState enum field checked at the top of every method. That's the fundamental trade-off against the earlier enum-based state machine: phantom-type typestate pushes "did you call things in the right order" to compile time (a strictly stronger guarantee, zero runtime cost, illegal states don't merely go unused — they have no methods to misuse at all), at the cost of (1) each transition consumes self and returns a differently-typed value, so you can't hold a Vec of mixed-state connections without erasing the state behind an enum or trait object anyway, and (2) it doesn't work when the state is only known at runtime — e.g. deserialized from a database row — where you need to branch on it as data, which is exactly what enums remain the right tool for. Reach for phantom-type typestate specifically for compile-time misuse prevention on a single value moving through a short, known sequence of states (builders, connection/session handles, transaction handles) — not as a wholesale replacement for enum-based state machines.
Q9The Command pattern encapsulates "an action to perform later" as a value. Thread-pool/task-queue jobs are usually boxed closures (Box<dyn FnOnce() + Send>). What's the alternative "enum of commands" design, and when would you actually prefer it over a boxed closure?▼ answer
Model answer
Box<dyn FnOnce() + Send + 'static> is the Command pattern in Rust — a closure capturing whatever state it needs, ready to be invoked later, exactly like a Command interface with one execute() method and infinitely many anonymous "implementing classes" (one per distinct closure). It's the default precisely because it needs zero upfront ceremony — no struct/enum to define ahead of time for every possible action. The alternative — enum Command { Shutdown, Log(String), SetLimit(u32), ... }, dispatched via match — trades that flexibility for two things a closure fundamentally cannot give you: (1) inspectability — a Command value can be logged, serialized (#[derive(Serialize)]), replayed from a queue or database, or asserted-on directly in a unit test; a Box<dyn FnOnce()> is an opaque black box you can only call, never print, compare, or persist. (2) exhaustiveness-checked dispatch — adding a new Command variant forces the compiler to flag every match site that needs updating, the same safety net discussed for the visitor-pattern question earlier, which a closure-based design has no equivalent for. Reach for the enum specifically when commands need to cross a serialization or persistence boundary — a job queue backed by a database or message broker, an undo/redo stack that must survive a restart, an audit log of "what actions were requested" — and stick with boxed closures when commands are purely in-process and ephemeral and never need to be inspected as data, which describes the overwhelming majority of thread-pool/task-queue use cases.
Q10A teammate wants a global, lazily-initialized AppConfig reachable from anywhere via a plain function call — the Singleton pattern. Show the idiomatic Rust mechanism, then make the case for why senior engineers usually push back on this design regardless of the mechanism used to implement it.▼ answer
Model answer
use std::sync::OnceLock;
static CONFIG: OnceLock<AppConfig> = OnceLock::new();

fn config() -> &'static AppConfig {
    CONFIG.get_or_init(|| AppConfig::load_from_env())  // thread-safe, initializes exactly once, no unsafe
}
OnceLock (stable std, having largely replaced lazy_static!/ once_cell::sync::Lazy for this exact case) is the correct, idiomatic mechanism — this genuinely is the right tool the instant you've decided you want global, lazily-initialized, shared state. The pushback is independent of mechanism. The objection senior engineers raise isn't "can you implement a singleton safely" (OnceLock settles that) — it's that a global singleton makes every function that transitively reads it implicitly depend on global state, which specifically breaks (1) test isolation — tests can't easily substitute a different config without a process-wide static leaking into every other concurrently-running test, and (2) honest function signatures — a function's parameter list no longer tells you everything it depends on; you have to read the body to discover it silently reaches into config(). The idiomatic alternative most Rust codebases converge on: pass configuration explicitly — load it once in main, wrap it in an Arc<AppConfig>, and thread that through function parameters/struct fields to whatever actually needs it. This costs some boilerplate at every layer in exchange for every function's real dependencies being visible in its signature, and tests being able to construct whatever AppConfig they want with zero shared global state. Naming this trade-off unprompted — rather than treating "can I make a working global singleton" as the whole question — is the actual senior signal; a working singleton is rarely what a real design review is contesting.

Modules, Crates & Cargo Mechanics
Questions & model answers
Q1How does Rust's module system actually work — how does mod foo; relate to a file on disk, what does use actually do, and where does a crate's module tree begin?▼ answer
Model answer
A crate's module tree starts at its crate root — src/main.rs for a binary crate, src/lib.rs for a library crate (a package can have both: one library plus one or more binaries, each with their own root file). Unlike Python or JavaScript, Rust does not auto-discover files as modules — a file sitting in src/ is invisible to the compiler unless something explicitly declares it as a module: 
// src/lib.rs (crate root)
mod parser;        // declares a module named `parser`; compiler looks for src/parser.rs (or src/parser/mod.rs)
mod util {          // OR define a module inline, right here, with no separate file at all
    pub fn helper() {}
}

use parser::Token;  // brings `Token` into scope so you can write `Token` instead of `parser::Token`
mod foo; both declares the module and tells the compiler which file its contents live in (following the standard naming convention above); the module's actual code is nested under parser:: in the path system regardless of which file it physically lives in. use does not affect visibility at all — it's purely a local, per-file shorthand for a path that already resolved successfully; conflating "I used use so now it's accessible" with "this is actually pub" is one of the most common early confusions. A submodule can always see into its ancestors' private items without any use/pub at all — privacy in Rust is scoped to "this item and everything nested inside it," not per-file.
Q2Walk through the full visibility spectrum — default privacy, pub, pub(crate), pub(super) — and explain what pub use re-exporting is actually for.▼ answer
Model answer
Default (no modifier) is private — visible only within the defining module and any of its descendant modules, invisible to siblings, parents, or other crates. pub makes an item visible from anywhere that can reach its path, including other crates. Between those two extremes: pub(crate) makes an item visible anywhere within the current crate but not to external crates — the standard choice for "shared internal API between your own modules, but not part of the crate's public contract," and a good default when you're not yet sure something needs to be fully public. pub(super) restricts visibility to just the parent module (and its descendants) — useful for a submodule exposing something specifically for its immediate parent to orchestrate, without leaking it crate-wide. pub(in some::path) generalises this to an arbitrary named ancestor module. A frequently-missed nuance: a struct can be pub while its fields stay private — the type is nameable and can appear in public signatures, but callers can't construct it directly or reach into its internals, forcing them through a public constructor/method that can enforce invariants. pub use re-exports an item at a new path — it lets a crate present a clean, curated, flat public API (my_crate::Config) while the actual implementation lives buried in whatever internal module structure makes sense for the maintainers (my_crate::internal::config::builder::Config); serde and tokio both do this heavily — the paths you actually import as a consumer are rarely where the type is truly defined.
Q3You're building a command-line tool. Why is "thin main.rs, real logic in lib.rs" the recommended structure, how do std::env::args() and clap differ for argument parsing, and what's the actual risk of calling std::process::exit directly?▼ answer
Model answer
Thin main.rs, real logic in lib.rs: a package can expose both a library and a binary target from the same crate; putting all actual logic in src/lib.rs (as ordinary, directly callable functions/types) and reducing src/main.rs to "parse arguments, call into the library, handle the top-level result" means the logic is directly unit-testable via cargo test with plain function calls — no subprocess spawning, no capturing stdout, no CLI-invocation ceremony in tests at all. Logic embedded directly in main.rs can really only be exercised by actually running the compiled binary, which is far slower and clunkier to test thoroughly. Argument parsing: std::env::args() returns a plain iterator of raw Strings with zero validation, type conversion, or help text generated for you — workable for a single positional argument, unmaintainable past 2-3 flags with any real validation needs. clap (specifically its derive API, #[derive(Parser)] on a struct whose fields become flags/positional args) is the modern idiomatic default: it generates --help/--version automatically, parses into real typed fields (a count: u32 field fails with a clean, user-facing error message if given --count abc, rather than a manual parse-and-match you'd otherwise write yourself), and supports subcommands (git commit-style CLIs) with minimal boilerplate. process::exit risk: it terminates the process immediately, skipping the normal unwind — anything still on the stack (open file handles, a BufWriter with unflushed buffered data, any type with a meaningful Drop impl) has its destructor silently skipped. The safer, now-idiomatic alternative is returning a value from main itself — fn main() -> Result<(), MyError> (errors get printed and exit non-zero automatically) or fn main() -> ExitCode for custom exit codes — which lets every value already on the stack drop normally before the process actually exits. Reach for process::exit directly only when you specifically need to bypass unwinding (e.g. after a caught panic you've deliberately decided not to let propagate further).
Q4What actually differs between Cargo's dev and release profiles by default, and what do lto, codegen-units, panic = "abort", and strip trade off when you tune a release profile further?▼ answer
Model answer
# Cargo.toml — tuning the release profile beyond its defaults
[profile.release]
lto = true
codegen-units = 1
panic = "abort"
strip = true
Defaults: dev builds with opt-level = 0 (essentially no optimisation, prioritising fast compile times over runtime speed) and debug-assertions = true; release flips to opt-level = 3 and debug-assertions = false. The debug-assertions flip is a real, easy-to-miss correctness gotcha: integer overflow on primitive types panics in a debug build but silently wraps (two's complement) in release by default — code that appears to "work fine" throughout local development can behave differently in production the moment an overflow condition is actually hit, which is exactly why relying on this difference (rather than explicit checked_add/wrapping_add/ saturating_add where overflow is a real possibility) is a latent bug, not a feature. Further tuning knobs: lto = true (link-time optimisation — lets the optimiser see across crate boundaries, often meaningfully improving runtime performance and shrinking binary size, at the cost of substantially longer link/build times); codegen-units = 1 (forces fully sequential, whole-crate codegen instead of parallel chunks, enabling more cross-function optimisation at the direct cost of build parallelism/speed); panic = "abort" (skips the unwinding machinery entirely on panic — smaller, sometimes faster binaries, but you permanently lose catch_unwind and, notably, Drop impls no longer run during a panic — a direct trade-off against the RAII/cleanup-on-every-exit-path guarantee discussed under the design-patterns topic); strip = true (removes debug symbols from the final binary, shrinking it, at the cost of much less useful backtraces/symbols if it ever needs to be debugged post-mortem). None of these are "always turn on" — each is a genuine build-time-vs-runtime-characteristic trade-off to make deliberately per project, not a checklist to blindly enable.
Q5What does cargo publish actually require, what does cargo yank do (and not do), and what's the one surprising rule about publishing crates that live inside a workspace?▼ answer
Model answer
Publishing requirements: a complete-enough Cargo.toml (a license — either an SPDX identifier or a license-file — plus a description are effectively mandatory in practice, since crates.io's UI and many downstream tools expect them), and a version number that follows SemVer discipline — this matters far beyond convention, because Cargo's own dependency resolver trusts your version number to decide whether an upgrade is safe to apply automatically (a ^1.2.0 dependency constraint will happily auto-upgrade to 1.3.0 or 1.9.9, but never to 2.0.0) — publishing a breaking change as a patch or minor version bump silently breaks every downstream consumer who trusted that constraint, which is a genuinely damaging mistake for any crate with real dependents. cargo yank: marks a specific published version as "do not select for any new dependency resolution" — it does not delete the version, and does not break any existing build that already has that exact version pinned in its Cargo.lock; it's a safety net for "I just published something broken and want to stop new projects from picking it up," not a way to erase a release from history. Workspace publishing surprise: there is no "publish the whole workspace as one atomic unit" — each crate in a workspace is published to crates.io independently, one cargo publish per crate. A common first-publish trip-up: an in-workspace path dependency (other-crate = { path = "../other-crate", version = "1.0" }) needs both the path (for local builds) and a version requirement that crates.io can actually resolve once published — crates.io has no concept of local filesystem paths, so a path-only dependency with no version constraint simply cannot be published at all.
